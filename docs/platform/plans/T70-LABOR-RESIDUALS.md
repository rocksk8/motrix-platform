# 勞報單權限與選派發：已知殘留（T70 記錄；整理自 T67／T68 審查）

本檔只記錄「已知、已裁示不在本班處理」的事項，避免之後的人以為是漏做。不改任何程式行為。

## 1. 勞報單權限（T67 `payroll.payslip.*` 六項能力）
- 只接了 6 項能力、20 支端點（`payslips.py` 14、`payslip_links.py` 6）。`get_signed_file`、`approve`、`reject`、`submit`、`delete`、`mark-paid`、`unpay` 仍走原本的閘（最高管理者或財務／出納判斷），不在權限設定頁。原因：財務／出納隨 `finance_mode` 變動，現有 DSL 表達不了（見 T68-PMS1-STEP-NOTES §7）。
- `查看勞報單`（`payroll.payslip.view`）同時涵蓋勞報單清單與內容（含金額、承攬人姓名）、派工連結與派工名冊的讀取（不含金額）。授予它＝授予看這些資料；它是一般風險（不需要確認期間、不需要第二位最高管理者核准）。若要把「看金額」拆成高風險能力（`view_money`），是產品決定，尚未做。
- 側邊欄入口仍看功能勾選：把『查看勞報單』勾給某角色，他能呼叫 API，但左側選單不會自動出現入口。

## 2. 派發頁的『派發 ↔ 勞報單關聯』三支端點
- `POST`（新增關聯）與 `DELETE`（解除關聯）`/api/contractor-dispatches/{id}/payslip-links` 仍是**最高管理者**判斷（`_guard_edit`／`_can_open`），不在權限設定頁。
- `GET`（列出某張派發已連的勞報單）**不是**只有最高管理者：持有「採購／案件管理／承攬商名冊／報價」任一功能勾選的人都能讀（還要通過該案件的讀取守門，看不到案件 ⇒ 404）；回應不含金額，只有單號、狀態、受領人姓名、開單日等，並帶 `canOpen`／`canEdit`（是否為最高管理者）讓畫面決定要不要顯示『連結』按鈕。
- 勞報單頁那一側（`/api/payslips/.../dispatch-links`）則已走 `payroll.payslip.view／create／edit`。兩側權限因此不一致：被授予『修改勞報單』的角色可以在勞報單頁連結，卻不能在派發頁新增或解除連結。這是已知取捨，另案處理。

## 3. 選派發清單的名單規則
- 勞報單的受領人必須在該派發的人員名單內，兩個入口（勞報單頁、派發頁）都由**伺服器**擋下；名單空白的派發，凡有選受領人的勞報單一律不能連到它（名單空白不等於不設限）；沒有選名冊人員的勞報單照舊可連。
- 清單裡『名單外』的派發顯示成灰色**只是畫面提示**（前端），真正的拒絕在伺服器。測試與驗收請以伺服器回應為準。
- `GET /api/payslip-dispatch-options` 走『查看勞報單』；清單不含金額；案件名稱只給通過案件讀取守門的人。派量到數千筆以上時建議改在 SQL 分頁（效能殘留）。

## 4. 其他
- 勞報單『付款方式』是開放清單，伺服器不驗證是否在清單內（既有行為）。
