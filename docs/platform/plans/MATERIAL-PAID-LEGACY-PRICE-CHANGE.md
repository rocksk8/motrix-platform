# 提案：已全額付款的舊單（材料申請）改價怎麼辦（第 33 班；d7；2026-10-02；**只提案，不實作**）

## 0. 結論先行
建議 **A：已付金額 ≥ 小計的材料申請，金額／數量／單價不可改（守門拒絕，code `paid_in_full`）；要調整就「取消＋另開一筆調整的材料申請」**。
另外對「部分已付的舊單」加一條 **B：新小計不得低於已付金額**。兩條都只在 `material_guard` 加規則，不動資料模型，不影響新單流程。

## 1. 現況（讀程式；對照 `material_guard._gate_orders`、`material_approval.on_substantive_change`、`material_payment.room_for／legacy_paid`）
舊單＝沒有疊加審核列、`paidStatus/paidAmount/paidDate` 是歷史手填或匯款前的登記。
1. 舊單實質欄位被改（單價、數量、小計…）⇒ `on_substantive_change` 建一列**草稿**（`legacy_to_draft`），要重新送審。**沒有**金額相關的限制：`has_payments` 只擋「有活的匯款申請」，歷史已付不算。
2. 草稿＝報表與總帳**不計**（權責口徑草稿／已退回不計；E12 只收已核准與舊單）⇒ 一筆**已付清**的歷史成本，只要有人改了單價就從營運報表與總帳**消失**，直到重新核准。錢已經付出去了，帳卻先少一筆。
3. 重新核准後：額度＝新小計 − 歷史已付（`room_for`）。
   - 改高 ⇒ 多出一段可申請額度，可開匯款申請補差額（合理）。
   - 改低 ⇒ 新小計 < 歷史已付，額度為負，`sync_order_paid` 仍把狀態投影成 `paid`／已付金額 > 小計；系統沒有「多付退款」的概念，也沒有任何畫面提醒。
4. 歷史已付金額在**第一張匯款申請**建立時才凍結進快照；在那之前改價，`legacy_paid` 讀的是當下的 `paidAmount`（已付欄位本身是唯讀的，所以不會被一併改掉，這點目前安全）。

## 2. 選項
| 選項 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| **A（建議）** | 已付 ≥ 小計：實質欄位不可改；要調整＝新開一筆調整的材料申請（走正常審核、匯款）；原單照舊 | 帳不會先少一筆；沒有退款概念也不會出事；規則一句話；實作小 | 要改價必須多開一張單（但這正是「已付清的單不改」的會計慣例） |
| B（輔助） | 已付 > 0 的舊單：新小計不得低於已付 | 擋住「改低造成多付」 | 只擋低不擋高；改高仍進草稿、報表先少一段 |
| C | 草稿期間報表繼續以「上一個已核准版本／舊單快照」計 | 帳不斷 | 要存快照、要改報表／GL 兩處的口徑，風險最大 |
| D | 允許，但改價時強制 superadmin＋理由 | 彈性 | 帳先少一筆的問題還在 |

## 3. 建議實作（第 33 班，S 級）
- `material_guard._gate_orders` 既有列實質變更分支：`paid = MP.legacy_paid(...)＋live 明細合計`；`paid >= 舊小計 - 0.005` 且變更含 `quantity/unitPrice/totalPrice` ⇒ 拒絕 `paid_in_full`（訊息：「這筆材料申請已全額付款，金額不能修改；要調整請另開一筆材料申請，或請管理員取消後重開。」）。非金額欄位（品名、備註、發票日…）照舊。
- 新小計 < 已付（B）⇒ 拒絕 `below_paid`（訊息帶已付金額）。
- 前端：已付清的列金額欄反灰並加說明（沿用 `moLocked` 旁的提示）。
- 測試：全額付款舊單改單價被拒且資料不變、其餘欄位照存；部分已付改低被拒、改高允許（進草稿）；有匯款申請者仍走 `has_payments`；反向控制（拿掉規則 ⇒ 紅）。
- 不溯及既往的處理：已經被改成草稿的歷史案例不自動修復；上機前用一支唯讀查詢列出「草稿且已付 ≥ 小計」的單，交使用者決定要不要手動撤回。
