LINE 通知矩陣：設計說明

分支 feat/line-events-matrix（設計階段，使用者看過才動手實作）。畫面見同資料夾 index.html（假資料、真實事件名稱與群組；左上可切到「現況（對照）」）。

一句話：把「70 個事件各自展開、各自勾 6 個角色」改成「一張矩陣一眼看完、點格子切換、勾選多項一次套用」， 並讓預設偏向「指定人員」而不是整份 Email 收件名單；後端資料結構不動，只加一支批次端點和每項用量欄位。

1. 現況的問題

以下數字來自目前程式（notification-settings.html、line_catalog／line_notify）：

問題具體情形
每項都要各自操作已接線事件 70 項（10 個群組）。每項一個開關、6 個角色勾選框（共 420 個）、再各自展開「設定誰要發」（選模式、選角色、加人員、按儲存）。把 8 個系統告警改成「只發給我」＝約 8 次展開＋8 次選模式＋8 次選人＋8 次儲存。
沒有批次、搜尋、篩選只有群組可收合。找不到「哪些事件已經開了」，也無法只看「還是發給整份名單」的事件。
每一下都是一次請求每個勾選各送一支 PUT …/events/{key}、…/roles 或 …/audience；批次沒有原子性，中途失敗會留下一半的設定。
預設與「LINE 只給特定人」相反事件一開，預設 mode=business＝發給該事件原本的 Email 收件名單（人數由各事件的收件設定決定，可能是整個部門）。要「只發給特定人」得另外展開改。
兩套「角色」語意擠在同一格列上的 6 個勾選是「原本收件人中，哪些角色可以收」（event_roles）；展開裡的角色是「另外指定誰」（audiences.roles）。同一頁出現兩組很像的勾選，意思不同。
看不到用量只有頁首的整體用量條，沒有「這個事件近 30 天發了幾則」，也不知道開了某個事件會耗多少額度（免費方案 200 則／月，每位收件人算一則；達 90% 非「重要」事件會暫停）。

2. 新設計（對照使用者的六點）

需求做法mockup 看哪裡

矩陣上「收件對象」三種模式與角色格的意思

沿用現有三種模式（AUDIENCE_MODES），不新增語意；角色格的顏色區分兩種意思：

收件對象角色格（6 格）指定人員對應的現有資料
照原本收件人（business）灰藍＝篩選原本收件人：只有這些角色的人才收（全亮＝不篩選）不可用（後端此模式不接受指定人員）event_roles[key]（全亮＝移除該鍵）
原本＋指定（business_plus）綠＝另外加入的角色另外加入的人員audiences[key]
只發給指定（only）綠＝收件角色收件人員（沒有任何人＝這則不會發，紅字提示）audiences[key]

人員挑選視窗沿用現行規則：沒有該事件所屬模組權限的人不能指定（ineligible_users）、尚未綁定 LINE 的人以刪除線標示（收不到）、本人自行關閉的仍會尊重。批次時，只要有一個選取的事件某人沒權限，該人就不能被指定（整批一致）。

3. 需要改的 API／後端（越小越好）

3.1 新增一支批次端點（唯一必要的新端點）

POST /api/settings/line-notify/events/batch      （最高管理者；比照現有端點）
{
  "keys": ["backup_stale", "cert_expiry", "..."],      // 1～100 個，必須全是已接線事件
  "enabled": true,                                    // 可省略＝不改開關
  "audience": { "mode": "only", "roles": ["superadmin"], "users": ["zhang"] },   // 可省略＝不改對象
  "roles": null                                       // 可省略；mode=business 時的角色篩選（null＝所有角色）
}
→ 200 { "ok": true, "changed": ["backup_stale", ...], "unchanged": [...] }
→ 400 { "detail": { "message": "...", "errors": [ {"key": "...", "message": "..."} ] } }   // 任何一項不合法 ⇒ 整批不改
  • 原子：先驗證全部（事件是否已接線、角色是否合法、帳號是否存在、指定的人是否有該事件的模組權限——沿用 set_audience 的檢查），通過才在同一把 settings_lock 下一次讀改寫寫回，不會出現半套狀態，也比 N 次單項請求少 N−1 次設定寫入。
  • 新 helper：line_notify.set_events_batch(keys, enabled, audience, roles)；單項函式 set_event／set_event_roles／set_audience 的規則不變，批次內部共用同一組驗證。
  • 稽核：一筆 settings.line_notify.batch（內容：事件清單、開關、對象、角色），不是 N 筆；單項端點仍各記一筆。
  • 「預設組合」不進後端：前端依目前登入者展開（「只發給我」＝users:[自己]；「最高管理者」＝roles:["superadmin"]；「照 Email 收件人」＝{mode:"business"}＋roles:null）。後端沒有組合表要維護。

3.2 每項用量（讀取端，純新增欄位）

  • GET /api/settings/line-notify 的 events[] 每項新增 sent30（近 30 天推出則數）；頂層新增 usage（總則數）。舊欄位與順序不動，舊前端忽略新欄位。
  • 現有資料只有「本月」計數（line_event_usage = {month, events:{key:n}}，推播成功後由 _usage_add 累加；換月歸零）。要做真正的「最近 30 天」需新增一份按日的計數 line_event_usage_daily = {YYYY-MM-DD: {key: n}}，在 _usage_add 同處累加、只保留 31 天（資料量＝已開事件數 × 31，很小）。見下方「要使用者決定的事」第 2 項。
  • （選配）events[].recipient_count＝目前會收到的人數估計，讓列上能顯示「約 N 人」。每項要解析一次收件人，70 項一次算會多 70 次查詢；建議只在矩陣頁的 GET 帶 ?with=recipients 才算，並快取數十秒。mockup 的「約 N 人」是示意。

3.3 前端

  • 矩陣寬（桌面約 1100px 以上）放不進目前「通知設定」頁裡的卡片，建議獨立頁 line-events.html（通知設定頁的 LINE 卡片留 token／啟用／綁定等設定，加一個「LINE 事件管理」入口）。這是要使用者決定的事之一。
  • 元件放獨立的 static/line-events-matrix.js＋CSS，不再增加 notification-settings.html（已 1100 多行）。

4. 相容性

項目結論
設定資料結構不變：line_notify.events／event_roles／audiences 與其讀寫規則（含 fail-closed）原樣；批次只是一次改多個鍵。
既有 API單項三支端點與回應不動；GET 只新增欄位。舊頁面與新矩陣頁可並存，切換前不影響任何人。
發送邏輯不動（deliver_event／resolve_audience／額度保留／每月上限／補發佇列都不碰）。
行為差異（需使用者同意）只有「新開啟時預設對象」一項是新行為：事件從關切到開時，預設改成「只發給我」而不是「整份名單」。若不採用，下拉預設改成「照 Email 收件人」即與現況一致。
測試與守門預期會動到：route_inventory／route_table_golden（新端點）、response_keys_baseline（GET 新欄位）、L1 snapshot 與 modules.json 的 L1.units（新 helper 函式若進公開介面）、core/CHANGELOG.md 的 (next)；line_notify 契約題加批次案例；e2e 要遵守 e2e lint（動作後先等再讀）。
權限與現有端點相同：只有最高管理者。

5. 要先讓使用者決定的事

  1. 新開啟事件的預設對象：採「只發給我」（建議，符合「LINE 只給特定人」），還是維持「照 Email 收件人」？這是唯一會改變現況行為的地方。
  2. 「近 30 天」要不要真的做滾動 30 天：(A) 新增按日計數（建議；小改動、之後才有資料，上線後要累積 30 天才完整）；(B) 先沿用現有「本月」計數（零後端改動，但月初會歸零、看起來沒資料）。
  3. 矩陣放獨立頁，還是留在通知設定頁的卡片裡（建議獨立頁，理由見 3.3）。
  4. 系統告警（「重要」）可不可以被批次關掉：mockup 允許，但關閉前的確認視窗會用紅字提醒；若要更保守，可以讓「重要」事件不出現在批次關閉的範圍。
  5. 角色格兩種顏色（篩選＝灰藍、指定＝綠）使用者看得懂嗎？如果覺得混淆，替代方案是把「照原本收件人」模式的角色篩選收進「進階」，矩陣主畫面只留「指定」語意。
  6. 預設組合清單要不要加：例如「管理者＋我」「財務角色」。目前只放使用者提的三個＋自訂。

6. 實作拆分（核可後）

  1. 後端：set_events_batch＋批次端點＋GET 新欄位（含按日計數，若選 A）＋契約題與守門更新。
  2. 前端：矩陣元件（桌面表格＋手機卡片）、批次列、確認視窗、人員挑選視窗、復原；通知設定頁加入口。
  3. e2e：開關／角色格切換、群組全開全關、批次預設組合、搜尋篩選、手機寬度無橫向捲動；不含重型全量測試。

7. mockup 的限制（請見諒）

  • 所有開關、對象、近 30 天則數、人員（王經理、李業務…）與「約 N 人」都是假資料；事件名稱、群組、「僅 LINE／LINE 細項／重要」標籤與模組權限需求取自真實事件目錄（70 項）。
  • 「預估每月推出」用近 30 天則數乘以收件人數的變化做粗估，只有已開啟、且有歷史則數的事件能推估；新開啟的事件會標註「無法推估」。
  • 復原、確認視窗、批次原子性在 mockup 只是示意；實作時批次由後端整批驗證、整批寫入。
