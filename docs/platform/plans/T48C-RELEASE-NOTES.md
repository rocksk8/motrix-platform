## 1. 使用者可見變更
**A. 勞報單人員連動（person-link）**
1. 勞報單新增頁：從外包名冊選人後，列出這位人員被排進的派工（勾選，預設不勾）；建立時伺服器在同一交易把勾選的派發關聯起來（任一不含此人 ⇒ 400、整張不建）。手打姓名（沒從名冊選）⇒ 只顯示「不會連到任何派工」提示，仍可建立。
2. 案件管理派發卡片「勞報單」區塊下多一行「同一人員的勞報單」：只列連到**同一案件另一張派發**的已確認勞報單（單號、狀態、受領人；無金額）。最高管理者可點進勞報單；一般人員純文字；待確認張數只給最高管理者。
3. 勞報單頁：舊單依姓名推測的名冊對應顯示「身分待確認」標籤；最高管理者按「確認受領人對應」才升格為正式對應（已簽回／已付款／已作廢的舊單不給確認）。
4. 手動新增／解除派發⇄勞報單關聯仍只有最高管理者；派發頁不出現金額、扣繳、身分、銀行資料。

**B. 採購單缺廠商收款帳戶擋付款（po-bank-block；開關預設關）**
5. 開關打開後（見 §3），出納待付款清單中「切換時間點之後建立、廠商收款人、銀行名稱或帳號任一為空」的採購單顯示紅字原因並停用「登錄付款」；後端 409 為最後防線（含用日期端點直接設付款日的繞道）。補資料走第 47 班既有的變更申請。舊單、其他單據類型、員工收款人不受影響。

## 2. Migration 與回滾
| 項目 | 內容 |
|---|---|
| payroll migration 5 | `payslips.contractor_guess_id INTEGER`（NULL＝無推測）。回填只對「`contractor_id` 與 `contractor_guess_id` 皆空、非已作廢、姓名去空白後**恰好對到一位**名冊人員」的舊單寫 guess；同名多位／查無不動；**絕不寫 `contractor_id`、不建任何連結**（金流／總帳／匯款候選只看 `contractor_id`，推測永遠流不進去）；冪等；名冊表不在 ⇒ 只加欄位、回 None。 |
| payroll migration 6 | 修復用：確保欄位存在；並修復「早期開發版 migration 5」的庫（把推測寫進 `contractor_id` 並加 `contractor_match` 欄）——**正式機沒跑過早期版，故正式機上 6 只會確認欄位存在、不改任何資料**。冪等。 |
| po-bank-block | 無 schema 變更；只有 `system_settings.po_bank_block_since`（缺／空＝關閉）。 |
| 回填還原 SQL（先做 DB 備份） | `UPDATE payslips SET contractor_guess_id=NULL;`（已被人工確認升格的 `contractor_id` 是人工決定，不還原）。 |
| 只回程式碼（不還原 DB）是否安全？ | **是**。模組 migration 載入器只跑「版號大於庫內記錄」的支、從不比對「庫比程式新」——實測（庫內 payroll=5、程式只認得 1～4）：無例外、無 incomplete、版號維持。新欄位有預設值，舊程式 INSERT 不帶；舊程式不認得 `contractor_guess_id` 無害；回填完全不碰 `contractor_id` ⇒ 回滾後**沒有金流面殘留**。依人建立時自動寫入的 `payslip_dispatch_links` 與手動連結同表同形，舊頁面照常顯示。po-bank-block 的設定鍵舊程式會忽略。 |
| 還原 DB 備份 | 依慣例（回滾須還原 DB 備份）可用；會一併回到備份當時的連結／確認狀態。 |

## 3. 設定與預設值
- person-link：**沒有設定、沒有開關**，上線即生效。
- po-bank-block：`system_settings.po_bank_block_since`，**預設關**。啟用＝最高管理者呼叫 `PUT /api/extra-expenses/po-bank-block` 帶 `{"enabled": true}`（切換時間點＝現在；可選 `since` 本地時間，不得是未來）；關閉 `{"enabled": false}`；每次變更寫稽核 `settings.po_bank_block.update`。`GET`（財務角色／最高管理者）可看開關、切換時間、目前被擋張數。**建議上線後先觀察、由使用者決定何時開**。

## 4. 驗收清單（使用者在畫面上可觀察；5～8 項）
1. 勞報單新增頁挑一位已排進派工的外包名冊人員 ⇒ 出現他的派工清單（無金額）；勾一張後建立 ⇒ 到案件管理該派發卡片，「勞報單」區塊看得到這張勞報單。
2. 同一案件下，另一張也有此人的派發卡片 ⇒ 「同一人員的勞報單」列出這張（最高管理者可點進、一般人員只有文字；兩者都沒有金額）。
3. 手打姓名建立的勞報單 ⇒ 頁面提示不會連到派工，且不會出現在任何派發頁。
4. 勞報單頁：上線前的舊勞報單若姓名恰好對到名冊一人 ⇒ 顯示「身分待確認」；最高管理者按「確認受領人對應」後標籤消失；已簽回／已付款的舊單沒有確認鈕。
5. 一般人員（非最高管理者）在派發頁看不到新增／解除勞報單關聯的控制項，也看不到「待確認張數」。
6. （啟用 po-bank-block 後）在出納待付款清單，一張新建、廠商銀行或帳號空白的採購單顯示紅字原因、「登錄付款」按鈕停用；同一張經變更申請補齊後可付；上線前建立的舊採購單與差旅單不受影響。
7. 未啟用 po-bank-block 時，出納待付款清單與付款行為與上線前完全相同。

## 5. 風險
1. **回填標記**：舊勞報單被標「身分待確認」的數量由名冊姓名唯一對得到的筆數決定；未確認前不會出現在派發頁（刻意：不靜默連結舊單）。上線後用 `SELECT COUNT(*) FROM payslips WHERE contractor_guess_id IS NOT NULL` 看張數，請最高管理者逐張確認。
2. **已簽回／已付款且帶推測的舊單永遠不能確認**（升格會改變已入帳分錄的對象鍵）；它們維持以姓名為對象，不出現在依人的派發清單。
3. **派發頁行為是刻意收斂**：「同一人員的勞報單」只顯示連到同案另一張派發的勞報單（避免跨案揭露某人的全部勞報單）；沒連到任何同案派發的勞報單不會出現。
4. po-bank-block 的已知取捨：收款人類型被改成 `employee` 的採購單不套這條規則（員工收款走員工帳戶規則）；關閉後再開，新的切換時間點會把「關閉期間建立的單」也納入。
5. 整合風險：兩支 `(next)` 區塊要併成一個、取號流程照常；golden／預檢（A0 產生檔過期）由列車重產。
6. 既有 e2e `test_viewer_without_any_related_module_gets_no_request_and_no_block` 在高負載下曾 timeout（單獨跑穩定通過）——整合閘門若出現請先單獨重跑。
