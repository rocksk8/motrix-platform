## 0. 結論先講

1. **「完全沒有關聯機制」屬實，而且比海光案寬**：系統裡有 4 條成本來源（品項手填實際、材料申請、額外支出、承攬商派發），**沒有任何一處比較「兩個來源是不是同一批工作」**。現有的防重複機制都只擋「同一種來源內」或「來源→採購單」的重複（§2.3）。
2. **用探針實跑確認了兩種會重複計入的情境（§2.4）**：①品項手填 12,500 ＋ 同金額的派發單 ⇒ 總成本把這 12,500 算兩次（**不論派發單有沒有對應到該品項**，只要該品項「不採用」）；②額外支出 6,800 與派發 12,500 都對應到同一品項並「採用」⇒ 品項實際＝兩者相加，系統**沒有任何提示**。
3. **T77 的 `offsets[].ref` 一對多機制不能直接延伸來解這題**（§2.6）：它做的是「一個來源的金額**分配**給多個品項」（分割，總額守恆）；重複計入要的是「兩個來源**互相扣抵**」（總額會變小）。語意不同，直接塞進 `offsets` 會破壞現有的守恆恆等式與總帳對帳測試。可重用的是**寫法與紀律**（`#` 語法、整數分、累計進位、凍結／驗證／失效警示的樣板），不是 `offsets` 的對應語意。
4. **三個方向（§4）**：A 只提示不扣（零資料結構變更）；B 精算層級的「扣抵關係」（新資料，不碰 `offsets`）；C 文件層級連結（同 S4c 單一歸屬，總帳／報表一併生效）。**建議先做 A，B 等使用者裁示 §7 的 Q3／Q4 後再開，C 在使用者明講「報表也要扣」之前不啟動。**
5. **兩件事要先於任何設計確認**：海光案實際的 `summary` 長怎樣（我沒看過，§9 前置查詢 4 仍未做）；以及「品項不採用＋派發已對應」目前是**加在手填之上**，這個不對稱是不是刻意（§2.4 S2，Q2）。

## 1. 範圍與名詞（請先確認我的解讀）

使用者／窗口轉述的「手填成本（material/extra）」我解讀為下列三者，本檔都涵蓋，並明標每個情境屬哪一種：

| 簡稱 | 是什麼 | 存放 | 進哪些合計 |
|---|---|---|---|
| **手填實際** | 精算頁品項的「實際成本」欄，使用者自己輸入的數字（海光案 Cat6 手填 6×6800 屬此類） | 精算存檔 `settlement.items[].actualTotalCost`（`manual_actual()`），**沒有單據** | 只進精算；已完結案經 `summary` 流到下游毛利／獎金／結案 PDF；**不進總帳／營運報表** |
| **材料申請** | 案件 `caseRecord.materialOrders[]`（叫料），可歸品項（`quoteItemId`）或經精算 `offsets(kind=material)` 歸品項 | 報價單 `data_json` | 精算、營運報表、總帳（`recognition.material_money_rows` 同源） |
| **額外支出** | `case_extra_expenses`（含沒連品項的採購單、雜項、類別「料件」等） | 資料表 | 同上（`recognition.extra_entries` 同源） |
| **承攬商派發** | `contractor_dispatches`（含稅承攬費＋外包人員） | 資料表；`items_json` 逐行 | 同上（`recognition.dispatch_entries`、`settlement_actuals.dispatch_rows` 同源） |

> 若「手填成本」只指材料申請／額外支出兩種，則 §2.4 的 S1／S2 屬「手填實際」，可視為範圍外，但它是海光案實際發生的型態，建議留在討論內。

## 2. 現況盤點（✅＝讀碼確認；🧪＝探針實跑）

### 2.1 總成本怎麼算 ✅

`settlement_actuals.compute()` 第 322 行：

```
totalActualCost = itemActualTotal + itemPoUnadopted(預設 0) + extraTotal(未對應額外支出)
                + materialUnassignedTotal(未對應材料申請) + remitFeeTotal + customExpenseTotal
                + dispatchTotal(全部派發的計入額) − dispatchAbsorbed(被「採用」品項吸收的派發)
```

品項層（第 262–274 行）：`purchased = po + material + extra + dispatch`（四種都是「對應到該品項」的金額）；`has` ＝有任何一筆；
`has 且 adopt` ⇒ `actual = purchased`（取代估計與手填）；否則 `actual = 手填 ?? 估計`。

**關鍵不對稱 ✅**：品項「不採用」時，po／材料／額外支出的金額**整個丟掉**（`UNADOPTED_IGNORE`，D8「手填取代、採購不另加」）；但派發不在這個品項層合計裡進出，而是**一律在 `dispatchTotal` 全額計入**，只有「採用」時才用 `dispatchAbsorbed` 扣掉。所以「不採用」的品項上，已對應的派發仍然是**加在手填／估計之上**（既有測試 `test_adopt_off_moving_between_unassigned_and_assigned_keeps_total` 釘住「不採用：不吸收」）。

### 2.2 各來源「怎麼記」的重點 ✅

- 手填實際：一個數字，無 id、無明細、無單據；`adoptSystem=false`（或舊存檔）時生效。
- 材料申請：`totalPrice`；連到有效採購單者金額由採購單負責（S4c 單一歸屬）；其餘歸品項（`link`／`offset`）或留未對應。
- 額外支出：整張單一個去處（`offsets(kind=extra)`，同 `(kind, ref)` 只能一個去處；「多品項拆分不做」是已知限制，USER-DECISIONS-TRAIN33 §C，標註「使用者回來可推翻」）；採購單類（`kind='purchase_order'`）本來就有逐行 `itemId`。
- 派發：整張（舊）／整行／拆分份（T77，`<id>#<行鍵>[#<份次>]` ＋ `amount`），餘額、外包人員留未對應；金額一律含稅口徑。

### 2.3 現有的「防重複」機制，以及它們不涵蓋的 ✅

| 機制 | 擋的是什麼 | 不擋的 |
|---|---|---|
| 規則 A＋「採用」（`SETTLEMENT-ACTUALS-SPEC` §3、D8） | 同一品項「實際採購」取代「估計／手填」 | **來源之間**是否同一批工作；`purchased` 是四種來源直接相加 |
| 單一歸屬 S4c（`purchase_items._link_check`、`material_money_rows.linked`） | 材料申請連到有效採購單 ⇒ 材料金額略過，只算採購單 | 只限「材料申請↔採購單」，且已付款者不算連結（`has_payment`，免得已付的錢從現金報表消失） |
| `offsets`（kind=material/extra/dispatch） | **歸屬**（金額放哪個品項）；`assigned＋unassigned＝total` | 不改總額，因此不可能消除重複 |
| T77 逐行／拆分 | 一張派發分給多個品項，`Σ份＋餘額＝該行` | 同上，是分配不是扣抵 |
| 精算頁「已對應」表、未對應仍計入、完結只警示（USER-DECISIONS §H） | 讓人看得出哪些已被帶入 | 沒有任何跨來源比較或提示 |

沒有 `recognition_flags` 項目在比對跨來源重複（現有旗標只有發票／付款日／階段比例等）。

### 2.5 總帳／報表層 ✅

營運報表與總帳讀同一批原語（`extra_entries`／`material_money_rows`／`dispatch_entries`），**每筆單據各算一次，沒有跨來源扣抵**：額外支出＋派發若是同一批工作，報表與總帳也各記一筆。而**手填實際不在總帳**，S1／S2 的重複只存在於精算 `summary`，經 `DOWNSTREAM_KEYS`（`totalActualCost`、`grossProfit`、`netProfit`…）流到已完結案的毛利、獎金、結案 PDF。
=> 方向要不要「報表也扣」是產品決定（Q3），不是技術細節。

### 2.6 T77 的 `offsets[].ref` 一對多，能不能延伸？ ✅（分析）

T77 做的事：`ref` 文法 `<派發id>#<行鍵>#<份次>` ＋ 每份帶 `amount`，把**一個來源**的金額切給**多個品項**。守恆律：`Σ各份＋餘額＝來源金額`；全部來源加總恆等於 `dispatchTotal`；總額不變。

| 面向 | T77 的分配（allocation） | 本題需要的扣抵（netting） |
|---|---|---|
| 關係 | 來源 → 品項（多對一的函數，因拆分變一對多） | **來源 ↔ 來源**（多對多：一行派發可能對應多張單據、一張單據可能涵蓋多行） |
| 對總額 | 不變 | **變小**（扣掉重複的部分） |
| 守恆律 | `assigned＋unassigned＝total` | `counted＝Σ來源 − Σ扣抵`；扣抵 ≤ 兩側各自金額 |
| 去重鍵 | `(kind, ref)` 唯一＝一個去處 | 同一筆錢最多被扣抵一次，但一個來源可同時出現在多個關係裡 |
| 手填實際 | 沒有 `ref`（不是單據） | 是「被涵蓋」的一側，但沒有 id，只有品項 id |

結論：**不延伸 `offsets` 語意**（也符合使用者「不要直接動 offsets 資料結構」）。可重用：①`#` 文法與百分比編碼（`dispatch_lines.py`）當作「派發側」的指稱；②整數分／累計進位；③凍結（`_freeze`）、驗證（`validate_offsets` 的「上次原樣放行」）、失效警示（`dispatch_line_split_exceeds` 的處理）三個樣板；④V2／V12 式的性質測試做法。

## 3. 不論哪個方向都必須成立的不變式（請審查者拿這份攻擊）

1. **舊資料逐位元不變**：沒有任何扣抵／提示資料時，`compute()` 的所有既有鍵與數值與今天相同；已完結（凍結）案不重算、不遷移。新鍵只能附加（`response_keys_baseline`）。
2. **錢不憑空增減，也不被悄悄藏起來**：扣抵必須由人明示（或明示確認系統建議），**系統不得自動扣**；每一元被扣掉都看得到是因為哪一對關係，且有撤銷路徑。
3. **每筆錢最多被扣一次**：同一來源金額 `Σ扣抵 ≤ 該來源金額`；超過＝422，失效時整組忽略並警示（比照 T77 `dispatch_line_split_exceeds`，不按比例裁、不猜）。
4. **現金是現金**：已付款（`paid_date`／`remit_actual`）的單據**不可被當作「重複」扣掉成本**——錢真的付出去兩次是另一個問題（重複付款，要追回），不是少記。比照 S4c `has_payment`。權責與現金口徑要分開處理。
5. **精算全含稅**（使用者 2026-10-06）：金額比較與扣抵一律用同一口徑（含稅），派發側用 T77 的累計進位分稅結果。
6. **凍結**：新資料隨 `summary` 凍結；`check_finalize` 重算要納入；`DOWNSTREAM_KEYS` 下游讀的鍵名與語意不變。
7. **可回滾**：舊程式／舊頁面遇到新資料不得悄悄丟失（T77 的教訓：舊 `settlement.html` 載入 `offsets` 時只保留 `{kind, ref, itemId}`，存檔會丟 `amount`）——**新資料放哪個鍵、舊頁面存檔會不會把它丟掉，必須在設計階段查證（§8 #10）**。

## 4. 方向

### 方向 0（基準，不開發）：用 T77 現有機制＋操作規範

把派發單逐行對應到品項並「採用」，不再手填同一批工作的數字；有第四種來源（沒有單據的人工／雜項）才手填。

- 解掉：S1（只要使用者改用對應＋採用）。
- 沒解：S2 的不對稱（對應了但仍不採用時仍重複）；S3～S5（單據之間）；使用者忘了這個流程時沒有任何提示。
- 成本：0。是其他方向的**對照組**——若審查者認為海光案用方向 0 就能解，則 A 以上都屬過度設計。

### 方向 A：只提示，不扣（重複嫌疑訊號）

- **做什麼**：`compute()` 附加一個唯讀頂層陣列 `overlapSignals[]`（純函式，無新儲存），畫面在品項列與完結前提醒顯示，不改任何金額。
- **訊號規則（皆為嫌疑，不是判決）**：
  - R1 品項「不採用」且有已對應的派發（S2，高信心：錢一定被算兩次或估計＋派發並存）。
  - R2 品項有手填實際（或估計）且案件內有未對應派發，金額相等或手填 ≥ 派發（S1，低信心）。
  - R3 同一品項上 `po／材料／額外支出／派發` 有兩種以上並存（S3～S5，資訊性）。
  - R4 未對應的額外支出（尤其類別「料件」）／材料申請，與某張未對應派發的**某一行含稅金額相等**（整數分比較）或品名相近（弱，預設只在金額相等時列）。
- **可選的小資料**：`settlement.overlapAck[]`（使用者按「已確認不是重複」的訊號鍵），避免天天提醒。這是唯一的新儲存，且不影響任何金額；若省略，則訊號每次都出現。
- **守恆/金額**：完全不變，§3 #1 自然成立。
- **優點**：零風險遷移；不碰 `offsets`、不碰總帳；可獨立上線；訊號規則可後續調整（不需資料遷移）。
- **缺點**：不解決，只提醒；R2／R4 有誤報；使用者仍要手動刪單／改對應／切換採用；報表層重複（額外支出＋派發）完全看不到。
- **規模**：後端小（一個純函式模組＋`compute()` 掛一個鍵＋響應鍵基準）；前端小到中（徽章＋完結提醒）；測試中（每條規則的正反例、誤報控制、效能 O(品項＋派發行)）。

### 方向 B：精算層級的「扣抵關係」（新資料，不碰 `offsets`）

- **資料模型（草案）**：精算存檔新增獨立頂層 `overlaps`：
  ```
  {"id":"<穩定id>", "covered": {"kind":"extra|material|itemManual", "ref":"<單據id>|<品項id>"},
   "by": {"kind":"dispatch", "ref":"<派發id>#<行鍵>[#<份次>]"},      // 沿用 T77 文法指稱派發側
   "amount": <含稅金額，整數分，> 0>}
  ```
  語意：「`covered` 這一側已經包含在 `by` 那一側裡，`amount` 元不要重複計入」。**被扣掉的一側由使用者明選**（預設建議扣沒有發票／沒有簽核的那一側，但不自動）。
- **計算**：`covered` 側的計入額減 `amount`（品項層：該品項 `purchased` 或手填數字減少；非品項的未對應列：該列減少）；新增 `totals.overlapNettedTotal`，`totalActualCost` 自然減少；`counted＝Σ來源−Σ扣抵`。
- **驗證**：兩側都存在且可計入；`amount ≤` 兩側各自當前金額；同一 `by` 行的 `Σ amount ≤` 該行金額；同一 `covered` 的 `Σ amount ≤` 該單據金額；**已付款單據不可作為 `covered`**（§3 #4）；`itemManual` 只在該品項「不採用」時有意義（採用時手填數字被整個取代），切換採用時要警示。
- **失效**：任一側被改小到超過 ⇒ 該關係整筆忽略＋警示（不裁減）；任一側被取消／退回 ⇒ 同。
- **凍結／完結**：`summary.overlapNettedTotal` ＋ `check_finalize` 重算；下游鍵名不變。
- **與總帳對帳**：現有恆等式「精算採購類＋未對應＋額外＝報表＝總帳」須改成 `… = 報表 − 精算層扣抵`（測試要顯式加這一項，**並在畫面標示「報表尚未扣除」**），否則漂移守門會紅。
- **優點**：直接解 S1～S5 的金額；範圍只在 `case` 模組；T77 的樣板可大量重用；可撤銷、可凍結、可審計。
- **缺點／風險**：新增一類資料與一個新的守恆律；精算與總帳／報表**刻意不一致**（需要清楚標示，容易被誤解）；`itemManual` 與「採用」互動複雜；兩側單據金額事後可變（需失效規則）；前端要新增一個「指認重複」的編輯器；舊頁面存檔可能丟失 `overlaps`（§3 #7）。
- **規模**：後端中（新純函式模組＋`compute`／`validate`／`_freeze`／`check_finalize`）；前端中到大；測試大（性質測試：隨機關係組合下守恆、舊結果逐位元不變、凍結、失效）。

### 方向 C：文件層級連結（同 S4c 單一歸屬；報表／總帳一併生效）

- **做什麼**：額外支出／材料申請（可選：品項手填不適用）新增選填欄位，指向派發單與行（`dispatchRef`＋可選 `amount`），意義＝「這筆單據的錢已包含在該派發單行」。`recognition` 原語（`extra_entries`／`material_money_rows`）對有連結的單據在**權責口徑**略過（或扣減）金額，營運報表、總帳、精算三處因同源而一致。
- **優點**：單一真相、無「精算與報表不一致」問題；解掉 §2.5 報表層重複；與已存在的 S4c 模式一致。
- **缺點／風險**：①需要儲存位置（額外支出新欄位／`lines_json`；材料申請在 `data_json`），涉及 migration 與（額外支出）審核雜湊／狀態機；②**既有已出報表／已入帳月份的數字會因補連結而改變**（需要生效日或凍結策略，會計影響要使用者與財務裁示）；③牽動 `reports.py`、`gl_events`、承攬商傳票、薪資付款等多個消費者；④誰有權限宣告連結；⑤現金口徑不能扣（§3 #4），權責與現金會在這筆上出現差異，需要說明；⑥**手填實際沒有單據，C 無法涵蓋 S1／S2**。
- **規模**：後端大（schema＋原語＋多消費者＋遷移＋回溯政策）；前端中；測試大且要跑全域守門。
