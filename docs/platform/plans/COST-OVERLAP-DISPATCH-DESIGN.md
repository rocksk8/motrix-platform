## 0. 結論先講（v4）

1. **「完全沒有關聯機制」屬實**：4 條成本來源（品項手填實際、材料申請、額外支出、承攬商派發）彼此不比對；現有防重複機制都只擋同一種來源內，或「材料申請→採購單」（§2.3）。
2. **「對應了卻仍重複」不是計算缺陷，是刻意設計**：`DISPATCH-OFFSET-SPEC` §1–2 明寫「不採用→估計不變；取消對應＝回未對應仍計入成本」，並被 `test_settlement_dispatch_offset_2026_10_04.py:59/92` 釘死。派發在精算裡「**永遠是成本**；『採用』只決定它要不要取代該品項的估計」。這是工程／PM 設計，**使用者從未被問過**（`USER-DECISIONS` §H 派發段沒有這題；D8 問的是採購）。
3. **單據之間（額外支出／材料申請↔派發，S3–S5）**：會計正解先在**來源端處理**（作廢重複單據、或開折讓單——折讓的報表／傳票影響**未驗證**）；正式機實測 **0 件**（小樣本，§2.7）。
4. **誘因與儲存是方向 3 的硬約束**：排除降成本→抬高 `netProfit`→影響獎金。現有金額閘 `require_case_money` ＝「財務角色**或案件擁有者**」（`case_access.py:68-74`），不可沿用；且 `quotation PUT` 只對 `settlement` 用 DB 現值覆蓋，**其它 `data_json` 頂層鍵取自 client 整包**（`quotations.py:2436-2444`、:2500），舊頁面副本會洗掉——所以新資料**唯一可行的形式是獨立表＋獨立端點＋獨立權限**（§3 #7、#8）。
5. **UI 關採用確實會重複計入（v4 修正 v3「不一定」）——PM 在正式機資料上重算**（§2.7，轉述、我未親驗）：`toggleAdopt`→`calcItemCost` 會用 `halfUp(actualQty×actualUnitCost)`（依稅別）重算並**覆寫** `actualTotalCost`。
   - 海光案 4 品項：Cat6／9U 機櫃／材料三項關採用後金額不變；保險費用 95,162→17,042（存檔的數量×單價只對應「團保三人」一行未稅 16,230，95,162 是 3 行派發合計）。全關後 `itemActualTotal` 97,262 ＋ `dispatchTotal` 175,382（不再被吸收）＝**272,644**，比現況多算 97,262。（v2／v3 的 350,764 是「伺服端直接假設 `actualTotalCost` 不變」的理論值，不是 UI 路徑。）
   - **MQ-202607-045（草稿、活案）**：關採用後該品項 33,400→25,000，加 `dispatchTotal` 33,400 ⇒ 相關成本 58,400，多算 25,000。**這是正式機上真會被觸發的案例，不是理論。**
   - `_actualsOk=false` 的舊路徑：關採用**不重算**、值不動 ⇒ 「存檔值＋派發」型重複。
   - 同時，「手填值＝派發行合計」對採用中的品項仍是套套邏輯（採用時 `actualTotalCost` 被頁面設成系統金額）；真正的手填值藏在 `actualQty／actualUnitCost` 欄位裡，關採用時才現形。

## 2. 現況盤點（✅＝讀碼；🧪＝探針實跑）

### 2.1 總成本與「採用」的設計模型 ✅

`settlement_actuals.compute()` :322：

```
totalActualCost = itemActualTotal + itemPoUnadopted(預設 0) + extraTotal(未對應額外支出)
                + materialUnassignedTotal + remitFeeTotal + customExpenseTotal
                + dispatchTotal(全部派發計入額) − dispatchAbsorbed(被「採用」品項吸收的派發)
```

品項層（:262–274）：`purchased＝po＋材料＋額外支出＋派發`（四種對應到該品項的金額）；`has` 且 `adopt` ⇒ `actual＝purchased`；否則 `actual＝手填 ?? 估計`。

**設計模型（M1 修正）**：
- po／材料／額外支出：品項「不採用」⇒ 整筆**從總額丟掉**（`UNADOPTED_IGNORE`，D8，使用者 2026-10-02 夜裁示「手填取代、採購不另加」）。
- 派發：**永遠在 `dispatchTotal` 全額計入**，「採用」才用 `dispatchAbsorbed` 扣掉（取代估計）；「不採用」＝估計／手填不變、派發另加。工程／PM 設計，使用者沒被問過，測試釘住。
- 兩者不對稱，但各有出處；**是否合理是產品問題（§7 Q-C），不是 bug**。

### 2.2 各來源怎麼記 ✅

- 手填實際：一個數字，無 id、無明細、無單據。舊存檔（品項有存但沒有 `adoptSystem` 鍵，第 32 班前）＝預設**不採用**（:266；頁面載入 :1383 的 `!!si.adoptSystem` 與後端一致，無漂移）。**採用中品項的 `actualTotalCost` 是頁面寫入的系統金額快照**（`calcItemCost` :2086；載入後 :1400 重新對齊），不是獨立手填。（v1 曾推論海光案屬 legacy 舊存檔——與 M4 的 `adopt=true` 矛盾，已撤回；正式機 `legacySave` 僅 MQ-202608-007 一案。）
- 材料申請：`totalPrice`；連到有效採購單者金額在採購單（S4c）；其餘歸品項（`link`／`offset`）或留未對應。
- 額外支出：整張單一個去處（`offsets(kind=extra)`）；「多品項拆分不做」是已知限制（USER-DECISIONS-TRAIN33 §C，標註「使用者回來可推翻」）；**不接受負值**（`expense_forms.py:92-97`：金額／數量單價為負 ⇒ 400）。
- 派發：整張（舊）／整行／拆分份（T77，`<id>#<行鍵>[#<份次>]`＋`amount`），餘額、外包人員留未對應；金額一律含稅口徑。

### 2.3 現有「防重複」機制與不涵蓋的 ✅

| 機制 | 擋的 | 不擋的 |
|---|---|---|
| 規則 A＋「採用」 | 同一品項「實際採購」取代「估計／手填」 | **來源之間**是否同一批工作；`purchased` 是四種直接相加 |
| 單一歸屬 S4c（`purchase_items._link_check`） | 材料申請連到有效採購單 ⇒ 只算採購單 | 只限「材料申請↔採購單」；已付款者不算連結（`has_payment`，免得已付的錢從現金報表消失） |
| `offsets`（material／extra／dispatch） | **歸屬**；`assigned＋unassigned＝total` | 不改總額，不可能消除重複 |
| T77 逐行／拆分 | 一張派發分給多品項，`Σ份＋餘額＝該行` | 同上（分配） |
| 「已對應」表、未對應仍計入、完結只警示（§H） | 讓人看出哪些已帶入 | 無跨來源比較 |

`recognition_flags` 沒有跨來源重複旗標。

### 2.6 T77 的 `offsets[].ref` 一對多能不能延伸？（v2 改寫）

T77 做的是**分配**：`<派發id>#<行鍵>#<份次>`＋`amount`，把一個來源的金額切給多個品項；守恆 `Σ份＋餘額＝來源金額`。

- **v1 說「不能」過強**。若在去處（品項）之外加第三個桶「**排除（重複）**」，同一套 partition 文法仍成立：`assigned＋unassigned＋excluded＝total`，其中 `total` 仍是毛額；舊資料沒有排除桶＝0，恆等式逐位相同。**這是擴充，不是破壞**。
- **也不需要「來源↔來源」的成對關係**（v1 以為需要）：記帳只需要「這筆／這行／這份被排除多少、為什麼」，`by`（對照哪一筆）只是備註。去掉成對關係，v1 方向 B 的「Σ≤兩側金額」「同一 by 行 Σ≤行金額」「兩側失效規則」大半不需要。
- **代價**：①失去成對的參照完整性——被拿來對照的那一筆日後被取消，排除的成本會**悄悄消失**（需警示，見 §4 方向 3 風險）；②使用者指示「不要直接動 offsets 資料結構」，所以若走這條，**要不要擴充 `offsets`，或另立平行頂層鍵，需使用者明確同意**（兩者都有 §3 #7 的舊頁面問題）。
- **仍可重用**：`#` 文法與百分比編碼（`dispatch_lines.py` 的同一個 parse，不可另寫）、整數分／累計進位、`_freeze`／`validate_offsets`「上次原樣放行」／失效警示的樣板、V2／V12 式性質測試。

## 3. 不論哪個方向都必須成立的原則（請審查者拿這份攻擊）

1. **舊資料逐位元不變**：沒有任何新資料時，`compute()` 既有鍵與數值與今天相同；已完結（凍結）案不重算、不遷移。
2. **錢不被悄悄藏起來**：任何扣減都要由有權限的人**明示**（附原因、可撤銷、留稽核軌跡），系統不得自動扣。**注意：既有 D8／IGNORE 本身就違反這條**（不採用時已對應的 po／材料／額外支出整筆消失，只警示）——所以 §7 Q-C 不能被當成「單純一致性」題。
3. **每筆錢最多被排除一次；失效方向統一為「不採用該排除（成本照算回來）＋警示」**：`Σ排除 ≤ 該來源金額`，超過＝422；任何失效（對照對象不再計入、金額變小、付款狀態變動、被排除項本身不再計入）一律**讓該排除不生效、錢算回總成本**，並發警示——這是安全方向，**絕不「警示但繼續藏錢」**（v2 §3#3 與方向 3 風險 2 曾自相矛盾，已統一）。不按比例裁、不猜。
4. **現金是現金**：付款狀態是排除決策的必要資訊，不是一律禁止。要排除的是「重複的那一側」，可能是派發（未付）而不是額外支出（已付）；資料模型**不得**預設排除哪一側。已付款側被排除須強制填原因並提示「疑似重複付款」。付款狀態事後變動（未付→已付）使排除失效（`compute()` 能讀額外支出 `paid_date` 與派發 `remit_actual`）；**完結案不重算，付款變動只對草稿案自動失效，完結案只顯示「快照之後對照對象已變」橫幅**。
5. **精算全含稅**（使用者 2026-10-06）：金額比較與排除一律用含稅口徑，派發側用 T77 累計進位分稅。
6. **凍結**：新資料隨 `summary` 凍結；`check_finalize`／`_expected_downstream` 等 6＋1 份公式同步（§2.5）；下游鍵名與語意不變。
7. **舊頁面會丟新鍵、以及新資料只能放哪裡（已確定的設計約束）**：
   - `settlement.html:2254-2290 buildPayload()` 是**白名單**；載入端 :1366 只讀已知鍵；後端 `settlement_api.py` `data["settlement"] = body.settlement` 是**整包取代、不合併**。⇒ 放在 `settlement` 裡的新鍵（`exclusions`／`overlapAck`）或 `items[]` 新欄位，沒改頁面的版本一存檔就全丟。
   - `quotation PUT`（`api/quotations.py`）只對 `settlement` 用 DB 現值覆蓋（:2436-2444）；**其它 `data_json` 頂層鍵取自 client 整包，:2500 寫回**。⇒ 放在 `data_json` 的任何新頂層鍵，都會被過期的頁面副本洗掉，除非另外加同樣的保留邏輯。
   - **結論**：持久化的新資料（排除、ack）**唯一可行的形式是獨立表＋獨立端點**。不走「後端對未知鍵合併」（會讓擁有者經整包 PUT 夾帶／覆寫該鍵，繞過授權）。獨立表上線前的檢查清單（**均未驗證**）：備份／匯出／刪除暫存區（回收桶）是否涵蓋新表、權限矩陣新增項（能力總數與預設角色）、`MODULE-GUIDE` 的模組邊界守門。
8. **誰有權宣告「重複」＝誘因與職責分離**：排除降成本→抬高 `netProfit`→影響獎金（`payroll/bonus.py` 讀 `netProfit`；`dashboard.py:218-221`、`reports.html` 也讀）。
   - **B1 不可沿用 `require_case_money`**：它是「財務角色**或案件擁有者**」才過（`case_access.py:68-74`），而現行精算 PUT 本來就允許擁有者（業務，獎金受益人）。沿用＝你要防的情境。需要**新的、與精算編輯分開的權限**（財務／超管），**獨立端點**。
   - **B2 不可搭在整包精算 PUT 上**：伺服端無法分辨 `exclusions` 是誰改的，「declaredBy 伺服端蓋章」得做 diff 與逐筆授權，脆弱（同 #7）。
   - **B3 補償性控制**（第二人核准之外）：排除必須出現在獎金 PDF／結案 PDF 的特例列；另提供一份「排除清單」給管理者月檢；核准門檻可依對 `netProfit` 的影響金額分級。
   - 是否比照 D-K1／定義治理「放寬需第二位最高管理者核准」、完結案補扣走「重新開啟＋理由＋再完結」，見 Q-A／Q-B。**重開已完結案補扣的獎金連鎖（獎金是否已發、是否重算）我沒有驗證**——標「未查」。
9. **金額可見度**：排除的讀寫端點有自己的權限閘；回應不得讓沒有金額權限的人看到金額。

## 4. 方向（v4：四類）

### 方向 1：來源端處理（基準做法；v1 漏列）

- **1a 作廢重複單據**：S3–S5 的會計正解是在來源取消重複的那張（額外支出已有 `VOIDED_STATUS`；派發可取消），同時修正精算、報表、總帳、獎金，**不需要新機制**。操作規範：先對應＋採用；確定重複就作廢。
- **1b 折讓／負數調整單（未驗證，不可列為已解）**：額外支出目前不收負值（`expense_forms.py:92-97`）。開放「折讓」類別（金額為負、走一般核准）理論上可處理「部分重複」並同時修正精算與報表／總帳，但**負值在認列、傳票、稅額拆分、報表的處理我與審查者都沒驗證**；`compute()` 註解提到採購單列層級已有「負數退款列」，先查它的處理可能比在額外支出新開負值便宜。
- **為何仍需要別的方向**：只在「兩張單據都合法、都不能作廢」時才有必要——**這才是真正的需求描述，使用者尚未被問過**（§7 Q-D）。若多數案例其實是「其中一張可作廢」，則方向 1 就夠，不必新增機制。
- 規模：1a 零；1b 後端小到中（驗證放寬＋報表顯示），風險在負值語意。

### 方向 2：提示（v4：兩層；PM 數據證實了前端路徑）

**背景**：PM 的重算（§2.7）證實「UI 關採用」是真會重複的路徑（海光 +97,262；045 活案 +25,000）。v3 一度把前端提示降級，v4 恢復——但實作約束比 v2 嚴格；同時後端偵測必須有顯示出口。

#### 層 A：前端「關採用」確認提示（針對已證實的路徑）

- **內容**：使用者按下關閉採用時，先模擬翻轉後的結果再確認：「關閉後此品項實際成本 A→B（依手填欄 數量×單價），已對應派發 Z 不再被吸收；預計總成本 T0→T1（+Δ）。確定？」只有 Δ>0（或超過門檻）才跳。
- **實作約束**：①用**頁面本地函式**模擬（`calcItemCost` 的重算分支、`itemActual` :1692、`systemActual` :1469、派發吸收、`calcSummary`），使用者看到什麼就提示什麼；②**必須涵蓋 `_actualsOk=false` 的退化分支**（`toggleAdopt` 不重算、值不動）；③**不得用 `actualIfAdopted`／`actualIfNot`**：頁面完全沒用它們；預覽端點 `PreviewIn` 只收 `offsets`（`api/settlement_actuals.py:46-50`），`compute()` 用 DB 已存檔的 `items`，不含頁面未存的編輯，漂移是結構性的；採用中品項的 `actualIfNot`＝存檔快照＝系統金額，會讓每個採用中的派發品項都跳假警報；④不存任何東西、不新增端點。
- **T-1 驗證（釘住不漂移，擴充既有 e2e）**：擴充 `test_e2e_settlement_dispatch_offset_2026_10_04.py:384` 已有的「`adoptSystem=false`＋`actualUnitCost=20`」案例，矩陣包含：`actualCostTaxMode`（`taxed` ÷1.05／`taxed_gross` ×1.05／其他）、`actualQty`、`_fromSave`／`_fromSystem`、`applyAdoptDefaults`、`_actualsOk=false`、save→reload→toggle（`schemaVersion<2` 載入分支）、已完結重開。每格以「頁面翻轉後的總成本」對照「用翻轉後的 settlement PUT 給後端 `compute()` 的結果」，兩者必須一致。

#### 層 B：後端 `compute()` 的 `warnings[]`（針對已存狀態與 UI 之外的路徑）

- **規則**（皆非阻擋）：
  - **W1** 品項 **`adoptSystem=false`**（採用中的品項不得觸發——採用中「手填＝派發」是恆真式）＋有手填金額（非空）＋已對應派發。
  - **W2（候選，未量測前不宣稱精準）** 品項手填（含 `legacySave` 預設不採用）＋案內有未對應派發＋手填與該派發含稅額相等（整數分，±1 元）。**它會漏掉海光真實型態**（手填＝指派到該品項的派發**行**之和，不等於整張）；上線前必須離線模擬。
  - **W3（兼任方向 3 偵測器）** 額外支出或材料申請與某派發行含稅額相等（整張／逐行含稅／逐行未稅×1.05／÷1.05，±1 元）。±1 加上 ×1.05／÷1.05 變體會撞巧合：**設金額下限（建議 ≥1,000）、限同案、訊息必須同時帶兩邊單據 ref**。
  - **W4（PM 的新訊號）** 採用中且有已對應派發的品項，其手填欄（`actualQty×actualUnitCost`，依 `actualCostTaxMode`）與存檔 `actualTotalCost` 差異 >1 元 ⇒ 「取消採用將把實際成本改寫為 X，且派發 Z 不再被吸收」。正式機命中 4 列（§2.7；其中 2 列單價為 0，關採用會變成 0 成本，訊息需分開）。**代價**：後端要複製一份 `calcItemCost` 的重算（`halfUp` 加三種稅別），是又一份公式副本，需以 golden vector 做前後端等值測試（先例：`profit_rules.py`／`profit-rules.js`）。
- **閘門**：`compute()` 先算 `warnings` 再 `_freeze`，所以**要明確閘：凍結路徑（`freeze=True` 且 `status=finalized`）不發 W 警示**；`check_finalize` 以 `freeze=False` 呼叫 `compute()`，完結當下可算。
- **顯示出口（v3 的「已有顯示管道」不成立，刪除）**：`settlement.html:1804 dlWarnings()` 只挑 `code` 以 `dispatch_line_` 開頭的；W 碼（連既有 `item_removed`／`item_unkeyed`）頁面都不顯示；後端 `compute()` 的外部呼叫只有 GET 與 POST preview，沒有任何地方記錄或彙整 `warnings`。**只加 `warnings[]` 不等於偵測器，沒人看得到。** 採用 **(b)＋最小 banner**：①完結時把 W 命中寫進 settlement 編輯歷史的完結快照（`settlement_api.py:145` 那條）；②PM 的唯讀正式機查詢定期重跑；③`settlement.html` 加一個最小 banner 顯示 W 碼（**需改頁面**——v3「不碰頁面」的說法撤回）。已完結案需要明確 banner，否則警示無處放。
- **受影響的既有測試（W 碼一加就可能紅）**：`test_settlement_dispatch_lines_2026_11_07.py` 對 `warnings` 做整列表相等斷言（已確認 :255、:257、:284、:288、:291、:298 等；hichan-8 另列 :393／:449）；`test_settlement_actuals_2026_10_03.py:172／:187`（整列表）；`test_dispatch_abnormal_amount_2026_11_08.py:53／:65` 用 `any()`／`not any()`，**看起來安全，待驗證**。夾具只要有「手填＋派發」組合就會命中。
- **精度與量測**：W1–W4 上線前必須用 2b 的 20 品項池加正式機資料離線模擬，記錄命中／誤報數，**把數字寫進本文件**；沒有數字不得宣稱精準。量測門檻見 §6。
- **棄用**：v1 的 R2「手填≥派發」洗版、R3「同品項多來源並存」是規則 A 的正常混合用法、R4 弱；**`actualSource` 規則作廢**（正式機 `legacy`／`labor` 皆 0 件）。

### 方向 3：精算層「排除（重複）」（先關閉；重啟條件見 §6 #3）

- **重啟條件**：①W3 或正式機查詢出現實例；②使用者在 Q-D 說明兩張單據都合法的真實情境。重啟前必須先裁示 Q-A／Q-B。
- **形狀**（不成對）：
  ```
  {"kind":"extra|material|dispatch", "ref":"<單據id>|<派發id>[#行鍵[#份次]]",
   "amount": <含稅整數分；整張可省略>,
   "reason": "<必填：重複／誤填／其他>",
   "against": {"kind":"…","ref":"…"},          // reason=重複 時必填、結構化
   "declaredBy":"<伺服端蓋>", "declaredAt":"<伺服端蓋>"}
  ```
  任一來源（含派發）都能是被排除側（解 §3 #4）；派發沿用 T77 文法（共用 `dispatch_lines` 的同一個 parse）。
- **放置與授權（§3 #7、#8）**：**獨立表＋獨立端點＋獨立權限（財務／超管）**，是唯一可行形式（其它 `data_json` 頂層鍵會被舊頁面副本洗掉）；不再考慮 `offsets` 第三桶或 `settlement` 內新鍵。
- **有效性在 `compute()` 的純函式內判定**：對照對象（`against`）仍計入成本（狀態）、對照對象金額 ≥ 被排除金額、被排除側與對照側付款狀態沒變；任一不成立 ⇒ 該排除失效（成本照算，§3 #3）＋警示。非「重複」原因可免 `against` 但要核准。完結案不重算，僅顯示橫幅；**獎金已發後重開完結案補扣的連鎖（重開→W 命中→調整→獎金重算）未驗證**。
- **不支援「扣手填」**：手填實際沒有單據，使用者直接改數字（或改採用派發）即等於扣抵；且 `_freeze` 對品項金額取存檔的 `actualTotalCost`，扣手填會使凍結金額與重算金額不同，`check_finalize`（容差 ±品項數）409，唯一解是把扣後值寫回 `actualTotalCost`——覆蓋原始輸入、失去稽核。
- **計算**：被排除的金額不計入；`totals.overlapExcludedTotal`；`totalActualCost` 自然減少；已被排除的來源不可再 `offsets` 對應（互斥）。
- **凍結／下游**：是否進 `DOWNSTREAM_KEYS`（:639）是關鍵決策——進了就被 `_check_downstream`／`fill_downstream`／`rebuild_summary_if_missing` 全部重算（§2.5 的公式副本表與讀取者都要改）。呈現端：報表 Excel 毛利表、獎金 PDF、結案 PDF 各加「已排除（重複）−X」特例列；被排除的是派發時還要處理 `_dispatch_split` 與 `check_finalize` 三項比對。
- **風險**：①誘因（§3 #8）；②對照對象日後變動——由 `against` 有效性判定處理；③付款狀態；④毛利與獎金變動但明細帳與總帳不變（精算與總帳刻意不一致，畫面與報表要明示）；⑤改動面大。
- 規模：後端大（新表＋端點＋權限＋純函式＋公式副本 7 處）；前端中到大；呈現端 3 處＋讀取者 5 處；測試大。

### 方向 4：文件層級連結（同 S4c；報表／總帳一併生效）

在額外支出／材料申請新增選填連結，`recognition` 原語在權責口徑略過有連結的金額，報表、總帳、精算三處同源一致。優點：單一真相。缺點：需 migration 與審核雜湊／狀態機；**歷史報表數字會因補連結而變**（需生效日與財務裁示）；牽動 `reports.py`、`gl_events`、傳票、薪資付款等消費者；手填實際無單據無法涵蓋；現金口徑不能扣。**不啟動**，除非使用者明講「明細帳與總帳也要扣」且財務確認回溯政策。
