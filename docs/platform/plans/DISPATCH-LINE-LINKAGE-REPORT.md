# 精算「承攬商派發單」聯動到報價品項：現況與逐行聯動的做法

> 2026-11-07｜讀程式＋正式機回報的資料整理，**沒有改任何程式、沒有碰正式機資料**｜案件：MQ-202607-025（大綜電腦系統，海光企業大樓拓樸圖案）
> 讀的程式：`backend/modules/case/settlement_actuals.py`、`frontend/pages/settlement.html`、`backend/modules/subcontract/`（派發單）、`frontend/js/case-management-dispatch.js`

## 1. 結論（先講）

使用者說的「各報價項目精算沒辦法聯動到承攬商報價的品項」**是對的，但不是壞掉，是目前功能的範圍就只到這裡**：

- 系統現在只能把**「整張派發單」對應到「一個」報價品項**。
- 派發單裡的**逐行品項**（這張單有 9 行）沒有任何欄位、也沒有畫面可以對應到報價品項。
- 這張案件甚至連「整張對應」都沒用到：精算存檔是 33 班前的舊格式草稿，沒有 `offsets`；使用者是手填實際數量與單價去對應派發單內容（例如 Cat6 線手填 6 × 6800，對應派發單那行「康普 UTP CAT6 網路線 6 箱 × 6800」）。

## 2. 現在的機制（程式面，已對照）

| 問題 | 答案 | 出處 |
|---|---|---|
| 對應存在哪？ | 精算存檔裡的 `offsets`：`[{kind, ref, itemId}]`。`kind="dispatch"` 時 `ref`＝派發單 id（`contractor_dispatches.id` 的字串），`itemId`＝報價品項 id。**不寫進派發單，也不改報價單。** | `settlement_actuals.py` `normalize_offsets`、`compute` 第 151、197–204 行 |
| 派發單怎麼被列出？ | `dispatch_rows()`：整張單當**一列**（`itemId`＝派發 id 字串），金額＝含稅承攬費＋外包人員。排除已取消、審核狀態為草稿、已退回者；待審核／簽核中照列並標 pending。 | 第 398–424 行 |
| 品項要什麼條件才能當對應目標？ | 品項要有**非空的 `id` 且有 `description`**（`plan_items`）；缺其一的舊品項視為 `unkeyed`，不能當目標。標題列（`type="header"`）不算。 | `purchase_items.py` `plan_items`；`compute` 第 129–141 行；`validate_offsets` 第 374 行 |
| `itemId` 怎麼產生、怎麼比對？ | 報價單新增品項時由前端 `genId()` 產生（UUID；更舊的資料可能是數字）。後端一律轉成字串後比對；前端下拉也用字串比對。 | `quotation-form.html` `genId`；`settlement.html` 第 659–661 行 |
| 一張派發單可以拆給多個品項嗎？ | **不行**。`off_dispatch` 是 `{派發id: 單一itemId}`，整張歸一個品項。 | 第 151、200–204 行 |
| 「未對應」是正常還是異常？ | **正常狀態**。未對應的派發單金額**仍照算**，計入總成本（`dispatchTotal`）；使用者在 2026-10-04 裁示完結時只警示、不擋。 | `USER-DECISIONS.md` §H；`settlement_actuals.py` 第 264–276 行 |
| 使用者怎麼建立對應？ | **手動**：精算頁「二之一」區塊，每列一個下拉選品項（`setOffset`），然後存檔。沒有自動比對。 | `settlement.html` 第 655–663、1692–1700 行 |

派發單本身的逐行（`items_json`）：每行只有 `id`、`description`、`qty`、`unit`、`unitPrice`、`amount`、`note`，**沒有 `quoteItemId` 之類的鍵**（`case-management-dispatch.js` `addDispatchItem`）。材料申請才有逐項連結（`quoteItemId`），派發單沒有同等機制。精算頁「三、承攬商派發成本」每張派發只顯示承攬商一列＋外包人員列，**不展開 `items_json` 的行**。

## 3. 一個要先確認的風險：這張案件可能重複計入成本

這張的精算是手填實際成本，而派發單 id=1（阿郎音響，未稅 167,030）沒有對應到任何品項，屬於「未對應」。依程式，**未對應的派發金額仍計入總成本**：

`totalActualCost = 品項實際成本合計 + … + dispatchTotal（全部派發） − 已被品項吸收的派發`

所以「手填品項實際成本」＋「整張派發單金額」會**兩邊都算進去**（只有派發被「採用」的品項吸收時才會扣掉）。若手填的金額本來就是派發單內容，總成本可能多算約一張派發單的金額。

⚠️ 這是我從程式推論，**我沒看過這張單的精算資料與合計**，需要用正式機實際的 `summary`（`itemActualTotal`、`dispatchTotal`、`dispatchAbsorbedTotal`、`totalActualCost`）核對，才知道是否真的重複。這張派發單今天 14:41 送完工簽核中，核對時只讀、不要改正式機資料。

## 5. 如果要做「逐行聯動」：要改什麼

### 設計方向（建議）：**對應存在精算的 `offsets`，不要寫進派發單**

正式機提的 (a)「派發單 `items_json` 加 `quoteItemId`」有一個副作用：`items_json` 是派發單「實質欄位」，核准當下會存雜湊，之後內容不同就**需要重新送審**（`dispatch_flow.substantive_hash`）。也就是已核准、簽核中的派發單不能為了做對應而改，這張今天剛送簽核中也一樣。

替代做法：派發單的每一行**本來就有 `id`**，所以把 `offsets` 的 `ref` 擴充成 `派發id#行id`（例如 `1#173...`）。對應仍存在精算存檔，不動派發單、不影響核准流程；舊的整張對應（`ref` 沒有 `#`）原樣有效。

### 需要改的地方

| 位置 | 改什麼 |
|---|---|
| `settlement_actuals.py` `dispatch_rows` | 選用展開：每張派發單除了整張那一列，附上逐行（`description`、`qty`、`unit`、`unitPrice`、`amount`）與稅額分攤 |
| `compute()`（`off_dispatch`） | 改成按行分配：被對應的行歸入該品項，**沒被對應的行＋外包人員＋稅額尾差留在該派發單的未對應列** |
| `normalize_offsets`／`validate_offsets` | 接受 `ref="派發id#行id"`；檢查行 id 存在於該張派發單；同一行只能有一個去處；整張與逐行不能同時對應同一張（避免重複） |
| 凍結／完結比對（`_freeze`、`check_finalize`） | `dispatchAssignedTotal`／`dispatchUnassignedTotal`／`dispatchAbsorbedTotal` 的拆分語意要用新口徑，並維持「已對應＋未對應＝`dispatchTotal`」恆等式 |
| `settlement.html` | 「二之一」改成可展開到行，每行一個下拉；「三、承攬商派發成本」展開顯示行；保存前的雙邊重複提示 |
| 測試 | 現有承攬商派發對應的測試（至少 4 個檔案提到 dispatch offsets）要補逐行案例；新增「恆等式」「舊整張對應不變」「重複對應被擋」測試 |

### 要先決定的事（我不替你決定）

1. **稅怎麼分到各行**：派發單含稅金額＝未稅承攬費×(1＋稅率)＋外包人員。逐行對應時，稅額按各行未稅金額比例分攤？尾差放哪一行？
2. **外包人員（點工）**：不在 `items_json` 裡，仍留整張層級（建議維持未對應或整體對應到一個品項）。
3. **一行能不能拆給多個品項**：建議不行（一行一個去處，與現在材料申請同一原則）。
4. **同一張派發單能不能一部分整張、一部分逐行**：建議二選一。

### 影響範圍評估

- **不受影響（總額不變）**：營運報表、總帳／傳票、承攬商傳票讀的是派發單的合計（`dispatch.row`／`dispatch.cost_for_case`）；逐行聯動只是在精算內重新**歸屬**，`dispatchTotal` 不變。
- **會受影響**：精算頁（前端）、`settlement_actuals.compute` 與驗證、完結凍結摘要的派發拆分欄位、讀取 `dispatchAbsorbedTotal` 的地方（營運報表 `reports.py`、PDF `pdf_gen.py`／`bonus_pdf.py`）——需確認語意不變或同步調整。
- **相容性**：舊整張對應與已完結的精算（凍結）必須原樣讀得出來，不需要資料遷移（對應存在精算存檔、舊格式照舊有效）。
- **不需要改**：派發單資料表、派發審核流程、報價單。
- **粗估規模**：後端中等（集中在 `settlement_actuals.py`），前端中到大（兩個區塊改版），測試要補不少。這是看程式後的粗估，不是工時承諾。
