# 承攬商派發：稅金輸入方式——設計（第 36 班候選；2026-10-03；**狀態：設計稿；優先度低／選配；使用者 2026-10-03 確認現行輸入習慣（輸入未稅、系統加稅）正確，無需資料修正；35b 上線前不實作**）

> 範圍：只寫設計，不改程式。基準：`origin/platform` 5d76b528（含第 35 班上線的程式；**不含** wip/t35c-settle-assigned 的精算稅基 B，下文凡提到「精算稅基 B」者指該分支）。
> 起因（使用者 2026-10-03，經主持轉述）：**使用者輸入的是承攬商的「含稅價」**；他們希望畫面顯示「未稅＋稅金」，並保留「含稅」為既有數字，避免 5% 爭議。使用者裁示「放到下一班就好」。

## 0. 結論先行（2026-10-03 更新：使用者確認 D10 為未稅輸入，現行作法沒有錯）

1. **現行作法正確、不需任何資料修正**：使用者輸入**未稅**金額，系統依稅率加稅（5%）。使用者已確認正式機派發 D10（小計 762,300＋稅 38,115＝800,415）就是未稅輸入、系統加稅正確；762,300＝726,000×1.05 只是巧合。附錄 A 的其餘派發沒有任何顯示雙重計稅的證據。
2. **可用性風險（未觀察到實際錯誤）**：稅率選單的標籤是「未稅（0%）」「含稅（5%）」，且預設 5%。「含稅（5%）」讀起來像「我輸入的是含稅價」，實際效果卻是「在金額上再加 5%」。若有人輸入承攬商的**含稅價**並選 5%，就會雙重計稅（承攬商報價含稅 10,500：輸入 10,500＋5% ⇒ 含稅合計 11,025，多 525）。這是**可能發生的誤用**，不是已發生的事。
3. 因此本設計降為**選配、低優先**，內容分三級（由便宜到貴）：
   - **L1（建議做、極小）**：改標籤與說明文字，讓金額欄與稅率選單寫明意思（例：金額欄「單價（未稅）」；稅率選單「未稅價，系統另加 5% 營業稅」「免稅／個人，不計稅」）；合計區固定三行「未稅／稅額／含稅」。純前端文字，不動資料。
   - **L2（選配）**：建立匯款申請前的「稅額確認」一行（見方案 C 補充）。
   - **L3（選配、最貴）**：新增「金額含稅」輸入模式（方案 A：`tax_mode`、伺服器拆稅）。只有在使用者之後真的要改成輸入含稅價時才需要。
4. 若採 L3，推薦的做法仍是方案 A（§2）：伺服器把含稅金額拆成未稅＋稅，存 `total_amount＝未稅`，所有下游照舊讀 `total_amount` 當未稅；舊資料用 `tax_mode`（空＝照輸入）標記、不改寫。

## 2. 方案

### 方案 A（推薦）：新增「金額含稅」輸入模式，伺服器拆稅後存未稅
- 表單：新欄位 `tax_mode`——`exclusive`（金額是未稅，系統另加稅；＝現行行為）／`inclusive`（金額是承攬商含稅價，系統拆出稅）。稅率仍是 0 或 0.05（免稅／個人承攬商維持 0，此時兩個模式結果相同）。
- 伺服器（建立／更新時）：`G＝Σ 品項金額`；`inclusive` 時 `total_amount＝pretax＝round_half_up(G÷(1＋rate))`，稅＝`G−pretax`（用整數／Decimal 運算：`pretax＝floor((200·G＋(100+100·rate))÷(200+200·rate))`，**不用浮點除法**）。另存 `gross_entered＝G`（顯示用）。`exclusive` 時行為與現在逐位相同。
- 結果：`total_amount` 永遠是未稅 ⇒ `dispatch_row`、E04、認列、報表、分期、精算（含稅基 B）**一行都不用改**。需要改的只有：表單、建立／更新 API、`dispatch_row` 多回 `taxMode`／`grossEntered`、`substantive_hash` 納入 `tax_mode`、E04 與快照用的稅額改成「`inclusive` 時用存下來的稅（G−pretax），不再重算 pretax×rate」（避免進位差 1 元）。
- **品項層級 vs 合計層級進位**：推薦**合計層級**拆稅（發票就是按整張開、稅額按合計算；E04 也是整張派發一筆）。品項列只顯示含稅小計，不單列每列未稅（單列顯示會有加總差 1~2 元的爭議，例：三列含稅 10 元，逐列拆各 9.52→10，合計 30；合計拆 28.57→29，差 1）。需要列單價未稅時另列「約」並註明。
- 免稅／個人承攬商：`rate＝0` ⇒ `pretax＝G`、稅 0，不論模式。

### 方案 B：輸入維持現狀，只加事後拆稅顯示
- 在畫面／PDF 上把 `total_amount` 當含稅，顯示「未稅＝÷1.05、稅＝差」。
- 缺點：**下游成本仍是含稅**（認列、報表、E04、精算都會多 5%），這正是使用者要避免的爭議；而且 `total_amount` 的語意會因案而異，沒有旗標可區分。**不推薦。**

### 方案 C（我的補充，建議併入 A）：讓「不可能弄錯」
- 把稅率選單改成「**這筆金額的稅**」的**單一選擇**，三個選項直接說明結果：
  1. 「承攬商含稅價（系統拆出 5% 稅）」→ `inclusive`＋0.05
  2. 「承攬商未稅價（系統另加 5% 稅）」→ `exclusive`＋0.05
  3. 「免稅／個人（不計稅）」→ `exclusive`＋0
  金額欄標籤隨選項變：「含稅單價」／「未稅單價」／「單價（免稅）」；合計區顯示固定三行「未稅／稅額／含稅」。這樣沒有「含稅（5%）」這種會誤導的字樣。
- 儲存前若 `tax_rate>0` 且 `exclusive`，**不阻擋**，但在畫面小字提示「系統會在金額上再加 5%，應付總額＝X」（讓使用者看到加稅後的數字再確認）。

## 3. 既有資料

### 3.1 處理原則：**不改寫**
- `tax_mode` 新欄預設 `''`＝「照輸入」（舊行為，逐位不變）。舊的已核准／已匯款／已完結精算的派發全部維持原值；程式讀 `''` 與 `exclusive` 同義。
- 舊單若使用者要改成 `inclusive`：屬「實質欄位變更」⇒ 既有規則會要求重新送審（雜湊含 `tax_mode`）；已有未作廢匯款申請者，沿用現有限制（只有最高管理者可處理）。
- **開啟中的草稿**：草稿沒有下游，上線後第一次編輯時表單顯示模式選單，預設帶「依舊資料推定」不可行（無從得知），所以**草稿也維持 `''`，編輯時強制使用者明確選一個模式才能存**（舊草稿存檔前必選）。
- 遷移：`ALTER TABLE contractor_dispatches ADD COLUMN tax_mode TEXT NOT NULL DEFAULT ''`、`ADD COLUMN gross_entered REAL`（NULL）；放 subcontract 模組 migrations（下一號），先檢查欄位存在（冪等）；不搬資料、不重建表，風險低。
- 精算／報表／總帳對新舊：因為 `total_amount` 語意不變（一律「系統當未稅」），三者對舊資料的處理與現在完全相同。已完結精算不重算；報表跨案件合計會混入「含稅輸入又加稅」的舊案——屬已知，不標示（與精算稅基 B 的既有說明一致）。

### 3.2 （選配；現況不需要）怎麼從資料判斷過去用哪種輸入方式——唯讀查詢，**不含任何名稱**
> 使用者已確認現行習慣是未稅輸入，本查詢目前**不需要執行**；留著是為了日後若有人懷疑某筆派發含稅輸入時，能用「實付金額 vs 系統應付」客觀判斷。
判斷依據是「實際匯出去的錢」與「系統記錄的應付」比較：
```sql
SELECT d.id,
       d.status,
       d.tax_rate,
       d.total_amount                                   AS entered_amount,
       CAST(ROUND(d.total_amount * (1 + d.tax_rate)) AS INTEGER) AS recorded_gross,
       v.kind, v.seq, v.voided_at,
       v.pretax_amount,
       CAST(json_extract(v.snapshot_json, '$.grandTotal') AS REAL) AS recorded_payable,
       v.remit_actual,
       v.remit_review,
       v.is_paid,
       substr(v.paid_at, 1, 10)                         AS paid_date,
       d.invoice_date,
       (SELECT a.value FROM gl_source_annotations a
         WHERE a.field = 'input_tax'
           AND ((a.source_type = 'contractor_dispatch' AND a.source_key = CAST(d.id AS TEXT))
             OR (a.source_type = 'contractor_voucher_invoice' AND a.source_key = v.voucher_no))
         LIMIT 1)                                       AS annotated_input_tax
FROM contractor_dispatches d
LEFT JOIN contractor_payment_vouchers v ON v.dispatch_id = d.id AND v.voided_at = ''
WHERE d.status <> 'cancelled'
ORDER BY d.id;
```
（表若沒有 `gl_source_annotations` 或欄位不同，拿掉最後一欄。不回傳廠商名稱、發票號碼、銀行帳號。）
判讀（每筆派發）：
- `remit_actual`（實付）≈ `entered_amount`，而 `recorded_payable` ≈ `entered_amount×1.05`、`tax_rate=0.05` ⇒ 誤用 1（輸入含稅又加了 5%）；`remit_actual` 為 NULL 時退回比對「發票上的含稅金額」（請財務提供，或看 `annotated_input_tax`：若註記的實際稅額 ≈ `entered_amount×0.05÷1.05`，也指向含稅輸入）。
- `remit_actual`（或 `recorded_payable`）≈ `entered_amount×1.05` 且與發票含稅金額一致 ⇒ 輸入的是未稅（設計用法，沒問題）。
- `tax_rate=0` 且 `entered_amount` ≈ 發票含稅金額 ⇒ 誤用 2（含稅輸入、選 0%）。
- 派發尚未產生匯款申請（`v.*` 全 NULL）⇒ 只能用發票金額判斷，請財務提供。
正式機回報（主持轉述，**非檔案**，2026-10-03 約 23:15）：表內 11 筆（1 草稿、10 筆計入：accepted 3、completed 7；`approval_status` 全為空，真實狀態看 `status`）；`tax_rate=0.05` 9 筆、Σ`total_amount`＝1,239,770；`tax_rate=0` 1 筆、`total_amount`＝0；沒有其他稅率。已完結精算 10 案，其中 1 案有計入的派發。**使用者已確認現行習慣是未稅輸入（D10 為例），表內沒有含稅輸入＋0% 的案例；兩種誤用都沒有觀察到。**

### 方案 C 補充：建立匯款申請前的「稅額確認」（付款前最後一道攔）
- 從派發建立匯款申請（整筆或分期）的畫面，在金額確認區**醒目並列**「小計（未稅）／稅額／含稅合計＝應付」，並加一行勾選確認：「我確認派發輸入的金額是**未稅**，系統加稅後應付為 X」（`inclusive` 派發改顯示「承攬商含稅報價 G，已拆出稅 T」，不需勾選）。舊單（`tax_mode=''`、稅率>0）一定要勾才能送出；勾選動作記入稽核紀錄。
- 這一步不改任何金額，只讓使用者在**付款前**看到「是否被加了第二次稅」。目前正式機的大額派發都還沒有匯款申請（附錄 A），這道檢查可以趕在它們付款前上線。

| 匯款申請單／PDF | 數字來源是快照：未稅小計、稅額、應付總額（含稅），`inclusive` 時同時可顯示「承攬商報價（含稅）G」。沒有給承攬商的獨立派發單。 |
| 獎金 | 讀精算淨利；新單未稅成本與精算稅基 B 一致，不新增偏差。 |
| 報表 現金／權責 | 權責讀 `totalAmount`（未稅）⇒ 新單正確；現金讀已付 `grandTotal`／實付（含稅）⇒ 不變。兩者對同一案的差＝稅額，與稅基 B 的說明相同。 |
| 已完結精算 | 不重算、不重驗；存檔的承攬商成本維持當時口徑。 |
| 進行中簽核 | 不變；`tax_mode` 只在新建／編輯時寫入，編輯核准中的單走既有「實質變更⇒重送審」。 |
| 遷移 | 一個 `ALTER ADD COLUMN`×2，冪等；不需重建表；回滾＝忽略新欄。 |
| 對外文件 | 沒有承攬商看的派發單；匯款申請單格式見上。 |

## 5. 風險
1. **語意風險**：`total_amount` 在新舊單都是「系統當未稅」，但舊單裡可能夾雜含稅輸入——不可由程式猜測，只能靠 §3.2 的查詢與人工確認。
2. **進位**：合計層級拆稅，稅＝G−pretax（不是 pretax×rate 再算）；E04／快照／分期都要用「存下來的稅」，否則會與發票差 1 元。測試要涵蓋 G 為奇數、小數單價、qty 非整數。
3. **舊草稿**：強制選模式才能存，避免舊草稿默默沿用 `''`；舊草稿編輯多一步。
4. **雜湊**：`tax_mode` 沒納入 `substantive_hash` 會讓核准後的模式變更繞過重審——必加。
5. **UI 誤導**：標籤改了以後，舊使用者的習慣（選「含稅（5%）」）語意會變——上線公告＋選單三個選項直接寫結果。
6. **跨模組只讀欄位**：`dispatch.row` 契約（IP-1）只准加鍵不准改；新增 `taxMode`、`grossEntered` 屬加鍵，符合。

## 6. 測試計畫
- 單元：拆稅函式（整數運算；G＝10,500→未稅 10,000／稅 500；G＝10→未稅 10（9.52 進位）／稅 0；G＝1→1／0；奇數、大額）；`exclusive` 逐位等於現行；`rate=0` 兩模式相同。
- API：建立／更新 `inclusive` 後 `total_amount`、`taxAmount`、`totalWithTax`、`grandTotal`；`tax_mode` 納入雜湊（核准後改模式 ⇒ 需重新送審）；舊單（`''`）讀出與現在逐位相同；遷移冪等（跑兩次）。
- 下游對帳（**用真實 API 走完整流程，不寫合成快照**）：建立 `inclusive` 派發→驗收→登發票日→產生匯款申請（整筆與分期）→標已付；逐一斷言匯款應付、E04 三行（成本／1268／應付）、E05、認列（權責＝未稅、現金＝含稅）、營運報表同案成本、精算成本，並對總帳試算表（借貸平衡、1268 餘額）與報表「與總帳差異」頁應為 0。
- 真實頁面 e2e：在派發表單選三個選項各存一次，讀 API 與畫面三行（未稅／稅額／含稅）一致；舊草稿開啟必須選模式才能存；選單文字與說明（防誤用）存在。
- 回歸：既有派發／匯款／分期／E04／認列／報表／精算測試全綠（尤其 `dispatch.row` 契約與 IP-1 守門）。
- 反向控制：把 `tax_mode` 從雜湊移除 ⇒ 重審測試要紅。

## 7. 規模與待使用者裁示（優先度：低／選配）

- **L2 匯款前稅額確認**：前端 約 40–60 行＋稽核紀錄 1 處＋測試；約 2 小時。
- **L3 含稅輸入模式（方案 A）**：後端 約 80–120 行＋遷移 1 支＋表單 約 60–100 行＋測試 約 400 行；約 1 個工作視窗。與精算稅基 B 無檔案衝突（只共用 `dispatch.row` 的鍵）。

請使用者決定（最多 2 題，括號內為建議預設）：
1. **要不要改標籤與說明文字（L1）？**（建議：要，成本極小，可預防誤用；選項文字寫明「未稅價，系統另加 5% 營業稅」。）
