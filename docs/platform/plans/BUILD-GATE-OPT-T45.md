## 3. 為什麼動到底層就強迫全量（機制鏈）

1. **`scope_gate` 規則 fail closed**（`tools/platform/bottom_layer.json`，由上而下第一條符合者；沒有符合 ⇒ bottom）：`**/conftest.py`、`backend/pytest.ini`、`requirements*`、`modules/*/migrations/**`、`backend/core/**`、`backend/helpers/**`、`backend/db.py`、`migrations_frozen/**`、`backend/main.py`、`backend/routers/**`、`backend/tools/**`、`tools/**`、`product/**`、`frontend/{static,js,css,fonts}/**`、`index.html` 全是底層。`decide()` 只要有**一個**底層檔 ⇒ `mode="full"`。第 44 班的 diff 動到多個 `helpers/**`、`core/CHANGELOG`、`frontend/static/attach-picker.js` ⇒ 一定全量。
2. **就算改用差異選題也擴不小**：`modtest --dry-run`（第 44 班 diff）挑出 169 單位、**9,120／10,331 題（88%）**。原因：(a) `import main` 組裝所有 router，靜態 import 圖裡 helper→router→`core:main`；(b) 規則 5：`client`／`live_server` fixture 讓所有 api／e2e 題隱含依賴 `core:main`；(c) `core:db` 的 `dynamic_sql` 保守擴大。**靜態圖分不出「哪一題真的執行到這個函式」**，只能往寬選。（`direct+iface` 規則只在 helper 私有改動時才縮得小。）
3. **段結果沿用只認整棵樹**（`build_test_reuse.fingerprint`＝`ls-tree -r HEAD`＋環境）：任何一個檔、包括不影響執行的文件，都讓兩段整個失效；`stage_select`（增量段）已設計但**只 dry-run、沒接進建包**，且遇「硬底層」仍強制全量（設計 §5.2）。
4. 以上都是**正確的保守**；要在不放寬下縮小，只能：提高依賴資訊精度（O9）、降低「為了找紅而重跑」的成本（O1／O4）、把同樣的工作更快做完（O2／O3／O5／O6／O7）。

## 6. 量測計畫（第 44 班落地、鎖空出後；一次一組、-n 不超過上限；只刪自己的暫存）

1. **同一棵樹 A/B**：序列（現況）vs 重疊（O2）各 2 次；記錄牆鐘、每段時間、CPU 利用率（Windows 效能計數器 `\Processor(_Total)\% Processor Time`，5 秒取樣）、可用記憶體最低值、逐 nodeid 結果集（fail_stream JSONL）。
2. **e2e 每 worker RSS**（chromium＋uvicorn＋python）：-n 2／-n 4 各取尖峰，決定 O3 的記憶體門檻。
3. **setup 佔比**：`--durations=0` 取非 e2e 的 setup／call／teardown 分布（現有紀錄沒有 setup 欄），確認範本庫之後 `client` 固定成本是否仍有大宗。
4. **O9 可行性（離線）**：用 `sys.monitoring` 在 20 個代表性測試檔上記錄執行區塊，量記錄開銷與「改動一個 helper 函式時被選中的測試檔比例」。
5. **負載下 e2e 紅**：第 43 班三題各在 -n 2／-n 4／序列重跑 5 次，區分真競態與資源爭用。

## 7. 不放寬守門的檢查表（每項落地前逐條過）

- 題數不減：`slice0 ∪ rest`、重排前後、`selected ∪ carried` 的 nodeid 集合與單一 `--collect-only` 相等（sha 記進 manifest）。
- 紅的語意不變：任何未登記紅 ⇒ 段記紅；停止／分流不可把「沒跑完」記成綠或被沿用；已登記偶發規則與到期日不動。
- 沿用只在「同樹或可證依賴不變」時發生；環境、選題器、時鐘、`MOTRIX_*`（非 allowlist）任一變 ⇒ 全量。

## 11. O9 影子期設計（兩週；只觀察，不影響任何真實閘門）

### 11.1 隔離（影子不得影響真實閘門）
1. **記錄器不進真實閘門的 pytest**：只在「影子夜跑」的 pytest 行程載入（`-p dep_recorder`，環境變數 `MOTRIX_DEP_RECORD=1` 才啟用）；建包腳本、`modtest --full`、列車一律不帶、不讀它的輸出。紀錄寫在主工作樹 `tools/platform/dep_records/`（gitignore，不進任何 tree 指紋；`REUSE_EXCLUDE` 不需動，因為不是 tracked）。
2. **預測器是離線唯讀工具**（`tools/platform/dep_predict.py`）：只讀紀錄與 git，不跑測試、不寫段紀錄（不呼叫 `record-stage`）。`build_test_reuse` 不 import 它（靜態題守住）。
3. **資源**：夜跑只占 1 格全機鎖、`-n 2`、BelowNormal、避開任何列車全閘門與使用者使用時段；全閘門起跑時自動讓位（鎖是排隊的，影子永遠後到）；一個總開關 `MOTRIX_DEP_RECORD`（拿掉＝完全停）。
4. 影子期間任何人看到「沿用」字樣於真實 manifest／段紀錄 ⇒ 就是缺陷（守門題：`manifest.verification` 不得出現 `dep_carried`）。

### 11.2 記錄器（record）
- 每個**測試檔**一筆：`{file, outcome（過/紅/略）, deps}`，`deps` 由三類組成：
  1. **執行到的程式區塊**：`sys.monitoring`（Python 3.12，`PY_START`／`LINE` 以 `DISABLE` 回傳減少開銷；退路：coverage.py 動態 context＝每測試）。單位＝函式（`file::qualname` ＋ 函式本體的內容雜湊）。**只記 call 階段與該測試專屬 fixture 的執行**；session／worker 啟動時（import、`_app`、`_template_db`）執行的區塊歸入「全域區塊」＝任何一個全域區塊的內容變 ⇒ 所有測試檔重跑（正確的保守）。
  2. **被讀的非 Python 檔與被列舉的目錄**：`sys.addaudithook` 的 `open`、`os.listdir`、`os.scandir`、`glob.glob`、`os.walk`（皆限 repo 內路徑）。依賴＝檔的內容雜湊；被列舉的目錄依賴＝目錄內檔名清單雜湊（新增／刪除檔也算變）。
  3. **逃生標記（一律 fail closed＝永遠重跑）**：audit `subprocess.Popen`／`os.system`（起 git、起子 pytest）、`socket.connect` 到非本機、`time`／日期敏感（`date_sensitive` marker 或讀系統時鐘）、`conftest`／`pytest.ini`／`requirements` 的任何變動、記錄不完整（記錄器錯誤、逾時被殺）。
- **依賴指紋**＝`sha256(env_sha ‖ 測試檔內容 ‖ 排序後的{執行區塊雜湊} ‖ 排序後的{被讀檔雜湊}) ‖ 全域區塊雜湊 ‖ 選題器版本`；`env_sha`＝`build_test_reuse` 既有環境指紋（Python、`pip freeze`、Playwright、瀏覽器、非忽略的 `MOTRIX_*`）。
- 穩定性要求：同一棵樹連跑兩次，每個測試檔的依賴指紋必須逐檔相同（不同＝該檔含非決定性依賴 ⇒ 標「不穩定」、永遠重跑，並列入報告）。

### 11.3 影子比對（怎麼比「依賴重用」vs「完整跑」）
- **資料來源**：影子夜跑每晚對當時的 `origin/platform`（或當晚列車分支）頭跑一次**完整**（兩段）並記錄 ⇒ 得到每晚一份 `(commit, 每個測試檔的結果＋依賴指紋)`。連續兩晚 `n-1`（基準 B）與 `n`（候選 H）構成一對。另加**列車對**：第 44／45 班全閘門（真實全量，不加記錄器）無法提供依賴資料，所以列車前後各補一次夜跑記錄。
- **預測**（離線）：對每對 (B,H)，對 H 的每個測試檔算依賴指紋（用 B 的記錄所列的區塊與檔，在 H 的 tree 上重算雜湊）。指紋與 B 相同且 B 該檔綠且非逃生標記 ⇒ **預測沿用 C**；其餘 ⇒ **預測重跑 S**。
- **判定（以 H 夜跑的真實結果為真值）**：
  - **假沿用（false-carry）**：屬於 C、但 H 上實際是紅（或收集不到／略過原因改變）。**容忍度 0。**
  - **漏選的新紅**：H 上實際新增的紅（B 綠→H 紅）必須全部落在 S。同上，容忍度 0。
  - **價值**：C 占全部測試檔的比例（沿用率）與估算省下的 worker‑秒；分別統計「動到底層檔」的對。
  - **穩定性**：同樹重跑指紋不一致的測試檔比例。
  - **開銷**：記錄器造成的夜跑牆鐘增幅（相對無記錄器的基準夜跑）。
- **補強（因為自然發生的紅很稀少，光靠夜對夜資料不足以證明召回）**：
  1. **植入突變目錄**：影子期內由獨立者維護 ≥ 30 個突變（條件反轉、刪 return、改常數、改 SQL 條件、改前端檔字面、刪／改 json 資料、改 docs 被測試讀的檔），涵蓋 helpers／core／routers／modules／frontend/static／docs。每個突變套在 H 樹上：真實全量跑出的紅集合 R，必須 ⊆ 預測重跑集 S。突變套用與全量都在 worktree 隔離、不碰共用樹。因全量昂貴，突變分批（每批 ≤ 8 個，只對「預測 S 以外的 C」抽樣＋所有 R 候選驗證）——抽樣規則與批次由審查者決定並寫進報告。
  2. **歷史反向重放**：取近 30 個「修紅」commit（BUILD-OPT-ITEM3 §R3-a 的做法），反向還原修正 ⇒ 該修正附帶的測試必須在預測 S 內，且在反向版本上紅。

### 11.4 通過條件（全部成立才算影子通過；任何一項不成立 ⇒ 不進入上線討論）
1. 假沿用＝0、漏選新紅＝0（夜對夜＋突變目錄＋歷史重放三個來源合計）。
2. 突變目錄召回＝100%（每個使會紅的突變，其紅測試都在 S 內）。
3. 至少 10 個夜對、其中 ≥ 4 對動到 `helpers／core／routers／frontend/static` 之一（底層）。
4. 動到底層的對：中位數沿用率 ≥ 50%（否則價值不足以承擔風險；放棄或改做 O2／O5 的更深優化）。
5. 同樹指紋穩定：不穩定測試檔 ≤ 3%（且全列入永遠重跑清單）。
6. 記錄器開銷 ≤ 15%（只影響影子夜跑；若上線需要在閘門內記錄，另行量測）。
7. 影子期間對真實閘門的影響＝0（守門題＋人工核對 manifest 沒有任何沿用字樣）。

## 13. 開放問題（設計階段，待鎖空出後的量測回答）
- `sys.monitoring` 在 xdist worker 內記錄的開銷與「全域區塊」切分是否乾淨（fixture 在 call 階段才首次 import 的模組算誰的）。
