## Q1：後端有沒有重複「報價單送審門檻」（有效期 >30 天、毛利 <30%、含折讓、非 5% 稅別）？
**有，而且是以後端為準。沒有守門缺口。**
- 後端單一來源：`backend/modules/case/quote_terms.py::compute_approval_reasons`（約 `:156–184`）。逐條移植前端 `checkApproval()`，字面數字相同：
  - `:159–160` 有效期限 >30 天 →「有效期限 N 天（超過 30 天）」
  - `:164–165` 單項 `cost>0` 且 `margin<0.30` →「第 N 項毛利率 x% 低於 30%」
  - `:166–167` `showDiscount` 且 `discount>0` →「含折讓（NT$…）」
  - `:168–176` 稅率 <5：零稅率／免稅寫稅別，舊 1～4% 寫「調整營業稅額為 N%（標準 5%）」
  - `:177–182` 與預設條款／條款組不同 →「報價條件已修改…」
- 送審時由後端重算並**覆蓋**前端送來的原因：`modules/case/api/quotations.py:1544–1557`（`_apply_server_submit_reasons`），在新建（`:1576`，狀態「待審核」）與更新（`:1871`）兩處呼叫。簽核人看到的原因不能由送件人決定。
- 前端 `quotation-form.html:2822–2845`（`checkApproval()`）只負責在表單上即時提示（按鈕改色、顯示原因）；**送審本身一律走簽核流程**，這些原因只是附在送審單上給簽核人看的「特殊條件」，不是決定要不要簽核的閘門。
- 已知限制（原註解已寫）：毛利率只看品項的 `margin` 欄位，使用者 2026-09-24 裁示接受。
- **要把門檻做成可設定時，必須兩處一起改**：後端 `compute_approval_reasons`（含字串裡的「30 天」「30%」要改成由數字產生）與前端 `checkApproval()`。建議做法：數字放設定中心（有上下限、調寬鬆走放寬流程），前端從已有的 `GET /api/settings/quote-terms-defaults` 取同一組數字（該端點已存在，不用新增請求）；測試延用原註解提到的「前端／後端 parity」題。
- 另一個發現：預設條款**本文**已有後端單一來源與管理者可改的機制——`DEFAULT_TERMS`（`quote_terms.py` 前段）、設定值 `default_payment_terms`、條款組 `quote_terms_presets`（`quotations.py:1550–1553`）。所以盤點 #7 裡「條款內容」大半已可調；真正寫死的是**條款標題**（`quote_terms.py` 的 `TERMS_FIELD_DEFS`、`pdf_gen.py:356–363,2238–2241` 的 `term_block('付款條件', …)`）以及其他四段（交貨／驗收／保固／售後）的預設文字（只有付款條件預設與條款組可改）。

## Q2：`-R1` 修訂號是怎麼產生的？
- 產生處只有一個：`quotations.py:212–222` `_next_revision_no(quote_no)`。規則：用 `^(MQ-\d{6}-\d{3})(?:-R(\d+))?$` 拆成「基底單號」與「目前版次」；沒有版次 → `-R1`，有版次 → 版次 +1（`MQ-202501-001` → `-R1` → `-R2` …）；單號不符合格式（例如舊資料）→ 直接在後面加 `-R1`。
- 觸發時機：**退回修改**（`reject_quotation`，`quotations.py:5150–5180`）。簽核人退回時，報價單「清除簽核、單號升版（-Rn）、狀態回草稿」；歷程 `statusLog` 記「草稿（退回，改為 {new_no}）」，`returnInfo.originalQuoteNo` 保留原單號。複製到新單（`copyToNew`）則是取全新單號 `MQ-YYYYMM-NNN`，不帶 `-Rn`。
- 全新單號：`_peek_next_no`／`quote_seq`（`quotations.py:717–750`、`:1596–1660`）以月份計數、序號 3 碼；正式格式用 `_QUOTE_NO_RE = ^MQ-\d{6}-\d{3}$` 擋掉前端送來的佔位字串（`:713–715`）。
- 對「單據編號前綴可設定」的影響：`MQ` 前綴至少寫死在這幾處（只掃了 `quotations.py`，其他模組與前端可能還有）——`_next_revision_no` 的 regex（`:214`）、`_QUOTE_NO_RE`（`:715`）、`_peek_next_no` 的 SQL 與字串格式（`:724–736`，`SUBSTR(quote_no, 11, 3)` 把前綴長度寫死為 2）、清單月份篩選 `quote_no LIKE 'MQ-…'`（`:872`）。**報價單單號前綴不建議開放設定**（改前綴會牽動搜尋、報表與匯入的字串比對，價值低、風險高）；其他單據（客戶 C、供應商 S、請款 PR、開票 IV、完工 CN、出貨 DN…）走共用的 `db.next_entity_code`，前綴只在呼叫端一處，才適合開放（只影響新單）。
