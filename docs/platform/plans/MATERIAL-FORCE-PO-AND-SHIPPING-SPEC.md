# 材料申請：強制對應採購單＋出貨單連動 規格（第 33 班；2e；docs only；rev.2）

2026-10-02 19:21（rev.2：納入使用者對 E1–E4 的裁示）。承 `MATERIAL-ORDER-LINK-SPEC.md`（S4a–e，第 32 班已實作）。
使用者裁示：
- 流程＝**請購單 → 採購單（皆送審）→ 材料申請（從採購單內容帶入）→ 出貨單連動材料申請內容出貨（出貨也送審）**；「五金另料」這種一個品項由多張採購單組成。
- 材料申請**強制**：沒有已通過的採購單就不能送審（舊單不受影響）；分頁名稱維持「材料申請」；出貨單連動納入第 33 班。
- **E1**：只能從已核准採購單明細帶入（移除手動新增）。**E2**：採購單必須已核准。**E3**：有對應採購單的材料申請不再開匯款申請，付款只走採購單請款。
- **E4（取代 rev.1 的混合模型）**：**一個品項只能有一筆材料申請；追加走變更申請、重新簽核。**（rev.1 的 `poLinks[]`、依品項群組小計、小數「式」比例全部移除。）
- E5（實收數量）、E6（出貨單是否強制連結）尚未問使用者，先用預設（見 D）。
本檔只寫規格，不改程式。用字照 `MATERIAL-REQUEST-WORDING.md`。

## 0. 現況（第 32 班實作）

- 材料申請＝`caseRecord.materialOrders[]`（內容）＋ `case_material_approvals`（審核疊加列，31-C）；連結鍵 `quoteItemId／poDocCode／poLine／overPlanReason`（選填；單一連結）。
- 連結判定唯一函式 `purchase_items.material_link_status`／`_link_check`（有效採購單＝同案件、待審核／簽核中／已核准、列序／品項對得上；已有付款紀錄者不視為連結）；連到有效採購單者金額由採購單負責（單一歸屬，S4c）。
- 送審檢查 `material_submit_check`（d7 送審路徑呼叫）：品項存在、連結有效、`po_line_taken`、超計畫要原因；**不要求有連結**。
- 31-C：核准後實質欄位變更依審核狀態處理（改完到重新核准前帳可能少一筆，a3 D7 已列為風險）。
- 出貨單 `shipping_notes`（supply／M03）：`items_json` 自由格式；`草稿→待審核→簽核中→已核准`（doc type `shipping`）；核准時序號庫存 `in_stock→shipped`，總帳 E10 只針對庫存序號。與材料申請沒有連動。
- 採購單／請購單的**變更申請**機制已存在（核准後 PUT change-request → 送審；核准前原內容仍有效）。

## A. 強制規則（E1／E2／E3）

### A.1 材料申請的新定義（E4 的結果）
- **一個報價品項最多一筆「活的」材料申請**（草稿、待審核、簽核中、已核准；已退回／已取消不占）。伺服器端唯一性檢查（新 code `item_request_exists`，取代 S4 的 `po_line_taken`；舊資料以 grandfather 處理，見 A.4）。
- 材料申請**涵蓋該品項所有已核准的採購單行**（`itemId` ＝ 該品項）：內容由系統帶入、不由使用者逐行連結——
  - 涵蓋範圍＝送審當下該品項所有**已核准**採購單行的**快照**（`poSnapshot: [{poDocCode, line, qty, unit, amount}]`，存在審核疊加列的 `approval_json`，簽核人看得到）；使用者不能增刪行、不能手填單號（因此**沒有 `poLinks[]`**，也不再有逐行連結 UI）。
  - 數量 `quantity`：品項單位，預設＝快照內採購單行數量合計（單位相同時）；單位不同（例：品項「五金另料」＝1 式、行是各種零件）預設 ＝ 品項報價量，使用者可往下調；上限警示＝報價品項數量（只警示不擋）。
  - 金額：`totalPrice`＝快照內採購單行金額合計（唯讀；單一來源在採購單，E3 之後材料申請本身不再有付款）。
- 沒有任何已核准採購單行的品項**不能建立材料申請**（報價單品項清單改顯示「尚未有已核准的採購單」並提供「去申請請購單／採購單」按鈕，沿用 S1 的品項挑選器）。
- 採購單行沒有 `itemId`（額外採購，不是報價品項）：以**採購單為單位**各一筆材料申請（`quoteItemId` 空、涵蓋該張採購單的所有無品項行；同一張採購單最多一筆活的）。此預設需使用者確認（D 的 N1）。

### A.2 送審條件（`material_submit_check` 新增 `po_required`、`item_request_exists`）
1. 品項（或額外採購的那張採購單）下至少一條已核准的採購單行（E2：**已核准**才算，待審核／簽核中不算）。
2. 同品項沒有另一筆活的材料申請。
3. 涵蓋的行必須尚未被其他活的材料申請占用（防額外採購單被兩筆認領）。
4. 新增品項已被刪除（`bad_quote_item`）沿用。
未滿足 ⇒ 400，訊息用字表：「需先申請請購單，再申請採購單；採購單通過後，才能對應這筆材料申請。」（沒有核准的採購單）；「採購單尚未通過，通過後才能對應這筆材料申請。」；「對應的採購單已退回（或作廢），請重新申請採購單。」；「這個品項已經有一筆材料申請（單號…），要追加請走變更申請。」。
草稿可以先存（預設，E7 預設值）；強制點在**送審**（伺服器唯一判定，d7 的送審路徑呼叫同一個函式）。

### A.3 入口與畫面（E1）
- 新增＝「從採購單帶入」：列出**有已核准採購單行且尚無活的材料申請**的品項（顯示該品項的採購單行數與金額小計給有財務檢視者），勾選品項 ⇒ 建立一筆草稿（內容照 A.1）。供應商由採購單廠商對照主檔帶入（對不到才要選）。
- 「從報價單品項帶入」改為清單視圖（只顯示狀態＋「去申請採購單」），不能直接建立。「＋ 新增項目」（手動）**移除**（新單）。舊單列照舊可編輯。
- 「該材料申請未申請採購單」標註只保留給 (a) grandfather（規則上線前已核准／審核中、無連結）與 (b) 連結失效（採購單作廢）；新流程送審的單一定有採購單，不會標。

### A.4 舊單、草稿與既有資料
- **不改資料**。正式機材料申請現為 0 筆，無影響面；一般性定義如下：舊單（`approval_status=''`）完全不受影響；上線前已核准／審核中且無連結者保留、標註、允許「補對應」（只補涵蓋範圍，不重簽、留稽核、金額欄不可動）；上線前未連結的草稿／已退回保留，送審被 `po_required` 擋，頁面提示「N 筆草稿需先對應採購單」。
- 既有已連結（`poDocCode`／`poLine`）的材料申請視為「涵蓋該行所在品項」的相容讀法；唯一性檢查對 grandfather 只對**新送審**生效（不溯及既往）。

### A.5 付款（E3）與有效連結
有對應採購單的材料申請**不可開匯款申請**，付款只走採購單的請款流程；舊單／補對應前無連結者的匯款照舊。判定一律用**有效**涵蓋（採購單仍已核准），不是鍵有沒有填：採購單作廢／退回而失效時，金額回到材料申請、匯款出口重新開放（第 32 包探針發現，已在 `wip/t33-material-link-fix-2e` 修正；強制規則上線後同理）。已有付款紀錄的材料申請不可新增涵蓋（沿用 32 包 has_payment 規則）。

## B. 多張採購單組成一個品項（五金另料）——E4：一品項一筆，追加走變更申請

- 五金另料的多張採購單**都屬於同一個品項**，全部被**同一筆材料申請**涵蓋（A.1 的快照）；不再有逐行連結、群組小計、小數式。
- **追加**：品項之後又有新的已核准採購單行（例：下個月又買一批）⇒ 在該材料申請上發起**變更申請**（重新簽核）：
  1. 變更申請＝建立「待審變更版本」（提案內容＝新快照＋數量／備註調整），**原已核准版本在新版本核准前持續有效**（成本、到貨、可出貨量照原版本）——不重現「改完到重新核准前帳少一筆」。
  2. 送審走原簽核流程；簽核人詳情並列「原版本／變更後」差異（新增的採購單行、金額、數量）。
  3. 核准後原子切換：新快照生效；到貨確認沿用（已到貨的數量不重置，新增部分需再確認到貨，見 C.3）；駁回／撤回 ⇒ 原版本不動。
  4. 限制：變更後數量／涵蓋範圍不得低於已出貨＋占用量（`change_below_shipped`）；有進行中的變更版本時不可再發起第二個。
  5. 資料：審核疊加列加 `change_json`（待審提案）；核准時寫入 `caseRecord.materialOrders` 並把舊版本推進 `history`（版本號 +1）。採購單的變更申請是現成機制，作法比照，不另創。
- 未被涵蓋的新採購單行在畫面上以「有 N 筆新採購單行尚未納入材料申請」提示並提供「申請變更」按鈕；不自動納入（納入要重簽）。
- 對照 rev.1：不再需要 `poLinks[]`、`po_line_exceeded` 的「行數量占用」、群組小計。

## C. 出貨單連動材料申請

### C.1 目標
出貨單的品項能指向材料申請（的可出貨量），做到「申請了多少、到了多少、出了多少」對得上；出貨本身仍走既有出貨單簽核（doc type `shipping`），不新增簽核類型。

### C.2 資料模型
- **不跨模組讀表**：出貨單屬 supply（M03），材料申請屬 case（M01）；以 L1 提供者互通（與 `approval.queue_items` 同機制），彼此不 import：
  - case 提供 `material.shippable(quote_no)` ⇒ `[{materialItemId, docCode, name, unit, quoteItemId, appliedQty, arrivedQty, status}]`（只含已核准＋已到貨確認、未取消；變更申請待審期間仍以已核准版本計）。
  - supply 提供 `shipping.material_shipped(quote_no)` ⇒ `{materialItemId: 已占用出貨量}`（來源＝`items_json` 內連結；計待審核／簽核中／已核准，不計草稿／已退回；退回核准＝回草稿＝自動釋放）。
- 出貨單明細列加選填 `materialLink: {materialItemId, docCode, qty}`（單一連結；一個品項只有一筆材料申請，所以一列對一筆；`items_json` 內、加性；舊出貨單沒有此鍵＝行為不變）。
- 材料申請端不存出貨量（避免雙向寫入）；**已出貨量一律由出貨單提供者推導**。

### C.3 數量對照與規則
四個量（每筆材料申請）：已申請 `appliedQty` → 已到料 `arrivedQty` → 已出貨 `shippedQty` → 占用中 `reservedQty`（待審核／簽核中的出貨單）。
- 到貨量：**預設整筆到貨（arrivedQty ＝ 當時已核准版本的 appliedQty）**；E5 預設：到貨確認可選填「實收數量」，沒填＝全數。變更申請核准後增加的數量，需再做一次到貨確認（確認新增部分）才計入 arrivedQty。
- 出貨檢查（出貨單**送審**時與**核准**時各一次，後者防競態）：本品項所有活的出貨連結數量合計 ≤ `arrivedQty`；超出 ⇒ 400（`ship_exceeds_arrived`）。連到未到貨／未核准／已取消／涵蓋已失效的材料申請 ⇒ 400。
- 一列不可同時帶庫存序號（`part_no`＋`serials`）與材料申請連結（庫存走 E08→E10、材料申請走採購單 E11，兩條成本路徑不重疊）。
- 取消材料申請：有活的出貨連結（占用或已出貨）時不可取消（訊息指出出貨單號）；變更申請不得低於已出貨＋占用量（B.4）。

### C.4 簽核與通知
沿用出貨單既有簽核流程與通知；簽核人詳情新增「對應材料申請」欄（單號、品名、本單出貨量／累計已出貨／已到料）。不新增簽核層、不新增 doc type。

### C.5 報表／總帳影響
無新增分錄、無金額變動：錢已在採購單（E11／報表料件，單一歸屬）；E10 維持只針對庫存序號。報表加唯讀欄「已出貨數量」。守恆測試：加出貨連結前後，報表／總帳／精算金額逐位相同。

### C.6 與現行出貨單相容
- 沒有 `materialLink` 的出貨單（含全部歷史單）：行為、驗證、PDF、通知完全不變。
- 出貨單頁新增「從材料申請帶入」（列出該案件已到料且有剩餘可出貨量者，勾選帶入、數量預設剩餘）；「從報價單匯入」「手動新增」「序號挑選」保留。PDF 不印連結資訊。
- E6 預設：**不強制**；有已到料且有剩餘可出貨量的品項卻沒連結時，送審前顯示警示，不擋。

### C.7 案件頁顯示
材料申請頁每筆顯示「已申請／已到料／已出貨（占用中）」三格＋出貨單連結清單＋「有 N 筆新採購單行尚未納入」提示與「申請變更」按鈕。

## 測試與 e2e 清單
- 後端：`po_required` 四種提示語；`item_request_exists`（活的／已退回／已取消／草稿的占用與釋放）；涵蓋快照（只含已核准行、不含待審核／簽核中／草稿、額外採購以採購單為單位）；已被占用的行不可被另一筆認領；grandfather 補對應（只增涵蓋、稽核列、金額守恆）；變更申請（原版本持續有效、駁回／撤回不動、核准原子切換、不得低於已出貨／占用、一次一個、並發）；匯款互斥（有效涵蓋）；出貨連結檢查（送審＋核准兩次、競態、占用釋放、序號互斥、取消阻擋）；提供者契約（不跨模組 import 的守門）；守恆（金額在出貨連動／變更申請前後不變）。
- 突變：強制判斷、已核准判斷、唯一性、快照範圍、變更下限、原版本持續有效（改成立即切換）、占用計算（草稿不計）、核准時重檢、序號互斥。
- e2e（連續流程）：請購→採購（核准）→材料申請從採購單帶入→送審核准→到貨確認→出貨單從材料申請帶入→送審核准→案件頁數字與報表／總帳金額；一題「五金另料」多張採購單同一筆申請→追加新採購單→變更申請→簽核人看差異→核准；一題 grandfather 與舊單不受影響。
