# T61 S5：內建畫面的自訂欄位（欄位目錄 `x_`）——設計（僅文件＋小型查證，沒有任何程式改動）

> 日期：2026-10-14　作者：hichan-3c　基底：`train/t59-int` 6424c8931　目標列車：T61
> 讀過：`PLATFORM-BUILDER-ARCHITECTURE-T57.md` §1、§2.1 積木 1；`FIELD-LAYOUT-FRAMEWORK-T56.md` §3、§7、§8（在 `wip/t56-crm-directive-r3`）；`CUSTOMIZATION-SPEC.md` §3.6；`helpers/custom_fields.py`；`helpers/custom_modules.py` 的欄位型別；`routers/definitions.py`；`wip/t60-s2-r1` 的 `def_pipeline.py`。
> 使用者要的結果：**管理者自己在案件資訊表單（等內建畫面）加一個欄位，發布前看得到實際畫面（即時預覽），可還原；不寫程式、不碰金額。**

## 0. 結論（先看）

1. **地基已經有，缺的是接線。** P4（CUSTOMIZATION-SPEC §3.6）早就定了：單據的 JSON 裡預留 `customFields: {}`；定義存在定義文件庫的 `custom_fields` kind（有草稿、版本、差異、還原、驗證器 `cf.validate_definition`）；`cf.clean()` 負責型別驗證、丟棄未定義的鍵、預設值。**但目前沒有任何內建畫面讀或寫 `customFields`**（程式裡只有 `custom_modules` 在用 `clean()`，以及一個預覽範例視圖的空 `customFields: {}`）。
2. **不需要新資料表、不需要 DDL。** 十個內建單據類型本來就有 `data_json`（見 §3 表）；欄位值放 `data_json.customFields`（案件資訊放 `caseRecord.customFields`，剛好是現有「分段存檔」多一段）。沒有 JSON 欄位的類型（開發案件、承攬人員名冊、料號、每日事項）第一版不做，要做就是 DDL，另案。
3. **第一版 = 五種型別（文字、數字、日期、單選、勾選）、沒有金額、預設只給內部看、不進客戶輸出。** 數字欄在「看不到金額的角色」眼中一律視為可能是金額而隱藏（除非另有核准的例外）。
4. **預覽沿用 P9 的做法**：編輯中的草稿定義直接畫在真實頁面上（同一個畫面元件），不是另一個假畫面；發布走既有的定義管線（3e 的 S2：放寬待核准、確認期間、快照與還原）。
5. **P9 版面引擎看不到動態欄位**（它的點只來自 `module.json`）。第一版把自訂欄位放在每個表單的**一個固定區塊「自訂欄位」**，順序由欄位定義自己決定；要讓 P9 能把自訂欄位拖到別的區塊，需要核心層小改（動態點），列為第二階段決定。
6. 工量（估，pd）：先導三個畫面（案件資訊表單、供應商、客戶）約 **12 pd**；每多一個單據類型約 0.5～1 pd。

## 2. 範圍與硬規則

**能做**：管理者替「一個單據類型」新增／改名／排序／停用欄位；欄位值跟著單據存；畫面上看得到、填得了；內部匯出可選擇帶出。
**不能做（寫死，不可由設定放寬）**：
1. 不能是金額型。第一版型別只有五種，沒有「金額」「公式」「參照」。（數字欄的特別處理見 §5。）
2. 核心欄位不動：key 不可與核心欄位同名（`_CORE_FIELDS` 擴充到每個單據類型）；自訂欄位不能改變任何計算、狀態、簽核。
3. 預設 `internal`、不進任何客戶可見的輸出（客戶版 PDF、回簽頁、客戶預覽）；第一版連「讓它進客戶輸出」的選項都不提供。
4. 只收 `dataClass = T1`；F2（個資）拒絕，並在編輯器明說「個人資料請走既有的個資欄位」。（文字欄仍可能被人拿去填個資，編輯器在文字欄旁固定提示。）
5. 定義與值都不含程式碼：值只存字串／數字／布林／日期字串；標籤與選項以純文字渲染（一律跳脫）。
6. 欄位不可刪除只能停用：停用的欄位值保留在資料裡（不遺失），畫面不顯示；超級管理員可在「已停用欄位」檢視。
7. 單據類型的白名單由程式登記（§3），管理者不能對沒登記的類型加欄位。

## 3. 儲存（D11 預設：沿用現有 JSON 欄位，不新增資料表）

欄位值：`<記錄的 JSON>.customFields = { <key>: <值> }`；沒有值就**不寫這個鍵**（⇒ 既有單據、既有回應的鍵集不變；回應基準與寫入金標不受影響）。定義：定義文件庫 `custom_fields` kind，**key＝單據類型鍵**（不是模組鍵），scope 一律 `company`。

## 4. 欄位型別與驗證（第一版）

- 型別：`text`（`maxLength` ≤ 2000，預設 200）、`number`（`min/max`，**非金額**）、`date`、`select`（選項 ≥ 1，不重複，每項 ≤ 40 字，最多 30 項）、`checkbox`。沿用 `custom_fields.TYPES`，**不新增型別**。
- 每個單據類型最多 **20 個**欄位（含停用）、單據的 `customFields` JSON 序列化後 ≤ 8 KB。
- 定義驗證沿用 `validate_definition`，加：①key 與該類型核心欄位同名擋（擴 `_CORE_FIELDS`）；②`dataClass` 必須 T1；③`label` 長度 1～30，且不可與同表單的核心欄位標籤相同（避免冒充）；④不得使用 `formula/ref/money` 等未登記型別（已由型別目錄擋）。
- 值驗證＝`cf.clean()`：伺服器端在**每一條寫入路徑**呼叫一個共用閘門 `custom_fields.gate(record_type, values, user)`：未定義的鍵丟掉並回報；型別不符回 400 並指名是哪一欄；`required` 只對**新建單據**生效（既有單據沒有值，不能因為管理者後來加了必填欄位就存不下去）。
- 閘門還處理：停用欄位的值不可被改（保留原值）、沒有可見權限的欄位值不可被改（保留原值，比照金額遮蔽的 `restore_*`）。

## 5. 可見性與金額遮蔽（新欄位預設 internal）

欄位屬性 `audience`（編輯器顯示為白話）：
- `internal`（**預設，也是第一版唯一能選的**）：能開啟這筆單據的內部使用者看得到；**不進任何客戶可見輸出**。
- （第二階段才考慮）`record`＝同 internal 但可進指定的內部匯出；`customer`＝可進客戶輸出——需第二位最高管理者核准＋高影響橫幅，**第一版不提供**。

金額遮蔽規則（硬規則，後端解析器剔除，不是 CSS）：
1. **數字欄**在沒有 `money_visible`／該單據對應金額權限的角色眼中**一律隱藏**（我們無法判斷管理者拿它放什麼）。管理者可在欄位上勾「這不是金額，所有能開單據的人都能看」，這是**放寬**，走 S2 待核准（`audience` 以外的第二個旗標 `nonMoney`）。
2. 文字、日期、選項、勾選欄預設對能開啟單據的所有內部角色可見。
3. 無權限者的 API 回應不含該欄位的**值**，也不含它的**定義標籤**（`GET` 定義端點對無權限者過濾），避免從標題洩漏結構（比照 FIELD-LAYOUT §7-4）。
4. 一致性守門測試：`customFields` 不得出現在任何客戶輸出的視圖建構函式中（`pdf_gen` 客戶版視圖、回簽頁、客戶預覽）；正對照：把一個欄位硬塞進視圖時守門必須變紅。

## 6. 畫面渲染與即時預覽

- **一個共用元件**（`frontend/static/custom-fields.js`，L1 靜態檔，登記 `docs/platform/modules.json`）：`MotrixCustomFields.init({recordType, deferred:true})` → 讀 `GET /api/custom-fields/{recordType}`（已發布定義，已按使用者權限過濾）；提供 `fields()`、`value(rec,k)`、`set(rec,k,v)`，頁面用 `x-for` 在表單的「自訂欄位」區塊畫輸入元件（五種型別各一種畫法）。
- **即時預覽**：欄位編輯器（見 §9）打開時，元件切到 `edit` 模式，**畫面上的區塊直接顯示草稿定義**（與 P9 的 `MotrixLayout.show(state,'edit')` 同模式）；另有「以角色預覽」（含無金額權限角色，確認數字欄被隱藏）。預覽不寫任何單據、不寫稽核以外的資料。
- 旗標：`builder_fields.<單據類型>` 一類一個，預設關閉；關閉時頁面不發請求、不畫區塊（比照 P9 的 `deferred`＋node 實跑中性值測試）。

## 7. 存檔路徑

- 案件資訊：`customFields` 是 `caseRecord` 的一個新分段。前端不需改存檔邏輯（`_snapSegments` 已涵蓋所有頂層鍵）；伺服器在 `PATCH …/case-record` 的分段處理中，對 `segments["customFields"]` 呼叫閘門（`cf.gate("case_info", …)`），並在 `_segLabel` 補「自訂欄位」。**只動分段存檔的一個分支，不動業務邏輯**。
- 供應商／客戶：在 `POST/PUT` 寫 `data_json` 之前呼叫閘門，把 `data["customFields"]` 換成乾淨的值。
- 所有路徑共同：①不存在的單據類型旗標關 ⇒ 閘門直接丟掉 `customFields`（不存）；②值與定義版本無關，只認欄位 key（第一版不凍結定義版本；等有輸出才需要 §3.6 的 `customFieldsVersion` 凍結）。

## 8. 匯出與 PDF 的行為

- 第一版：**PDF、客戶輸出、回簽頁完全不含自訂欄位**（守門測試，§5-4）。
- 內部匯出（案件批次 XLSX 等）：預設不含；每個欄位有「列入內部匯出」勾選（預設不勾），勾了才多一欄（標題＝欄位名稱；數字欄遵守 §5-1，無金額權限者的匯出沒有該欄）。
- 輸出版型以 `customFields.<key>` 引用是第二階段（需要版型編譯器與凍結版本）。

## 9. 與 P9 版面引擎、治理的接法

- **P9**：第一版自訂欄位放在每個表單的固定區塊「自訂欄位」（`module.json` 登記一個只有區塊標題的 `section`，管理者可改區塊名稱與位置，但不能把個別自訂欄位拖到別區）。第二階段（需核心層裁示）：`core.catalog` 加「動態點提供者」，把已發布的自訂欄位合成 P9 的 `field` 點（`x_<key>`），P9 的隱藏／改名／移動／換區塊即自動可用；核心欄位鎖定規則不變（自訂欄位一律 `display` 等級）。
- **編輯器**：不另建一套——欄位編輯器就是 layout-editor 的「兄弟面板」：同一個面板框架（草稿／存草稿／差異／發布／版本還原／兩段式確認／待核准顯示），列表換成「新增欄位、改名、型別、選項、排序、停用」。發布走 `/api/definitions/custom_fields/{單據類型}/…`。
- **治理（3e S2）**：`custom_fields` 已在 `ACTIVE_KINDS`。⚠ 現行比較函式把「新增欄位」一律判為放寬 ⇒ 開著治理旗標時，管理者**每加一個欄位都要第二位最高管理者核准**。對 `internal` 的非數字欄這太重。建議（要 3e／使用者決定）：新增一個 `internal` 的文字／日期／選項／勾選欄＝`neutral`；新增數字欄、`nonMoney`、列入匯出＝放寬。快照／還原／差異用既有的版本與帳本，不需新做。

## 10. 測試與守門

1. 定義驗證：key 格式、與核心欄位同名、F2 拒絕、型別越界（金額／公式）拒絕、欄位數／大小上限、選項重複。
2. 閘門 `gate()`：未定義鍵丟掉並回報、型別錯 400 指名欄位、`required` 只對新單據、停用欄位值不可改、無權限欄位值不可改（保留原值）、巨大值拒絕。
3. 逐角色矩陣（admin／sales／finance／cashier／engineer／viewer）：數字欄只有 `money_visible` 者看得到（除非 `nonMoney`）；GET 回應與定義端點都不含無權限欄位；改動前後無權限角色的回應位元相同。
4. 輸出守門：客戶版 PDF／回簽頁／客戶預覽的視圖不含 `customFields`（正對照：硬塞一個欄位 ⇒ 紅燈）。
5. 旗標關閉：頁面不發請求、不畫區塊（node 實跑，同 BP-1 的中性值題）；回應鍵集基準（response-keys baseline）與寫入金標不變——因為沒有值就不寫 `customFields` 鍵。
6. 案件分段存檔：同時改 `customFields` 與其他分段不互相衝突；他人改了 `customFields` ⇒ 409 且標籤是「自訂欄位」；回歸 `test_e2e_case_save_*` 系列。
7. 預覽：草稿預覽不寫入、以無權限角色預覽看不到數字欄。
8. 突變（只在本機）：拿掉閘門 ⇒ 未定義鍵被存進去的題變紅；拿掉數字欄遮蔽 ⇒ 角色矩陣變紅。

## 11. 風險

| # | 風險 | 對策 |
|---|---|---|
| R1 | 管理者把金額放進文字欄（無法技術上禁止） | 編輯器固定提示；文字欄預設 internal、不進客戶輸出與匯出；金額單據不開放；稽核有欄位標籤歷史 |
| R2 | 自訂欄位成為個資洩漏面（文字欄填身分證／電話） | F2 拒絕＋固定提示；匯出預設不含；`audience` 第一版鎖 internal |

| R4 | 回應鍵集基準／寫入金標漂移 | 沒有值不寫鍵；導入時跑 U0 基準比對 |

| R6 | 值與定義脫鉤：欄位改型別後舊值不合 | 第一版**不允許改型別**（只能停用再新增）；改選項時舊值不在選項內仍保留並標示「已不在選項內」 |
| R7 | P9 看不到動態點，管理者以為能拖 | 編輯器明說「自訂欄位固定在『自訂欄位』區塊」；第二階段補動態點 |

## 13. 需要使用者決定的事

1. **第一版範圍**：先導三畫面（案件資訊、供應商、客戶）是否對？是否要把報價單頭部提早（風險最高，建議不要）。
2. **數字欄預設對無金額權限者隱藏**，要不要保留「`nonMoney` 例外」（需第二人核准）？還是第一版乾脆不給數字型別？（最保守＝先不給數字型別。）
3. **「加欄位」要不要第二位最高管理者核准**？建議 `internal` 的非數字欄＝免核准（立即生效、可還原），數字欄或對外可見才核准。
4. **欄位數量上限**（建議每類型 20 個）與**是否允許必填**（建議：只對新建單據生效）。
5. **欄位 key 要不要加 `x_` 前綴**（T57 提過）：值已放在 `customFields` 這個命名空間下，不會與核心欄位撞名；加前綴只影響匯出欄名。建議不加，匯出欄名用管理者設定的標籤。
6. **沒有 JSON 欄位的類型**（開發案件、承攬人員、料號、每日事項）要不要為此做 DDL（每表加一欄 `custom_json`）？建議不在第一版。
7. **P9 動態點（核心層）** 與 **T60-S3 的核心層登記**可否合併成同一個核心層案（兩者都要讓 `core.catalog` 認得「非 module.json 來源的點」）？
