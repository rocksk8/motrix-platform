## 〇、給老闆看的一頁（白話）

**使用者說得對，而且比「畫面分散」更嚴重：資料真的分成兩條互不相通的線。**

1. **案件這條線**：請購單 → 採購單 → 材料申請（叫料）→ 確認到貨 → 材料卡 → 設備登錄。全部掛在「案件」上。
2. **倉庫這條線**：料號 → 庫存「進貨」→ 序號 → 出貨單 → 設備認領。掛在「庫存」上。

兩條線只靠「序號字串剛好一樣」才會碰在一起。所以同一批貨到了：案件這邊按「確認到貨」，倉庫那邊**不會有任何東西**（庫存頁會顯示 0 件），要另外到「庫存管理」把料號、數量、每一台序號、供應商、發票重打一次。我們用假資料實際走了一遍，庫存頁在「4 台交換器已到貨」之後仍然是 0。

**我們實際走了三種人的第一天（假資料、真畫面，截圖在 shots 資料夾）：**

- **新進採購**（只給「採購」權限）：看得到「採購管理」，但那頁**只能看、不能做事**；唯一的按鈕把他帶到案件頁，而案件頁預設落在「案件資訊」，要自己再找「執行管理 → 材料申請」。他想開請購單，會看到「你沒有這個頁面的權限」（系統目前要求「報價單」權限）。供應商頁對他是**空的**。
- **業務／專案經理**：一件採購從案件到保固，要經過約 **8 個不同畫面、至少 12 次換頁或換分頁**，同一批資料被重打：**供應商 4 次、到貨日 2～3 次、每台序號 3 次、保固起算日 2 次**。
- **現場工程師**：寫工作日誌時**沒有「案件」欄位**，寫的日誌進不了案件的動態與專案報告；每日工作事項他不能新增；階段看板點進去只落在案件資訊。「某天現場做了什麼」散在 5 個地方。

**我們建議的「一條龍」做法（一句話）**：在每個案件裡加一個「**物料流程**」畫面——橫向時間軸「叫料 → 採購 → 到貨 → 入庫 → 領用／出貨 → 設備登載 → 保固」，每一段顯示狀態、**卡在誰手上**，以及一顆「**下一步**」按鈕，按下去會**帶著上一步的資料**（品名、數量、供應商、序號）直接開下一張單。到貨時**一次**登載（貼上序號清單），同時完成確認到貨、入庫、預填設備。熟手原本的獨立頁面全部保留，點擊數不增加。

**不是一次大改。** 我們把它切成 6 批，第一批只修「死連結、找不到入口、權限對不上」這類小而確定的事（半天～1 天的量級），就能先改善大部分抱怨；真正合併資料的在後面幾批，每批都能單獨上線、單獨回退。

**需要老闆（使用者）決定的事**，見第九節；最關鍵三件：
1. 所有叫來的料都要「入庫」嗎？還是允許「直送客戶現場、不經倉庫」？（影響第 3 批設計）
2. 要不要做「領料」？（現在系統根本沒有領料單，只有出貨與設備認領兩種消耗）
3. 保固起算日預設取哪一天：到貨日、出貨日、還是完工日？

## 一、盤點方法

- **讀程式**：三組盤點（A 案件→叫料→採購→供應商；B 到貨→入庫→領用／出貨→設備→保固；C 施工紀錄／日誌／案件頁）逐步記錄：頁面、資料表、API、權限鍵、狀態、下一步誰做、重打欄位、資料帶不帶到下一步、斷點。每條斷點附 `檔案:行號`，未實測的標「（推測）」。底稿在 `PROCUREMENT-FLOW-ONEPIPE-inventory/`。
- **實際走一遍**：在本機測試站灌一個假案件（宏達科技「總部網路升級」：報價 3 個品項、請購單／採購單已核准、2 筆叫料已核准、其中 1 筆已確認到貨、材料卡與設備列各一）與 3 個假帳號（採購、業務、工程師），用瀏覽器逐頁截圖。腳本留在 `shots/_onepipe_shots.py.txt`，可重跑。
- **限制**：點擊數與重打次數是依畫面與程式推算（不是計時測量）；標「推測」的項目請在審查時抽查。

## 三、斷點（合併後依主題歸類，嚴重度＝是否直接造成「零散」）

**T1 兩條線沒有主幹**（高）
- 到貨不會變成庫存：全系統只有庫存頁「進貨」會寫 `stock_items`（`inventory.py:468`）；「確認到貨」「已到料」完全不碰庫存（`material_approvals.py:297`、`case-management-exec.js:1144`）。
- 案件軌的材料卡只有自由文字品名，沒有料號 `part_no`；庫存軌只認料號。兩邊的唯一接點是序號字串。
- 出貨與設備登載對同一序號互相衝突：出貨核准把序號設 `shipped`（`shipping_notes.py:596`），設備登錄只認領 `in_stock`（`inventory.py:728`）→ 「先出貨、再現場登載」必然報衝突。
- 出貨列的「材料申請連結」與「庫存序號」互斥（`material_link.py:64`），一條線上追不到「採購單→序號→出貨」。

**T2 同一批東西被核准兩次、記錄三次**（高）
- 新材料申請**強制**由已核准的採購單帶入（`PO_REQUIRED`，`material_approval.py:39`），所以一筆採購 = PO 簽核 + 材料申請簽核；到貨記在三處（`received_on`／材料卡 `arrived`／認列路徑 `arrivedOn`）。
- 供應商 4 處各填（PO 廠商文字、叫料單 `supplierId`、材料卡 `supplier`、庫存批次 `supplier_id`）；PO 已有廠商，叫料時仍必須重選（`SUPPLIER_REQUIRED_ON_NEW`）。
- 材料卡「從報價單匯入」不存報價品項 id，與叫料單／PO 的連結靠手選或品名字串比對；認列採購單預設只有最高管理者能做，其他人按了整件被取消並寄「被拒」信。

**T3 入口、權限、角色對不上**（高）
- 請購／採購單要離開案件頁，頁面不收 `quote_no`；案件頁只有一行文字叫人「先申請請購單」，沒有按鈕（`case-management.html:2444`、`payment-request.html:408`）。
- 純「採購」角色：看得到唯讀進度表，做不了下一步（叫料需管理員／財務／專案管理＋金額檢視；請購入口需報價單權限）；供應商名單對非管理員是空的（`suppliers.py:84`）。
- 到貨、出貨、設備登載、保固全是唯讀看板或藏在案件子分頁；深連結只到「分頁」層級，不到子頁籤（`?q=` 落在「案件資訊」）。
- 死連結／誤導：信件與通知指向不存在的 `shipping-notes.html`；保固頁案號不可點；保固信的按鈕連到報價單頁。

**T4 紀錄散成五處、與案件脫鉤**（高）
- 「某天現場做了什麼」：階段出勤、工作日誌、動態留言、每日工作事項回報、客戶日誌，互不引用。
- 工作日誌頁沒有案件欄、不顯示案號與照片；案件頁的發文框同一個框寫兩張表。
- 完工單不吃施工資料（開工日、施工摘要手打）；保固月數與設備保固是兩份獨立輸入，程式註解明寫「刻意不自動連動」。
- 每日工作事項只有最高管理者能新增，也不接收案件上下文。

**T5 保固接縫**（高／中）
- 設備保固起始日不取到貨、出貨、完工任何一天；通知只掃「已成案」；去重記號不含到期日（續保後不再通知，推測）；沒填起始日的設備不會被提醒。

**T6 詞彙與通知**（中）
- 同一件事四套狀態詞（待採購／待材料申請／草稿…／suggested…）；成案、PO 核准、到貨確認都沒有通知「下一個人」。

**T7 效率**（中）
- SN／MAC 全為逐台手打，沒有貼上多行、匯入或掃碼；「一鍵同步保固」只能套用全部。

## 四、提案：案件「物料流程」一條龍

### 4.1 設計原則（先講不做什麼）

1. **案件仍是主幹**；入口永遠是「從案件進去」。
2. **第一階段不改資料模型**：先做「讀取合併」（時間軸只讀現有各表），再逐步補外鍵與一站式動作。每批可單獨上線、單獨回退。
3. **各模組原頁面全部保留**（熟手效率）。新畫面是「總覽＋下一步捷徑」，不取代任何既有頁面；任何既有操作的點擊數**不增加**（見 4.6）。
4. **權限沿用各模組**，不新增權限鍵；時間軸只顯示呼叫者有權限的段落，每一段的資料與按鈕在**後端逐段檢查**，不因為「能看流程」而多給權限。
5. **不替人做決定**：自動帶入的值都可以改；有金額或庫存影響的動作仍要人按確認。

### 4.2 主畫面：案件「物料流程」（見 mockup M1）

**怎麼進去**：案件頁加一個頁籤「物料流程」（或案件標頭的按鈕）；側欄「採購與庫存」群組的看板每一列也直接連到「該案的物料流程」，不再落在「案件資訊」。

**畫面**：上方一條橫向時間軸，7 段：**叫料 → 採購 → 到貨 → 入庫 → 領用／出貨 → 設備登載 → 保固**。每段一個格子，顯示：
- **狀態**（沿用該段現有的狀態字，不另創新詞）與數量進度（例：叫料 12／採購 12／到貨 4／入庫 4／出貨 0）；
- **卡在誰手上**（例：「待當層簽核人 王經理」「待採購下單」「待到貨確認：案件業務」「待登載序號」）；
- **「下一步」按鈕**：只在該段能做且呼叫者有權限時出現，按下去帶著上一步的資料開下一張單（4.3）。

**下方**：選一段後展開該段的明細列（以報價品項為列：品名、需要量、已叫料、已採購、已到、已入庫、已出貨、已登載、保固到期），可勾選多列批次「下一步」。右側欄放這個案件的「登載」：最近的工作日誌、階段出勤、動態（4.5）。

**每列的資料來源**（第一階段全是讀取，不新增表）：報價品項 `items[]` → 叫料單 `materialOrders[]`（靠 `quoteItemId`）→ PO（靠 `poDocCode/poLine`）→ 到貨 `received_on` → 庫存序號（靠序號字串；第二批起靠外鍵）→ 出貨單 `items_json` → 設備 `devices[]` → 保固。

### 4.3 「下一步」會帶什麼

| 從 | 按鈕 | 開哪張單 | 自動帶入 | 現況需重打 |
|---|---|---|---|---|
| 報價品項 | 建請購單 | 請購單（開在新畫面，案件已選好） | 案件、品名、數量、單位、單價、報價品項 id | 重新搜尋案件、品項 |
| 請購單（已核准） | 建採購單 | 採購單 | 全部明細、請購單號 | 已可帶入（保留） |
| 採購單（已核准） | 叫料 | 材料申請 | 品名、數量、單價、**供應商（取自 PO 廠商，若對得上供應商主檔）** | 供應商必須重選 |
| 叫料（已核准） | 到貨登載 | **一站式到貨**（4.4） | 品名、數量、供應商、PO 號、預計到貨日 | 確認到貨＋材料卡勾選＋庫存進貨＋序號 |
| 到貨 | 入庫 | 在「一站式到貨」中同時完成（或「直送現場」跳過） | 料號、供應商、發票、序號、成本 | 庫存頁整張重打 |
| 庫存（在庫） | 出貨 | 出貨單 | 序號、料號、客戶、地址（來自案件） | 重選序號 |
| 出貨（已核准） | 登載設備 | 設備登錄（批次） | 名稱、序號、MAC、**保固起始日（預設＝出貨日，可設定）** | SN／MAC／保固全重打 |
| 設備 | 保固追蹤 | 保固頁（已篩該案） | — | — |

### 4.4 減少重複輸入（逐欄）

| 欄位 | 現在要打幾次 | 提案 | 批次 |
|---|---|---|---|
| 案件（請購／採購單搜尋案件） | 每張單重搜 | 從案件進去即帶入；`payment-request.html` 收 `?quote_no=` | P0 |
| 供應商 | 4 次（PO 文字、叫料 supplierId、材料卡、庫存批次） | PO 改為「從供應商主檔選（可手填備援）」；叫料沿用 PO 的供應商；材料卡與庫存批次讀同一來源 | P3/P5 |
| 品名／數量／單位 | PR、PO（帶入）、叫料（帶入）、材料卡（手動匯入）、庫存（重打）| 材料卡由叫料自動建立並存報價品項 id；庫存料號在到貨時由「品名→料號」選擇一次，之後記住對應 | P2 |
| 到貨日 | 2～3 次 | 只在「一站式到貨」填一次，寫回所有位置 | P2 |
| 序號／MAC | 3 次（材料卡、庫存、設備列） | **貼上多行／匯入 CSV／掃碼連續輸入**，一次登載後寫入材料卡、庫存、設備列 | P2 |
| 保固起始日／月數 | 設備列、完工單各一次 | 預設取出貨日（或完工日，設定決定）；完工單保固月數預填設備保固 | P4 |
| 發票號碼 | 庫存批次 | 到貨時填一次，帶入庫存批次與付款流程 | P2 |

### 4.5 「登載」：把紀錄收進同一個入口

案件的「動態」發文框目前混用兩張表（`case_updates`、`work_logs`）。提案：案件頁／物料流程右側固定一個「**登載**」區，單一入口選類型（工作日誌／階段出勤／留言／待辦），**案號與日期自動帶入**；工作日誌頁補上「案件」欄位並顯示案號與照片；階段出勤的「新增記錄」預填日期與人員；每日工作事項接收 `?case_no=`；完工單預填開工日（最早階段出勤）與施工摘要（工作日誌彙整，可改）。不合併資料表（第一階段），只統一入口與預填。

### 4.6 專家效率：點擊數不增加（承諾與檢查方式）

- 所有既有頁面與路徑原封保留（庫存頁、設備頁、出貨單分頁、簽核佇列…）。
- 新增的動作都是**捷徑**：從物料流程做一件事 ≤ 既有路徑的點擊數；每批驗收時列「既有操作 → 點擊數 前／後」對照表，只許減少或持平。
- 「一站式到貨」是新增的一個**選用**入口；原本「確認到貨」「庫存進貨」兩處仍能獨立操作。
- 時間軸的下一步按鈕有權限才出現，不會出現做了才被擋。

估算（一件採購從叫料到保固，業務角色）：現況約 **12 次換頁／換分頁、8 個畫面**；提案完成後在案件內約 **4 次**（物料流程 1 屏＋簽核佇列＋「一站式到貨」＋出貨單），其餘為各段「下一步」的 1 次點擊。

### 4.7 權限

- 每一段沿用該段原本的模組權限與逐案可見規則；時間軸 API 回傳**每段各自的資料與 `canAct`**，不給的段落整段不回傳（不是回傳後前端藏起來）。
- 「採購」角色目前做不了叫料、看不到供應商名單、開不了請購入口：這是**政策決定**（第九節 D3），不是時間軸能偷偷補的；時間軸會如實顯示「這一步需要 xx 權限」。
- 沿用既有稽核：每個動作寫與原路徑相同的稽核事件，新增 `via=material_flow` 標記來源。

### 4.8 三個前後對照（`mockups/mockups.html`）

- **M1 案件「物料流程」時間軸**：從案件進去一眼看到 7 段狀態、卡誰手上、下一步。對照：現況要在財務分頁最下面＋執行管理＋庫存頁＋設備頁各看一次。
- **M2 一站式到貨**：一張單同時完成確認到貨、材料卡、入庫、預填設備；貼上序號。對照：現況 3 處各打一次。
- **M3 出貨→設備→保固**：出貨核准後一鍵帶入設備與保固起始日；保固通知含已結案案件；保固頁案號可點。

## 五、資料與技術接縫（給實作班次）

**最小接縫**：以「叫料列」（`materialOrders[].itemId`，已有 `quoteItemId`、`poDocCode`、`poLine`）為主幹。
- P1（唯讀）不加欄位：新 API 把既有各表聯起來。
- P2 起加外鍵欄位（core migration，純新增）：`stock_batches.quote_no`、`stock_batches.po_doc_code`、`stock_items.material_item_id`；叫料列／材料卡補存 `partNo`（選填）。
- P3 修狀態機：庫存序號 `shipped → installed` 在**同一案件**內合法；出貨列允許「材料申請連結＋序號」並存。
- 為什麼不一次大合併：叫料與材料卡存在 `quotations.data_json`（整份覆寫，靠 `material_guard` 守不變式），貿然改結構風險高；先包一層讀取與一站式動作，再決定要不要把叫料列拆成獨立表（另案評估）。

## 七、驗收清單（每批都測；以「新進採購／業務／工程師」三種人為準）

1. 新進採購 5 分鐘內能從「採購管理」進到「某案的叫料」並知道下一步是什麼（P0/P1）。
2. 從案件開請購單不需重新搜尋案件（P0）。
3. 一批 N 台設備到貨，序號貼上一次，庫存、材料卡、設備列都有（P2；N≥10）。
4. 先出貨、後現場登載，不再報序號衝突（P3）。
5. 已結案案件的保固到期仍會通知（P0）。
6. 工程師在工作日誌選案件後，該日誌出現在案件動態與專案報告（P0/P4）。
7. 既有頁面操作點擊數前後對照表：無一項增加。
8. 任何角色看不到自己無權限的段落資料（API 層驗證，不只是畫面隱藏）。
9. 回退：每批可單獨關閉入口而不影響既有頁面。

## 八、風險

- **資料雙邊寫入**（P2）：案件資料內嵌 JSON 與庫存表要同時寫，需交易邊界與失敗補償設計；先在測試機用假案件演練（本次的假資料腳本可重用）。
- **權限擴張疑慮**：一站式動作跨越「案件擁有者」與「庫存管理員」兩種權限；預設做法是**各段檢查各自權限**，沒有權限的段落只顯示、不能按。
- **熟手抗拒**：嚴格執行 4.6，不替換既有頁面。
- **盤點限制**：材料卡到貨日是否自動同步、專案報告叫料管控欄位是否空白、預設工務角色看不到支出申請——三項為推測，P0 開工前先實測。
