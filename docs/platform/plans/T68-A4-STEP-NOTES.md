# T68 A4（勞報單「選派發」下拉）步驟檔筆記

給整合者寫第 68 班步驟檔用。原稿 `wip/t68-labor-dropdown-r1`（審查 `D:/Claude-pm/reports/audit-t68-a4.md`），本檔隨 r2 修正一起提交。

## 1. 使用者看得到的變化（白話）
1. 勞報單詳情的「手打派發編號」與新增勞報單表單，改成可搜尋的下拉清單（共用元件 `static/dispatch-picker.js`）。預設只列「這張勞報單的受領人在該派發人員名單內」、且非草稿、非已取消的派發；可勾「顯示全部」列出其他派發。清單不顯示任何金額；案件名稱只給看得到該案件的人。
2. 國籍、所得類別、付款方式、執行業務細項的下拉選項，管理者可在設定中心改顯示名稱。國籍與所得類別是固定清單：只能改名稱，不能新增或停用，改名稱不會改變扣繳判斷。
3. 清單新增一項設定「派發清單每頁筆數」（10 到 100，預設 30）。

## 2. 權限（明講）
- 新端點 `GET /api/payslip-dispatch-options` 走 `payroll.payslip.view`（和 T67 的 `payslip-person-dispatches` 一樣是讀取）；預設等價：最高管理者，或持有「勞報單」功能勾選的人。
- 在『權限設定』頁對某角色或某人設「禁止查看勞報單」，這支清單也會一併被擋（r1 沒接，r2 已接）。
- `POST /api/payslips/{單號}/dispatch-links`（連結派發）走 `payroll.payslip.edit`（隨 T67）。
- 勞報單 6 項能力不變，沒有新增能力鍵。（其他班可能另外新增別的功能的能力，本班不影響。）

## 3. 行為收緊（N2，必須列入驗收）
關聯勞報單與派發時，**勞報單的受領人必須在該派發的人員名單內**。這和建立勞報單時選名冊人員的規則一致，舊版連結端點沒有這道檢查（任何人員都能連）。從勞報單頁、從派發頁連結名單外的受領人，現在都會被擋下，並顯示「這張派發的人員名單沒有這張勞報單的受領人，不能關聯」。沒選名冊人員的勞報單、舊呼叫端不受影響。

### 驗收項（給使用者，白話，只用測試資料）
1. 在勞報單詳情，點「選派發」：看到可搜尋的清單，預設只有受領人在名單內的派發；清單裡沒有金額。
2. 勾「顯示全部」可看到名單外的派發，但名單外的那幾筆是灰的、不能選。**灰色只是畫面上的提示；真正擋下的是伺服器**——就算有人繞過畫面直接送出，名單外的連結一樣會被拒絕（見第 3 項）。
3. 在派發頁，對一張「受領人不在這張派發名單內」的勞報單按連結：被擋下，並看到上述原因（不是默默失敗）。
4. 受領人在名單內的勞報單，兩個入口都能正常連結。
5. 〔寫入，測試資料〕到『權限設定』對測試用帳號設「禁止查看勞報單」：他打開「選派發」清單會被擋（沒有權限）。
6. 設定中心：改國籍、所得類別的顯示名稱後，勞報單表單的下拉顯示新名稱，但已存的資料與扣繳結果不變；這兩個清單看不到「新增」「停用」。

### 特殊情況：派發的人員名單是空的
如果一張派發沒有登記任何人員（名單是空的），那麼「有選受領人」的勞報單一律不能連到這張派發（受領人不在名單裡），兩個入口都一樣被擋；「沒選名冊人員」的勞報單照舊不檢查，仍可連結。這是刻意的：名單空白不等於不設限。

## 4. 步驟檔（正式機驗證）提醒
- 路由多 1 支（`/api/payslip-dispatch-options`，需登入；未登入 401）。後續檢查「未登入請求」請加上它。
- 能力登錄檢查：勞報單 `payroll.payslip.*` 仍是 6 項、鍵名與 T67 相同；全系統的能力總數以步驟檔當時凍結樹實際值為準，不要拿 6 去比。
- 本批沒有 migration、沒有新旗標、不改簽核與付款。

## 5. 已知殘留
- 派發端的 `GET/POST/DELETE /api/contractor-dispatches/{id}/payslip-links` 仍是最高管理者判斷（`_can_open`），不在權限設定頁（和 T67 的範圍一致，另案）。
- 選項清單的「付款方式」是開放清單，伺服器不驗證 `paymentMethod` 是否在清單內（既有行為）。
- 效能：`dispatch_search` 一次取出所有符合列再逐列算案件可見性（審查 N1）；派發量到數千筆以上時建議改在 SQL 分頁。
