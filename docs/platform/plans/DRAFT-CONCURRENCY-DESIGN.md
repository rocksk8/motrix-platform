# K-2 設計提案：定義草稿的並行保護（只設計，先不實作）

狀態：提案（c7，2026-10-02）。對象：`core/definitions.py`（L0 核心）、`PUT /api/definitions/{kind}/{key}/draft`、兩個編輯端（模組建構器、請款類型頁）。實作要走 PLAYBOOK §C-7（核心介面變動）。

## 1. 問題

兩位最高管理者同時編輯同一份定義草稿：`save_draft` 是無條件 upsert（`ON CONFLICT DO UPDATE SET body_json=…`），後存的**靜默覆蓋**先存的，沒有任何人會被告知。草稿表只有一列（`kind,key,scope,version=0`），沒有版本戳。模組建構器自動存檔、請款類型頁手動存檔，兩者都有此風險；設計器讓編輯變得更密集，風險略升。

## 2. 目標與非目標

- 目標：**後存的人在存檔當下被告知「這份草稿在你載入之後被別人改過」**，由他選擇「重新載入」或「用我的覆蓋」；不靜默丟資料。
- 非目標：即時共同編輯、欄位層級合併、鎖定（lock）。三者成本與誤用風險都比提示高；本提案只做「樂觀並行控制」。

## 3. 方案比較

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A. 用 `created_at` 當戳 | PUT 帶 `expected_created_at`，不符 ⇒ 409 | 不改 schema | 該欄 `timespec="seconds"`（1 秒解析度）：同一秒內兩次存檔戳相同、偵測不到；欄名語意是「建立」卻每次改寫 |
| B. 加 `rev` 整數欄 | core migration 加 `rev INTEGER NOT NULL DEFAULT 0`，每次存檔 +1，PUT 帶 `expected_rev` | 單調、無時鐘問題、可讀 | 要 core migration（L0）；舊庫補欄 |
| **C. 內容雜湊（etag）** | 伺服器對「目前存的 `body_json` 字串」算雜湊，GET／PUT 回應都帶 `etag`；PUT 帶 `base_etag`，伺服器重算比對，不符 ⇒ 409 | **不改 schema**、無時鐘問題；語意正是「內容在你載入後有沒有變」；別人存了相同內容不算衝突（ABA 無害）；雜湊只在伺服器算，前端當不透明字串 | 每次 PUT 多一次雜湊（毫秒級） |

**建議採 C**（無 migration、語意最貼切）。若主持偏好「可在列表上看到修訂序號」才選 B。

## 4. 介面（C 方案，向下相容）

**讀**：`GET /api/definitions/{kind}/{key}` 回應的 `draft` 物件新增 `etag`（`sha256(body_json)[:16]`）；沒有草稿 ⇒ `etag: ""`。`PUT …/draft` 回應也回新的 `etag`。
**寫**：`PUT /api/definitions/{kind}/{key}/draft` body 新增選填 `base_etag`：
- 缺（舊前端）⇒ 行為與今天相同（後寫者勝）。**過渡期保留**，並在稽核加 `unguarded:true` 以便盤點還有誰沒帶。
- 帶了且與目前草稿的 etag 相同 ⇒ 存；回新 etag。
- 帶了但不同 ⇒ **409** `{detail: "這份草稿在你載入之後被別人改過", code: "draft_conflict", current: {etag, created_by, created_at}}`；**不寫入**。
- 草稿原本不存在而 `base_etag` 為 `""` ⇒ 正常建立；草稿存在但 `base_etag` 是 `""` ⇒ 409（別人剛建了草稿）。
- `force: true`（使用者在提示裡選「用我的覆蓋」）⇒ 無視比對、照存，稽核 `definitions.save_draft_override`（記錄被覆蓋的 `created_by`／`created_at`／舊 etag）。
**比對在寫鎖內做**（`begin_write`）：讀目前 body→算 etag→比對→寫入同一交易，避免兩個 PUT 同時通過比對。
**發布**：`POST …/publish` 同樣可帶 `base_etag`（發布的是「我看到的那份草稿」）；不符 ⇒ 409，避免發布到別人剛改的內容。

## 5. 前端行為

- 兩個編輯端各存一個 `draftEtag`：開啟時取 GET 的 `draft.etag`，每次 PUT 成功用回應的新 `etag` 更新。
- 存檔收到 409：自動存檔**停止**（不再重試，避免洗稽核），頂部出現不可忽略的提示：「**別人剛改過這份草稿**（王小明，14:32）。」三個按鈕：
  1. **重新載入**：丟掉我這幾分鐘的修改，載入最新草稿（先顯示「你有 N 處未存的修改會消失」並提供「複製我的內容（JSON）」）。
  2. **用我的覆蓋**：以 `force:true` 再存一次（二次確認，說明會覆蓋誰、什麼時候的內容）。
  3. **先不處理**：維持畫面，仍可繼續編輯、不再自動存；離開前有未存提醒。
- 設計器本體（`form-designer.js`）**不用改**：它只回報 `onChange`；衝突處理全在宿主頁（建構器核心、請款類型頁）。重新載入後用 `setDef()` 帶入新草稿。
- 狀態列：「已存草稿 14:32」旁，衝突時變紅「未存：草稿被別人改過」。

## 6. 稽核與流量

每次存檔仍寫一筆 `definitions.save_draft`（K-1 已把設計器的自動存檔拉到閒置 4 秒，量已降低）。409 不寫稽核（沒有發生寫入）；`force` 寫 `…_override`。是否合併連續同人存檔的稽核列（原 §12-7 選配）可與本案一起做，也可不做。

## 7. 測試計畫

- 後端單元：①缺 `base_etag` 照舊（含 `unguarded` 稽核）；②相同 etag 存成功、回新 etag；③不同 etag ⇒ 409 且資料庫不變；④`base_etag:""` 的兩種情形；⑤`force` 存成功並寫 `_override`；⑥並發：兩個執行緒帶同一 etag，恰一個成功、一個 409（寫鎖內比對）；⑦別人存了相同內容 ⇒ 不衝突（ABA）；⑧發布帶不符 etag ⇒ 409。反向控制：把比對拿掉 ⇒ ③⑥紅。
- e2e（雙瀏覽器 context）：A、B 同開一份草稿，A 改名存檔，B 改別處按存檔 ⇒ B 看到提示；B 選「重新載入」⇒ 看到 A 的改名、B 的修改消失；B 選「用我的覆蓋」⇒ DB 是 B 的內容且稽核有 `_override`。兩個編輯端各一份。
- 相容：舊前端（不帶 `base_etag`）的既有 e2e 全綠；`test_definitions*` 既有題不變。

## 9. 風險與取捨

- **過渡期**：舊分頁（尚未重新整理的瀏覽器）不帶 `base_etag`，仍是後寫者勝；可在發版後第二版把 `base_etag` 改為必填。
- **雜湊對象**：用資料庫存的原字串，不重新序列化，避免 JSON 鍵序／空白差異造成假衝突；伺服器是唯一計算者。
- **誤報**：使用者自己開兩個分頁編輯同一份草稿也會互相衝突（正確行為：提示他）。
- **不處理**：自訂模組的「已發布版」並行（發布本身有版本號且不可變，不在本案）。
