# 閘門沿用的等價性論證：O3（增量沿用）與 O6（分段指紋）

> 作者：node-ab｜2026-10-08｜分支 `wip/t47-build-optimization`｜性質：**書面論證＋反例搜尋＋建議，無程式**；使用者在讀完後裁示。
> 背景：`BUILD-VERIFY-OPTIMIZATION-T47.md` §3 把 O3／O6 列為「會弱化閘門、需要書面等價性論證」。本文件就是那份論證。
> 事實來源標記：[讀碼]＝讀過的檔案與行為；[實測]＝本機實際跑出的數字；[推論]＝我的推理（未實測）；[設計]＝`BUILD-OPT-ITEM3-INCREMENTAL-DESIGN.md` 已有的結論。

## 0. 結論（先看這裡）

1. **O6（分段指紋，單獨做）不值得做，也不安全**：①安全的排除範圍（沒有任何測試讀到的檔）實測只佔最近 10 天 commit 的 **1.4%（20／1421）**，省不到什麼；②更要緊的是**有測試讀的不是檔案內容而是 git 歷史**（commit 日期、各檔最後一次修改的 commit），所以即使 commit 只動「沒人讀的檔」，這些測試的結果仍會改變（§3.3 反例 C1，本週實際發生過）。要安全就得把這些測試拉出來每次重跑——那就是 O3 的「底板」，O6 退化成 O3 的一個子集。
2. **O3（增量沿用）可以有等價性保證，但只在迭代期**：規則是「**沿用某個測試的前一次綠 ⇔ 該測試的讀取集合與這次的改動集合不相交，且前一次與這次的環境指紋相同、前一次是嚴格全綠的同日基準，且該測試不在底板**」，並且**發布候選一律真全量**（不弱化發布閘門）。保證成立的前提是四個假設（§2.2），其中兩個今天**不成立**（讀取集合不完整、有順序相依的測試），必須先補才能開（§5）。
3. **建議**：①不做 O6；②O3 只作「迭代期輔助」，上線前提＝動態讀取集合追蹤（§5 R-1）＋兩週影子全量零差異（§5 R-3）；③發布候選維持現行「同樹全綠」。短期要壓縮時間，先走已核准的 O1／O2／O4／O5，不靠 O3。

## 1. 現行保證的精確陳述（O3／O6 要拿來比的基準）

**G0（現行）**：`build_test_reuse.find_reusable_stage` 只在下列全部成立時沿用某段的綠：[讀碼 `backend/tools/build_test_reuse.py`]
1. 指紋相同＝`sha256(ls-tree -r HEAD 去掉 REUSE_EXCLUDE)`（整棵 tracked tree 的 mode/type/blob sha）＋執行環境（python 版本、`pip freeze`、playwright 版本與瀏覽器清單、未被忽略的 `MOTRIX_*` 環境變數、`PYTEST_ADDOPTS`）；
2. 工作樹乾淨（含未追蹤檔，否則指紋為 `None`）；
3. 該段**嚴格全綠**（exit 0，或失敗題經隔離重跑通過且已登記 known_flakes）、**同一天**、**12 小時內**。

**G0 為什麼是等價的**：測試結果是 `f(程式與資料樹, 環境, 時間, 隨機性)`。tree sha 相同 ⇒ 所有 tracked 檔相同；環境指紋相同 ⇒ 依賴套件與設定相同；同日＋12 小時 ⇒ 日期型斷言不會翻面；剩下的非決定性（偶發）由「嚴格全綠」排除（綠的那一次沒觸發偶發）。**G0 沒有假設任何關於「測試讀了什麼」**——這是它最強的地方，也是 O3／O6 的代價所在：它們都得**主張一份讀取集合**。

**G0 已有的一個先例**：`REUSE_EXCLUDE={tools/platform/known_flakes.json}`——該檔「登記一題偶發不改變任何題目過或不過」（見檔頭註解）。它是目前唯一被排除的檔，論證是「它不是任何測試的輸入」。O6 就是把這個論證推廣到更多檔。

## 2. 共同模型與語言

- **讀取集合 R(t)**：測試 t 在一次執行中**實際讀取**的所有檔案與目錄枚舉結果（`open`、`stat`、`listdir`／`glob`／`rglob`／`os.walk`、`import`、子行程 `git ls-files／ls-tree／log／blame／diff`、讀 sqlite 種子檔等）。**目錄枚舉讀的是「名字的集合」**，所以新增／刪除／改名一個檔也改變 R(t) 的內容，不只是改內容。
- **改動集合 Δ**：基準 commit B 到這次 HEAD 的新增／修改／刪除／改名的路徑。
- **環境 E**、**日期 D**、**git 歷史 H**（commit 日期、作者、每個路徑最後一次修改的 commit）——H 是第三種輸入，容易被忘記（§3.3）。

### 2.1 想要的性質（等價性）
**EQ**：對每個 t，「沿用前一次的綠」與「這次重跑」得到相同的 pass／fail。

### 2.2 EQ 成立的充分條件（四個假設）
- **A1 讀取集合完整**：R(t) 包含 t 的結果所依賴的**全部**輸入（含 H、D、環境變數、時鐘、隨機）。
- **A2 決定性**：給定相同輸入，t 的結果相同（或偶發已被「嚴格全綠基準」排除）。
- **A3 測試間獨立**：t 的結果不依賴同一次執行裡其他測試跑了沒有／跑在哪個 worker／順序。
- **A4 環境指紋涵蓋執行器**：python、套件、瀏覽器、`MOTRIX_*`、`PYTEST_ADDOPTS`、以及**執行器本身的程式**（conftest、plugin：`fail_stream`、`failfast`）。

**今天這四個假設的現況**（這是整份論證最重要的一段）：
| 假設 | 現況 | 證據 |
|---|---|---|
| A1 | ❌ **靜態 test_map 不完整**；動態掃目錄的測試 118 個，其中 27 個沒有任何 `dir:` 單位且不在底板；git 歷史讀取者（`test_module_changelog_follows_code`、`test_version_manifest*`）沒有被建模 | [設計 §4.1 第 1、2、3 點，實測] |
| A2 | ⚠ 大致成立；已知例外＝效能門檻題（`perf_100k_rows`）、e2e 逾時 | [設計 §4.1 第 9 點] |
| A3 | ❌ **有順序相依的測試**：`test_expense_prefill…::test_last_value_hook…` 單獨跑（或當 xdist worker 的第一題）會 `no such table`，整檔跑才綠；origin/platform 上同樣重現（本班查明並修掉） | [實測 2026-10-08] |

## 3. O6：分段指紋

### 3.1 提案
指紋由「整棵 tracked tree」改成「**stage 讀取集合內**的檔」＋環境：`fp_stage = H({path: blob_sha | path ∈ R*(stage)}, E)`；不在 R*(stage) 的檔（例如純文件）改動不使該段失效。

### 3.2 精確規則（要讓 EQ 成立，O6 必須同時滿足）
**R6.1** R*(stage) ⊇ ⋃ₜ∈stage R(t)，且 R* 以**動態追蹤**得出（§5 R-1），不是靠 grep。
**R6.2** 目錄枚舉型讀取要把「該目錄的名字清單」也放進指紋（新增／刪除／改名一個檔也要失效）；任何對祖先目錄（含 repo 根）做 `rglob`／`git ls-files` 的測試，會讓整個子樹進 R*（實際上 ⇒ 沒有可排除的）。
**R6.3** **git 歷史輸入 H**：只要 stage 內有任何測試讀 git 歷史（`git log／blame／diff／rev-list／ls-files`），指紋必須再加上 **HEAD sha（或至少 HEAD commit 日期＋每個被讀路徑最後修改的 commit）**。——這一條使 O6 在現況幾乎沒有空間（§3.3 C1）。
**R6.4** 測試檔、conftest、plugin、工具程式一律在 R*（它們本來就是輸入）。
**R6.5** R* 每 N 次（建議 3）或每次 `tests/**`／`conftest.py`／`tools/platform/**` 變動時，**重新追蹤**；追蹤本身失敗 ⇒ 退回 G0（整棵 tree）。

### 3.3 反例搜尋（O6 會漏什麼）
- **C1（真實發生過，推翻「純文件 commit 可沿用」）**：本班 `tests/test_version_manifest_2026_09_22.py::test_vr1_…` 因「manifest 最新日期 2026-10-07 < 最新 commit 日期 2026-10-08」轉紅。**tree 內沒有任何被它讀取的檔變動**，變的是 **HEAD 的 commit 日期（H）**。若指紋只看「被讀到的檔」，這一題的「前一次綠」會被錯誤沿用。同類：`test_module_changelog_follows_code`（用 git 歷史比對「程式最後改動」與「版號條目寫入」的 commit 先後；本班因此紅過兩次）。⇒ R6.3 是必要的，且使「只動沒人讀的檔」的 commit 照樣改變這些題的結果。
- **C2 目錄枚舉**：新增一個檔到 `frontend/pages/` 或 `docs/platform/`——沒有任何既有測試「讀」它，但 `rglob`／`os.listdir` 型測試（歸屬、頁面清單、單位卡）的結果會變。路徑層級的排除會漏；必須用 R6.2。
- **C3 刪除／改名**：被排除的路徑之一被刪除，若某測試對「不存在」有斷言（例如「這個檔不得存在」）——不在 R* 但結果會變。⇒ 排除規則要對刪除也生效，或不排除會被斷言「不存在」的路徑（靜態可辨者）。
- **C4 產生檔**：`dep_graph.json`／`test_map.json`／`UNIT-INDEX.md` 是測試的輸入，也是**測試檢查的對象**（與重產結果相等）。它們在 R*，所以改了就失效——正確；但這也表示「產生檔只由列車提交」的班次，每次重產都使整段失效（本班 2 次），O6 對這類無幫助。
- **C5 時鐘**：同日 12 小時規則在 O6 下仍要保留（日期型斷言）；O6 不處理。
- **C6 環境**：與 G0 相同（A4）。
- **C7 追蹤不完整**：子行程（`subprocess` 起的 pytest／node／git／powershell）讀的檔，Python 的 `sys.addaudithook` 看不到。⇒ 追蹤要涵蓋子行程（或把會起子行程的測試整檔放入「永遠重跑」底板）。

### 3.4 效益（實測，決定 O6 值不值得）
最近 10 天 origin/platform 非合併 commit 共 **1421** 筆。[實測 `git log --since=10.days --no-merges --name-only`]
| 類別 | 筆數 | 占比 |
|---|---|---|
| 只動「沒有任何 py 引用」的目錄（`docs/quick/` 17 檔、`docs/platform/prod-tasks/` 20 檔、`docs/handover/` 0 檔） | 20 | **1.4%** |
| 只動 `docs/**`（任何文件，含被測試讀取的 `docs/platform/`、`docs/windows/`） | 241 | 17% |
| 至少碰到上述「沒人引用」的目錄 | 93 | 6.5% |
即使完全正確，**可安全排除的範圍占 commit 的 1.4%**；而且列車閘門是以「一整班的樹」為單位，不是逐 commit，一班之中幾乎一定有程式變動 ⇒ 實際效益趨近 0。

## 4. O3：增量沿用（以測試為單位）

### 4.1 提案
迭代期（作者分支／整合樹小改後重跑）：不重跑「讀取集合與改動集合不相交」的測試，沿用基準的綠；其餘（改動相關＋底板＋基準紅重選）重跑。發布候選仍真全量。

### 4.2 精確規則（EQ 成立所需）
**R3.1（沿用條件，逐測試）**：t 可沿用 ⇔ ①基準 B 的同段為**嚴格全綠**（非 fail-fast 中止、非 flaky 重跑才綠）、同日、≤6 小時；②`R(t) ∩ Δ = ∅`（含刪除／改名／目錄枚舉的名字清單，R6.2）；③環境指紋與基準相同；④t 不在底板；⑤`H` 不需要或已併入（R6.3：讀 git 歷史的測試一律在底板）。
**R3.2（底板＝永遠重跑）**：`tests/platform/**`、`global_tests`、test_map `unmapped`、所有讀 git 歷史者、所有會起子行程者、`test_generated_maps` 等產生檔／快照型、`test_module_changelog_follows_code`、`test_e2e_classification` [設計 §5.1，約 219 檔、~11 分]。
**R3.3（強制全量，fail closed）**：Δ 含硬底層（`db.py`、`conftest.py`、`core/**`、`helpers/**` 的 L1）、選題器自己改了（`selector_sha`）、test_map／dep_graph 壞了或現場重算失敗、`unmapped_changes` 非空、基準缺 40 碼 SHA／跨日／>6 小時／鏈長>2／鏈根不是真全量、**連續 3 次增量後下一次全量**、任何 `aborted_by` 的段不當基準 [設計 §5.2]。
**R3.4（發布）**：出貨包必須是真全量，或「根為全量、距今≤6 小時、`selector_sha` 同」且**零增量鏈**。使用者旗標 `-ForceTests`／`-Release` ⇒ 一律全量。
**R3.5（可稽核）**：manifest 逐段記 `selected／carried／floor／collected` 的**檔名清單與 sha**；`carried ∩ ran = ∅`；`selected ∪ floor ∪ red_reselect ∪ carried ⊇ collected`（集合守恆，漏一個就擋）[設計 §6 R3-b]。

### 4.3 在 A1／A2／A3／A4 下的證明（簡述）
設 t 被沿用：基準那次 t 為綠（A2 ⇒ 該次輸入下結果為綠）；R3.1②＋R3.2⑤＋R3.1③＋R3.1①（同日 12h→6h）⇒ t 的全部輸入（檔案內容與名字清單、git 歷史、環境、日期）與基準相同（A1）；A3 ⇒ 其他測試是否執行不影響 t；A4 ⇒ 執行器相同。故這次重跑 t 的結果＝綠＝沿用結果。∎
**證明只在 A1、A3 成立時有效**，而 §2.2 已指出今天不成立。

### 4.4 反例搜尋
**方法（突變式）**：對一個全綠的基準樹，逐一做「單一改動 m」（改一個程式檔／文件／golden／設定／測試／刪檔／改名／新增檔），分別 ①跑**真全量**得到紅集合 RED(m)；②用 O3 的選題得到 `RERUN(m)`；**判準：RED(m) ⊆ RERUN(m) 對所有 m 成立**。任何 `m` 使 RED(m) ⊄ RERUN(m) 即為反例，並回頭補 R(t) 或底板。成本高（每個 m 一次全量），所以：
- **歷史重放（便宜，已做 [設計 §4.2]）**：以 t29／t30 的真實「紅→修」為 m，召回 25／25（確定性）；**未把掃目錄型 27 檔入底板前是 24／26，不達標**——證明 A1 的缺口是真的。
- **本班補充的真實 m（用 file 位置推論 [推論]）**：過期產生檔×2、模組 CHANGELOG 守門、測試裡寫死的 116、VR1 日期守門、filehub probes、`audit_account_permissions` 的 `--db` 測試——**全部落在 `tests/platform/**` 或 global／產生檔型 ⇒ 全在底板**，所以 O3 會抓到；順序相依的 prefill 偶發題**既不被 O3 造成、也不被它抓到**（A3 的缺口，與選題無關）。
- **人工構造的反例（判定表）**：

|---|---|---|---|

## 5. 上線所需的證據關卡（若使用者選擇 O3）
**R-1 動態讀取集合追蹤**：用 `sys.addaudithook`（`open`／`os.listdir`／`os.scandir`／`glob`／`subprocess.Popen`）在一次真全量中逐測試記錄 R(t)，含子行程；輸出 `read_sets.json`（不進 git，或進 git 但由列車重產）。這取代 test_map 的字面靜態對應，直接補 A1。**驗收**：對 §4.4 的 C-a／C-b／C-h 構造反例，R-1 能把它們選進重跑。
**R-2 底板守門**：底板清單由 R-1 + 規則自動產生（讀 git 者、起子行程者、`tests/platform/**`）；手動從底板拿掉任何一檔 ⇒ 守門題轉紅（突變①，設計 R3-d）。
**R-3 影子全量（兩週）**：每個增量放行的包，夜間閒置仍跑一次**全量**，逐 nodeid 比對；**差異＝0** 才算通過；任何差異 ⇒ 退回並寫入「選題洞」清單 [設計 R3-e]。同時量測 A3：對每個測試做「單獨重跑」抽樣（至少 5%）找順序相依的題。
**R-4 突變式反例搜尋（§4.4 方法）**：每次改選題器／底板規則後，對 ≥30 個種子改動（含刪除／改名／新增檔）跑一次，要求召回 100%。
**R-5 開關與退場**：`MOTRIX_STAGE_INCREMENTAL=0`（預設關，逐步開）；manifest 標示每個包是增量或全量；出貨包永遠走 R3.4。

## 6. 建議（給使用者裁示）
| 選項 | 建議 | 理由 |
|---|---|---|
| **O6 單獨實作** | ❌ 不做 | 安全可排除範圍僅 1.4% 的 commit；git 歷史型測試使「沒人讀的檔」也影響結果（C1）；需要的保護機制就是 O3 的底板 |
| **O3 作迭代期輔助** | ⚠ 條件式：先做 R-1、R-3，兩週零差異再開 | 可把紅後重跑由 ~66 分降到底板＋受影響檔（設計估 10～12 分），但 A1、A3 今天不成立；規則 R3.1–R3.5 能在補上後給出 EQ |
| **O3 用於發布候選** | ❌ 不建議 | 發布閘門的價值就是「同一棵樹全綠」；增量沿用在發布上的風險（一次漏測 ＝ 正式機事故）遠大於省下的時間 |
| **短期替代** | ✅ 先做 O1（preflight）、O2（regen_all）、O4（分支輕量）、O5（`-n 4`，已核准） | 不碰任何等價性假設；已把「有紅燈的班」從 160～200 分壓回 ~65～93 分 |
