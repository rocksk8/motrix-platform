# 業務開發案件「指派／進度回報」重設計（2026-11-04）

> 緣起：T73 上線後使用者實機操作，反映 `dev_cases` 的指派／進度回報設計不好用（進度單欄整段覆寫、無時間戳與作者、換人後舊進度誤導、管理員代填、重存就重發通知）。設計由 hichan-3（原稽核 `AUDIT-hichan3-t73.md` S1／S5／S6 作者）與 hichan-7（T73 步驟檔審查）討論收斂，主持（hichan-74）核定「逾期提醒要寄信」後定稿。
> 實作：hichan-3。複核：hichan-7（對抗審查，不同人）。完成並通過複核後才排上線，走正常列車流程（本票不急）。

## 1. 進度回報：改成只增不改不刪的歷史表

- 新表（crm 模組自帶 migration 0003，冪等；是 L2 遷移，失敗會讓整個 crm 模組下線——必須用含 T73 後真實資料的庫實測）：
  `dev_case_progress(id, case_id, author_id, content, created_at)`
- `POST /dev-cases/{id}/progress` 取代現有 `PATCH`；另加 `GET /dev-cases/{id}/progress`（依 `row_access` 判可見者）列出歷史。
- `content` 1～4000 字、不得空白；稽核標籤只取前約 40 字。
- 新增一筆時連動 `dev_cases.updated_at`（維持既有「最後更新」語意）。
- **權限：只有目前被指派人（`assigned_to` 本人）可以新增；不是被指派人的管理員（含 superadmin）403；管理員本人就是被指派人時可寫（主持 2026-11-04 裁示）**（前端 `canEditProgress` 與後端 403 判斷式都要改——這是使用者已經確認的需求，不是討論項）。
- 被指派人離職／帳號停用的出口是「重新指派」，不是另開管理員代填或更正端點（更正＝再新增一筆，不改舊的）。
- 不併入「開發記錄」（`dc-logs`）：那張表混了客戶拜訪紀錄、推行事曆、算通路統計，還有代填走核准流程，語意跟「被指派人自己回報進度」不是一回事。

## 2. 指派／回覆期限：只有真的變才動作

- `PATCH /dev-cases/{id}/assign` 存檔前先跟舊值比對：
  - 對象與期限都沒變 ⇒ 不寫 DB、不稽核、不通知、`updated_at` 不動（純粹重按一次儲存鍵不該有任何副作用）。
  - **換人**：新負責人照現行（站內＋信）；前任收到一則站內通知「您已不再負責《案名》」；取消指派（改成未指派）只有前任收到站內通知。
  - **只改期限（對象不變）**：只發站內通知，不寄信（換人那封信本來就帶期限，單獨為改期限再寄信太吵）。
- 新增驗證：期限這個值如果是「這次有被改動」且早於今天 ⇒ 400（不能把人指派成一開始就逾期）。

## 3. 換人時舊進度怎麼處理

- 舊進度**全部保留**（每筆自帶作者與時間，不會像現在這樣被誤讀成現任寫的）。
- 畫面上「目前進度」＝**目前被指派人**寫的最新一筆；換人後新負責人還沒寫過 ⇒ 顯示「新負責人尚未回報」，但歷史時間軸照樣列出前任留下的全部紀錄（有完整脈絡，不會搞混）。
- `dev_cases` 新增 `assigned_at`、`assigned_by` 兩欄，只在換人（含首次指派／取消指派）時更新。

## 4. 逾期提醒（新功能，補上現在完全沒有的缺口）

- 判定條件：`status='洽談中'` 且 `reply_deadline` 非空且早於今天（當天不算逾期）且 `assigned_to` 非空且**自 `assigned_at` 之後該被指派人沒有新增任何一筆進度**。
- 畫面：案件詳情與清單上標紅「逾期 N 天未回報」；一旦有進度就消失（不需要人工清除）。
- 每日排程（比照既有 `_check_dev_case_stale`）：每個符合條件的案件提醒一次，不重複催促；防重入用 guard key＝`案件＋期限＋被指派人`（換人或改期限會重新武裝，不會漏提醒也不會炸鍋式重發）。
- 收件人＝被指派人＋`assigned_by`；任一帳號停用、或舊資料沒有 `assigned_by`（遷移後常見）⇒ 退回通知全體 admin（跟既有 `_check_dev_case_stale` 收件人退路一致）。
- **主持裁示（2026-11-04）：逾期提醒要寄信，不是只有站內＋紅標。**
  理由：這是整個逾期機制唯一的主動催促點——人沒在用系統時，站內通知沒有意義；信件成本有界（一個新 `mail_type`：`dev_case_reply_overdue`，照 T73 的 `dev_case_assigned` 同樣的方式登進 `notification_prefs.EVENT_GROUPS`「案件與到期提醒」群組＋`mail_types.register`，並比照 T73 稽核 N1 的教訓把「排程收件人有沒有漏列」補上真實測試），而且只寄一次（不是天天轟炸）。

## 5. 既有資料遷移（crm migration 0003 的一部分）

- `dev_cases.progress_report` 非空的案件 ⇒ 搬成 `dev_case_progress` 的第一筆：`author_id = assigned_to`（搬遷當下的值）、`created_at = updated_at`。
- 同時把該案的 `assigned_at` 設成 `updated_at`（避免遷移跑完當下，大量既有案件因為「assigned_at 很舊、沒有進度」被誤判逾期、炸出一輪假警報）。
- `assigned_to` 本身是 NULL 的案件：`author_id` 留空，畫面顯示「（舊資料）」。
- 舊的 `progress_report` 欄位**保留但不再使用**（不刪欄位，符合模組 migration 只增不破壞的既有規則）。

## 6. 實作時別漏的既有守門

- `POST` 取代 `PATCH` 會讓路由統計跟著變：`route_inventory.json`（`endpoints_total`／`endpoints_api`）與寫入路由 golden 清單都要同步更新（T73 已經在這件事上栽過一次，見 `20261104-t73-apply.md` 已知殘留）。
- 新端點（`POST`／`GET` progress）要補未登入 401 測試、權限測試（非被指派人 403、管理員現在也要 403）。
- `dev_case_reply_overdue` 這個新 mail type 照 T73 稽核 `AUDIT-pm-sub-t73.md`（T73A-M1）的教訓，排程收件人名單要有真實 HTTP／排程呼叫測試釘住，不能只靠人工檢查程式碼。
- crm 模組版號、`module_schema_versions.crm`（這次會到 3）、core CHANGELOG 依慣例取號。

## 7. 範圍外（本票不做）

- 進度內容的管理員「更正」或刪除端點（離職／寫錯的处理方式就是重新指派／再新增一筆）。
- 逾期之外的其他提醒（例如期限前 N 天預告）——非本次使用者反映的問題，另開票。
