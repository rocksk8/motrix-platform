## 1. audit-log.html「歷史紀錄」

**1) 基本資訊**：menu「歷史紀錄」／perm 模組 `audit_log`（P 無角色硬擋；B/routers/system.py:444 `require_any_module(user,["audit_log"],"歷史紀錄")`）。一句話：查「誰在什麼時間對哪張單做了什麼、哪些操作被系統擋下」。hub 描述：「稽核日誌：誰在何時對哪張單做了什麼」(system_hub_l1.json:8)。

- T1 分類邏輯：命名「歷史紀錄」與 hub 描述「稽核日誌」兩個說法；另有「出貨單歷史紀錄」(第9頁) 與「版本紀錄」同名風格但內容完全不同（那兩頁不是稽核）。見 menu_l1.json:233、242 vs supply/module.json:114。
- T2 用語：見上表（影子模式、閘門、佇列、邊緣路徑、MQ-）。
- T3 填寫方式：「所有操作」下拉 ~190 個選項、依「業務模組」分組（P:~140-270），要先知道哪個動作屬於哪個模組；已有「所有模組」＋「分層瀏覽」重複了這個功能。起訖日期為兩個獨立 date（無「今天／本週／本月」快捷）。
- T4 缺預設值：進頁面預設查全部（樹狀圖預設近 N 天，列表卻不限日期）；沒有預設「近 7 天」之類。
- T5 錯誤訊息：載入失敗 `catch(e){}` 完全靜默（P:~519-523、init `fetchTree` 同），畫面只會顯示「暫無紀錄」＝與「真的沒紀錄」無法區分（建議顯示「讀取失敗，請重新整理」）。
- T6 危險設定沒分層：無（唯讀頁），但此頁權限是模組 key `audit_log`，可個別勾給非最高管理者；紀錄可能含員工操作與金額，需提醒只給老闆／管理層。

**5) 不該給一般人碰**：「所有標籤」(簽核標籤)、「影子模式」「複查暫停」動作、status_code、「分層瀏覽」的範圍擴大。可收進「進階篩選」。
**6) 歸屬建議**：這是老闆最想看的頁（誰改了什麼），應留在主要位置，但改名為「操作紀錄」或「誰改了什麼」，並加「近 7 天／本月」快捷與「只看刪除／只看被擋下」快速鈕。

## 2. module-versions.html「版本紀錄」

**1) 基本資訊**：menu「版本紀錄」／perm 模組 `module_versions`（B/routers/module_versions.py:46-47）；新增需 admin 以上（:15-19）；刪除需 superadmin（:119-121）。一句話：看／手動登記「各模組的更新說明」，像產品 changelog。hub 描述：「目前版本與各模組更新紀錄」(system_hub_l1.json:216)。

**2) 區塊與欄位**
- 工具列（:~420）：標題「版本紀錄」｜「依模組／時間軸」切換｜search「搜尋模組或內容…」｜「+ 新增」（admin 以上才顯示）。
- 過期警示（:~438）：「⚠️ 版本紀錄已經 N 天沒有更新（最後一筆：…）。這段時間如果有出貨，表示有人忘了寫 —— 而不是沒有東西可以寫。」（>14 天觸發，`STALE_AFTER_MS` :~668）。
- 左：模組清單（模組名＋筆數＋「最新版本 · 日期」）；右：該模組歷史時間線（「NEW」徽章、版本徽章、日期、「✕ 刪除」（superadmin）、內容、「（無說明）」、更新人 `e.updated_by || 'system'`）；「新增此模組版本」。
- 時間軸視圖：依日期分組「N 項更新」。
- 新增彈窗「新增版本記錄」(:~609-640)：
  - 模組名稱｜input＋datalist｜placeholder「選擇或輸入模組名稱」｜預設空（從右側選中模組帶入）｜必填（alert「請填寫模組名稱」）。datalist 寫死 24 個名稱：報價單、簽核佇列、案件管理…「系統安全」「系統備份」「測試框架」「版本紀錄」。
  - 版本號｜input｜placeholder「例：v1.2.0 或 2026-07-21」｜預設空｜必填（alert「請填寫版本號」）。
  - 更新內容｜textarea｜placeholder「描述此版本的主要變更…」｜選填。
  - 按鈕「取消／儲存」。

**3) 工程師用語**
| 原文 | 為什麼看不懂 | 白話建議 |
|---|---|---|
| 「版本號」placeholder「例：v1.2.0 或 2026-07-21」(:~625) | 語意化版本號是軟體開發慣例 | 「更新日期或版次（例：2026-07-21 第 2 次更新）」 |
| 「模組名稱」datalist 含「測試框架」「系統安全」(:~611-616) | 「測試框架」是開發內部；一般客戶不該看到 | 該頁顯示客戶版的「更新公告」，內部項目剔除 |
| 「依模組／時間軸」 | 「模組」對老闆是什麼？ | 「依功能／依日期」 |
| 過期警示「這段時間如果有出貨，表示有人忘了寫」 | 對象是開發商出貨流程，客戶看了莫名其妙（客戶沒有「出貨」這件事） | 客戶版整段移除 |
| 作者欄 `updated_by \|\| 'system'` (:~528) | 英文 `system` | 「系統自動」 |
| 儲存失敗訊息 `alert('儲存失敗：' + e)` (:~758) → 後端 409「此模組已有相同版本號的紀錄，請換一個版本號」、422「模組名稱不可為空」「版本號不可為空」(B/routers/module_versions.py:91-100) | 後端句子可讀，但 e 為 HTTP 碼時（r.json() 失敗）只剩「儲存失敗：500」 | 加「請稍後再試或聯絡系統管理員」 |
| 刪除失敗 `alert('刪除失敗：'+e)` e＝HTTP 狀態碼數字 (:~776) | 使用者只看到「刪除失敗：403」 | 白話說明（只有最高管理者可刪） |

**4) 問題分類**
- T1：這頁是「開發商的出貨日誌」性質（寫給維護者看「誰忘了登記」），放在一般系統設定群組語意不合；與「歷史紀錄」同名風格易混。證據：過期警示 P:~438、datalist 「測試框架」。
- T2：版本號格式（v1.2.0）、「模組」、「出貨」。
- T3：版本號自由文字，無格式驗證；「更新內容」無範本；datalist 不提供客戶實際已安裝模組（含寫死名單 P:~609-616，與動態 `modules` 合併）。
- T4：版本號無預設（可預設今天日期）；模組名稱已選中時有預設（openNew :~726）。
- T5：載入失敗只有 `console.error('fetch failed:', e)`（:~706），畫面停在「載入中…」消失後「無符合結果」；新增失敗見上表。
- T6：admin 可新增、superadmin 才能刪，已分層；但「新增」讓客戶端自己的管理員也能偽造「版本更新紀錄」，與開發商出貨紀錄混在同一張表（updated_by 才區分）。

**5) 一般人不該碰**：整頁的「+ 新增」「✕ 刪除」。
**6) 歸屬建議**：給維運／開發商：移出「系統」群組或收進「進階（工程師）」。客戶想看的是「這次更新改了什麼」→ 可改成登入後的「更新公告／關於系統」小視窗，只讀、不含新增刪除與過期警示。

## 3. online-stats.html「在線時數統計」

**1) 基本資訊**：menu「在線時數統計」／perm superadmin（前端 P:250-258 擋「你沒有這個頁面的權限／在線時數統計僅限最高管理者檢視。」；後端兩支端點 superadmin）。一句話：看各帳號「實際在操作的時數」與「逐條操作軌跡」。hub 描述「各帳號登入與在線時數」(system_hub_l1.json:22)。

**2) 區塊與欄位**
- 標題 eyebrow「系統設定」(:76)、副標「只統計有實際操作的活躍時間，每 5 分鐘累計一次」(:78)。
- 「目前在線」晶片：N 人、姓名＋角色；「目前沒有人在線」。每 60 秒自動重整 (:261)。

**4) 問題分類**
- T1：名稱「旅宿檔案更新」vs 主要功能「查詢紀錄／詢價」；hub 歸在「資料與備份」。使用者會誤以為是「更新我們自己的旅宿檔案」。屬專案出差住宿查詢的小工具，是否納入通用系統選單值得商榷。
- T2：OSM／TGOS／zip／JSON／環境變數。
- T3：詢價表單 7 欄尚可；金額欄沒千分位提示；計價與管道已是下拉（好）。
- T4：已有預設（今天、每晚、電話）；查詢半徑等在地圖頁。
- T5：lastError 原樣外露（見上）；錯誤統一為「…失敗：HTTP N」。
- T6：「更新旅宿資料」會整批替換快照並對外連線（B/modules/lodging/api.py:52-54 docstring「整批替換快照（最高管理者；唯一的對外連線）」），已限 superadmin，但按鈕無確認提示。

**5) 一般人不該碰**：「更新旅宿資料」鈕與其狀態／錯誤文字、匯出 JSON。
**6) 歸屬建議**：功能是業務／專案人員可能用，但「資料檔更新」是維運動作。建議：把查詢紀錄／詢價併到地圖或專案頁；「更新旅宿資料」改成自動，只在失敗時通知管理者；選單名改「旅宿查詢紀錄」。

## 9. shipping-export-history.html「出貨單歷史紀錄」

**1) 基本資訊**：menu「出貨單歷史紀錄」(supply/module.json:114)／perm 模組 `shipping_export_log`（B/modules/supply/api/shipping_notes.py:151-152）。一句話：列出每一次出貨單「匯出／列印」的紀錄（誰、何時、對內或對外、第幾次）。hub：「出貨單匯出與列印的歷史」，影響：「只是查看，不會改動任何資料。」(module.json:122-123)。

**2) 區塊與欄位**
- 標題「出貨單歷史紀錄」；副標「共 N 筆匯出紀錄」。
- 篩選：search「搜尋單號／客戶／專案…」｜「年份」下拉（「2026年」）｜「月份」下拉（「1月」…）｜「清除篩選」。全選填、預設空。
- 列表：單號（連到 `case-management.html?q=<quoteNo>`）｜徽章「對內／對外」｜「第 N 次」｜「客戶 ／ 專案」或「（無客戶／專案資訊）」｜匯出時間｜「出貨日 …」｜「匯出人員：…」。
- 空狀態「尚無符合條件的匯出紀錄」(:~78)。

**3) 工程師用語**
| 原文 | 為什麼看不懂 | 白話建議 |
|---|---|---|
| 「對內／對外」(`e.mode==='internal'`，:~62) | 沒有說明＝內部版（含成本）／客戶版？ | 「內部版（含成本）／客戶版」並加 tooltip |
| 「匯出」 | 實際指列印／下載 PDF？ | 「列印／下載」 |
| 連結目標「case-management.html?q=…」文字只顯示出貨單號，點了去案件管理 | 連結目標不明 | 加「前往案件」 |

**4) 問題分類**
- T1：同名風格「歷史紀錄」與第 1 頁混淆；它其實是「稽核」的子集（誰列印了出貨單），應整併進歷史紀錄的「匯出」類型（audit-log 已有「匯出 PDF／Excel」動作）；hub 放「稽核與紀錄」是對的，但 menu 在「系統」群組最底。
- T2：輕微（對內／對外）。
- T3：搜尋為前端過濾（全量載入後在瀏覽器篩，P:~123-137），資料多時變慢（性能，非 UX 文字）。
- T4：無預設期間（顯示全部）。
- T5：**載入失敗靜默**：`.catch(e => console.error('load failed:', e))`（:~113），UI 顯示「尚無符合條件的匯出紀錄」，使用者會誤以為從沒匯出過。
- T6：不適用（唯讀）。

**5) 一般人不該碰**：無。
**6) 歸屬建議**：老闆可能想知道「出貨單被誰印過幾次」，但這屬「稽核」。建議併入「歷史紀錄」的篩選（類型＝匯出／列印、模組＝出貨單），不單獨占一個選單項，並補失敗提示。
