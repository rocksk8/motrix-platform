# 全調整制盤點（第 54 班）：哪些寫死的東西該改成管理者可調

基準 `origin/platform` `b2486535c`；作者 node-39；2026-10-10。唯讀盤點，沒有改任何程式。明細在 `configurability_items_t54.csv`（141 筆：編號、群、位置、今天的值、誰會改、風險、現有機制、工作量、建議優先序）。
使用者方向：「還有哪些已有的功能，能改成全調整制放入開發內」——權限矩陣由 1d 另做，本稿不含。

## 0. 結論

1. 盤到 **141 項**寫死的規則（5 路平行掃描，每筆 `file:line` 都自動核對過，0 筆行號錯誤），分 **16 群**；涉及金額或法規的 60 項、涉及安全的 18 項；工作量 S 89／M 41／L 11；建議優先序 **P1 23 項**、P2 36 項。
2. **不必從零蓋**：系統已有 85 個 `system_settings` 鍵、11 個專屬設定頁，以及一套現成的「草稿→驗證→發布→差異→還原」定義文件庫（`core/definitions.py`）。缺的不是儲存，是**統一入口、統一驗證／稽核／上下限**——現在每個設定頁各寫各的。
3. 最大的實際風險是**重複與不一致**，不是「沒得調」：營業稅 5% 散在十餘處、利潤率燈號有 12／20／10 三種門檻（報價單、精算頁、營運報表各寫各的）、`PR`／`PO` 前綴各被兩種單據使用。要先收斂來源，再開放編輯。
4. 建議機制：**在定義文件庫新增一種 kind（設定群組）＋「系統 > 設定中心」頁＋一個帶快取的讀取函式**；已有專屬頁的（簽核、款別、費用類型、版面、法規參數）維持原處，設定中心只放索引。
5. 建議先做的五件（價值×低風險）見第 4 節；必須維持寫死的見第 5 節。

## 1. 現有機制：哪些可以直接重用

| 機制 | 現況 | 缺口 |
|---|---|---|
| `system_settings`（`helpers/settings.py` `_get/_set_setting`） | 任意 JSON；85 個鍵（核心 38、模組各 1～8） | 無 schema、無驗證、無版本；稽核由各端點自己呼叫 `_audit` |
| 11 個專屬設定頁 | 簽核、承攬商匯款簽核、公司資料（含備份保留）、帳務、法規參數、郵件、通知、模組、儲存位置、匯款款別、Google 日曆 | 各頁各自驗證；沒有總入口 |
| **定義文件庫** `core/definitions.py`、`/api/definitions/{kind}/{key}` | 草稿、驗證器、發布（版本不可改）、差異、還原、範圍（`company`／`role:x`）、`register_kind()` 可擴充；已用於 layout、output_template、custom_fields、custom_module、remit_kinds、費用類型 | 只有結構化文件用法；單值設定尚未使用 |
| 法規參數 `helpers/legal_params.py` | 依**生效日**版本化，已生效不可改，單據凍結快照（CUSTOMIZATION-SPEC §9） | 只含所得稅、健保；**不含營業稅** |
| 利潤口徑 `/api/overhead/settings` | 開關、預設比率、`confirm`、遷移旗標 | 前端 `profit-rules.js` 另抄一份常數；警示門檻（12／20／10）是各畫面寫死值，沒有任何設定（`operating_targets` 是財務年度營收／毛利目標，與警示無關） |
| 簽核 `approval-flow`、`approval-flow-scope`、`register_doc_type` | 每種單據的層級與簽核人可設 | 預設分組、組織鏈兩層仍寫死 |
| 郵件 `mail_types`、`email_notify`、`mail_recipient_overrides` | 逐類型開關與收件人覆寫 | 「角色→收件人」規則寫死；站內通知沒有逐類型開關 |
| 備份保留 `backup_retention` | GET／PATCH 與設定頁都有（1～3650 天） | **稽核紀錄保留可被設成 1 天，沒有法遵下限**；通知 90 天、請求日誌 90 天不在內 |
| 選單／角色／授權 | `apply_layout`、`modules_disabled`、`custom_roles`、`role_labels` | 內建角色與角色字面值判斷（約 240 行）屬 1d 專案 |

**確認是缺功能、不是寫死**：簽核沒有「金額級距」（`tiered_approval.py` 完全沒有金額欄位）；沒有找到「建案自動帶預設階段」的範本。

## 2. 建議機制（一套，不另起儲存）

- **儲存與版本**：定義文件庫新增 kind `setting_group`（key＝群組，例 `reminders`、`security.policy`；scope 預設 `company`）。直接得到草稿／驗證／發布／差異／還原。
- **登錄**：每個可調項在程式裡登錄 `SettingDef(key, 型別, 預設, 下限, 上限, 單位, 風險等級, 稽核標籤)`（放 `module.json` 的 `settings` 區塊或 `register_setting()`）。**上下限由程式決定**，管理者改不了。
- **讀取**：`settings.get("reminders.payable_soon_days")`，15 秒快取（仿 `helpers/auth.py` 的 `_finance_mode`）；缺值或壞值回程式預設並留 warning，不靜默。前端所需的值由一支端點一次回傳，**取代把常數抄進 JS**。
- **寫入分級**：風險 `none／ops` 一鍵發布；`money／legal／security` 需最高管理者＋`confirm`＋影響預覽＋稽核，可選「生效日」。
- **法定數字**（稅率、扣繳、費率）不進一般設定，走 `legal_params` 的生效日版本。
- **分工**：業務結構複雜的（簽核、款別、費用類型、版面）留在專屬頁；單值或小表（門檻、天數、容量、保留期）進設定中心。設定中心頁依群組列出，已有專屬頁的項目只放連結。

## 4. 建議順序（前五）

1. **K01 利潤警示單一來源**：同一指標三種門檻、前後端各一份，修了就消除一個真實的不一致；只影響警示顏色與文字，不動算式。工作量 M。
2. **K08 提醒與逾期天數**：7 個 P1，全是 S，風險低、使用者最容易感受到。同時要更新 `payable_reminders` 的「08:00＋補跑」假設與對應守門。
3. **K05＋K06 保存與容量**：把通知／請求日誌保留併入現有 `backup_retention`、補稽核下限；單檔與每單附件數改讀設定。大部分是接線，S。
4. **K10 狀態顏色與選項清單**：同一行 badge 對照被複製 5 次、四套寫法並存；抽共用函式後零金額風險。S。
5. **K04 登入與安全政策**：全是檔頂常數、沒有任何一個讀設定；加上下限與稽核即可。S，但風險屬 security，需評審。

之後：K02 `vat_rate`（價值高但 L，需先收斂）、K09 費用單據前綴、K13 通知對象、K14 措辭字串。

## 5. 必須維持寫死

| 項目 | 理由 |
|---|---|
| 密碼雜湊參數與格式（`helpers/auth.py:94/103`） | 改了舊雜湊無法驗證，只能版本化升級 |
| superadmin 直通（`auth.py:156` 等）、`_PUBLIC_API_PATHS`（`main.py:191`）、`_MUST_CHANGE_PW_ALLOWED`、`_COMPANY_SETUP_ALLOWED` | 權限根基與未授權入口；第 52 班起 w1b 守門逐條登記理由，只能改碼過審 |
| 稽核日誌 append-only、路徑逃逸檢查、簽章檔驗證、選單 `perm` 值域 | 安全不變式 |
| 舊口徑管銷 10%（`profit_rules.py:31`）、`FORM_VERSION`、傳票已過帳不可改、401 媒體碼、損益類科目型別 | 歷史資料凍結／法定格式／會計結構 |
| 報價單號 `MQ-` 格式 | 稽核、獎金、遷移以 regex 反推；改前要先遷移 |
| 暫存區 30 天、D1「只有草稿能刪」 | 使用者已裁示固定／不放寬 |
| 狀態名稱字串 | 至少 9 個模組以裸字串比對，且「駁回／退回」「作廢／取消」用詞不一；只開放**顯示標籤**與顏色 |

## 6. 限制

- 掃描以 grep 為主，會有遺漏；**未覆蓋**：前端每頁筆數／日期／幣別格式、PDF 個資告知範本、會計年度規則、城市／產業／流失原因下拉、郵件主旨與內文逐一。
- 代理有兩個結論經我更正：備份保留其實有設定頁（只是缺稽核下限）；暫存區的保留期只在 `wip/t53-*` 分支、尚未進 platform。
- 「風險」「優先序」是依價值×低風險的初判，需 PM 與使用者複核；CSV 欄 `found_by_blocks` 為哪幾路掃描找到（11 筆被兩路以上找到）。
