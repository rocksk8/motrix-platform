| | v1 | v2 |

## 二、設計變更

### 2.1 資料模型：每一階段「今天能算什麼」

| 時間軸格 | P1'（不改資料模型）能算 | 要等到 |
|---|---|---|
| 叫料 | ✔ `materialOrders[]`＋`case_material_approvals`（狀態、簽核人） | — |
| 採購 | ✔ PO（`poDocCode/poLine`）與請購 | — |
| 到貨 | ✔ **逐張叫料單**：到了／沒到、到貨日 | 數量進度「4／12」要等 D7（`received_qty`） |
| 入庫 | ✘ 沒有案件外鍵 | P2（supply 模組新增 `quote_no`、`po_doc_code`、`material_item_id`） |
| 出貨 | ✔ `shipping_notes` | — |
| 設備登載 | ✔ `devices[]` | — |
| 保固 | ✔ 設備列的起迄日（沒填起始日的標「未設定」） | 起算預設值見 D4 |

**時間軸的格子狀態要有四種**：進行中／完成／**略過（直送現場）**／**不適用／尚未提供**。v1 的 7 段線性時間軸對不上「直送、耗材、退貨」等分支，所以「略過」「不適用」是畫面的正式狀態，不是例外。

### 2.2 跨模組介面草案（IP）

現況：案件側碰庫存**只**經註冊表提供者 `stock.serial`（`quotations.py:3334`）；M03（倉儲）不在 ⇒ 不同步並回 `STOCK_UNAVAILABLE`。這是為了「賣只含案件、不含倉儲的客戶」而刻意的設計，v2 不破壞它。

| 方向 | 提供者（草案名） | 內容 | M03 缺席時 |
|---|---|---|---|
| 讀 | `stock.case_summary(quote_no, caller)` | 某案的序號彙總：在庫／已安裝／已出貨／作廢各幾台、對應料號；呼叫者無金額權時不含成本 | 時間軸「入庫」格整段隱藏 |
| 讀 | `stock.serial_history(part_no, serial_no)` | 這台序號曾出現在哪些案件／批次（P3，B8） | 該查詢入口不出現 |
| 寫 | `stock.receive(quote_no, lines, caller)` | 一站式到貨的入庫那一半；沿用 `create_batch` 的規則與權限（見 D9） | 一站式到貨只做案件那半，並明示「未連倉儲」 |

- 這是**新增 IP（介面契約）**，不是「不改資料模型」：需先出一頁正式的 provider 介面規格＋每一格在 M03 缺席時的顯示，**再**開 P2。
- 時間軸 API 本身放在案件模組（`modules/case/api/material_flow.py`），每一段由該段的模組提供資料；案件模組**不 import、不直查** `stock_*` 表。

### 2.3 兩條寫入路徑並存的處理

1. **對帳表（唯讀，P2 之後）**：兩欄——「案件已到貨、庫存沒有」「庫存有、案件沒有」，逐案可點進去補登。
2. **舊入口提示**：舊「確認到貨」在該案有料號對應的庫存時，加一行提示並預設導向一站式（仍可選「只確認到貨」）。熟手不被強迫、也不會默默雙邊不一致。
3. **點擊數**：舊路徑原樣保留；新路徑是捷徑。提示只是一行字，不增加點擊。

### 2.4 權限與金額

- 時間軸 API 每段各回自己的資料與 `canAct`；無權的段落**整段不回傳**。
- **案件可見性**在聚合層重做一遍（非該案成員 ⇒ 403）；**金額遮罩**同（無金額檢視權 ⇒ 回應內無任何金額欄位，不是前端隱藏）。
- 預填單價：有金額檢視權才帶；沒有則只帶品名、數量、單位。
- 入庫權限見 **D9**；D3 的採購角色項目同樣是政策，時間軸只能如實顯示「這一步需要 xx 權限」。

### 2.5 旗標與回退（每批共通）

- 每批一個設定中心旗標，**預設關**；關＝畫面與 API 行為與今天**逐位元相同**，並附一條測試（旗標關時比對該頁／該 API 的回應與基準）。
- 旗標名（草案，沿用既有「功能旗標」命名風格）：`onepipe.links`（P0a）、`onepipe.worklog_case`（P0b）、`onepipe.ship_install_ok`（P0c）、`onepipe.warranty_closed_notify`（P0d）、`onepipe.timeline`（P1'）、`onepipe.receive_wizard`（P2）…；實作班次可改名，但**每批必須有一個**。
- 動到熱點頁 `case-management.html` 的批次，先與 hichan-4 排序（§六）。

### 2.6 效能預算

聚合 API 一次讀整份 `quotations.data_json`（大案件可達數百 KB）＋多表。驗收加：單案 API p95 < **N ms**（N 由 P1' 前量到的基準決定，先量再訂）、逐段快取；**首頁看板每列的連結只帶案號、不得變成 N 次聚合**。

### 2.7 點擊數：先量基準

v1 的「12 次換頁→4 次」是推算。v2：P1' 之前用 Playwright 逐步計數（擴充既有 `_onepipe_shots.py`），對三種人（採購／業務／工程師）各量「現況」基準並**凍結成表**（`docs/platform/plans/` 下一份 `ONEPIPE-CLICK-BASELINE.md`），之後每批驗收引用這張表；4.6 的「點擊數不增加」才有可驗收的前值。

另外兩個**隱性增加**要處理：①側欄看板每列改連到「物料流程」會讓原本要去「案件資訊」的人多一步 ⇒ 連結旁保留原落點；②新入口要使用者先判斷走哪條 ⇒ 兩條路徑的結果一致（§2.3），才不增加認知成本。

## 三、分批（v2）

規模：S＝1～2 天、M＝3～5 天、L＝一週以上。每批可單獨上線、單獨回退。

### 開工前清單（做完才開 P0a）
1. 實測 v1 §八 三項「推測」：材料卡到貨日是否自動同步；專案報告叫料管控欄位是否空白；預設工務角色是否看不到支出申請。
2. 讀 `case_deadlines.py` 的實際去重與信件節流（決定 P0d 的 cutoff 與靜默基準做法）。
3. 查請購單表單目前對單價欄的金額權限處理（決定預填規則）。
4. 量點擊數基準（§2.7）。

## 四、驗收（v2；以「新進採購／業務／工程師」三種人為準）

1. 新進採購 5 分鐘內能從「採購管理」進到「某案的叫料」並知道下一步（P0a／P1'）。
2. 從案件開請購單不需重新搜尋案件（P0a）。
3. 先出貨、後現場登載不再報序號衝突；他案已 installed 仍報衝突（P0c）。
4. 一批 N 台設備到貨，序號貼上一次，庫存、材料卡、設備列都有（P2；N≥10）；重複序號逐列回報、其餘照寫。
5. 已結案案件的保固到期會通知，**且上線首次掃描不寄任何歷史通知**（P0d）。
6. 工程師在工作日誌選案件後，該日誌出現在案件動態與專案報告；日誌可見範圍沒有變寬（P0b／P4）。
7. 聚合 API：非該案成員 403；無金額檢視權的帳號回應內無金額欄位；無權段落整段不回傳（雙帳號負向測試）。
8. 倉儲模組缺席時，物料流程頁照常顯示其餘各段，入庫段隱藏、不報錯。
9. **每批旗標關＝與今天逐位元相同**（測試比對）；旗標可單獨關閉而不影響既有頁面。
10. 點擊數前後對照表（引用 §2.7 的基準）：無一項增加。
11. 單案聚合 API p95 在預算內；首頁看板不產生 N 次聚合。
12. 新畫面用語走狀態顯示名稱表與禁用詞單一來源，不自創。

## 五、需要使用者裁示的事（選單版）

> 格式：每題 = **問題**／**選項**／**建議**／**影響**。D3、D9 是高影響權限變更：放寬權限須第二位最高管理者核准＋確認期間（依既有的最高管理者核准規則，條文請 PM 核對）。不確定就選建議項，之後可改。

### D1　叫來的料都要入庫嗎？
- **A（建議）**：到貨時二選一——**入庫**或**直送客戶現場**。直送者仍可登載序號與設備。
- B：一律入庫。
- 影響：選 A，時間軸入庫／領用格對直送列顯示「略過」；直送者序號沒有任何庫存側紀錄（`_sync_device_stock` 找不到序號時靜默略過，設備登載不受影響）。選 B 較單純，但無倉庫的現場直送案會被卡住。

### D2　要不要做「領料」（領用單、扣庫存、記領用人）？
- **A（建議）**：先不做；出貨與設備登載已覆蓋主要消耗，等 P2 之後再評估。
- B：現在就做。
- 影響：選 A，**耗材怎麼辦要由 D8 回答**，否則現場工程師的耗材需求整段落空。選 B 會多一整張單據（範圍變大一倍）。

### D3　「採購」角色可以做什麼？（高影響權限）
- **A（建議）**：可建請購單、可看供應商**唯讀**名單；叫料仍需金額檢視權（避免採購看到報價成本）。
- B：另加「可建叫料」。
- C：維持現況（只能看）。
- 影響：選 A，P5a 動請購入口權限與供應商名單可讀性（**銀行資料欄位先遮罩**）。選 C 則新進採購第一天仍做不了事。**選 A／B 都需第二位最高管理者核准＋確認期間。**

### D4　保固起始日預設取哪一天？
- **A（建議）**：預設**出貨日**；沒有出貨單（直送）時依序退到到貨日→完工日；**只預填，不自動寫入**，存檔前由人確認。設定中心可改成以完工日為預設。
- B：預設完工／驗收日。
- C：維持空白（現況）。
- 影響：保固起算常是合約條款（出貨？驗收？），預設值是商業判斷；不自動寫入可避免「靜默改保固」。選 C 則沒填起始日的設備永遠不會被提醒。

### D5　每日工作事項是否開放現場人員新增？
- **A（建議）**：開放「建立與自己相關、掛案件的事項」；修改刪除仍限最高管理者。
- B：維持僅最高管理者可新增。
- 影響：選 A，工程師不用請最高管理者代建；權限放寬需依規則核准。

### D6　PR→PO→材料申請的「兩次核准」要不要維持？（v2 改為必選）
- A：**維持**——PO 核准一次、叫料再核准一次（現況，`PO_REQUIRED=True`）。
- **B（建議評估）**：叫料**免二次簽**，以 PO 簽核為準，保留「到貨確認」。
- 影響：重複核准與重複輸入才是使用者說「難用」的主因（時間軸只是總覽）。選 B 會動簽核設定，且是放寬簽核門檻——需第二位最高管理者核准＋確認期間；舊單不受影響（沿用既有 grandfathered 規則）。這個常數本來就設計成可調（`material_approval.py:39`），技術上可回退。

### D7　分批到貨／短交怎麼記？（新）
- **A（建議）**：叫料單加 `received_qty`（可分批累計），時間軸才能顯示「到貨 4／12」。
- B：維持拆單重簽（現況：到貨後改數量要退回草稿重簽，因 `quantity` 屬實質欄位）。
- 附帶選項：是否新增「預計到貨日」欄位（現在**沒有**，系統也刻意不追前置時間）。建議先不加。
- 影響：選 A 動叫料資料結構與簽核不變式（`SUBSTANTIVE_KEYS` 需拆開「數量」與「到貨數量」），是 P2 的前置；選 B 則分批到貨永遠只能拆單。

### D8　耗材（無序號：線材、接頭）怎麼處理？（新）
- **A（建議）**：以叫料單數量為準、**到貨即視為現場領用**；不進序號庫存。
- B：進庫存但以數量計（不要求序號），要領料才扣。
- 影響：現行庫存全案假設每件有序號；選 A 最小，但看不到耗材餘量；選 B 要新增「數量型庫存」概念，等同 D2 選 B。

### D9　誰能入庫？（新；高影響權限）
- **A（建議）**：入庫權限開放給「採購」「庫存」兩種角色（現在 `create_batch` 僅管理員）；案件擁有者與現場工程師不含。
- B：維持僅管理員（一站式到貨對非管理員只做案件那半，並明示）。
- 影響：不放寬，則新進採購與現場工程師按「一站式到貨」時入庫那一半必被擋，整張單要嘛失敗、要嘛雙邊不一致。放寬是高影響權限變更：**需第二位最高管理者核准＋確認期間**。

### D10　退貨／RMA／換貨要不要納入？（新）
- **A（建議）**：本輪不納入；序號狀態機維持 in_stock／installed／shipped／void，另案評估。
- B：納入（加退貨狀態、對應案件／保固處理）。
- 影響：選 A，換機／退貨仍靠人工處理與留言；選 B 會動狀態機與保固，範圍接近 P3 再加一批。

### D11　要不要通知「下一個人」？（新）
- **A（建議）**：做——成案／PO 核准／到貨確認時站內通知下一步的人（P6；LINE 由 hichan-6 接）。
- B：不做，靠時間軸「卡在誰手上」讓人自己看。
- 影響：選 B，採購仍要每天打開畫面查；選 A 多一批小工，且要避免通知轟炸（只通知「輪到你」的人）。
