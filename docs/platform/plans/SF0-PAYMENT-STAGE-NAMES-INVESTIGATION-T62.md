# S-F0：款項類型／期別名稱的來源與使用者（唯讀調查）

> 作者 hichan-1f，2026-10-14。基準 `origin/train/t60-int`（c917bebbc）。靜態閱讀，**未改任何程式、未跑測試**。

## 結論（先看）
「款項類型／期別」其實是**四個互不相干的詞彙**，不是一個：
| # | 詞彙 | 存在哪裡 | 來源 | 是 key 嗎 | 現況 |
|---|---|---|---|---|---|
| V1 | **案件款項期別名稱**（報表的「款項類型」欄） | `caseRecord.payment.items[].type`（字串） | **寫死的下拉**＋「自訂義」自由輸入 | **文字本身就是 key**（沒有另外的代碼） | 本切片（S-F1）的主角 |
| V2 | **請款單款項類別** `stage` | DB 欄位 `payment_requests.stage`（代碼 full/deposit/delivery/acceptance/final） | 後端字典＋前端下拉＋PDF 字典（共 3 份標籤） | 代碼是 key，標籤可改 | 標籤可做成設定（客戶可見 PDF） |
| V3 | 承攬商匯款款別 | 定義 kind `remit_kinds`（有代碼與名稱） | 管理者在「匯款款別設定」頁維護 | 代碼是 key | **早就可設定**，不動 |
| V4 | 報價單付款條件文字（「第二期：交貨款（總價款30%）…」） | 條款本文（設定 `default_payment_terms`、條款組） | 自由文字 | 否 | **早就可設定**，與 V1 無程式連動 |

## V1 案件款項期別（主要）
**怎麼來的**
- 下拉選項寫死：`frontend/pages/case-management.html:1871`——`訂金款／交貨款／驗收款／進度款／完工款／收款後出貨／自訂義／其他`（8 個）。選「自訂義」時出現自由輸入框（`item.customLabel`，`:1873–1874`）。
- 新案件的預設三期寫死在 `frontend/js/case-management-core.js:464–475`（也在 `:419–420` 另一處）：訂金款 30%、交貨款 30%、驗收款 40%。
- **後端完全不驗證**這個字串（沒有白名單）；缺值時各報表補 `第N期`（`reports.py:443,2646,3239,3328`、`cashier.py:472`）。
- 儲存的就是中文字串；沒有獨立代碼。

**誰在用它（全部只是『顯示』，沒有任何一處用它做判斷或算帳）**
| 消費者 | 位置 | 用法 |
|---|---|---|
| 營運報表（收款明細、應收、案件款項等工作表與 PDF／郵件） | `reports.py:443,1134,1199,1248,1801,2374,2646,3239,3328` | 當作「款項類型」欄的文字 |
| 出納收款明細（頁面與 Excel） | `cashier.py:472,712`；`cashier.html:599` | 同上 |
| 儀表板的待收款清單 | `dashboard.py:135` | `label` 欄 |
| 收款／到期行事曆事件 | `modules/case/receipt_calendar.py:44–58`（`_label`） | 事件標題的一部分；**款項名稱是事件變更簽章的一部分**：改名會讓事件重新同步 |
| 案件頁 | `case-management.html:1865–1926` | 下拉本身 |
- **金額不看它**：`tax_calc.payment_item_amounts` 只看 `amount`／`pct`；結案關卡②（款項收齊）只看 `received`；T100 傳票的摘要是「客戶＋單號＋發票號碼＋收款」，**不含款項類型**。所以改名**不影響任何金額、傳票或結案判定**。

**發現的缺口（與設定無關，但 S-F1 順手要修）**
- 選「自訂義」時，使用者輸入的名稱存在 `customLabel`，但**後端全部（報表、出納、儀表板、行事曆）只讀 `type`**，所以報表／出納上顯示的是「自訂義」三個字，不是使用者打的名稱。（grep 全專案：`customLabel` 只出現在案件頁。）修法：顯示字 = `type == '自訂義'` 時用 `customLabel`。

## V2 請款單 `stage`（客戶可見）
- 代碼 `full／deposit／delivery／acceptance／final`：`modules/arap/api/payment_requests.py:100–106`（`PAYMENT_STAGES`）；建立（`:371`）與更新（`:467`）時驗證必須在字典內；存 DB 欄位（`db.py:84,2602`，v57）。
- 標籤有三份：`payment_requests.py:100`（回應 `stageLabel`，`:159`）、`pdf_gen.py:2120`（`_PAYMENT_STAGE_LABELS`，**客戶端請款單 PDF**）、前端 `payment-request-form.html:377`（`STAGES`）。
- 可做成：代碼固定、標籤由選項清單提供（三處改讀同一份）。新增階段（新代碼）要連動驗證字典與 DB 既有資料——**建議本版只開放『標籤』，不開放新增代碼**。

## 對 S-F1 的建議（等你確認後做）
1. **V1 做成選項清單 `payment_stage`**（沿用 t62 option-lists 的 kind）：
   - 值（`value`）＝今天存在資料裡的字串（訂金款／交貨款／驗收款／進度款／完工款／收款後出貨／自訂義／其他）——**發布後不可刪、不可改字，只能停用、改顯示名稱、重排、新增**（PM 暫定：可新增、不可刪、key 不變）。
   - 顯示名稱（`label`）可改：案件頁下拉、報表「款項類型」、出納、儀表板、行事曆事件標題都用 `label` 顯示（後端查表：`type` → 顯示名稱；查不到 ⇒ 原字串）。
   - 「自訂義」維持特殊值（保留自由輸入）；順手修 `customLabel` 顯示缺口。
   - 新案件的預設三期（比例）暫不開放（是金額分配的預設，屬 money，另案）。
2. **V2 只做標籤**（`payment_stage_label`，代碼不變）：三份標籤改讀同一份；客戶可見 PDF 的改動走治理核准。
3. **T100／報表同步**：T100 不含款項類型，所以**不需要改傳票**；報表只換顯示字。**會計對照欄位（科目）不受影響**，因此本切片沒有『要新增會計對照欄位』的事（與料件分類不同）。
4. 風險：money（顯示字），ledger 無直接影響；`receipt_calendar` 的簽章含款項名稱 ⇒ 改標籤後第一次存檔會更新行事曆事件（預期行為，要在說明文字寫明）。
5. 需要 3e 盤點財務的哪些地方（我沒看到）：出納頁其他讀 `type` 的地方（`cashier.html`/`cashier.js`）、`settlement`（結算）頁、應收／帳齡報表的分組是否依 `type`。

## 這份調查沒有涵蓋的地方
`frontend/pages/cashier.html`／`cashier.js`、結算頁、`reports.html` 的前端是否有自己的款項名稱判斷；`ledger` 模組（總帳）的摘要是否使用款項名稱。我只確認了後端 `type` 的讀取點（上表）與 T100 摘要。
