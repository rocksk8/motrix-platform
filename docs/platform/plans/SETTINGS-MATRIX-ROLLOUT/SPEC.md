## 0. 目標（使用者 2026-11-13：「介面辨識度跟選擇都很難懂；每個項目都做」）

每個設定項目，使用者掃一眼就要知道四件事：**它叫什麼（白話）→ 現在是什麼值、從哪來 → 改了會怎樣 → 能不能一次改很多**。
矩陣與批次解決「項目太多、逐項操作」；白話名稱、說明、來源、標籤解決「看不懂」。同一個元件、同一份規格。

## 2. 每一列固定要有

```
[☐] 中文名稱（白話，粗體）  ?   [標籤…]        目前值（控制項）   與預設不同●
    小字代碼（等寬字，灰）  一句說明（影響什麼、預設值是什麼）
    來源：公司設定 · 王經理 10/28 ／ 系統預設
```

### 2.1 名稱、代碼、說明、標籤
1. **中文名稱**（`label`）：白話、一句話看懂；問句（`question`）在展開／手機卡片顯示。
2. **小字代碼**：`key`（`group.field`），灰色等寬小字；給客服與開發者對話用，**不當名稱**。
3. **標籤**（多個；顏色固定）：
   - 🔴「影響大」：`risk ∈ {money, legal, security}`，或 `requires_pending`，或 `loosen`。
   - 🟠「需外部設定」：要先到外部服務／伺服器做事才有用（Google OAuth、SMTP、LINE token、S3、Edge 路徑…）。登錄表目前沒有此欄 ⇒ 見 §7。
   - 🔵「影響別人」：改了會影響其他使用者的畫面、通知或簽核（權限、簽核人、收件人）。**使用者已裁示要上，逐欄標註**；盤點表「影響別人／危險標示」欄就是逐欄的依據。
   - ⚪「進階」：`advanced`，收在「進階」區。
   - 🟣「個人」：個人偏好，只影響自己。
   - 🟢「影響隱私」：會影響個人資料或客戶名稱是否外露（目前：`download_name` 下載檔名可能含客戶名稱、`quote_privacy` 報價單個資欄位）。外框顯示在設定頁標題與各列。
4. **與預設不同**：值 ≠ 預設時列左側橘條＋「●與預設不同」；工具列有同名篩選。**「預設：X」只在與預設不同時才顯示，並附「還原預設」鈕**（使用者裁示）；值＝預設時不重複顯示。逐列「重設為預設」；`risk ∈ {security, money, legal}` 或受 change_control 管的欄位不進批次重設，只能逐項（走原流程）。
5. **一句說明**必含「影響什麼」與「預設值」；不放代碼與工程用語（UX-PRINCIPLES §6.5 禁用清單）。
6. **選項型欄位**：每個選項顯示「白話標籤＋後果一句」（`choices` 第三項 `impact`，已是必填）；不顯示整數代碼。

### 2.2 群組的風險標示（PM N5）
群組標題**不另外標高／低風險**（會和欄位層級矛盾）：欄位各自顯示自己的標籤；群組標題只在其中有任一欄屬「影響大」時顯示一個 🔴「內含高風險項目」，點開看是哪幾項。

### 2.3 「目前生效值」與來源（PM N3）
來源徽章只有：**預設**（值＝預設、從沒改過）／**公司**（有最後修改人、時間、原因）／**等待生效**（顯示何時生效、誰要核准）／**舊位置**（來自 legacy 儲存位置，唯讀提示）。
**「個人」徽章只出現在真的有個人設定層的欄位**（目前已知：`login_greeting.style`（登入問候語風格，個人可選「跟隨公司／正式／幽默／關閉」；`login_greeting.py:116` `personal_pref`，經 `user_prefs`）、`list_view`／`list_prefs` 清單偏好；個人通知偏好）。`login_greeting.style` 有個人層（h11 收回 r2 的 N3：`login_greeting.py:116` `personal_pref`）；`login_greeting` 的公司設定仍是預設／公司兩種來源，個人選擇另以「個人」徽章顯示。其他欄位一律只顯示「公司」或「預設」，不得為了版面一致而假裝有個人層。
`field_views` 已回 `value／valueText／isDefault／defaultText／recommendedText／banner`；新增 `source:{kind,by,at,reason}`（由 `config_ledger` 最後一筆＋是否預設＋有無 pending 推得）。

## 3. 欄型別（`SmCell`）與宣告式用法

```js
SettingsMatrix.mount(el, {

  columns:[{id,title,cell:'switch'|'check'|'select'|'chips'|'number'|'text'|'value'|'readonly'|'custom'}],
  filters:['changed','external','heavy',…],
  batch:{ eligible(row), actions:[…] },    // §4
  save: async (changes, ctx)=>{…},         // 頁面提供：呼叫既有 API（一律走 publish／既有端點）
```

`value` 依欄位 `type`／`choices` 自動挑控制項。LINE 的角色格雙色、人員挑選＝`chips`／`custom`，**不進核心**。

## 4. 批次規則（PM M1；硬規則，守門要驗）

1. **可批次**：欄位 `risk ∈ {none, ops}`，且非 `requires_pending`、非 `loosen`、無待生效項、非 `sensitive` 群組。`ops` 欄位在確認視窗內另加一行提示；`none` 直接確認即可。
2. **永不進批次**：`risk ∈ {security, money, legal}`，以及一切受 change_control 管的欄位（`requires_pending`／`loosen`）。核取方塊灰掉，tooltip 寫原因；群組標題的全選與批次動作**自動略過**，確認視窗列出「已略過 N 項：原因」。
3. **設定中心的批次只有三種動作**（實測：`risk=none` 的 63 欄中沒有任何 bool，全是 str／int／float，勾選格與全開全關沒有東西可作用）：
   - **套用建議值**（`recommended`）
   - **套用預設組合**（`presets`；沿用 `/api/settings-center/profiles/{name}/apply`、`settings_registry.apply_profile`）
   - **重設為預設值**（逐欄 `default`）
4. **寫入一律走既有路徑**：`settings_registry.publish()`／`apply_profile()`；不另開新的寫入點。`publish` 內部自己會把變更 `_split` 成待生效／立即／放寬，批次無法繞過。
5. 同一群組內＝對 `POST /api/settings-center/groups/{group}` 一次送多欄（群組內原子）；跨群組＝逐群組各送一次，**中途失敗要明講「已套用 X 項、未套用 Y 項」**並提供復原已套用的部分（不假裝原子）。真原子跨群組端點預設不做。
6. 批次要填「變更原因」（現有 API 必填 `reason`）：確認視窗內一個欄位，預設「批次調整（N 項）」。
7. **`eligible()` 可由頁面覆寫**（hichan-6 提出）：設定中心頁用本節的嚴格預設；LINE 事件頁依使用者已裁示「重要（系統告警）可批次關閉，但要第二道警告視窗列出會停止通知的情況」，由伺服器強制 `confirm_critical`。覆寫只能由頁面**自己的**裁示放寬，且守門要列出所有覆寫處（見 §9）。
8. **非設定中心的矩陣頁**（權限、信件收件、個人通知偏好、簽核流程、LINE 事件）的批次動作是各頁自己的領域動作（授予／取消、信件開關、套用流程範本…），但同樣遵守：高敏感／影響大的列不進批次、寫入走該頁既有的驗證與稽核路徑、確認視窗＋復原這一批。

9. **批次拒絕清單（使用者裁示 C4；另列一份，不改 N2a 的高敏感清單）**：權限鍵 `project_approve_eng`（案件待辦－工程主管確認）、`project_approve_biz`（案件待辦－業務確認）、`quotation`（報價單／簽核佇列）、`expense_forms`（費用單據＝請款／請購／採購）、`file_center`（檔案中心）、`contractor_list`（外包名冊）——**禁止批次授予；批次取消可以**。清單由 API 以 `batchGrantRefused` 回傳（和 `highSensitiveKeys` 並列），前端不寫死。
10. **文字欄位一律不批次**（型別 `str` 且無 `choices`）：每家公司內容不同，不能「一鍵套同一段字」；樣式＝`逐列編輯＋預覽`，盤點表「可批次?」＝「否（文字欄位，逐列編輯）」。
11. **影響大的欄位不進批次、也不適用「復原這一批」**（使用者裁示，PM 已定）：它們維持各自的原因＋確認句型＋等待期／第二位最高管理者核准；批次與復原只對 `none`／`ops` 欄位。
12. **盤點表的兩個欄位（PM M4、r3.2 ⑥）**：「可批次?」拆成兩欄，**往後對使用者報的數字一律以 ② 為準**。
    - **① 規則上可批次**：依本節 1～3、10 判斷（含 `sensitive` 群組、文字欄位、`loosen`、`requires_pending`）。
    - **② 畫面提供勾選格**：① 為「是」、不是文字欄位、**該設定頁的呈現方式是勾選格**、而且**有可重複套用的對象**才給。判斷單位是「**實際呈現的設定頁**」，不是 registry 群組：頁面對應在 `data/shell_groups.json`（`pages.<id>.groups`／`style`）。例：13 個 `builder_*` 群組合併成一頁「自訂功能的開關（13 組）」（總開關＋子開關階層，PM 認可的例外），其中只有一欄的 10 個群組因此都可勾選；`list_view`＋`list_prefs`＋`download_name` 合併成「清單與下載檔名」、`ui_format`＋`login_greeting`＋`brand` 合併成「首頁外觀、數字與日期」、`lodging_freshness`＋`tender_closing` 合併成「旅宿與標案地圖的小設定」。`style` 另有 `form`（卡片＋預覽、不畫勾選格）與 `preset-only`（只透過預設組合）兩種，目前沒有頁面使用。
    - 「有可重複套用的對象」＝本頁還有其他 ① 為是的欄位（可一起勾選），或該欄的建議值≠預設值（「套用建議值」與「重設為預設」是不同動作）。不給的要寫原因：「否（永不進批次）」「否（文字欄位，逐列編輯）」「否（單項表單：…）」「否（只透過預設組合：…）」。
    - 目前數字：① 68（甲 27、乙 41）；**② 65（甲 24、乙 41；乙＝自訂功能開關 22、清單 7、下載檔名 5、首頁外觀 5、小設定 2）**，與 h12 乙份 mockup 一致。
13. **兩種等待（pending）要分開講，而且文字不寫死**（PM M4、r3.2 ④）：
    - `requires_pending`＝**只等待**：送出後要等確認期，期滿**自動生效**，不需要別人核准，期間可撤銷。
    - `loosen`＝**等待加第二人核准**：放寬類變更要等確認期，**且要第二位最高管理者核准**才生效——**但只有系統裡還有其他在職的最高管理者時才如此**（`settings_registry.py:843` 的 `others>0`）；只有一位最高管理者時，這項放寬改為「填原因、等確認期後生效，並留下紀錄」（同檔 warnings 文字）。
    - 因此確認視窗、「待生效」頁的「誰要核准」欄、通知預覽一律從伺服器的 `plan().kind`／`otherSuperadmins` 取文字與核准人，**前端不寫死任何一種**（mockup 有「只有一位最高管理者」切換可看兩種）。兩者都不進批次、不適用復原（§4.11）。
14. **自我檢查**：`data/gen_seed.py --check` 不經產生器的函式，另依本節文字與 `shell_groups.json` 的頁面對應獨立重算 ①②，與種子檔、工作檔逐列比對；並與盤點表自己填的「套用樣式」交叉比對（②不給勾選格卻寫「勾選批次」、或給了卻沒寫勾選批次／預設組合，都算不一致）——不符即失敗。regen 只重寫 `*.seed.csv`，不覆蓋工作檔的【填】欄。

**兩種等待（pending）要分開講**（PM M4）：
- `requires_pending`＝**只等待**：送出後要等確認期，期滿**自動生效**，不需要別人核准，期間可撤銷。提示文字：「要等 N 天確認期，不需要別人核准，滿 N 天後自動生效。」
- `loosen`＝**等待加第二人核准**：放寬類變更要等確認期，**且要第二位最高管理者核准**才生效。提示文字：「放寬：要等 N 天確認期，並要第二位最高管理者核准。」
- 兩者在確認視窗、「待生效」頁（「誰要核准」欄：前者寫「不需核准（期滿自動生效）」）、通知預覽都分開呈現，不得共用同一句。兩者都不進批次、不適用復原（§4-11）。

## 5. 確認與「復原這一批」（PM N2）

1. 勾選 → 批次列 → 選動作 → **確認視窗 C4**：「將變更 N 項、略過 M 項」→ 展開每項「現在 → 之後」（`valueText`）→ 影響估算（`impact_fn`／`live_impact`，沿用）→ 變更原因 → [套用][取消]。
2. 套用成功 → 吐司「已套用 N 項　[復原這一批]」（停留 6 秒，避免漏看；但**復原的條件不是計時，是版本**）。
3. **復原這一批＝逐欄 compare-and-set（r3，取代 r2 的「群組版本號」）**：套用當下記下**這一批自己寫入的欄位與值**；復原時，只有「那些欄位的目前**生效值**（含已到期的待生效覆蓋層）仍等於我套用的值」才回寫套用前的值。**同一群組內任何一欄已被別人改過 → 該群組整批拒絕復原**，顯示「誰、何時、改了哪一項」，請使用者到「變更紀錄」或手動調整。**跨群組的批次是逐群組各自判斷，結果可能是部分復原**（見第 5 點）。不覆蓋別人的修改，也不因為「同群組裡別的欄位被改」以外的原因誤拒。
4. **不做欄位層級的 6 秒復原**：單項修改直接生效、吐司只說「已更新（要還原請到變更紀錄）」；影響大欄位維持原本的「原因＋確認句型＋等待期／核准」，沒有復原（§4.11）。
5. **後端規格（要先審才實作）**：
   - `settings_registry.publish(group, values, …, expected_values=None)`：帶了 `expected_values={key: 期望目前值}` 就在 **`begin_write` 之後、寫入之前**逐欄比對目前**生效值**（要含到期的 pending 覆蓋層，和讀取畫面看到的一致；同一個寫入鎖內，避免「檢查後、寫入前」被插隊）；任一不符丟 `SettingConflict(keys, by, at)`，`by`／`at` 取自 `config_changes`（config_ledger）該欄最後一筆；**沒有 `config_changes` 紀錄時退路**：`by`＝「系統預設」（值仍是預設）或「舊路徑寫入，時間不明」（值被舊儲存位置改過）。
   - 路由 `POST /groups/{g}` 接受 `expectedValues`；衝突回 **409** 並帶 `{code:'conflict', keys, by, at}`。
   - 復原＝以 `expected_values=套用後的值` 回寫套用前的值，走同一個 `publish`、原因固定寫「復原批次」，不另開寫入點。
   - **跨群組批次**逐群組各送一次，復原也逐群組：部分群組衝突時只拒絕該群組並明講「已復原 X 項、未復原 Y 項（原因）」，不假裝原子。確認句型與 §11 一致。
   - **非設定中心的頁面**（權限、信件、LINE、簽核）比照辦理：比對「這一批改到的格」在套用前後的值（LINE 已由 hichan-6 以 `expect` 實作，見 §10），不做整頁版本號。
   - **預設組合**目前 `profiles()` 為 0 個：mockup 的「套用預設組合」顯示「之後提供」，內容由團隊提案、使用者看過才上線（INVENTORY §五-2）。

## 6. 「?」說明：從登錄表產生（PM N4，取代原 `settings_help.json`）

**不另建說明檔，只維護一個來源。** 四段由 `SettingDef` 既有欄位產生：

| 說明段 | 來源 |
|---|---|
| 這是什麼 | `question`＋`help` |
| 什麼時候要改 | **新增 `SettingDef.when`**（選填；沒填就不顯示該段，守門逐步要求補齊） |
| 改了會影響什麼 | `impact`（＋風險欄位的 `risk_text`） |
| 建議值 | `recommended`／`recommendedText`（＋選項型各選項的 `impact`） |

- API：`field_views` 回傳每欄 `help:{what,when,impact,recommend}`，前端直接用；不需新端點、不需新檔案。
- 非設定中心的頁面（信件類型、個人權限鍵、LINE 事件、簽核單據類型）：各自的登錄處（`mail_types`、`module_registry`、`line_catalog`、`tiered_approval`）已有 `name／event／impact／action` 等欄位，用同一個「四段 → 欄位」對照函式產生；缺 `when` 的先不顯示。
- 守門（實作時）：四段都不得出現禁用詞；`when` 不得與 `help` 完全相同（防複製貼上）。

**按鈕**：套用建議值｜套用預設組合｜重設為預設｜還原預設｜套用 N 項｜取消選取｜復原這一批｜展開全部｜收合全部｜儲存｜放棄｜確認儲存

**不得出現**：欄位代碼當名稱、`true/false`、整數選項代碼、「影子」「閘門」「確認期間」（改寫成「要等 N 天才生效」）等工程用語（UX-PRINCIPLES §6.5）。

## 12. 使用者權限頁的規則（hichan-11 審查＋PM 裁示；丙份）

1. **角色基礎**：批次授予以**職責角色（連動）**為主，自訂角色併入（使用者裁示 INVENTORY §五-1）；固定 6 碼範本只是「套用範本」的來源。
2. **伺服器端單一共用檢查點**：高敏感鍵的「原因 ≥ 4 字」與寫入 `permission_changes` 由一個共用函式強制，**四條路徑都必須經過它**：①`PUT /api/users/{id}`（單筆修改）、②批次端點、③範本套用、④**`POST /api/users`（`create_user`，`routers/auth.py`：新增使用者時可帶 `modules`，原本沒有原因也不寫 `permission_changes`）**。第④條 h10 已在 `9361f1033` 修好；本規格列入是為了「只擋新的批次端點，其他路徑就繞過」不再發生——驗收＝四條路各一個測試。
3. **清單來自 API**：`highSensitiveKeys`（目前 `financial_view`、`finance`、`cashier`、`settings`、`audit_log`、`module_versions`、`payslip`）與 `batchGrantRefused`（§4.9）都由 API 回傳，前端不寫死。
4. **財務三鍵**（`cashier`、`finance`、`financial_view`）：「**由角色決定**」，這頁唯讀、批次永遠不動。
5. **授予／取消不對稱**：高敏感與批次拒絕清單的鍵——**授予不能批次**（逐人填原因）；**取消可以批次**（例如離職），但同樣要填原因（≥ 4 字）並寫權限變更紀錄。
6. **角色範本套用**：伺服器在預覽時就把範本展開成「每人明確的鍵清單」，套用時照這份清單執行；逐人重跑 `refuse_unknown_new_keys`／`_subtracted_clash`，被跳過的要明確回報。確認視窗逐人列出「取消 N 項（…）／新增 N 項（…）」，並提示「他們目前的個別加減會被範本取代」。
7. **每人個別撤銷清單**：範本套用會保留／重算每人的 per-person revoked 清單，不是整個覆寫。
8. **略過最高管理者**：批次與範本一律不含 superadmin。
9. 「管理者範本」只含權限鍵，不含管理者角色本身的通行權；確認視窗要寫這句。

## 13. 草稿＋儲存列＋離開警告＋儲存通知（使用者新規則；所有設定頁共用）

1. **點擊＝草稿**：改任何值、勾任何格、按任何批次動作，都只改畫面上的**草稿**，不寫入。草稿列左側黃條＋「未儲存」標籤；原值留在 `sv`，可隨時放棄。
2. **固定儲存列**：頁面頂端黏住一條「你有 N 項未儲存的修改　[放棄] [儲存]」；沒有草稿時不顯示。
3. **儲存 → 確認視窗**：列出每項「現在 → 之後」、被略過的項目與原因、**通知預覽**（誰會收到）；含影響大／高敏感項目時必須填「變更原因」（≥ 4 字）。
4. **結果吐司**：「已生效 N 項」或「等待核准（預計 ○/○ 生效）」；同一批可能兩者並存，分開寫。
5. **離開警告**：有未儲存草稿時，關閉或重新整理頁面一律警告（`beforeunload`）。設定中心內**切換群組不會丟草稿**：草稿跨群組保留、儲存列常駐在頂端，一次儲存全部（因此外框的導覽不需要攔截）；不同頁面（例如從設定中心到權限頁）之間切換則站內導覽攔截並詢問。
6. **復原這一批**：儲存成功後才有（§5）；放棄草稿不需要復原。
7. **儲存通知**（實作是**另一張票** `feat/settings-change-notify`，h9 負責；本規格只規定**所有頁共用同一個通知元件**，包括 LINE 矩陣、權限頁、信件頁，不各自發明）：
   - **現況與缺口（h11 驗證）**：h9 的 `feat/settings-change-notify` 目前只是 registry 層（只在**單一次伺服器呼叫內**合併、沒有收件人預覽）；h6 的核心也還沒有 eligible／lock／草稿／儲存列、且保留「全開／全關」群組動作。本節的**收件人預覽、跨呼叫合併一則（批次／範本分多次寫入時）、LINE 高風險**都是**需求**，不是現有能力——實作票要補（通知元件＋核心 C-a～C-c）。
   - 站內通知：發給**最高管理者**與**受影響的角色／人**，內容＝誰、改了什麼、舊 → 新、原因。
   - **高風險**（security／money／legal，或權限的高敏感鍵）另外發 **LINE 給最高管理者**。
   - **批次／範本套用合併成一則**（「王經理把 5 位同仁加了 8 項權限」，點開看明細），不是每格一則。
   - 設定中心以外、立即生效的項目（獎金預設、營運目標、報價條款）存檔後同樣發通知（§15）。
   - 通知對象（mockup 示範）：權限＝最高管理者＋受影響同仁及其主管；信件＝最高管理者＋該信件原本的收件角色；個人偏好＝最高管理者＋本人；簽核流程＝最高管理者＋受影響單據類型的簽核人與申請人。

- **頁面對應是可勾選數的判斷單位**（§4-12）：合併頁、`style`（`checkbox`／`form`／`preset-only`）都寫在這個檔；改了必須重跑 `gen_seed.py` 與 `--check`。

### 15.A S5 補強：四項變更管制怎麼接（r3.4＝依 h11 規格審 MUST-FIX 1–8 修訂；原 r3.3 見 git `62defafcd`；依據＝`h3/S5-WRITE-POINTS.md`）

**原則**：**不做第二條等待路徑**。四項都登記成登錄表群組，用「舊儲存轉接器（legacy adapter）」讀寫原本的儲存位置，讓 `plan()`／`publish()`／待生效／第二位最高管理者核准（`otherSuperadmins`）／帳本／通知全部沿用。**讀取端**：只改 4 個咽喉點，改為經登錄表讀「生效值」（§15.A.5-1）；舊鍵雙寫保留作回退。

#### 15.A.1 登錄表要新增的通用能力（S5 前置；與 S1c 同一檔，h4 實作、h12 審）
1. **自訂舊儲存轉接器**：`register_group(..., legacy_adapter=Adapter(read, write))`；有 adapter 時忽略 `legacy_key`。
   - `read(conn) -> {欄位: 值}`：讀舊儲存並**經原本的正規化**（扣繳走 `load_versions`：`tax_rules` 舊鍵退路、`_backfill`、`sort_versions`；預設值必須等於各模組原有預設——`DEFAULT_TAX_RULE_VERSIONS`、傳票科目 6111／2191／2252／2252／1113、口徑與公益比例取 `profit_guard` 的預設）。
   - `write(conn, values, *, old=None)`：**只用傳入的 `conn`、在生效當下的同一筆交易內執行**，可一次寫多鍵、刪標記，**必須冪等**。**不得**呼叫 `legal_params.save_versions`／`_set_setting` 這類自開連線並 commit 的函式（會與登錄表寫鎖互相卡「database is locked」，或在交易外 commit）；要各自提供「接受 conn」的版本。
2. **`json` 欄位型別（不透明）**：值是 list／dict，儲存為 JSON；沒有逐欄差異、沒有預設組合；`summarize(old,new)->[白話行]` 產生「改了什麼」（確認視窗、通知、待生效頁用，例如「新增 1 個版本（2027-01-01 起）」「銀行帳戶 A 的科目 1113→1112」；**畫面一律顯示摘要，不傾倒原始內容**）。驗證交給群組 `cross_check`。CAS 與大小限制見 §15.A.5-5／6。
3. **`loosen="both"` 擴到非數字欄位**（str／json／choice）：任何變更都算放寬＝需要第二位最高管理者核准（只有一位時改為原因＋等待 N 天＋警告＋通知）。要改的位置：`SettingDef` 建構子的型別限制（`settings_registry.py` ~139–141；**對應的既有測試要反過來**：`both` 可用於所有型別，`up`／`down` 仍只限數字）、`_split._loosens`（~665；數字走原邏輯，str／json 用正規化後的 `!=`）、`banner_of`（~582–587；非數字欄位目前會落到 `if f.loosen:` 分支，要確認文字）、`show_value`（json 走 `summarize`）。`impact_scope` 一致性檢查（~107）不用改。**新增差異測試**：改完後所有現有群組的 `plan()` 輸出與改前逐字相同（目前沒有任何群組對非數字欄位設 `loosen`，預期零回歸）。
4. **`cross_check(values, conn=None)`**：現行 `cross_check(合併後的值)` 沒有連線，但「科目存在且未停用」「T100 科目存在」「遷移標記存在」都要查資料庫。改成可接 `conn`（`publish` 傳它的交易連線；覆蓋層與 materialize 傳各自的）。**注意部分驗證**（覆蓋層、materialize）合併的是**預設值**而不是目前值——每條檢查都要寫成對「只有單一欄位」也成立。
5. **`external=True` 群組旗標**（§15.A.5-7）：登記但不出現在設定中心一般群組清單與全域搜尋；待生效與最近變更仍會顯示它們。
6. **`pending_exists` 衝突碼與 `supersede`**（§15.A.5-6，僅限 json 欄位）。

#### 15.A.3 邊界與注意
1. **待生效當下的前置條件重驗**：materialize 寫入時轉接器要重驗（見 §15.A.5-2 的失敗處理）。
2. **同一鍵的其他寫入者**：S5 開工第一步全專案 grep 上述舊鍵的所有寫入點（tools／migrations／測試夾具除外），其餘寫入點也要改走 `publish()`，結果貼進 PR 說明；**但 grep 擋不住未來新增的旁路**，所以另加每日漂移檢查（§15.A.5-1）。

#### 15.A.5 h11 規格審 MUST-FIX 1–8 的決定
1. **讀取端落差（選 A）**：待生效只在 `materialize_due()` 寫進舊鍵，而它由每日排程（`daily_checks.run_once`）執行；若讀取端直接讀舊鍵，會出現「設定頁說已生效、薪資／傳票／T100 還在用舊值」最多一天（排程失敗則更久）。**決定**：只改 4 個咽喉點，改為經登錄表讀生效值（含到期待生效覆蓋層）——`legal_params.load_versions`、`bonus_vouchers.configured_accounts`、`accounting_export._t100_config`、`profit_guard.rule_mode`／`charity_mode`／`migration_done`；體量小、其餘 9 處扣繳讀取端因此自動正確；舊鍵雙寫保留作回退。**另加每日漂移檢查**（併入 `daily_checks`）：`adapter.read(conn)` 對比登錄表「已 materialize 後的生效值」，不一致就警示最高管理者（`_stored` 偏好定義列，任何登錄表以外對舊鍵的寫入——工具、還原——都會讓登錄表看不見，光靠 §15.A.3-2 的 grep 擋不住未來新增的）。
2. **`adapter.write` 的交易**：(a) 只用傳入的 `conn`（§15.A.1-1）；為 `legal_params`、獎金科目、T100、口徑各提供 conn 版寫入函式，原函式改成它的薄包裝。(b) `materialize_due` 目前所有群組同一筆交易，一個 `write` 丟例外會整批回滾、隔天又失敗，餓死其他群組。**決定**：每個群組各包一個 `SAVEPOINT`；轉接器失敗時 `config_ledger.cancel` 該群組的到期列並帶原因、**通知最高管理者**（現行取消路徑只有 `logger.warning`）、其餘群組照常。
3. **`cross_check` 接 conn**：§15.A.1-4。
4. **口徑連動放進「值」**：§15.A.2 最後一列。
5. **json 待生效大小懸崖**：待生效列把新值放在 `config_changes.new_json`，`config_ledger._dump` 對超過 `_VALUE_MAX=20000` 字元的值會換成 `{"_truncated":true,…}`，覆蓋層讀到的是垃圾、驗證失敗、待生效被取消，復原與差異也會錯。**決定**：送出時 json 欄位超過 **15000 字元**就拒絕並回白話訊息（「這份設定太大，請聯絡工程師」）；上限放在欄位定義可調；加強制超大值的測試。
6. **整份文件的遺失更新**：`publish` 會取代同一欄位先前未到期的待生效列，而 CAS 比對的是**生效值**（不含未到期待生效）。兩位管理者編輯扣繳參數時，B 的 CAS 通過並無聲覆蓋 A 的待生效整份文件——純量無妨，整份 json 不行。**決定**：json 欄位送出時若同欄位已有另一筆未到期待生效，回 409 新代碼 `pending_exists`（含 `by`、`at`），除非呼叫端帶 `supersede=true`（畫面確認後才帶）。**CAS 雜湊**＝標準 JSON（`sort_keys`、`separators=(",",":")`、`ensure_ascii=False`），**兩邊都對「正規化後的值」計算**（`adapter.read` 已經過 `_backfill`／`sort_versions`；送進來的值也先正規化），避免儲存形狀與讀出形狀不同造成假衝突。
7. **群組集合守門**：註冊 4 個群組後登錄表由 50 變 54 個，會自動出現在一般清單，S2 的「頁面登錄＝登錄表群組集合」守門與 gen_seed／INVENTORY 的數字（①68／②65、186 欄）都會動。**決定**：新增 `external=True` 旗標（§15.A.1-5）——只放連結、不進批次／草稿、**排除在 ①② 之外**；S2 守門改成「頁面登錄 ∪ external 群組 ＝ 登錄表群組集合」；`gen_seed.py` 要跳過 external 群組（`--check` 也要認得），重跑後 ①②與群組／欄位數**不得因這 4 群組 9 欄而改變**（現行 ①68／②65；T83 凍結後預期 51 群組／186 欄，都不含這 9 欄）。
8. **治理檢查**：每個新 money／legal 欄位要有 `risk_text` 與 `impact_scope`（`effective="pending"`），共 9 欄（§15.A.2）。
- **(d) 扣繳生效日規則改為兩段**：送出時**軟檢查**——新增／修改的版本 `effectiveFrom` 必須晚於「今天＋確認天數」，白話提示；**硬檢查在 materialize**——以 `frozen_changes` 對當時的實際狀態重驗，若期間已變成凍結 ⇒ 取消該筆並通知（同 §15.A.5-2b）。「完成日」在需要核准時送出當下算不出來（實際生效＝max(生效日、核准時間、下次 materialize)），所以不在送出時硬擋。**緊急追溯更正**的逃生口明講：由工程師用工具處理（類似 `overhead_migrate`），設定中心做不到。
