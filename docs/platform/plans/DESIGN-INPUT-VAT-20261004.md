# 設計：進項稅 5% 在報價與精算的處理（待使用者裁示；本檔不實作）

2026-10-04｜rev-7f｜基準 `origin/platform` @ `af722139`｜只讀碼，數字例為手算，未跑程式。

## 0. 結論

1. **現況是三種稅基混加**：品項（估計與採購／材料申請）含 5% 稅、承攬商未稅、額外支出「未拆稅」。同一個總成本裡口徑不一，是「5% 爭議」的根源，不是單一 bug。
2. **推薦選項 C 的簡化版（見 §3）**：預設「可扣抵」＝成本記未稅；只有「不得扣抵」的類別或沒有合法進項發票的單據，稅額才算成本。總帳已經有同一套概念（`doc_type=='invoice'` 且類別 `nondeductible=0` 才拆進項稅額），精算與總帳對齊最不會漂。
3. **現在就能做、不改任何數字的第一步（§5）**：精算頁每一列標明稅基，並把「原始成本」與「精算後成本」的稅基差異講清楚（頁面現況本身就有 5% 的口徑落差，見 §1 註 ③）。
4. 要使用者裁 4 題（§4）。**在裁示前不要動任何金額公式。** 已完結案件一律不變（凍結）。

## 2. 三個選項

記號：c＝未稅成本，v＝5%；以下金額例統一：**報價稅前收入 100,000；品項成本 c＝60,000（皆有採購單、金額含稅 63,000）；承攬商未稅 20,000（稅 1,000）；額外支出 5,000（單據含稅金額）**。管理費＝稅前×10%＝10,000，公益金＝毛利×1%（四捨五入）。

| | 現況 | A 全未稅＋分拆稅額 | B 全含稅 | C 逐筆旗標（有合法進項發票才拆） |
|---|---|---|---|---|
| 品項 | 63,000 | 60,000（稅 3,000 另列） | 63,000 | 有發票 60,000／無 63,000 |
| 承攬商 | 20,000 | 20,000 | **21,000**（回到含稅，推翻 35c） | 20,000 |
| 額外支出 | 5,000 | 4,762（稅 238） | 5,000 | 有發票 4,762／收據 5,000 |
| 總成本 | 88,000 | 84,762 | 89,000 | 例（品項有發票、額外是收據）85,000 |
| 毛利 | 12,000 | 15,238 | 11,000 | 15,000 |
| 公益金 1% | 120 | 152 | 110 | 150 |
| **淨利（＝獎金基數）** | **1,880** | **5,086（+3,206）** | **890（−990）** | **4,850（+2,970）** |

### A．全部未稅，稅額拆出另列
- 公式：`成本 = Σ 未稅金額`；`稅額（進項）= 單據稅額`，只顯示不入成本。估計＝`qty×cost`（拿掉 ×1.05）。
- 儲存：採購單／材料申請／額外支出明細加 `tax`（整數）、`docType`（`invoice`／`receipt`／`foreign`）——**與總帳事件欄位同名**，總帳已吃這兩欄（`category_map.py:5-10`）。精算 `summary` 新增 `vatBasis:"pretax"`＋`inputVatTotal`（資訊）。
- 舊案：`summary` 沒有 `vatBasis` ＝舊口徑（含稅），**凍結不改寫、不重驗**；做法與 35c `dispatchBasis` 相同（`settlement_actuals.py:25`、`_freeze` 結尾）。
- 報價 `inputVat`：改為「不得扣抵部分」；預設 0 ⇒ 估計毛利全面上調約 `0.05×成本/稅前`（本例 3 個百分點）。已送審／已成案的報價不重算（`tot` 已存），新舊報價的「原始 vs 精算」要標稅基。
- 缺點：沒有稅額資料的舊採購單／材料申請**無從拆**，只能以 ÷1.05 推估並標「推估」；若實際沒拿到發票，成本被低估（淨利與獎金高估）。

### B．全部含稅
- 公式：承攬商改回 `grandTotal`＋人員；額外支出與品項不動。**直接推翻使用者 2026-10-03 對承攬商的裁示**，且與總帳（稅額進 1268 資產）、營運報表（未稅）不一致，爭議只是換個地方出現。**不建議**。
- 唯一優點：零 schema 變更、零遷移。

### C．逐筆旗標（有合法進項發票才拆；沒有就稅算成本）
- 公式：`成本 = Σ（可扣抵 ? 未稅 : 含稅）`；可扣抵＝`docType='invoice'` 且類別 `nondeductible=0`（**直接重用總帳判準**）。估計列：預設可扣抵（未稅），品項／類別標「不得扣抵」才 ×1.05。
- 儲存：同 A 的 `tax`、`docType`，另用既有 `gl_category_map.nondeductible`（類別層）；舊資料缺 `docType` ⇒ 視為「未拆稅／不可扣抵」（＝含稅，舊行為不變，這是 C 比 A 安全的地方）。`summary` 加 `vatBasis:"mixed"`、`inputVatDeductible`、`inputVatCost`（進成本的稅額，供稽核）。
- 舊案：同 A，凍結。**未升級的資料自動維持舊結果**，所以不需要大批遷移。
- UI：每列一個稅基標籤（未稅／含稅／推估）；有「含稅但缺進項發票」的列在完結前提示；總帳補登 `input_tax` 後精算要能引用（單一來源，不要兩邊各補一次）。
- 缺點：需要現場把 `docType` 填好；填錯的影響＝成本與獎金基數。

### 三者的共同影響（要一併處理）
- **報表**：營運報表權責收入本來就用未稅；支出現在是混合。A／C 完成後 `taxNote` 由「未拆稅」逐步變「未稅」，報表與精算才一致。
- **獎金**：基數 `netProfit` 改變 ⇒ 同一案件新舊口徑獎金差一個 `Δ淨利`（本例 A＋3,206、C＋2,970、B −990）。**這是金錢分配的改動，必須使用者明確同意**；已完結案不重算。
- **測試**：恆等式（總成本 ＝ Σ各源，各源只出現一次）、舊案 parity（無 `vatBasis` 逐位相同）、凍結、`finalize` 後端重算（`check_finalize`／`_expected_downstream` 要認新口徑，否則頁面與後端 409）、前後端同一函式（避免再加第三份公式，見上一份審查 F-09）。
- **工作量（以列車計）**：A：2 班（資料欄位＋精算後端＋頁面；報價單與報表再 1 班）。C：2–3 班（A 的全部＋判準與提示＋總帳補登串接）。B：0.5 班但需先收回 35c 決定。
- **風險**：A 最大（成本被低估、獎金多發）；C 次之（填錯 `docType`）；B 的風險是與已上線承攬商口徑、GL、報表三方不一致。

## 3. 建議

**採 C，分兩階段、第一階段不改任何數字**：
1. 階段 0（§5，可立即做）：只標示稅基。
2. 階段 1：新增 `tax`／`docType` 明細欄與 `vatBasis`，**預設全部「含稅未拆」＝今天的結果**；逐步讓採購單、材料申請、額外支出能填發票類型與稅額；有資料的列才改稅基。
3. 階段 2（使用者裁示後）：把品項估計與報價 `inputVat` 的預設改為可扣抵（未稅），並公布對獎金的影響。

理由：與會計已有的判準一致；舊資料自動維持舊結果；不需要一次性大遷移；不推翻 35c。

## 4. 需使用者裁示的題目（一題一決定）

1. **報價估計成本要不要含 5%？** ⒜ 維持（保守，視為不可扣抵）⒝ 改未稅（預設可扣抵，報價估計毛利上升約 3 個百分點）⒞ 只對有標「可扣抵」的品項未稅。
2. **精算品項採購單／材料申請（現為含稅最終金額）**：⒜ 全額計成本（現況）⒝ 有合法進項發票者拆稅額、稅額不入成本（C）⒞ 一律拆稅額（A，缺資料用 ÷1.05 推估）。
3. **額外支出（收據居多）**：⒜ 全額（現況）⒝ 有統一發票才拆稅（C）。
4. **獎金基數**：口徑改變後是否仍用精算「淨利」？⒜ 是，新案採新口徑、舊案不動 ⒝ 是，且通知受影響人員 ⒞ 另設獎金專用基數（與精算脫鉤；工作量大）。

另需確認：**承攬商維持未稅（35c）不再議**（建議視為已定）。

## 5. 現在就能做、且不改任何數字的第一步

1. 精算頁每個成本列加稅基標籤（純文字）：品項估計「含稅 5%（假設不可扣抵）」、品項手填依 `actualCostTaxMode`、採購單／材料申請「含稅最終金額」、額外支出「未拆稅」、承攬商「未稅（稅額 X 不計成本）」。
2. 修正頁面現存的口徑落差說明：「原始 vs 精算後」成本列註明「原始＝未稅成本（`settlement.html:1312`）；精算後含 5%」，毛利列註明「原始毛利已扣 5% 進項稅（`:1316`）」。
3. 結案 PDF／獎金明細的成本分項旁加一行「口徑：品項含 5%、承攬商未稅」（`pdf_gen.py:2567-2571`、`payroll/bonus.py` `SETTLEMENT_ROWS`）。
4. 補一題守門：`ESTIMATE_RATE` 與前端 `1.05` 同值（現在靠註解，`settlement_actuals.py:19`）。
- 工：S（約 0.5 班）；風險：低（只改文字與顯示，金額與 `summary` 欄位不動；舊完結案不受影響）。
