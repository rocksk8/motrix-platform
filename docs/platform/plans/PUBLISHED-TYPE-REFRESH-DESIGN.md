# 已發布請款類型（purchase_req v1–v4）如何跟上新範本／新說明 — 設計提案

> 2026-10-02，W1/a3，**設計提案，未實作、不動任何資料**。範圍：公司已發布的 `expense_type` 定義（使用者說 `purchase_req` 已有 v1–v4）要怎麼取得出貨預設（程式預設，版本 0）日後的改動——例如已排進第 32 班的「申請人」說明白話化（`wip/t32-applicant-help-a3`）、以及第 33 班「已發布請購單類型範本」要帶來的新欄位／新版面。

## 1. 現況（已查證，origin/platform `a5dea50c`）
- **出貨預設＝版本 0**，讀 `helpers/expense_type_defs/<code>.json`（`helpers/expense_types.py:_default_for`、`get_type(version=0)`）；沒有版號、沒有雜湊紀錄。
- **公司發布版（≥1）是發布當下的完整副本**，存在 `ui_definitions`（`core/definitions.py:publish`）；之後出貨預設再怎麼改，公司的副本都不會動。生效順序：`company 最新發布 ＞ 程式預設`（`D.resolve`）——**只要公司發布過一次，出貨預設就永遠不再生效**（不是欄位級合併，是整份取代）。
- 單據在建立與送審當下把 `def_version` 釘在列上（`modules/case/expense_forms.py:current_def_version`），所以改定義不影響已開單據的驗證與輸出（顯示用文字除外）。
- 編輯頁（`expense-types.html`）有：存草稿、與已發布版差異、版本列表、還原為新版本、發布。差異端點 `GET /api/definitions/{kind}/{key}/diff?a=&b=` 說明寫「`default`＝程式預設」，**但實作是 `D.resolve(...)`，公司發布過後回的是公司最新發布版而不是出貨預設**（`routers/definitions.py:332–334`）——所以現在**無法**拿公司版對出貨預設做差異（既有缺口，下面所有方案都需要先補）。
- 沒有任何機制記錄「這份公司副本是從哪一版出貨預設起算的」。

## 2. 三類改動，風險不同
| 類 | 例 | 對公司副本的意義 |
|---|---|---|
| 說明文字（`help`、`label`） | 申請人說明白話化 | 只影響顯示；公司沒動過那個字串就該自動跟上，動過就保留公司的 |
| 結構（新增欄位、改明細欄、版面分組、`ui.list.columns`） | 範本新增「案件品項」欄 | 影響填單與輸出；套用要逐項看過，不能靜默 |
| 輸出版型（`output.template`） | PDF／列印 | 影響單據輸出外觀；有 def_version 釘住，舊單不變 |

## 3. 可行做法

### 做法 A：通知重新發布（最小、零風險）
- 編輯頁在「有公司發布版 且 出貨預設已不同」時顯示提示：「出貨範本有 N 項更新（說明 X 項、欄位 Y 項…），你的版本沒有套用」＋「查看差異」。
- 使用者自己在設計器裡逐項改（或手動複製），再發布成 v5。
- 需要：補 `diff` 的 `default` 真正取出貨預設（獨立 `D.default_body()`，不經 `resolve`）；一個「出貨預設 vs 公司版」摘要端點。
- 優點：不改資料、不會誤蓋公司修改；缺點：靠人，容易放著不管。

### 做法 B：一鍵套用新範本、保留公司修改（三向合併）
- 需要「基底」＝公司當初複製時的出貨預設。沒有紀錄 ⇒ 用**出貨預設歷史**：程式內保存已出貨過的每一版預設的正規化雜湊（以及必要時整份）；公司副本以「是否等於某一版歷史預設」判定基底，無法判定（公司在複製後改過很多）時退回「以最早一版預設為基底」或要求人工確認。
- 合併規則（逐欄位、逐屬性）：公司值 ＝ 基底值 ⇒ 採新預設；公司值 ≠ 基底值（公司改過）⇒ **保留公司值**；新預設新增的欄位 ⇒ 加入（放在最後一個區塊並提示）；新預設刪除的欄位而公司有用 ⇒ 保留並標記；衝突（雙方都改同一屬性且不同）⇒ 保留公司值並列在「需要你看一下」清單。
- 輸出：**只產生草稿**（不自動發布），畫面逐項列出「已自動更新／保留你的修改／需要你決定」，使用者確認後按發布 ⇒ v5。可「還原為新版本」回到任一舊版。
- 優點：說明類更新幾乎零成本；缺點：實作量最大（合併器＋歷史預設＋UI），誤判會悄悄改到公司的設定——所以一定只出草稿＋全程可見差異。

### 做法 C：並列版本比較（唯讀）
- 編輯頁新增「與出貨範本比較」：三欄（出貨預設／公司目前版／草稿）並列，逐欄位標示相同／不同，使用者可**逐項**「採用出貨的」或「保留我的」，結果寫入草稿。
- 是 B 的手動版（沒有自動判斷，全由人逐項選），也解決 A 的「靠人」問題（有明確清單與按鈕）。需要同樣補 `default` 取值。

### 做法 D（不建議）：讓出貨預設直接蓋掉公司副本／不再發布 v0 覆蓋
- 會無聲改掉公司自訂的欄位與流程；違反「發布版是公司的」；已開單據的行為也可能變。排除。

## 4. 建議路線
1. **先做 A＋補 `default` 差異**（半班）：解掉「看不到差異」的洞；說明白話化這類只影響顯示的更新，給提示與一鍵「複製出貨的 help 到我的草稿」即可。
2. **範本（結構）更新用 C**（約 1 班）：逐項採用，避免合併器誤判；每次出貨預設有結構更新時，在 CHANGELOG 與公告註明「已發布的請購單需到編輯頁『與出貨範本比較』套用」。
3. **B 等到有第二次以上的範本更新、且公司版修改量大時再評估**（需要歷史預設保存機制，現在還沒有）。
- 不論哪個做法：**一律只改草稿、由超級管理員按發布**；發布成 v5 後新單據釘 v5，舊單據仍釘原本版本（不重算）；全程寫稽核（誰、哪些項目採用了出貨的）。

## 5. 風險
1. **差異來源有洞**（§1）：先補，否則所有方案都建在錯誤的比較上。
2. **欄位代碼**：公司副本與新預設的同一欄位代碼可能語意不同（公司改過用途）；C 逐項人工確認可擋，B 要有衝突清單。
3. **鎖定／預填來源**（`locked`＋`$requester`／新註冊表 token）：新預設若改了這類屬性，套到公司副本會改變單據填寫行為 ⇒ 屬「結構」類，必須人工確認，不可自動套用。
4. **版面與清單欄**（`ui.form.groups`、`ui.list.columns`）：合併後不得產生孤兒欄位或引用不到的 key（驗證器會擋，但要在草稿階段就指出）。
5. **輸出版型**：新範本若改 `output.template`，PDF 外觀會變；已開單據不變（def_version）。要提示「新單據起生效」。
6. **多人編輯**：草稿只有一份且 `save_draft` 無並發戳記（`core/definitions.py:110`，既有）——兩位管理者同時套用會互蓋。→ 與設計器的「有人剛改過」提示一起處理。
7. **回溯**：發布 v5 後若發現問題，用既有「還原為新版本」回到 v4 內容（會成為 v6，不是刪除 v5）。

## 6. 需要使用者裁示
- **Q1 更新方式**：A 只通知＋差異（最小）；A＋C 逐項採用〔建議〕；B 一鍵套用並保留公司修改（量最大）。
- **Q2 誰可以套用**：僅最高管理者（現況，編輯頁本來就僅最高管理者）〔建議〕；或另開權限。
- **Q3 要不要在公告中強制提醒**：每次出貨預設有變動，公告列出「哪些已發布類型需要到編輯頁比對」〔建議〕。
- **Q4 purchase_req v1–v4 的現況**：v1–v4 各是什麼差別？目前生效的是 v4？這幾版是使用者自己改的，還是只是試發布？（需正式機唯讀查詢，見下）
