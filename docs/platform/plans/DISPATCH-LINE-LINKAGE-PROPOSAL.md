## 1. 問題陳述

精算頁現在只能把「**整張**派發單」對應到「**一個**報價品項」（`settlement_actuals.py` 的 `off_dispatch`）。派發單裡的逐行品項（MQ-202607-025 的派發單有 9 行）沒有任何欄位、也沒有畫面可以對應到報價品項，所以使用者只能手填品項實際成本，而那張派發單整張留在「未對應」、仍照算進總成本（可能與手填重複，見報告 §3）。

來源註記：MQ-202607-025 的資料（9 行、舊格式精算草稿、每行只有 `id/description/qty/unit/unitPrice/amount/note`）是正式機回報轉述，本檔作者未直接看到；機制部分是讀程式確認。

## 2. 設計原則（不變式）

1. **對應只存在精算存檔的 `offsets`**。派發單、報價單一個位元都不改；派發審核流程（`substantive_hash` 含 `items_json`）不受影響。
2. **金額守恆**：任何對應組合下，每張派發單「已對應各份＋未對應剩餘＝該張計入成本的金額」，所有派發單加總永遠等於 `dispatchTotal`。逐行對應只改「歸屬」，不改總額。
3. **舊資料原樣有效**：舊的整張對應（`ref` 不含 `#`）、已完結（凍結）的精算，結果逐位元不變，不需遷移。
4. **沿用現有口徑**：精算全含稅（使用者 2026-10-06）；35c／36 期間存的未稅草稿（`dispatchBasis="pretax"`）維持其口徑，直到使用者轉換。
5. **未對應仍是正常狀態**：沒被對應的行照算、計入額外支出；完結時只警示不擋（使用者 2026-10-04）。
6. **拆分守恆（Q3 可拆）**：一行拆給多個品項時，**各份金額（含稅額）加上「尚未分配的餘額」恆等於該行金額（含稅額）**；份金額加總不可超過該行（超過＝錢憑空增加，一律擋）。

## 3. 資料模型

### 3.1 `offsets` 擴充

現有：`{"kind":"dispatch", "ref":"<派發id>", "itemId":"<報價品項id>"}`（整張）。
新增兩種逐行寫法（`kind` 都是 `"dispatch"`）：

```
ref := <派發id>                          整張歸一個品項（舊，語意不變）
     | <派發id>#<行鍵>                    整行歸一個品項（不拆；金額＝該行全額）
     | <派發id>#<行鍵>#<份次>             拆分份：該行的一份（必須帶 amount）
```

整行：`{"kind":"dispatch","ref":"101#1730000000000.123","itemId":"<品項id>"}`
拆分份（同一行可有多份，各份各自一個 `offsets` 列）：
`{"kind":"dispatch","ref":"101#1730000000000.123#1","itemId":"<品項A>","amount":3000}`、
`{"kind":"dispatch","ref":"101#1730000000000.123#2","itemId":"<品項B>","amount":2500}`

- `ref` 不含 `#` ＝整張；一個 `#` ＝整行；兩個 `#` ＝拆分份。**每個 `ref` 仍是唯一的一個去處**，所以 `normalize_offsets` 以 `(kind, ref)` 去重的規則不變——拆分只是把「一行」變成多個 `ref`，每份一列、各自一個品項與金額，不改這個去重鍵。
- **`amount`（只有拆分份才有、也一定要有）**：這一份的**未稅**金額（NT$，JSON 數字，最多 2 位小數、必須 > 0）。整張與整行**不得**帶 `amount`（帶了＝422），金額＝全額，沒有第二個真相來源。
  含稅金額由系統依 §3.4 推算，**不存**（稅率或口徑改變時不會與存檔打架）。
- **份次**：`1` 起的正整數，由畫面在使用者新增一份時指定，存檔後不重排；**同一行的份次互不相同**。排序（稅額分攤、顯示）一律依份次由小到大。刪掉某一份後，其餘份次保持原值（允許有空號）。
- **一行只能是「整行」或「拆分」二選一**：同一行不可同時有整行列與拆分份列（422）。拆分允許只有一份（例如只把其中 6000 元對應到某品項，其餘留在未對應）。
- **行鍵**＝派發單 `items_json` 該行的 `id`（派發表單 `addDispatchItem` 產生，`Date.now()+Math.random()`，是帶小數的數字）的**正規化字串**：數值若為整數則寫成整數字串，否則取最短可還原表示；字串型 id 去頭尾空白；**再做百分比編碼：`%`→`%25`、`#`→`%23`**（其餘字元原樣），才不會與 `ref` 的分隔符衝突。前後端必須用同一規則（見驗收 V7，附跨語言測試向量）。
- **缺 `id` 的行不能逐行對應**（畫面標示，並引導整張對應）。上線前請正式機只讀查有多少派發單的行缺 `id`（§9 前置查詢）。
- **舊程式相容**：`normalize_offsets` 目前只留 `{kind, ref, itemId}`，**會把 `amount` 丟掉**——必須改成保留 `amount`（見 §4）；否則存檔一次拆分份金額就消失。

### 3.2 一張派發單的金額分解

以 `vendor_contractors._dispatch_row` 的現行算式為準（本提案不改它）：

- `total`＝`total_amount`（為 0 時取各行 `amount` 加總）；`tax`＝`round_half_up(total, tax_rate)`；`personnelTotal`＝外包人員合計（不計稅，不在 `items_json`）。
- 逐行對應只在 **各行 `amount` 加總＝`total`（容許 0.005 內）** 時開放；不一致的派發單只能整張對應，嘗試逐行時回明確訊息（避免出現負的殘差）。
- 單行金額：taxed 口徑＝`該行未稅金額＋該行分攤稅額`；pretax 口徑＝`該行未稅金額`（稅額只顯示，不計成本）。
- 該張派發單的「未對應剩餘」＝外包人員合計＋所有未被對應的行（各含其分攤稅額）。

### 3.3 稅額分攤（§8 Q1 已裁示）

**累計進位法**：行依 `items_json` 順序，`第 i 行稅額 = R(前 i 行未稅累計) − R(前 i−1 行未稅累計)`，`R(x)＝round_half_up(x, tax_rate)`。
性質：全部行稅額加總**恰好等於**整張派發單的稅額 `R(total)`；與「哪些行被對應」無關（分攤只由派發單本身決定），所以守恆恆成立。
例（稅率 5%，三行各 10 元）：各行單獨進位會得 1、1、1（合計 3，與整張 `R(30)=2` 差 1 元）；累計進位得 1、0、1（合計 2，一致）。

### 3.4 拆分份的金額與稅額（Q3 可拆）

記號：某行未稅金額 `A`、該行分攤稅額 `tL`（§3.3 的累計進位法算出的整數元）、份依份次排序的未稅金額 `a1…ak`（`Σ ai ≤ A`）。
**全部以「分」的整數運算**（`Decimal`／整數，**不用浮點**；金額先轉成整數分）。

- **餘額**：`r = A − Σ ai ≥ 0`，視為排在最後的一個「虛擬份」，**留在該派發單的未對應**。
- **各份稅額（累計比例進位）**：`RH(x)＝round-half-up（整數運算 (2·分子＋分母) ÷ (2·分母)）`，
  `C_j＝a1＋…＋aj`，`第 j 份稅額＝RH(tL × C_j ÷ A) − RH(tL × C_{j−1} ÷ A)`，`餘額稅額＝tL − RH(tL × Σai ÷ A)`。
- **性質**：`Σ 各份稅額 ＋ 餘額稅額 ＝ tL` **恰好成立**（最後一步 `RH(tL × A ÷ A)＝tL`）；各份稅額 ≥ 0（`RH` 單調）；與「別的行／別的份怎麼分」無關，所以守恆恆成立。
  例：行 100 元、稅額 5 元，拆 33.33／33.33／33.34 → 稅額 2、1、2（合計 5），全拆完餘額稅額 0；只拆前兩份 → 稅額 2、1，餘額稅額 2。
- **各份計入成本的金額**：taxed 口徑＝`ai ＋ 該份稅額`；pretax 口徑＝`ai`（稅額只顯示）。
- **餘額的處理（設計決定，非使用者裁示，請審查挑戰）**：份金額加總**不要求**剛好等於 `A`——只要 `Σ ai ≤ A`，不足的部分（含其稅額）**自動留在未對應**，畫面顯示「尚未分配餘額」。這樣「錢憑空增減」不可能發生：`已對應（各份）＋未對應（餘額）＝該行`。`Σ ai > A`（容許 0.005 內的誤差，之後以整數分判定）＝錢憑空增加，**存檔 422、計算端整行拆分忽略**（§4 失效處理）。若產品之後要求「拆了就必須拆完」，只需在畫面與驗證加一條 `Σ ai ＝ A`，守恆不受影響。
- 份金額的精度與上限：> 0、最多 2 位小數；每行最多 **20 份**（避免畫面與 `offsets` 失控）。

### 8.1 Q3 選了「可依金額拆」對設計的影響（摘要；細節在 §3.1、§3.4、§4、§5、§7）

| 面向 | 影響 |
|---|---|
| **`offsets` 的 `ref`** | 不改去重鍵。一行拆成多份＝多個 `ref`：`<派發id>#<行鍵>#<份次>`，**每份一列**、各自 `itemId` 與 `amount`；整行對應仍是 `<派發id>#<行鍵>`（無 `amount`）；整張仍是 `<派發id>`。同一行不可整行與拆分並存 |
| **金額從哪來** | 拆分份**存未稅金額 `amount`**（唯一新增欄位）；含稅金額不存，由 §3.4 推算。整張／整行不帶 `amount`，避免兩個真相來源 |
| **加總要等於行金額嗎** | 守恆保證改成「**各份＋尚未分配餘額＝該行**」：`Σ份 ≤ 行金額`，不足的餘額（含稅額）自動留在未對應；`Σ份 > 行金額` 存檔 422、計算端忽略該行拆分。這比強制 `Σ份＝行金額` 更寬，但**錢不會憑空增減**（餘額一定在未對應）。要不要強制拆完是畫面／驗證的一條規則，不影響守恆 |
| **稅額** | 累計比例進位（§3.4）：各份稅額加餘額稅額恰等於該行稅額；已用 6 萬組隨機拆分驗證 0 組不一致、無負稅額。全程整數分運算 |
| **V7 要不要擴充** | **要**：行鍵（含 `#`、`%` 的編碼）、`ref` 組合與解析互為反函數、份次為正整數、`amount` 兩端正規化（以整數分比較）——見 V7 |
| **後端改動** | `normalize_offsets` 要**保留 `amount`**（目前只留 `kind/ref/itemId`，會丟）；`validate_offsets` 新增拆分驗證，「原樣放行」比對鍵含 `amount`；`compute()` 多一個「份」查表與餘額；失效處理新增 `dispatch_line_split_exceeds` |
| **前端改動** | 拆分編輯器（品項＋金額、餘額、填入餘額、平分）；**兩處必改否則 `amount` 丟失**：載入 `offsets` 的重組與「有未存變更」指紋（§5） |
| **新增驗收** | V12 拆分守恆、V13 `amount` 往返、V14 拆分失效、V15 拆分 e2e、V16 拆分與完結 |
| **規模** | 比「一行一個去處」多：驗證與失效規則、稅額子分攤、前端拆分編輯器、約 5 項驗收。後端仍集中在 `settlement_actuals.py`。**切片建議（不強制）**：先做「整行對應」（不含 `amount`），再做「拆分」——`ref` 格式與 `amount` 保留欄位已預留，第二階段不必改第一階段已存的資料 |
| **風險** | ①使用者拆分輸入錯誤（金額加總對不上）→ 畫面即時餘額＋紅字防呆；②舊單行金額被改後拆分失效（V14）；③`amount` 在前後端被無意丟掉（V13 專門鎖）；④浮點誤差（V12／V16：整數分運算） |

## 10. 風險與邊界（規格需處理）

- **派發單核准後被改會退回草稿**（`PUT /api/contractor-dispatches/{id}` 實質欄位變動 → `approval_status` 回草稿），而 `dispatch_rows` 排除草稿 ⇒ 該張在精算整張消失、對應暫時失效；重新核准後（行 id 不變）對應恢復。這是設計行為，V5 鎖住「不丟錢」。
- **舊單（`approval_status=''`）可被實質修改而不重設審核**：行金額可能在精算存檔後改變。逐行金額一律取**現況**，對應只記行鍵；金額變動自然反映（與現在整張對應取現況金額一致）。
- **行 id 型別**：派發單行 id 是帶小數的浮點，Python 與 JS 字串化需一致（V7）。若實務上發現不穩，備案是改用「行序＋描述雜湊」，但行序在可編輯期間不穩，不建議作為首選。
- **整張與逐行同時存在於同一張派發單**：Q4 已裁示互斥——驗證擋下；舊存檔只會有整張對應，不會有逐行或拆分，所以沒有歷史資料要處理。
- **使用者手填與派發重複**：本案不自動偵測重複（報告 §3）；畫面守恆列與「未對應仍計入總成本」的提示已存在，是否要加「這張派發單未對應且你已手填成本，可能重複」的提醒，列為可選項（需使用者決定，不在本案必做範圍）。
