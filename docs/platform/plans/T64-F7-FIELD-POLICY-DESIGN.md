# T64 切片 D：F7 欄位可見政策（共用欄位目錄）——設計

> 日期：2026-10-15　作者：Claude（hichan-61 視窗）　基底 `origin/train/t63-int`（26a0a07d4）　分支 `wip/t64-f7-design-r1`　**僅文件，沒有任何程式改動、沒有跑測試**。
> 對應 `quote-case-finance-coupling` §4 的 F7，以及 T64 切片順序 D。依賴：T63 匯出欄位（`helpers/export_templates.py`）、T63 Q0 設定（`quote_privacy`）、T61 S5 欄位目錄設計（`x_` 自訂欄位）、定義管線（放寬需第二位最高管理者核准）。
> 目標一句話：**『誰能看到哪個欄位』變成一份可設定的政策；金額類欄位永遠不會超出後端遮蔽允許的範圍；沒設定時行為與今天逐位元相同。**

## 0. 結論（先看）

1. 今天有**三份互不相通的欄位清單**（金額遮蔽的鍵、版面引擎的欄位點、匯出的欄位目錄），加上自訂建構器各自的 `visibleTo`。同一個欄位（例如品項成本）在三處各登記一次，改一處不會動另外兩處——這就是『第二個來源』。
2. 做法：**一份共用欄位目錄**（`fieldCatalog`，只收集、不擁有，沿用 `core/catalog.py` 的 `register_section` 手法），每個欄位一筆：代號、白話名稱、資料分類、金額等級、**天花板**（後端遮蔽規則）、今天的預設。三個既有清單改成**從目錄衍生**（鍵集合與今天逐字相同，有守門測試）。
3. 政策只有一個基本式：**實際可見 ＝ 天花板 ∧ 政策**。天花板是程式裡的後端遮蔽（`financial_mask`／`export_templates` 的 `visible`），**政策只能在天花板之內再縮小或指定**，不能超出。⇒ 金額欄位不可能因為設定錯誤而洩漏給後端本來就擋掉的人。
4. 『放寬天花板』本身（例如讓工程師也算有成本權限）不在這份政策裡，而是既有的**權限勾選制**（`finance_via_effective` D5／權限矩陣）；本設計只負責把它的結果**顯示出來並預覽影響**，不另開第二條路。
5. 預設＝今天；政策不存在或旗標關 ⇒ 全部走原本的函式。放寬一律走定義管線（第二位最高管理者核准＋影響預覽『N 人將看得到成本』），縮小立即生效。
6. **組織單位維度納入 T65 設計（2026-10-15 使用者裁示）**。查核結果（§12）：U0a 已建好單位樹（`org_units`＋`org_unit_closure`）與成員表（`user_units`），所有人預設歸根單位；**缺的是執行期讀取**（沒有任何程式讀 `user_units`）、單位管理畫面、以及舊『處／部門』（`departments`、`users.department_id`）與新單位樹兩套並存的對應。結論：『受眾含單位』現在就能做（S5a），『依資料列所屬單位過濾』要等 U1。
7. **受保護層（`protected`）取代『永久鎖定』（2026-10-15 使用者裁示）**：薪資、銀行帳號、身分證類個資、單位鍵**預設鎖定，但最高管理者可以放寬**——只能走治理（第二位最高管理者核准＋確認期間＋紅字警告＋影響預覽＋稽核），且是**天花板層**的放寬，不是政策層。見 §11（含法務風險）。單位鍵列入目錄但本期不可授權（等 U1）。

## 2. 共用欄位目錄（`fieldCatalog`）

只收集、不擁有（沿用 `core/catalog.py` 原則：寫死的那一份就是第二個來源）。擁有者（模組、L1 helper）以 `register_section("fieldCatalog", owner, fn)` 登記自己的欄位；目錄 `build()` 合併並驗證。

每個欄位一筆：

| 欄位 | 說明 |
|---|---|
| `id` | 穩定代號 `<實體>.<鍵>`，如 `quote_item.cost`、`case.payment.actualAmount`、`quotation.net_margin_pct`。**一旦發布不改名**（政策引用它）；改名＝新增＋停用 |
| `label` | 白話名稱（『品項成本』），畫面與影響預覽用 |
| `family` | 家族：`cost`（成本）、`margin`（毛利）、`price`（單價／金額）、`payment`（款項）、`pii`（個資）、`plain`（一般）。**同家族一起判斷**：成本藏了、毛利率卻露出來＝可反推成本，所以 `margin` 依賴 `cost`（`derivedFrom`） |
| `moneyClass` | `none`／`money`／`protected`。`protected`＝**受保護層**：預設鎖定，政策層不可放寬、只能走 §11 的『受保護欄位授權』（原稱 `hardlock`，2026-10-15 改名並改為可經治理開放）。代號 `hardlock` 不得出現在程式裡 |
| `ceiling` | 天花板：一個**具名能力**（`quote_money`＝今天 `quote_money_visible`；`finance_money`＝今天 `money_visible`；`material_money`；`cashier`），由後端函式回答，不是角色清單的複本 |
| `surfaces` | 這個欄位出現在哪：`api`（JSON 回應）、`screen`（版面欄位點，帶 `entity/key`）、`export`（匯出欄位，帶 `exportId/columnId`）、`pdf_internal` |
| `default` | 今天的規則（由 `ceiling` 推出）；政策不存在時就是它 |

**衍生，不是複製**：
- `financial_mask` 的 6 個元組 ⇒ 改為從目錄依 `surfaces.api` 與 `family` 產生；守門測試比對『產生結果＝今天的元組（逐字、順序）』，不一致即紅。`HISTORY_MONEY_FIELDS` 的顯示名稱一併登記為 `legacyLabels`（舊紀錄比對用，不再當鍵）。
- 版面欄位點 ⇒ `module.json` 欄位點加選填 `catalogId`；有 `catalogId` 的點，其可見性來自目錄（政策），沒有的維持今天。目錄驗證：每個 `catalogId` 必須存在、`entity/key` 必須與登記一致。
- 匯出欄位 ⇒ `columns[]` 加選填 `catalogId`；`money` 旗標與 `visible` 由目錄的 `moneyClass/ceiling` 推出（登記端不再各寫一份；遷移期兩者並存並互相驗證）。

**版面的『隱藏』≠ 安全**：版面操作只影響畫面，API 與匯出照樣會回該欄位。凡 `moneyClass != none` 的欄位，`layout` 驗證器在**發布前**提示『隱藏這個欄位不會讓沒權限的人看不到，請改用欄位可見政策』。

## 3. 政策定義（新 kind `field_policy`）

沿用定義管線（草稿、版本、差異、還原、影響預覽、放寬進待核准），key＝`company`（一份）。

```json
{ "version": 1,
  "rules": [
    { "field": "quote_item.cost",                 // 欄位代號；或 "family:cost" 一次套一個家族
      "audience": { "roles": ["superadmin","admin","finance"],   // 空＝今天預設
                    "users": ["王大明"],
                    "units": [] }                  // 第一版必須為空
    } ] }
```

規則：
1. **求值**：`可見(欄位,人) = 天花板(欄位,人) ∧ (沒有規則 ∨ 規則命中(人))`。最高管理者直通**仍須過天花板與受保護層（天花板對最高管理者必為真，這是今天的不變式 `has_finance_access` 含 superadmin）。
2. **個人例外**只能在天花板內加人：政策裡列了某人、但他過不了天花板 ⇒ 仍看不到，並在影響預覽標『此人沒有金額權限，政策無效』。
3. 家族規則自動涵蓋 `derivedFrom`：把 `cost` 範圍縮小，`margin` 家族不得比它寬（驗證器擋：`margin` 的受眾必須是 `cost` 受眾的子集；否則發布被拒並白話說明『毛利可以反推成本』）。
4. 政策只存**受眾**，不存值；停用一條規則＝回到今天的預設。
5. 後端是最後一道關：所有出口（API 回應、匯出、內部 PDF、通知占位符、搜尋結果、回收桶、稽核檢視）都必須經同一個求值函式 `field_policy.visible(field_id, user)`；既有 `mask_*` 變成它的薄包裝。

## 4. 套用點（要遷移的出口，先列清單才算數）

`grep financial_mask` 實際引用者（可由守門測試固化為清單）：`helpers/rule_catalog.py`、`modules/analytics/api/{reports,ledger_diff}.py`、`modules/case/{alt_lock,completion_sync,material_guard,rule_provider}.py`、`modules/case/api/{alt_plan,material_approvals,material_changes,material_orders,material_payments,project_margin,quotations}.py`。另有不經 `financial_mask` 但各自判斷金額的出口：`notify_actions._expand_text`（`has_finance_access`）、匯出範本（`visible=`）、`recycle_bin.mask_obj`、建構器 `mask_record`。

遷移順序：先**只登記不改行為**（目錄＋等價守門），再逐出口改成呼叫 `visible()`，每改一處用『角色 × 欄位』矩陣金標證明與舊函式輸出逐格相同。**不新增路由、旗標關時零新請求。**

## 5. 預設＝今天、旗標、治理

- 旗標 `builder_field_policy.enabled`（設定中心，預設關）＋既有 `builder_governance.enabled`。關 ⇒ `visible()` 直接回舊函式的結果；開但沒有已發布政策 ⇒ 同上（rules 空）。
- **放寬**（任一個『欄位×人』由不可見變可見）：進待核准，需**第二位最高管理者**核准（與 D-K1 簽核門檻放寬同一條規則），核准前保持舊行為。**縮小**：立即生效。
- 求值錯誤（目錄讀不到、政策壞掉）⇒ **fail-closed 到天花板的預設**（今天的行為），不是全開。

## 6. 影響預覽與遷移

發布前『看看會怎樣』（沿用 `_PREVIEW_ENFORCED_KINDS`：未看預覽不能發布）：
- 對每位在職使用者算出『改前／改後』可見欄位集合，只列**有差異**的格子，彙總成白話：『**3 位**同仁將看得到「品項成本」：王小明（業務）、李小華（業務）、陳大同（工程師，⚠ 此人沒有金額權限，設定無效）』『**1 位**同仁將看不到「毛利率」』。
- 同時列出受影響的**出口**（畫面、匯出『案件批次匯出』、內部 PDF、通知內容）。
- 不含金額值本身，只含人名與欄位名；預覽不寫任何資料，只留一筆稽核 `field_policy.previewed`（比照 `notify_action.previewed`）。
- 遷移＝**沒有資料遷移**：政策是新定義；目錄是程式登記；舊行為由 `default` 提供。上線第一天『已發布政策』為空，所有人看到的與昨天相同。

## 9. 需要使用者決定的事（每題附建議預設；能做成設定的都已做成設定，這裡只列『不能是設定』或『預設值要先選一個』）

1. **成本與毛利預設誰看得到？**　建議：**維持今天**（報價層級：最高管理者、管理員、業務、財務；精算與款項：只有最高管理者與財務）。之後可在設定改。
2. **放寬欄位可見是否一律要第二位最高管理者核准？**　建議：**是**（與簽核門檻放寬同一條）。若公司只有一位最高管理者，放寬維持『確認期間』後生效。
3. **允許『指定個人』加看嗎？**　建議：**允許**，但只能在系統金額權限之內，且算放寬（走核准）。
4. **要不要讓『毛利比成本寬』成為禁止而不只是警告？**　建議：**禁止**（發布被拒，白話說明可反推成本）；若要例外，請明說理由並由最高管理者承擔。
5. ✅ **已裁示（2026-10-15）**：薪資單金額、銀行帳號、身分證類個資、單位鍵列為**受保護層**——預設鎖定，最高管理者**可以**開放，但只能走治理（§11）。受保護清單本身（哪些欄位屬於受保護層）仍由程式登記，不能用設定新增或移除。
6. ✅ **已裁示（2026-10-15）**：組織單位維度納入 T65 設計（§12）。

## 10. 風險與不做

- **寫回風險**（`financial_mask` 檔頭）：看不到的人送回來的資料沒有那些鍵，照單全收會用空值蓋掉真值。目錄上線後凡經 `visible()` 隱藏的欄位，寫入路徑必須沿用 `restore_*` 補回現值；S1 的矩陣金標要含『隱藏帳號存檔後金額不變』。
- **推論洩漏**：家族依賴（§3 規則 3）只擋已登記的關係；未登記的衍生值（例如總額與其他部分相減）仍可能反推——目錄新增欄位時 `derivedFrom` 是必填審查項。
- **公式／通知／搜尋**：建構器的 `leaking_formulas()` 規則延伸到政策；通知占位符（`notify_actions`）已逐收件人遮蔽，S1 要改走同一個 `visible()`。
- **不做**：改變任何計算、簽核、狀態；改變天花板（走權限勾選制；受保護欄位的授權除外，見 §11）；依資料列所屬單位過濾（S5c／U1）；客戶可見輸出（維持『內部欄位不進客戶輸出』的既有規則）。

## 11. 受保護層（`protected`）與受保護欄位授權（2026-10-15 使用者裁示後新增）

### 11.1 裁示重點
鎖定清單不再『絕對』：預設仍鎖定，最高管理者可開放；任何放寬都走治理，且後端遮蔽仍是最後一道關。受保護欄位**不會**因為政策設定錯誤而洩漏——要看到它，必須有人**刻意**對『該欄位』發布一筆授權，並通過下列所有關卡。

### 11.2 為什麼是『天花板層』而不是『政策層』
§0.3 的原則是『政策只能在天花板之內縮小』。受保護欄位的裁示要求的是**把天花板本身降低**，所以不能塞進 `field_policy`。做法：**另一種定義 `protected_grant`**，只對 `moneyClass=protected` 的欄位有效，內容是『這個欄位的天花板額外納入哪些受眾』；`field_policy.tier_allowed(ceiling, user)` 對 protected 欄位多讀一層：`(原天花板 ∨ 授權受眾命中) ∧ 政策`。其餘欄位完全不讀授權。

授權規則（2026-10-16 PM 裁示修訂）：
1. **受眾可為角色、個人、單位**。不允許『所有人』；不允許 `viewer` 類唯讀角色、客戶／外部身分；**根單位禁止**（含 `includeChildren`）。人數上限為**設定**（`protected.grant.max_headcount`，預設見 §11.7），超過不能送出。
2. **受眾一律於核准當下快照成『人名清單』**：單位以 `members_of(..., explicit_only=True)` 展開成員、角色展開現有持有者；**展開結果含根單位者一律拒絕**；**人數上限比對的是快照人數**（不是單位數）；空快照拒絕；之後單位或角色成員變動，新進者**不自動取得**，需重新核准。（避免『調動／升職即取得薪資』。）
3. **單位成員只認明確的 `user_units` 列**：『沒有列＝根單位』的慣例**不適用**於受保護授權；沒有明確列的人不屬於任何授權單位。
4. **單位鍵（`owner_unit_id`／`unit_id`／`legal_entity_id`）列入目錄但本期不可授權**，等 U1 後另議（需先改 `core/internal_cols.py`）。
5. 授權**只加不減原有權限**；縮小或收回＝立即生效。
6. 授權必填**用途**與**依據**，送出後**不可修改**（要改＝撤銷後重提）；留在稽核與影響預覽。
7. **沒有永久授權**。期限上限＝設定 `protected.grant.max_days`（預設 90 天，**程式硬上限 365 天**，設定值超過硬上限者拒存）；到期自動收回，續期＝**新的一筆核准**（不是延長舊的）。
8. 到期判斷於**讀取時**求值（讀的當下比對時間），不依賴排程是否有跑。
9. **讀取時求值（受保護欄位）**：每次讀取都**不經快取**（略過 resolver 的 30 秒快取與 `invalidate` 機制，直接查資料庫）；一般欄位的資料變動最長有 30 秒延遲，此為已知且接受的視窗。每次讀取檢查：①使用者為**啟用**狀態（受保護路徑自己檢查，不依賴呼叫端）；②使用者**仍符合原授權條件**（快照只能縮小、不能放大：仍持有該角色／仍在該單位的明確 `user_units` 列、該單位與其祖先**直到快照建立時所用的那個單位**皆啟用，規則同 resolver §3.3a）；③授權未到期、未撤銷、未逾時。**只有『正向不符』才自動撤銷**：①使用者停用、②明確列或角色已不存在、單位或其祖先（至快照單位）已停用 ⇒ 該使用者的授權**自動撤銷**並寫稽核 `revoked`（原因 `criterion_no_longer_matched`），本次回遮蔽值。**暫時性錯誤**（資料庫鎖定、sqlite 錯誤、逾時）不算不符：**只拒絕該次讀取**（回遮蔽值），授權維持、**不寫 `revoked`**，錯誤只記日誌。

### 11.3 治理關卡（全部成立才生效）
1. 提出者為最高管理者；**第二位最高管理者**核准（與 D-K1 同一條）。**提出者≠核准者**；兩人**都不得在受眾名單內**，除非預覽以紅字明示『提出者／核准者自己在名單內』並額外確認。**啟用瞬間，以及確認期間內兩次『我確認要放寬』按下的當下**，各重新驗證兩人仍是最高管理者且帳號啟用（任一人被降權或停用 ⇒ 該提案作廢）。
2. **只有一位最高管理者的公司：受保護授權停用，且『放寬受保護相關設定』（確認期間、期限、人數上限等）的路徑一併停用**（沒有第二雙眼睛，不留退路）。
3. **確認期間**：預設 72 小時；期間內提出者與核准者各須再按一次『我確認要放寬』。**各設定的放寬／縮緊方向**（下限與上限為**程式常數**，不是設定，設定值不得越過）：

| 設定 | 放寬方向（需第二位最高管理者核准） | 縮緊方向（立即生效、不需核准、仍寫稽核） | 程式常數 |
|---|---|---|---|
| `protected.confirm_hours` | 調**低** | 調高 | 下限 24 |
| `protected.grant.max_days` | 調**高** | 調低 | 上限 365 |
| `protected.grant.max_headcount` | 調**高** | 調低 | 下限 1；不得『不限』 |
| `protected.proposal.timeout_days` | 調**高** | 調低 | 下限 1 |

4. **待核准提案逾時**：設定 `protected.proposal.timeout_days`（預設 7 天），逾時自動作廢（讀取時求值）；作廢需重新提出。
5. **紅字警告框**：白話列出『這會讓 N 位同仁看到〈欄位〉』、列人名（快照）、列出現的出口；必須勾選『我了解可能涉及個人資料保護法責任』。
6. **影響預覽**（沿用 `_PREVIEW_ENFORCED_KINDS`）；預覽只含人名與欄位名，不含值。
7. **稽核**：`field_policy.protected_proposed／approved／activated／expired／revoked／timed_out`，含提出者、核准者、用途、依據、受眾快照、期限；`activated` 另記 `self_in_audience`（提出者／核准者是否在受眾內）；稽核紀錄不得含欄位值。
8. **存取紀錄**：涵蓋**所有讀取路徑**——列表、詳情、匯出、PDF／列印、報表建構器、API；被授權者**每次檢視一筆資料列**記一筆（誰、何時、哪個欄位、哪張單、哪一列；不含值；一列一筆，不合併）。
   - 保存期限 **≥ 稽核紀錄**；存取紀錄本身屬受保護資料，只有最高管理者與稽核角色可讀，且不可刪改。
   - 列表／匯出／報表一次含多列時，**與讀取在同一交易中批次寫入**；**寫入失敗＝整頁（整批）拒絕讀取（fail-closed）**，回遮蔽值，不是只略過該列。

### 11.4 程式不變式（不是設定，**不可授權**；以『出口層排除』實作）
共 **5 條**，**在寫入時就強制**，不依賴讀取時過濾，任何授權、任何設定都不能解除：
1. **受保護值不進搜尋索引**（建索引時排除）。
2. **受保護值不進稽核差異內容**（`audit_log` 前後差異 payload 寫入時以占位符取代，只記『欄位已變更』）。
3. **受保護值不進回收桶快照**（刪除時快照即遮蔽；還原時用 `restore_*` 從現值補回）。
4. **客戶可見輸出與外部 API 不含受保護值**。
5. **『全選欄位匯出』不含受保護欄位**（逐欄明示且該使用者有授權才可）。
另有一條**通知規則**（同屬不可授權）：通知／電郵／LINE 會離開系統，視同外部輸出，占位符遇受保護欄位一律輸出『（受保護）』。

同一原則延伸（實作規則，同屬出口層排除）：
- **日誌、追蹤（trace）、錯誤報告、備份匯出**：寫入時排除或遮蔽受保護欄位；備份中的資料庫檔本身屬系統層，不在此列，但備份檔不得被產品功能當成讀取受保護值的旁路。
- **彙總／報表建構器**：由受保護欄位衍生的值（總和、平均、可反推者）**沿用該欄位的受保護層**（推導規則＝實作規則：衍生值的 `derivedFrom` 含受保護欄位 ⇒ 繼承 protected）。
- 寫回：沒有授權的帳號送回的資料沒有這些鍵 ⇒ 沿用 `restore_*` 補回（§10）。
- 求值錯誤 ⇒ fail-closed（隱藏）。
- 單位／角色解析遇壞資料（懸空列、停用單位、缺閉包）⇒ 該受眾**回空集合，絕不退成根單位**。
- 『margin 不得比 cost 寬』家族規則對受保護欄位同家族同樣適用。

### 11.5 法務風險（需法務／使用者本人確認；本節不是法律意見）
- 薪資、銀行帳號、身分證字號屬個人資料；開放給原作業範圍以外的人，可能違反**個人資料保護法**『特定目的內必要範圍利用』與『採行適當安全措施』；員工為資料當事人，公司是蒐集者，責任在公司。
- 系統提供的只是**工具**：紅字警告、雙人核准、期限、稽核、存取紀錄使決定**可追溯、可收回**，**不能**取代公司自己的法遵評估；『預設鎖定』是我們給出的防線，放寬後由使用者承擔。
- 建議：①用途／依據必填且永久留存、不可修改；②存取紀錄保存期限不短於稽核紀錄；③**員工告知（隱私聲明）是否需更新，不在系統範圍內**，需公司自行處理；④不再列『絕對不可授權欄位清單』——絕對限制僅 §11.4 的三條出口不變式。
- 風險等級：高。誤放寬的後果（個資外洩、勞資糾紛）不可逆；**P1 上線前須取得使用者的書面確認（§11.6），此關卡保留**。
