## 14 資料範圍維度與組織單位（多據點／多法人；使用者 10-13 14:15 裁示 r2 增補）

> **使用者裁示（經 1c 轉達）**：①排程由 PM 安排，本稿給選項與人日；②**資料範圍的自訂維度（部門、客戶、專案類型…）= YES，是框架核心**；③『哪些欄位只有最高管理者看得到』**也由框架設定**，不寫死（只有 H5 稽核、6 項鎖死簽核、不得自我鎖死維持寫死）；④**新需求**：跨區域／多據點／多法人必須可分離，例如『A 分公司、B 母公司』：母公司依設定看得到子公司，**平行單位預設互相隔離**。
> 本節把 §4.5『資料範圍不進矩陣』**改為**：資料範圍是矩陣的第二個軸（授權時可帶『範圍』），組織單位樹是第一個內建維度。**§4.5、§6.2、§12 已依此改寫。**

### 14.1 兩個概念，先分清楚
| 概念 | 回答的問題 | 例 |
|---|---|---|
| **法人（legal entity）** | 這份單據**法律上屬於誰**：統編、抬頭、帳冊、法定連號、稅務申報 | B 母公司、A 分公司（若獨立報稅則是另一法人） |
| **組織單位（org unit）** | 這份資料**歸誰管、誰看得到**：資料範圍、簽核、通知、設定覆寫 | 母公司 → 北區、南區、A 分公司… |
- **做法（使用者 10-13 答覆：法人＝混合）**：一棵**單位樹**；**每個節點都帶『是否為法人』旗標**（有些分支是獨立公司、有些不是）；**統編、法定連號、帳冊按『法人節點』切；非法人節點歸屬於它上面最近的法人節點**（所屬法人＝自己或最近的有標記的祖先）。**起點＝單一根法人**（今天的公司）。這樣『同一法人的多個據點』與『多個法人』用同一個結構表達，不需要兩套。
- **現況事實**：今天已有兩個**局部**概念——①`departments`／`divisions`（v48，純組織分類；`users.department_id`、`projects.department_id`，簽核流程的『部門主管』展開用）；②`company_profile.locations`（據點，只決定**單據抬頭與匯款帳號**，`helpers/company_identity.py`，使用者 2026-09-22『我們有分公司』）。**兩者都不控制『誰看得到什麼』，也沒有法人之分。** 本設計把它們收編為單位樹的特例（部門＝單位、據點＝帶抬頭的單位），遷移見 §14.9。

**法人快照（0d r6：混合法人下必須固定）**：法律單據（傳票、稅務／發票號碼、勞報單、`PS-YYMM` 薪資單等）在**建立當下**就把所屬法人 `legal_entity_id` **寫成不可變的快照欄位**，**不在讀取時由單位樹推導**。因此：
- 日後**更改某節點的法人旗標**，或**搬移單位**，都**不會**改動既有單據的法人歸屬，也不會動既有序列（歷史不重寫）。
- **對已有單據的節點翻轉法人旗標＝高影響**：需雙人核准＋確認期間＋影響預覽（『該節點已擁有 N 張單據、M 條序列』）；規則：新法人節點**從自己的 `seq_by_entity` 列開始**，舊法人的序列與已發出的號碼原封不動；原法人與新法人的帳冊從切換日起分開，歷史帳冊不搬。
- 單據編輯、作廢、沖銷一律沿用快照上的法人；金額與連號相關查核（H-D）以快照法人為準。

### 14.2 自訂範圍維度（框架核心）
- **維度宣告**：`scope_dimensions(key, label, kind tree|flat, applies_to[物件鍵])`，值表 `scope_values(dimension, id, parent_id, label)`。內建維度 `org_unit`（樹、必填、所有業務物件都有）；其他維度（客戶群、專案類型、部門…）由最高管理者在畫面定義，**物件可選擇帶哪些維度**（欄位值存在記錄上）。
- **授權帶範圍**：矩陣的一格從『角色 × 能力』擴成『主體 × 能力 × **範圍**』，範圍＝每個受限維度的值集合（含子樹旗標）。未指定範圍＝『全部』＝今天的行為。判定：一筆記錄可被存取 ⇔ 存在一個授權，其能力相符，且對**該授權有限制的每個維度**，記錄的值落在範圍內。
- **與逐案守門並存**：擁有者／成員／被指派（`row_access.OwnerRule`）仍是『個人關係』軸；範圍維度是『組織／分類』軸；**兩者是 OR 的放寬（個人關係可跨範圍看自己的案）還是 AND 的收窄，需使用者確認（§12 確認 7；預設：範圍是硬邊界＝AND，個人關係只在範圍內有效）。**

### 14.3 每筆記錄的所屬單位（`owner_unit_id`）
| 領域 | 所屬單位怎麼定 | 備註 |
|---|---|---|
| 案件／報價單／額外支出／材料申請／完工單／出貨 | 建立當下由建立者選擇（預設＝其主要單位）；子單據**繼承案件的單位**，不可獨立改 | 轉單位＝有權限者的明確動作，寫稽核（H-E） |
| 財務（請款、開票憑據、匯款、出納） | 繼承案件；無案件者取建立者所選 | 金額帳冊按**法人**切 |
| 薪資（勞報單、獎金） | 承攬人／員工所屬單位（可選）；預設繼承案件 | 個資高度敏感，預設最嚴 |
| 採購／庫存 | 倉庫（或 SKU 批次）屬於某單位 | 跨單位調撥是明確動作 |
| 會計（傳票、總帳、稅務） | **所屬法人（建立時寫成不可變快照 `legal_entity_id`）**（帳冊獨立） | 法定連號按法人切（見 14.4） |
| 主檔（客戶、供應商、承攬商、料號） | 三選一（每類主檔宣告預設）：**全域共用**／**單位專屬**／**共用給指定單位** | 預設＝全域共用（今天的行為） |
| 附件、稽核紀錄、通知 | 隨所屬記錄；稽核另存 `unit_id` | 母公司稽核員可依設定看子單位稽核 |

### 14.4 單位對各領域的影響
| 領域 | 今天（事實） | 多單位後 |
|---|---|---|
| **編號** | 報價單 `quote_seq(month)` 全域一條；傳票 `YYYYMMDD-NNN`；勞報單 `PS-YYMM-NNN` | **根法人沿用既有序列表原樣**；其他法人使用**新增的 `seq_by_entity`**（見 §14.10）；前綴可按法人設定；**法定連號（傳票、稅務發票號）絕不可跨法人共用**（H-D） |
| **稅務／抬頭** | `company_profile` 單一份＋`locations`（抬頭／匯款帳號） | 按法人持有統編、抬頭、帳號；單據依所屬法人取身分（`company_identity` 已是這個形狀） |
| **簽核** | 每種單據的 tiers 由簽核流程設定挑人；簽核人目錄 | 流程可按單位覆寫（沿用上層）；簽核人預設限『該單位子樹內』，跨單位需明確列為『跨單位簽核人』（H5 目錄原則不變） |
| **角色／權限** | 全域角色＋模組勾選 | 使用者在**某單位**擔任某角色（見 14.6）；能力授予帶範圍（14.2） |
| **設定** | `system_settings` 全域鍵值 | 見 14.5 |
| **信件／通知** | 全域收件設定、信件類型 | 寄件身分與收件人按單位解析；通知收件人預設限單位範圍，避免洩漏跨單位內容 |
| **備份／還原** | 單一資料庫整份備份 | 見 14.8；整體備份仍整份，單位匯出為獨立工具 |
| **匯出／報表** | 依角色與金額遮蔽 | **範圍篩選永遠先套用**；母單位可選『合併』或『逐單位』檢視 |
| **附件儲存** | 儲存位置代號＋子夾（建構器插槽） | 位置代號可按單位指定不同根目錄（根仍由部署決定） |

### 14.5 設定的範圍：全域 vs 單位，繼承與覆寫
- **宣告**：設定群組／鍵新增選填 `scope`：`global`（預設，今天的行為）｜`unit`（可按單位覆寫）。法規／安全類（如確認期間下限、備份最低保留、H 層上界）**固定 `global`，單位只能收緊不能放寬**。
- **解析順序**：該單位的覆寫 → 沿父鏈往上最近的覆寫 → 全域預設。**繼承顯示**：設定中心每個值標『來自：本單位／上層「母公司」／全域預設』。
- **儲存**：`system_settings_unit(unit_id, key, value_json)`（只存與繼承不同者）；寫入走同一條發布管線（`config_ledger` 領域加 `unit_id`），**放寬判斷以『相對於繼承值』為準**。
- **誰能改**：全域設定＝最高管理者；單位設定＝可授予『單位管理員』能力 `org.unit.config`（範圍＝該單位子樹；低風險立即、高影響仍走雙人核准）。
- **權限頁同理**：能力格也可按單位覆寫（A 分公司的『業務』能做的事可以與母公司不同）。

### 14.6 使用者屬於多個單位
- `user_units(user_id, unit_id, is_primary, role_binding)`；一個人可在多個單位各有不同角色（A 分公司業務＋母公司財務）。
- **生效權限＝各歸屬的授權（帶範圍）取聯集**；禁止優先於允許，且『禁止』可指定單位。
- **建立資料時**必須選『所屬單位』（只列其有建立權限的歸屬；預設主要單位）；清單與搜尋以『可見單位集合』過濾。
- **預覽**：權限頁『依人看』增加**單位切換**：選一個人＋一個單位 → 他在該單位『能做什麼、看得到哪些資料範圍』；另有『他在所有單位的總覽』與『某筆記錄為何他看得到／看不到』（逐步說明：單位、範圍、個人關係、能力）。

### 14.7 跨單位可見性規則（預設值與可設定）
| 關係 | 預設 | 可設定 |
|---|---|---|
| 同單位 | 依角色能力 | — |
| 母 → 子（祖先看子孫） | **看得到**（使用者：『母公司依設定看子公司』）；每條母子連結有旗標 `parent_sees_children`（預設開） | 可逐連結關閉；可限制為只看『彙總』不看明細 |
| 子 → 母 | **看不到** | 明確授權（例如把某客戶共用給子單位） |
| **平行（A 分公司 ↔ 其他分公司）** | **互相隔離**（使用者要求） | 明確『共用』：某記錄類型或某主檔指定共用給某單位（唯讀或可編輯，雙方單位管理員核准） |
| 跨單位簽核人 | 不允許 | 明確列入簽核人目錄 |
- 放寬任何一條（母看子的明細、平行共用）屬**高影響**（雙人核准＋確認期＋影響範圍預覽『N 位使用者將看到 M 筆記錄』）。

### 14.8 單一資料庫＋單位鍵 vs 每單位獨立資料庫
| 面向 | 單一庫＋`owner_unit_id` | 每單位一個庫（或一個安裝） |
|---|---|---|
| 隔離強度 | **靠程式**（每個查詢必須帶範圍）；漏一個就外洩 → 以集中過濾＋金標測試緩解 | **硬隔離**（檔案層分開），管理員誤操作也看不到 |
| 母公司合併檢視 | 天然支援（同庫彙總） | 需要跨庫彙總（ETL／聯邦查詢），成本高、延遲 |
| 使用者／權限 | 一份帳號、多單位歸屬 | 帳號每庫一份或另做聯邦 |
| 升級／維運 | **一次升級一個庫**（現有 `apply_update`／備份／建包流程不變） | ×N（版本漂移、N 次套用與驗證） |
| 共用主檔（客戶、料號） | 容易（單位鍵或共用旗標） | 需同步 |
| 法人分離（獨立帳冊、賣掉子公司） | 以法人鍵切；**單位匯出／分拆工具**需另寫 | 天然（直接交出該庫） |
| 備份／還原 | 整份；單位級還原困難 | 各自獨立，簡單 |
| SQLite 並行 | 共用寫鎖（現況本來就是單庫） | 各自寫鎖，互不干擾 |
| 資料落地規範（不同地區法規要求資料不得同機） | 無法滿足 | 可滿足（分機部署） |
**建議**：**單一資料庫＋強制 `owner_unit_id`＋集中強制點（再加未經範圍讀取的 AST 棘輪，見 §14.12）＋法人鍵切帳冊**，理由：符合『母公司看子公司、同一套帳號與升級』；產品本來就是『一個安裝＝一家公司』，**真正互不相干的公司（不同集團、不同資料落地要求）應該各自一個安裝**（現有 `install_identity` 模型），不必在一個庫裡硬塞。保留未來『單位匯出／分拆』工具作為出口（U4）。**使用者若需要『管理員誤操作也不可能看到』的硬隔離，答案是獨立安裝，不是單位樹**（§12 確認 8）。

### 14.9 遷移：今天的單一公司＝一個根單位，行為完全相同
1. 建單位樹，只有**根單位**（＝今天的公司；標 `is_legal_entity`；承接 `company_profile`、`locations` 轉成根下的『據點型』子單位或抬頭設定，**抬頭解析結果逐字相同**）。
2. 所有業務表加 `owner_unit_id`（預設根單位＝1）；所有使用者歸屬根單位（主要）；所有設定 `scope=global`；所有序列的法人鍵＝根；所有授權範圍＝『全部』。
3. **單位感知功能由旗標 `multi_unit_enabled`（預設關）啟動**：關閉時所有範圍過濾為恆真、介面不出現單位選項。
4. **等價關卡**：①有效權限快照（§10）前後相同；②每個清單／搜尋／匯出／儀表板在單根單位下的結果前後逐列相同（金標）；③編號序列的下一個值前後相同。
5. 法律單據的 `legal_entity_id` 快照欄位在 U0 預留（預設根法人）；回滾：旗標關閉即回到單根行為；`owner_unit_id` 欄位保留（無害）。

### 14.10 現在就做的最小預留（U0；r3 依 0d M1／M2／S2／S3 重寫）
**原則**：只做**加法**（新欄位帶預設值、新表）；**不改主鍵、不改約束、不重建既有表**；舊程式遇到新欄位與新表必須照常運作（可回滾）。目標：把『單位鍵』這個結構性決定落地，**對使用者看得見的行為完全不變**。

**1. DDL 放在哪裡（0d M2）**：`db._MIGRATIONS` 已凍結在 V9 基準 118（`test_v9_baseline`），**U0 不動它**。做法：①用 **`core` 的模組 migration**（`module_schema_versions` 的 `core` 由 9 升為 10），全部寫成**冪等**（表／欄位先檢查是否存在，沿用 `_col_exists`）；②屬於 `db.py` 基準內的表（案件、報價單、使用者、稽核、通知…）由這個 core migration 補欄；③**模組自有的表**（`permmatrix` 五張表、各模組 migration 建的表）由該模組自己的 migration 升版補欄（U0 只做 core 與 `permmatrix`，其餘隨 U1／U3 逐模組；各表屬哪一邊由 U0 開工第一件事的掃描定案，UNKNOWN）。因此 **U0 結束時 `owner_unit_id` 並未覆蓋全部表**，覆蓋率由守門棘輪追蹤（只增不減）。
**對步驟檔／驗證／回滾的影響（必須同班更新）**：
- 套用步驟檔 #12：`schema_version` 仍 **118**；`module_schema_versions` 的 `core` 由 9 → **10**（若同班有模組 migration，該模組也 +1），**不再是『全部列完全相同』**；`sqlite_master` 表清單**多出**新表（`org_units`、`org_unit_closure`、`user_units`、`system_settings_unit`、`seq_by_entity`）；既有表欄位清單改為『只多出 `owner_unit_id`／`unit_id`』。
- `verify_package`、VR7（需資料庫快照）與 `--expect-db-version`：版本仍 118；欄位清單類檢查（若有）的基準檔要同班更新；`table_digests` 要排除新欄位（見 #4）。
- **演練範圍（交 0d 並行審查，約 10-20 提供核心遷移與演練腳本）**：回滾演練必須涵蓋 ①舊 loader 對 `module_schema_versions.core=10` 的容忍度；②`verify_package`／VR7（含 `--expect-db-version 118` 與欄位清單基準）；③套用步驟檔 #12 的新預期（`core` 9→10、新表、既有表只多出 `owner_unit_id`／`unit_id`）；④從 MS1c 狀態升級再回滾的完整流程。
- **回滾**：舊程式忽略多出的欄位與表（加法）；但 **`module_schema_versions.core=10` 領先舊程式所知的 9**——舊 loader 是否容忍較高的已記錄版本**不得假設**，必須在建包前的**回滾演練**實測；若不容忍，回滾工具需在同一動作內把該列還原（寫進回滾步驟）。步驟檔回滾文字要明寫『資料庫保留新欄位與新表、不還原；若使用者要求還原資料庫，用套用前備份』。

**2. 核心表加欄**：約 **25～30 張**核心業務表加 `owner_unit_id INTEGER NOT NULL DEFAULT 1`（SQLite `ADD COLUMN … DEFAULT` 為 O(1)、不重寫整表；索引分批補）；`audit_log`、`notifications` 加 `unit_id DEFAULT 1`。

**3. 序列（0d M1：不改主鍵）**：**不動** `quote_seq(month)` 的主鍵與 `ON CONFLICT(month)` 寫法（`quotations.py` 依此；改成複合鍵＝重建表、破壞加法規則，且回滾到舊程式後會無法配號）。改為**新增** `seq_by_entity(entity_id, kind, period, seq, PRIMARY KEY(entity_id, kind, period))`：**根法人永遠使用既有序列表（原樣）**，只有非根法人（功能開啟後才存在）使用新表。傳票（`YYYYMMDD-NNN`，`next_voucher_no(conn, voucher_date)`）與勞報單（`PS-YYMM-NNN`，`next_slip_no`）的計數邏輯**U0 開工時逐一讀碼確認**其取號方式（查最大值或獨立序列）；若是『查資料表最大值』，則在 U2 加上法人條件，U0 不動（UNKNOWN，需讀碼）。

**4. `SELECT *` 外洩（0d S2：U0 並非零改動）**：掃描顯示約 **269 處** `SELECT *` 在 `modules/`、**85 處**在 `archive.py` 匯出、11 處在 routers、10 處在 helpers；表加欄後，`owner_unit_id` 會**洩進 API 回應、匯出檔與 `table_digests`**。U0 交付（**r4：防線放在 U0a，不等 U0b**）：①**回應鍵集**——先在 MS1c 凍結樹（`d995e5be4ca4dc163fde5fafd11f8a0a4fc69243`；MS1c 套用後即正式機 commit）上**記錄基準**（**須涵蓋 Excel／CSV 匯出表頭，並有正對照：故意不剝除的端點必須使檢查轉紅**，否則檢查本身可能是假綠燈）；U0a 含**最小回應鍵集檢查**（涵蓋 `SELECT *` 的路由與匯出路徑），**『與基準 diff 為空』是 U0a 的凍結條件**；完整金標（對約 830 路由）在 U0b 補齊；②**預設序列化時剝除**內部欄位（集中的 `strip_internal_cols`，功能開啟後才輸出給有權限者）；③`archive.py` 匯出與備份工具改為明列欄位或剝除；④`table_digests`／資料庫健檢的欄位清單基準更新。這是 U0 人日從 6～9 上修到 **9～13** 的主因。**切分**：U0a（含中央剝除 `strip_internal_cols`、`archive.py`／`table_digests` 處理、最小回應鍵集檢查）7～9 人日；U0b（完整金標＋AST 棘輪＋模組自有表補欄）2～4 人日。**U0a 套用當天欄位就不得外洩**，否則 `SELECT *`（269／85／11／10 處）會在 U0a 與 U0b 之間的數日漏出新欄位。

**5. 其他預留**：`perm_role_caps`、`perm_user_overrides` 加 `scope_json`（可為空＝全部）；新表 `user_units`（全部使用者歸根）、`system_settings_unit`（空）；設定宣告加 `scope` 屬性（預設 `global`）。

**6. 守門（棘輪）**：①新建的業務表若沒有 `owner_unit_id` 且未標 `global`，建包前即紅（基線只減不增；宣告方式見主檔 §4.6 第 7 點，與脊柱掃描同形）；②**未經範圍讀取的 AST 棘輪（0d S3）**：掃描對帶 `owner_unit_id` 的業務表的 SELECT，凡不經 `filter_sql`／核准的查詢 helper 者，必須在基線登記（`unscoped_reads_baseline.json`），**只准縮小**；U0 交付掃描器與起始基線，U1 起對案件領域強制。

**7. 開關（0d S-b）**：單位功能是否啟用，**不另設設定旗標**，而是一個宣告的功能（`org_units`）的狀態。**但 `spine.feature_enabled(code)` 對『未宣告』的功能回傳 True（脊柱是 fail-open）——單位強制若直接用它，刪掉宣告就會把過濾打開或關掉到錯誤方向。** 因此規則是：**啟用＝『已在 `core/features_l1.json` 宣告為 `org_units`』且『狀態＝open』**，兩者缺一即視為關閉；U0 在該檔宣告 `org_units`＝`planned`。測試：**刪除宣告後範圍過濾必須仍為關閉（恆真）**，且不影響任何現有查詢結果。關閉時所有範圍過濾恆真、介面不出現單位選項。
**8. 不做**：任何過濾、介面、對使用者看得見的行為改變。
**不做這一步的代價**：日後每張表要重建（SQLite 改約束＝建新表搬資料）、所有寫入點補參數；越晚做，資料越多、風險越高。

### 14.11 對既有產物的影響
- **`case_read_scope.json`**（目前三類：`row_access`、`module`、`own_rule`）：每條路由加欄 `unit_filter`：`via_case`（經案件單位）｜`own`（記錄自帶單位）｜`global`。**`module` 類（CORE-SPEC Z-5：『有該模組即可看全部案件的子資料』）——使用者 10-13 答覆：由使用者『依模組』自行設定，沒有統一預設**：`case_read_scope.json` 的 `module` 列改為『**可設定，預設＝全部案件（今天的行為）**』，設定值只存在**權限頁**（一個閘只有一個家，設定中心不另設同名項）。
  | 方向 | 分類 | 規則 |
  |---|---|---|
  | `限單位範圍` → `全部案件` | **放寬** | 另一位最高管理者核准＋確認期間＋影響預覽（『N 位使用者將多看到 M 筆』） |
  | `全部案件` → `限單位範圍` | 收緊 | 即時生效，仍顯示影響預覽（『N 位使用者將少看到 M 筆』） |
  | 單根單位（尚未啟用單位功能） | — | 兩個值的行為完全相同（過濾恆真），設定值照存 |
  **守門測試**：①**儲存值＝實際行為**（對每個設定為『限單位範圍』的模組，建立兩個平行單位的案件，驗證該模組的子資料端點確實過濾；設為『全部』則不過濾）；②**預設值等於今天的回應**（金標：單根單位下所有 `module` 類路由的回應與改版前逐位元相同）；③`case_read_scope.json` 的每條 `module` 路由必須有可查得的設定項，缺漏即紅。
- **逐案守門／`row_access`**：`OwnerRule` 增加單位規則；`filter_sql()`／`visible()` 繼續是唯一來源（單位條件走閉包表子查詢＋索引）。
- **報表／儀表板（analytics）**：所有彙總以範圍過濾；母單位可『合併』或『逐單位』；快取鍵必須含範圍；跨單位彙總不得含使用者無權看的明細（只給總數時也要確認不洩漏小樣本）。
- **設定中心**：群組顯示『範圍』（全域／可覆寫）、繼承來源；E-b 的功能狀態維持全域。
- **匯出／PDF／信件**：模板解析身分（抬頭、帳號、寄件人）依單據所屬法人。
- **備份**：整份備份不變；新增『單位匯出』工具屬後期。

### 14.12 風險
| 風險 | 對策 |
|---|---|
| **漏過濾＝跨單位外洩**（最大風險） | **強制點不是單一的**（0d S3：`case_read_scope.json` 只涵蓋 52 條案件 GET 路由，其餘業務表有大量直接 SQL 讀取）：集中點（`row_access`、`guard_case_access`、`filter_sql`）＋**未經範圍讀取的 AST 棘輪**（§14.10 #6，基線只減不增）＋逐領域強制；跨單位金標（建立 2 個平行單位、各 N 筆，逐路由驗證互不可見）；搜尋、自動完成、儀表板、通知、匯出逐一測 |
| 效能（每查詢多一個子樹條件） | 閉包表＋`owner_unit_id` 索引；快取可見單位集合（隨權限版本失效）；單根單位時恆真省略 |
| 法定連號被誤共用 | 非根法人使用 `seq_by_entity`（鍵含法人），根法人沿用既有序列；金標：兩法人各自連號；H-D 不可編輯；回滾演練證明舊程式仍能配號 |
| `SELECT *` 把單位欄位洩進 API／匯出／`table_digests` | §14.10 #4：回應鍵集金標＋預設剝除＋匯出與健檢基準更新 |
| 設定繼承造成『為何是這個值』難查 | 設定中心逐項顯示來源；變更紀錄含單位 |
| 使用者多單位時權限混淆 | 『依人看』按單位預覽；建立資料必選單位並顯示 |
| 簽核跨單位繞過 | 簽核人目錄預設限子樹；跨單位須明確列入；H5 不變 |
| 母子連結關閉／改樹造成存取驟變 | 改樹＝高影響；預覽『N 人將失去/取得 M 筆』；快照可還原；樹的環狀偵測與深度上界（沿用 H8 精神） |
| 遷移鎖表／時間 | `ADD COLUMN DEFAULT` O(1)；索引分批；先在備份副本演練並計時（沿用 M2 的 8 小時教訓） |
| 範圍複雜度蔓延（自訂維度過多） | 每個物件可帶的維度數上界；第一期只做 `org_unit`＋最多 2 個自訂維度（上界寫死，管理者只能調小） |
| 「單位樹」被當成硬隔離 | 文件與介面明講：硬隔離＝獨立安裝（§14.8） |
