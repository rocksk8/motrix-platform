## 14 資料範圍維度與組織單位（多據點／多法人；使用者 10-13 14:15 裁示 r2 增補）

> **使用者裁示（經 1c 轉達）**：①排程由 PM 安排，本稿給選項與人日；②**資料範圍的自訂維度（部門、客戶、專案類型…）= YES，是框架核心**；③『哪些欄位只有最高管理者看得到』**也由框架設定**，不寫死（只有 H5 稽核、6 項鎖死簽核、不得自我鎖死維持寫死）；④**新需求**：跨區域／多據點／多法人必須可分離，例如『A 分公司、B 母公司』：母公司依設定看得到子公司，**平行單位預設互相隔離**。
> 本節把 §4.5『資料範圍不進矩陣』**改為**：資料範圍是矩陣的第二個軸（授權時可帶『範圍』），組織單位樹是第一個內建維度。**§4.5、§6.2、§12 已依此改寫。**

### 14.1 兩個概念，先分清楚
| 概念 | 回答的問題 | 例 |
|---|---|---|
| **法人（legal entity）** | 這份單據**法律上屬於誰**：統編、抬頭、帳冊、法定連號、稅務申報 | B 母公司、A 分公司（若獨立報稅則是另一法人） |
| **組織單位（org unit）** | 這份資料**歸誰管、誰看得到**：資料範圍、簽核、通知、設定覆寫 | 母公司 → 北區、南區、A 分公司… |
- **做法**：一棵**單位樹**；樹上的節點可標 `is_legal_entity`；每個節點的『所屬法人』＝自己或最近的有標記的祖先。這樣『同一法人的多個據點』與『多個法人』用同一個結構表達，不需要兩套。
- **現況事實**：今天已有兩個**局部**概念——①`departments`／`divisions`（v48，純組織分類；`users.department_id`、`projects.department_id`，簽核流程的『部門主管』展開用）；②`company_profile.locations`（據點，只決定**單據抬頭與匯款帳號**，`helpers/company_identity.py`，使用者 2026-09-22『我們有分公司』）。**兩者都不控制『誰看得到什麼』，也沒有法人之分。** 本設計把它們收編為單位樹的特例（部門＝單位、據點＝帶抬頭的單位），遷移見 §14.9。

### 14.2 自訂範圍維度（框架核心）
- **維度宣告**：`scope_dimensions(key, label, kind tree|flat, applies_to[物件鍵])`，值表 `scope_values(dimension, id, parent_id, label)`。內建維度 `org_unit`（樹、必填、所有業務物件都有）；其他維度（客戶群、專案類型、部門…）由最高管理者在畫面定義，**物件可選擇帶哪些維度**（欄位值存在記錄上）。
- **授權帶範圍**：矩陣的一格從『角色 × 能力』擴成『主體 × 能力 × **範圍**』，範圍＝每個受限維度的值集合（含子樹旗標）。未指定範圍＝『全部』＝今天的行為。判定：一筆記錄可被存取 ⇔ 存在一個授權，其能力相符，且對**該授權有限制的每個維度**，記錄的值落在範圍內。
- **與逐案守門並存**：擁有者／成員／被指派（`row_access.OwnerRule`）仍是『個人關係』軸；範圍維度是『組織／分類』軸；**兩者是 OR 的放寬（個人關係可跨範圍看自己的案）還是 AND 的收窄，需使用者確認（§12 確認 7；預設：範圍是硬邊界＝AND，個人關係只在範圍內有效）。**

### 14.3 每筆記錄的所屬單位（`owner_unit_id`）
| 領域 | 所屬單位怎麼定 | 備註 |
|---|---|---|
| 案件／報價單／額外支出／材料申請／完工單／出貨 | 建立當下由建立者選擇（預設＝其主要單位）；子單據**繼承案件的單位**，不可獨立改 | 轉單位＝有權限者的明確動作，寫稽核（H-E） |
| 財務（請款、開票憑據、匯款、出納） | 繼承案件；無案件者取建立者所選 | 金額帳冊按**法人**切 |
| 薪資（勞報單、獎金） | 承攬人／員工所屬單位（可選）；預設繼承案件 | 個資高度敏感，預設最嚴 |
| 採購／庫存 | 倉庫（或 SKU 批次）屬於某單位 | 跨單位調撥是明確動作 |
| 會計（傳票、總帳、稅務） | **所屬法人**（帳冊獨立） | 法定連號按法人切（見 14.4） |
| 主檔（客戶、供應商、承攬商、料號） | 三選一（每類主檔宣告預設）：**全域共用**／**單位專屬**／**共用給指定單位** | 預設＝全域共用（今天的行為） |
| 附件、稽核紀錄、通知 | 隨所屬記錄；稽核另存 `unit_id` | 母公司稽核員可依設定看子單位稽核 |

### 14.4 單位對各領域的影響
| 領域 | 今天（事實） | 多單位後 |
|---|---|---|
| **編號** | 報價單 `quote_seq(month)` 全域一條；傳票 `YYYYMMDD-NNN`；勞報單 `PS-YYMM-NNN` | 序列鍵加上**法人**（`(entity, 期間)`）；前綴可按法人設定；**法定連號（傳票、稅務發票號）絕不可跨法人共用**（H-D） |
| **稅務／抬頭** | `company_profile` 單一份＋`locations`（抬頭／匯款帳號） | 按法人持有統編、抬頭、帳號；單據依所屬法人取身分（`company_identity` 已是這個形狀） |
| **簽核** | 每種單據的 tiers 由簽核流程設定挑人；簽核人目錄 | 流程可按單位覆寫（沿用上層）；簽核人預設限『該單位子樹內』，跨單位需明確列為『跨單位簽核人』（H5 目錄原則不變） |
| **角色／權限** | 全域角色＋模組勾選 | 使用者在**某單位**擔任某角色（見 14.6）；能力授予帶範圍（14.2） |
| **設定** | `system_settings` 全域鍵值 | 見 14.5 |
| **信件／通知** | 全域收件設定、信件類型 | 寄件身分與收件人按單位解析；通知收件人預設限單位範圍，避免洩漏跨單位內容 |
| **備份／還原** | 單一資料庫整份備份 | 見 14.8；整體備份仍整份，單位匯出為獨立工具 |
| **匯出／報表** | 依角色與金額遮蔽 | **範圍篩選永遠先套用**；母單位可選『合併』或『逐單位』檢視 |
| **附件儲存** | 儲存位置代號＋子夾（建構器插槽） | 位置代號可按單位指定不同根目錄（根仍由部署決定） |

### 14.5 設定的範圍：全域 vs 單位，繼承與覆寫
- **宣告**：設定群組／鍵新增選填 `scope`：`global`（預設，今天的行為）｜`unit`（可按單位覆寫）。法規／安全類（如確認期間下限、備份最低保留、H 層上界）**固定 `global`，單位只能收緊不能放寬**。
- **解析順序**：該單位的覆寫 → 沿父鏈往上最近的覆寫 → 全域預設。**繼承顯示**：設定中心每個值標『來自：本單位／上層「母公司」／全域預設』。
- **儲存**：`system_settings_unit(unit_id, key, value_json)`（只存與繼承不同者）；寫入走同一條發布管線（`config_ledger` 領域加 `unit_id`），**放寬判斷以『相對於繼承值』為準**。
- **誰能改**：全域設定＝最高管理者；單位設定＝可授予『單位管理員』能力 `org.unit.config`（範圍＝該單位子樹；低風險立即、高影響仍走雙人核准）。
- **權限頁同理**：能力格也可按單位覆寫（A 分公司的『業務』能做的事可以與母公司不同）。

### 14.6 使用者屬於多個單位
- `user_units(user_id, unit_id, is_primary, role_binding)`；一個人可在多個單位各有不同角色（A 分公司業務＋母公司財務）。
- **生效權限＝各歸屬的授權（帶範圍）取聯集**；禁止優先於允許，且『禁止』可指定單位。
- **建立資料時**必須選『所屬單位』（只列其有建立權限的歸屬；預設主要單位）；清單與搜尋以『可見單位集合』過濾。
- **預覽**：權限頁『依人看』增加**單位切換**：選一個人＋一個單位 → 他在該單位『能做什麼、看得到哪些資料範圍』；另有『他在所有單位的總覽』與『某筆記錄為何他看得到／看不到』（逐步說明：單位、範圍、個人關係、能力）。

### 14.7 跨單位可見性規則（預設值與可設定）
| 關係 | 預設 | 可設定 |
|---|---|---|
| 同單位 | 依角色能力 | — |
| 母 → 子（祖先看子孫） | **看得到**（使用者：『母公司依設定看子公司』）；每條母子連結有旗標 `parent_sees_children`（預設開） | 可逐連結關閉；可限制為只看『彙總』不看明細 |
| 子 → 母 | **看不到** | 明確授權（例如把某客戶共用給子單位） |
| **平行（A 分公司 ↔ 其他分公司）** | **互相隔離**（使用者要求） | 明確『共用』：某記錄類型或某主檔指定共用給某單位（唯讀或可編輯，雙方單位管理員核准） |
| 跨單位簽核人 | 不允許 | 明確列入簽核人目錄 |
- 放寬任何一條（母看子的明細、平行共用）屬**高影響**（雙人核准＋確認期＋影響範圍預覽『N 位使用者將看到 M 筆記錄』）。

### 14.8 單一資料庫＋單位鍵 vs 每單位獨立資料庫
| 面向 | 單一庫＋`owner_unit_id` | 每單位一個庫（或一個安裝） |
|---|---|---|
| 隔離強度 | **靠程式**（每個查詢必須帶範圍）；漏一個就外洩 → 以集中過濾＋金標測試緩解 | **硬隔離**（檔案層分開），管理員誤操作也看不到 |
| 母公司合併檢視 | 天然支援（同庫彙總） | 需要跨庫彙總（ETL／聯邦查詢），成本高、延遲 |
| 使用者／權限 | 一份帳號、多單位歸屬 | 帳號每庫一份或另做聯邦 |
| 升級／維運 | **一次升級一個庫**（現有 `apply_update`／備份／建包流程不變） | ×N（版本漂移、N 次套用與驗證） |
| 共用主檔（客戶、料號） | 容易（單位鍵或共用旗標） | 需同步 |
| 法人分離（獨立帳冊、賣掉子公司） | 以法人鍵切；**單位匯出／分拆工具**需另寫 | 天然（直接交出該庫） |
| 備份／還原 | 整份；單位級還原困難 | 各自獨立，簡單 |
| SQLite 並行 | 共用寫鎖（現況本來就是單庫） | 各自寫鎖，互不干擾 |
| 資料落地規範（不同地區法規要求資料不得同機） | 無法滿足 | 可滿足（分機部署） |
**建議**：**單一資料庫＋強制 `owner_unit_id`＋集中強制點＋法人鍵切帳冊**，理由：符合『母公司看子公司、同一套帳號與升級』；產品本來就是『一個安裝＝一家公司』，**真正互不相干的公司（不同集團、不同資料落地要求）應該各自一個安裝**（現有 `install_identity` 模型），不必在一個庫裡硬塞。保留未來『單位匯出／分拆』工具作為出口（U4）。**使用者若需要『管理員誤操作也不可能看到』的硬隔離，答案是獨立安裝，不是單位樹**（§12 確認 8）。

### 14.9 遷移：今天的單一公司＝一個根單位，行為完全相同
1. 建單位樹，只有**根單位**（＝今天的公司；標 `is_legal_entity`；承接 `company_profile`、`locations` 轉成根下的『據點型』子單位或抬頭設定，**抬頭解析結果逐字相同**）。
2. 所有業務表加 `owner_unit_id`（預設根單位＝1）；所有使用者歸屬根單位（主要）；所有設定 `scope=global`；所有序列的法人鍵＝根；所有授權範圍＝『全部』。
3. **單位感知功能由旗標 `multi_unit_enabled`（預設關）啟動**：關閉時所有範圍過濾為恆真、介面不出現單位選項。
4. **等價關卡**：①有效權限快照（§10）前後相同；②每個清單／搜尋／匯出／儀表板在單根單位下的結果前後逐列相同（金標）；③編號序列的下一個值前後相同。
5. 回滾：旗標關閉即回到單根行為；`owner_unit_id` 欄位保留（無害）。

### 14.10 現在就做的最小預留（成本小、避免日後改結構）
**目標：把『單位鍵』這個結構性決定現在落地，行為完全不變。** 一班 migration＋守門，約 **6～9 人日（估）**：
1. 建 `org_units`（含根列）與 `org_unit_closure(ancestor, descendant, depth)`（子樹查詢用的閉包表，空樹只有根自連）。
2. 約 **25～30 張核心業務表**加 `owner_unit_id INTEGER NOT NULL DEFAULT 1`（SQLite `ADD COLUMN … DEFAULT` 是 O(1)、不重寫整表；索引分批補）；`audit_log`、`notifications` 加 `unit_id DEFAULT 1`。
3. 序列表（如 `quote_seq(month)`）改成 `(entity_id, month)` 複合鍵——**這張最小，現在做最便宜，之後要重建主鍵很痛**。
4. 權限覆寫表（`perm_role_caps`、`perm_user_overrides`）加 `scope_json` 可為空（空＝全部）。
5. 新表 `user_units`（全部使用者歸根）、`system_settings_unit`（空）、設定宣告加 `scope` 屬性（預設 `global`）。
6. **守門（棘輪）**：新建的業務表若沒有 `owner_unit_id` 且未標 `global`，建包前即紅（仿既有表單守門）；既有表基線只減不增。
7. **不做**：任何過濾、介面、行為。
**不做這一步的代價**：日後每張表要重建（SQLite 改約束＝建新表搬資料）、序列要遷移、所有寫入點補參數；越晚做，資料越多、風險越高。

### 14.11 對既有產物的影響
- **`case_read_scope.json`**（目前三類：`row_access`、`module`、`own_rule`）：每條路由加欄 `unit_filter`：`via_case`（經案件單位）｜`own`（記錄自帶單位）｜`global`。**尤其 `module` 類（CORE-SPEC Z-5：『有該模組即可看全部案件的子資料』）在多單位下必須改成『有該模組且案件在你的單位範圍內』**——這是一項**語意變更，需使用者確認**（§12 確認 7）；單根單位下結果不變。守門測試 `test_case_read_scope.py` 擴充。
- **逐案守門／`row_access`**：`OwnerRule` 增加單位規則；`filter_sql()`／`visible()` 繼續是唯一來源（單位條件走閉包表子查詢＋索引）。
- **報表／儀表板（analytics）**：所有彙總以範圍過濾；母單位可『合併』或『逐單位』；快取鍵必須含範圍；跨單位彙總不得含使用者無權看的明細（只給總數時也要確認不洩漏小樣本）。
- **設定中心**：群組顯示『範圍』（全域／可覆寫）、繼承來源；E-b 的功能狀態維持全域。
- **匯出／PDF／信件**：模板解析身分（抬頭、帳號、寄件人）依單據所屬法人。
- **備份**：整份備份不變；新增『單位匯出』工具屬後期。

### 14.12 風險
| 風險 | 對策 |
|---|---|
| **漏過濾＝跨單位外洩**（最大風險） | 單一強制點（`row_access`、`guard_case_access`、`filter_sql`）；AST 守門：業務表的 SELECT 未經強制點即紅；跨單位金標（建立 2 個平行單位、各 N 筆，逐路由驗證互不可見）；搜尋、自動完成、儀表板、通知、匯出逐一測 |
| 效能（每查詢多一個子樹條件） | 閉包表＋`owner_unit_id` 索引；快取可見單位集合（隨權限版本失效）；單根單位時恆真省略 |
| 法定連號被誤共用 | 序列鍵含法人；金標：兩法人各自連號；H-D 不可編輯 |
| 設定繼承造成『為何是這個值』難查 | 設定中心逐項顯示來源；變更紀錄含單位 |
| 使用者多單位時權限混淆 | 『依人看』按單位預覽；建立資料必選單位並顯示 |
| 簽核跨單位繞過 | 簽核人目錄預設限子樹；跨單位須明確列入；H5 不變 |
| 母子連結關閉／改樹造成存取驟變 | 改樹＝高影響；預覽『N 人將失去/取得 M 筆』；快照可還原；樹的環狀偵測與深度上界（沿用 H8 精神） |

### 14.14 §12 補充確認（可用預設前進）
7. **範圍與個人關係的關係**：預設＝範圍是硬邊界（AND）；個人關係（擁有者／成員／被指派）只在範圍內有效。另，`module` 類『有模組即可看全部案件子資料』在多單位下改為『且在你的單位範圍內』（單根單位不變）。
8. **隔離強度**：單位樹是『程式強制的邏輯隔離』；若要硬隔離（管理員也不可能看到），請用獨立安裝。預設：邏輯隔離。
9. **法人 vs 單位**：A 分公司是否為獨立法人（獨立統編、帳冊、連號）？預設：由最高管理者在單位上標記，未標＝沿用上層法人。
10. **母看子**：預設『看得到明細』，可逐連結改為『只看彙總』或關閉。
