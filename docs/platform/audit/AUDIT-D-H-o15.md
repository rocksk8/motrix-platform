## 0. 結論

## 1. 主持重點

| 項目 | D 的驗證 | 結果 |
|---|---|---|
| 修法 | `fetchRefOptions` 以 `try/catch` 包住 `this.api(...)`；例外 ⇒ `r = {ok:false, status:'network'}`，走原本的 error 分支（下拉＋可重試）。序號比對仍在 catch 之後、更新狀態之前 | 成立 |
| 真的 403 不會被誤導 | `_json` 解析本文失敗時不丟例外（非 JSON 本文放進 `data`），只有網路層讀不到本文才丟 ⇒ 伺服器回的 403（不論本文）仍是 `status 403` ⇒ `denied`（改手動輸入）。突變「網路失敗當 403」⇒ 紅 | 成立 |
| 重試與序號防護不衝突 | 重試呼叫同一支 `fetchRefOptions`，序號遞增；較舊的回應在序號比對處丟棄。重試進行中畫面停在 error（`refState` 已有值不重設為 loading），這是既有行為 | 成立 |
| 錯誤訊息不外洩 | 畫面只顯示「讀取選項失敗（network）」；例外物件本身不顯示 | 成立 |
| 新題 | `route.abort` 決定性重現 ⇒ `data-ref-state="error"`、仍是 `SELECT`；取消攔截按重試 ⇒ `ok` 且選項有資料；無 pageerror。整檔 12 過。突變「拿掉 try/catch」⇒ 紅（等不到 error 狀態） | 成立 |

## 2. 觀察

- **O15-O1**：同頁其他請求（列表、儲存、狀態轉換、核准退回）都有 `try/finally`，網路層失敗時不會卡在 loading／busy；但例外沒被接住，畫面不會出現任何錯誤訊息（使用者按了儲存、網路斷掉，只看到按鈕恢復）。不在本包範圍，建議之後比照處理。
