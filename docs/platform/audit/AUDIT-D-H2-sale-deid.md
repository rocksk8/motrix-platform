## 1. T1：凍結 migration 裡的本公司字面值

### 1.1 先分類：db.py 裡的字面值有三種，處理方式不同

| 類 | 位置（origin/platform） | 作用 | 會不會執行到 |
|---|---|---|---|
| A 註解／docstring | :763-768 的註解、`_m106` docstring、:4445、:4894 附近的 docstring | 不影響行為 | — |
| B 守門條件（拿來比對） | `_m106` 的統編相等判斷；`_m008` 的舊顯示名清單、`username=` 條件 | 決定要不要動 | 每次跑 migration 都會比對 |
| C 寫進庫的值（payload） | `_m106` 的公司英文名；`_m008` 的真實人名與個人 email | 只在 B 成立時寫入 | 只在「開發者自己的資料」上 |

C 類的可達性（這是解題的關鍵）：
- 全新安裝：migration 跑在空表／空種子上 ⇒ B 不成立 ⇒ C 不執行
- 災難還原：還原的庫已記錄這些 migration 版號 ⇒ 不再執行
- 其他客戶的既有庫：B 比對的是開發者的統編與舊帳號名 ⇒ 不成立（`_m008` 的帳號名是常見英文名，但它只在 migration 當下存在該帳號、且 email 為空時才寫；目前沒有其他客戶的 V9 庫）
- **唯一會走到 C 的**：把開發者自己的 V9 庫再轉換一次（演練、重建正式機）

### 1.2 為什麼文件提的 ① 與「sale 投影」都不行

- **① 讀 own 專用檔（沒有釘住內容）**：同一支 migration 的結果取決於「這個包有沒有那個檔」。sale 包在一個 B 成立的庫上會**成功完成**、記下版號、而沒有回填 ⇒ 之後換 own 包也不會再跑。兩種包各自寫出一段不同的歷史，而且沒有錯誤訊息＝〈凍住的歷史不要呼叫活的程式碼〉要防的「歷史被重新詮釋」
- **sale 包投影 db.py（建包時改寫程式碼）**：
  - 出貨的 `db.py` 跟 git blob 不同 ⇒ 逐檔對 git blob 的出貨驗證失效
  - 測試跑的是 repo 的程式碼，客戶跑的是另一份
  - 全新安裝與災難還原在 sale 與 own 之間走不同的 migration

### 1.3 建議做法（不讀活檔、sale 與 own 的歷史一致或明確拒絕）

1. **A 類（註解）**：直接改寫成不含識別值的文字。證明行為不變：一題把舊版（`git show <舊 commit>:backend/db.py`）與新版的每一支 `_mNNN` 編譯後比較 `co_code`＋`co_consts`（排除 docstring）⇒ 必須逐一相等
2. **B 類（守門）**：就地改成雜湊比較，只用標準庫、不讀任何外部檔。例：`hashlib.sha256(x.strip().encode()).hexdigest() == "<常數>"`；`_m008` 的 `IN (...)` 改成先在 Python 端以雜湊集合篩出 id 再 UPDATE。
   - 這**不違反**〈凍住的歷史不要呼叫活的程式碼〉：沒有呼叫任何會演進的程式碼，只把比較的兩邊一起換成同一個函數的輸出
   - 對所有輸入逐一等價（雜湊碰撞可忽略）；strip／大小寫等前處理必須與原比較完全相同
   - 證明：契約題以**舊版函式**（從舊 commit 載入）與新版函式跑同一組語料（全新庫、開發者形狀的庫、客戶形狀的庫、空白與全形變形），比對執行後的整庫內容逐位元組相等
   - 雜湊可被窮舉還原（統編 8 碼、帳號名很短），這與 T3（統編屬公開登記資料）同一個接受理由；目的是「不再有可 grep 的明文」
3. **C 類（寫進庫的值）**：搬到一個**內容被釘住的凍結資料檔**，例如 `backend/migrations_frozen/own_payload.json`，只隨 own 包出貨（`sale_prune.json` 剪掉）：
   - migration 內寫死這個檔的 sha256；只在 B 成立時才讀
   - 檔不在或雜湊不符 ⇒ **丟例外**（migration 失敗、啟動失敗、整包回滾），不可以跳過並記下版號
   - 資料檔被釘住就不會演進，所以不是「活的程式碼」；sale 與 own 的結果只有兩種：**相同**，或 **sale 明確拒絕**，不會出現「兩段都成功而不同」的歷史
   - 讓 sale 包永遠不會走到拒絕：
     - 全新安裝與災難還原走不到（§1.1）
     - 開發者資料的庫在 sale 包上要先被擋：V9 轉換工具與 apply 預檢以 E4 的開發者指紋判定，命中就拒絕並說明「請用 own 包」
   - 題：sale 全新安裝跑完全部 migration ⇒ 不丟例外，且整庫以 HMAC 清單掃描 0 命中；開發者形狀的 V9 庫＋own 檔 ⇒ 與舊版函式結果逐位元組相等；開發者形狀的庫＋沒有 own 檔 ⇒ 丟例外（反向控制）
4. 優先順序：`_m008` 的 C 類是**真實人名與個人 email**（個資），比公司英文名（Q1 的預設 LOGO 圖裡已經有）更該先處理

## 3. 建議

- **H2-S1　投影要能從 git 重算**：version_manifest 投影與剪裁讓 sale 包不再逐檔等於 git blob。`deploy_manifest.deid` 記下投影的輸入（基準版號、overlay 檔的 blob 雜湊、剪裁清單的 blob 雜湊），並提供一支重算工具：由 commit＋這些輸入重建出一模一樣的 version_manifest.json 與檔案清單。這樣出貨前的逐檔驗證可以改成「除了投影檔，其餘等於 blob；投影檔等於重算結果」
- **H2-S2　建包時的金鑰**：sale 建包要讀 HMAC 金鑰，而建包常由開發視窗的 Claude 執行。要寫明：建包腳本不印、不寫 log、不寫進 deploy_manifest 任何衍生值（除了 key_id）；金鑰路徑由參數或環境變數給，Claude 不讀內容（比照交付簽章金鑰）。或者比照簽章：sale 建包的「掃描」這一步由使用者執行
- **H2-S3　清單 30 天期限的落點**：「超過 30 天 ⇒ 拒絕建 sale 包」要求每月到正式機跑一次 export。建議正式機回報流程裡加一項「清單到期日」，並在到期前 7 天由開發機建包工具預先提示，免得急修時才發現不能出包
- **H2-S4　own 包的套用限制要等 E4 合回**：§2.2d 依賴 E4 的安裝識別檔與簽章確認檔。實作順序要寫明 E4 先合；在那之前 own 包的套用端檢查不可以用「讀不到 E4 ⇒ 放行」的方式過渡
