修完系統設定頁那支之後，e2e 整組連跑 3 輪：2 輪全綠，第 1 輪這支紅了一次
（單跑是綠的）。**與這一輪的改動無關**，是既有課題。

**已備妥的查法**（不要重跑整套 10 分鐘去等它重現）：

```
cd backend
python -m pytest tests/ -q -m "e2e" --basetemp <暫存目錄> --tb=short
```

**先檢查這兩個模式**，今天兩支 flaky 都是它們造成的：

1. **斷言打在會自我銷毀的元素上**——搜該頁的
   `setTimeout(() => ...Msg = '', N)`。訊息 N 秒後消失，測試卻等更久，
   等於「等一個已經死掉的元素」。改成斷言不會過期的契約（例如「請求有沒有送出」）。
2. **雙重初始化**（見 ④）——第二次載入的回應晚一步蓋掉前面的狀態。
   `python tools/check_double_init.py --todo` 看那頁在不在待修清單裡。

⚠️ **驗證時不要靠「數 conhost / 數行程」**，那是假綠燈（今天實測踩過：拿掉修正
照樣顯示 PASS）。要數就數「API 被呼叫幾次」這種確定性的東西。

## ④ 全站 Alpine 雙重初始化：47 頁待修　🟠 中（獨立課題）

**已備妥**：`backend/tools/check_double_init.py`（掃描＋風險排序，可重複跑）。

```
cd backend
python tools/check_double_init.py --todo
```

**問題**：`<body x-data="foo()" x-init="init()">` 在 Alpine 3 會讓 `init()` 跑兩遍
（Alpine 自己就會叫一次），**完全沒有警告**。第二次載入的回應晚一步抵達，會把
使用者這段期間改過的欄位用伺服器舊值**無聲蓋回去**。已經因此踩過兩次
（`case-management.js`、`company-profile-settings.html`，後者還是 e2e 偶發紅的根因）。

**修法**（兩行，沿用既有慣例）：

```js
_initDone: false,

async init() {
  if (this._initDone) return
  this._initDone = true
  ...
```

**先修這 9 頁**（🔴 高，可編輯面積最大）：

```
reports.html            quotation-form.html     suppliers.html
customers.html          access-guide.html       automation-guide.html
gateway-guide.html      monitor-guide.html      switch-guide.html
```

⚠️ 風險分級用 `x-model` 欄位數當代理，**會低估用 `:value`/`@change` 綁定的頁面**
——`settlement.html` 被分到 🟢 低但它其實是重編輯頁。排序拿來決定先後就好，
不要當成「低風險就不用修」。

**驗證**：比照 `test_e2e_system_settings_ui_2026_09_11.py::test_init_runs_exactly_once`
——數該頁的載入 API 被打幾次，必須是 1。那是確定性斷言，不必等競態重現
（實測：拿掉守門一定是 2、加上一定是 1）。
