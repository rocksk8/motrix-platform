### ~~1. 案件管理：合約資訊要跟報價單連動~~
**狀態**：✅ 已完成。三個待裁示點照建議做了——單向（報價單→案件）、
只在第一次建立 contract 時自動帶一次、已存在的案件用「從報價單帶入」按鈕
手動帶。不論自動或手動都**只填空白欄位、不覆蓋案件已有的值**。
（原始分析如下保留）

已查證**目前確實沒有連動**——所以這條成立：

| 位置 | 現況 |
|------|------|
| 報價單 | `q.deliveryAddress`、`q.deliveryTerms` 有這兩個欄位（`quotation-form.html`，且可選擇是否印在 PDF 上） |
| 案件管理 | `caseRecord.contract` 有同名的 `deliveryAddress`／`deliveryTerms`，但 `case-management.js` 初始化時一律給空字串，不讀報價單 |

要決定的事（動手前先問，不要自己選）：

- **連動方向**：報價單→案件單向帶入，還是雙向同步？單向比較安全——案件成立後
  現場條件本來就可能跟報價時不同，雙向會讓改案件反過來改到已簽核的報價單。
- **帶入時機**：只在「案件第一次建立時」帶一次（之後各自獨立），還是每次開啟都
  以報價單為準覆蓋？前者符合「報價是當時的約定、案件是現場的實況」。
- **已存在的案件怎麼辦**：現有案件的 contract 多半是空的，要不要補一次帶入。

另：`contactPerson`／`contactPhone`／`contractNote` 在報價單沒有對應欄位，
這三個維持案件自己填。

### ~~2. 業務開發與案件動態要能上傳照片／檔案~~
**狀態**：✅ 已完成（**DB v82**）。四個待裁示點的答覆：①multipart ②加浮水印
（含當天日期與 GPS）③刪附件限 admin+ ④不限張數與總量。
實作中踩到 `CURRENT_VERSION` 忘了 +1（migration 永遠不會執行），實機重啟才發現。
（原始分析如下保留）

跟前面那些純介面調整不同級別：要加欄位、改 API 契約、跑 migration，
使用者部署時要留意（目前正式機是 DB v81，這項會是 **v82**）。

**可重用的既有基礎**（不必從頭做）：

- `helpers/uploads.py::save_document_files()`——已處理 demo 帳號隔離、
  副檔名白名單（jpg/jpeg/png/pdf）、單檔 20MB 上限，回傳 metadata 陣列給
  呼叫端存進 JSON 欄位。報價單回簽／出貨單回簽／開票憑據三處已經在用。
- 既有的 `GET /api/uploads/{file_path:path}` 簽名 URL 服務端點，不必新增。
- `archive.py::_mirror_uploads()` 會自動把 uploads/ 增量同步到雲端備份，
  `_demo_` 前綴的目錄本來就排除，不必改備份邏輯。

**要加的東西**：

| 層 | 內容 |
|----|------|
| DB | `_m082_feed_attachments`：`case_updates` 與 `dev_logs` 各加 `files_json TEXT NOT NULL DEFAULT '[]'` |
| API | `POST /api/quotations/{no}/updates`、`POST /api/dev-cases/{id}/logs` 收檔案；GET 回傳 files |
| 前端 | 案件管理「動態」分頁、業務開發的開發記錄表單：上傳控制項 + 圖片縮圖／PDF 連結 |

**動手前要裁示的四件事**（不要自己選）：

1. **API 形狀**：現在這兩支 POST 收的是 JSON body。要改成 multipart
   （一次送出、無中間狀態，但改變契約），還是留 JSON、另開一支
   `POST .../{id}/files` 補傳（契約不變，但會有「文字存了、檔案失敗」的
   半完成狀態）？建議 multipart。
2. **照片要不要浮水印**：專案照片走 `photos.py` 會加浮水印與 GPS EXIF；
   單據附件走 `uploads.py` 不加。動態的照片算哪一種？
3. **誰能刪附件**：比照留言本身（發文者或 admin+），還是更嚴？
   已核准的開發記錄若還能抽換附件，等於審核過的內容可以事後被改。
4. **張數與總量上限**：單則幾張、單案總量多少。uploads/ 是會進雲端備份的，
   沒有上限的話備份會跟著長。

## 其餘模組分頁的盤點結果（2026-09-14）

原本估「約 20 頁需要改」，實際掃過之後**那個估計是錯的**。我修的是
「同一組數字用兩個控制項顯示」這個問題（上方統計條＋下方分頁），
而它只集中在少數幾頁，不是普遍現象：

| 頁面 | 盤點結果 |
|------|---------|
| `warranty` `procurement` | 有這個問題 → **已修** |
| `network-plans` | 沒有統計條，但有方向性流程只給了數字看不出比例 → **已修** |
| `devices` | 統計條看保固、分頁看成案狀態，**是兩個不同的軸**，不是重複 |
| `daily-tasks` | 統計條只有 3 格且不與分頁重複；頁面本身已有行事曆＋分組清單＋今日標記，已經在做視覺化管理 |
| `case-stage-board` | 2026-08-23 就是為跨案視覺化建的，已有逾期色階與時間桶分欄 |
| `customers` `suppliers` `parts` `payslips` `contractors` `vendor-contractors` `work-log` `settlement` `audit-log` `online-stats` | **沒有統計條也沒有分頁**，是純表格或主檔維護頁。沒有狀態或時效軸可以視覺化，套壓力帶只會變裝飾 |
| 選型導覽 7 頁、各設定頁、登入頁 | 同上，不適用 |
| `sales-orders` `cashier` `receivables` | 已退役的導向 stub |

結論：**這一套語彙該套的地方已經套完了**。剩下的頁面如果還有問題，
會是各自不同的問題（欄位太多、流程不順、缺欄位），要個別看，
不是再套一次壓力帶。

## 已知但尚未排入的既有問題

這些是改版過程中查到、與本次交辦無關的既有落差，記著避免重複發現：

1. **`deal_tag` 有兩個讀取口徑**：清單／矩陣走 `SQL_DEAL_TAG`（欄位優先、
   再退回 `data_json.dealTag`），但 `update_deal_tag()` 讀的是 `d.get("dealTag")`
   （只看 data_json）。正常寫入路徑會同步兩邊，但一旦不同步，矩陣會顯示案件為
   已成案、完結案卻回 400。
2. **開發機有一件已結案案件的進度關卡是 blocked**（`MQ-202607-126`，進度 4/5）。
   結案前置條件是 2026-08-26 才加的，之前結的案子沒被檢查過。
3. **營運報表的「近 12 月成案趨勢」是雙 Y 軸圖**（件數在左、金額在右）。兩個不同
   量綱疊在同一張圖上，線的相對高低沒有意義——這是圖表設計裡最典型的錯誤。
   要修的話得拆成兩張圖或改成指數化同基期。**已先補上數值明細表與軸上金額當緩解**
   （現在至少讀得到真實數字，不必靠線的相對高度去猜）。
4. **`frontend/js/reports.js` 的圖表色票停在舊主色藍** `rgba(37,99,235,…)`。
   2026-09-14 主色已改成品牌紅、儀表板的 `initCharts()` 也改成讀 CSS 變數，
   這一支沒跟上。順帶一提，「合約總額藍／已收款綠」這個配對對紅綠色盲的分離度
   偏低，換色票時要一起用色盲檢查跑過，不要只挑順眼的。
5. **檢索骨架（階段 5）未做**：`/api/dev-cases` 沒有 `limit`／`offset`、
   案件管理寫死 `limit=500` 全量拉回前端篩選、`/api/quotations` 缺業務員篩選與
   跨欄關鍵字。案件量長大之後會先撞到這裡。見 §12 第八輪的「長期檢索骨架」。
