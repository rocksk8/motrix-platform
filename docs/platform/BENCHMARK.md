## 1. 結論與建議優先序

**結論**：MOTRIX 在「單據、簽核、會計連動」這條主線上已經接近鼎新中小型方案的骨架。最大的風險不在功能少，而在**法規參數沒有生效日**：勞報單的稅率、門檻與最低工資只有一套，寫在 `routers/payslips.py:60-80`，修改舊單時會套用當下的規則；另外，**獎金分潤單沒有扣繳與二代健保**。2027 年最低工資已經審議為 30,900 元（尚待行政院核定），會直接影響兼職薪資的補充保費門檻，以及非居住者 6% 扣繳率的適用範圍。
自訂平台方向（CUSTOMIZATION-SPEC）與 NUEiP、Ragic 的做法一致，但簽核引擎還缺三項積木才撐得起「積木式流程」：會簽、並簽，條件分流，以及退回指定關卡。

### 2.2 值得借鏡

1. **單據性質（單別）參數化**：同一種單據可以有多個「單別」，各自設定編號、是否需要簽核、是否自動拋轉。對應 MOTRIX 的「單據類型＋簽核設定＋傳票科目設定」，目前這三項分散在 `approval_flow_scope`、`*_approval_flow` 與 `bonus_case_voucher_*_code`。建議在 P1 能力目錄把它們收斂成一份「單據類型描述」。
2. **自動分錄的「預覽→產生」與科目記憶**：MOTRIX 的 `helpers/bonus_vouchers.py` 已經是「產生草稿」模式，可以推廣到 A6、A7、A8b 的所有連接器；「科目記憶」可以用 `system_settings` 做每個客戶或廠商的對應。
3. **依金額設定簽核層級**（EasyFlow）：這是缺口清單第 4 項的直接依據。
4. **模組月租、依模組授權**（A1）：與 CORE-SPEC §9c「模組選配與啟停」方向一致，也印證「每個模組獨立販售」的商業模式在台灣中小企業市場有前例。

### 2.3 不適合 MOTRIX 的部分

| 項目 | 原因 |
|---|---|
| T100 的單一資料庫多集團、多營運中心 | MOTRIX 的客群是單一法人加分公司；已經有「據點」抬頭（`helpers/company_identity.py:19-30`），足夠了。多法人帳務會牽動會計科目、關帳與合併報表，成本高 |
| 製造模組（BOM、工單、MRP） | 工程業是以案件為核心，用料記在報價與出貨上，不需要生產排程 |
| 獨立 BPM 產品（EasyFlow）另外串接 | MOTRIX 的簽核內建在單據裡，這是優勢；拆成獨立產品會多一層同步（鼎新需要透過 Web Services 串接） |
| 顧問導入式的參數設定 | 目標客戶沒有 MIS，參數要有預設值加上說明，不能依賴顧問 |

### 3.3 「區塊自訂」讓非工程師建立功能的關鍵，以及它的限制

**做得到的原因**（兩家共通）：
1. **元件有限而且可列舉**：欄位型別是固定清單，公式只有少數函數。這正是 CUSTOMIZATION-SPEC §1「從目錄挑，不能寫程式」的做法。
2. **流程與表單分開定義**，流程關卡從組織資料取人（直屬主管、部門、欄位中的使用者），所以組織異動時不必改流程。
3. **權限設定在欄位層**，多人處理同一張表單時可以各看各的欄位。
4. **動作按鈕**（Ragic）把「狀態轉換加上寫入其他表」包成一個積木，相當於 MOTRIX 規劃中的「流程轉換掛串接」（CUSTOMIZATION §3.1）。

**限制**（對 MOTRIX 是警訊，也是差異化空間）：
- 自訂表單碰不到**核心計算**（稅額、扣繳、補充保費、分潤）。NUEiP 把薪資留在 nuHRM 這個程式模組裡，不是用表單拼出來的。MOTRIX 的裁示「核心欄位與計算不動」與此一致。
- Ragic 的流程要事先定義，申請人無法臨時加層級。如果 MOTRIX 要開放「加簽」，要先決定加簽能不能改變原本的層級（見第 5 章）。
- 公開資料**查不到**這兩家對「已送出單據的表單版本凍結」怎麼處理。MOTRIX 規格已經要求「發布產生不可變版本、已送出單據凍結」（CUSTOMIZATION §3.1），這是可以寫進賣點的地方。
- 資料庫式平台（Ragic）的關聯與報表強，但會計帳務的借貸平衡、關帳、傳票編號等限制要靠使用者自己設計，容易出錯。MOTRIX 應該把這些留在內建模組。
