## 3. 選項（每項：預期節省／風險／回滾開關）

**O1　便宜守門前置（preflight slice）——不弱化任何閘門，只改順序**
- 做法：非 e2e 段開跑前（或與其並行的前 2～3 分鐘），先跑一組「確定性、秒級」守門檔：產生檔過期（dep_graph／test_map／UNIT‑INDEX）、模組 CHANGELOG 隨程式、版本紀錄日期（VR1）、V9 基準、stepfile、佔位取號、module 邊界；任何一個紅就**立刻停**並指出重產指令。`gate_slices.json` 的 slice0 已是這個概念，但它含 2 359 題、約 12～19 分，**太大**；需要再切出「preflight（<3 分）」。
- 節省：本班本人分支 7 次紅中的 6 次可在 3 分鐘內發現（原本 5～44 分鐘）→ 117 分降到約 25 分；整合閘門的紅燈約一半同類。**每班預期省 40～100 分。**
- 風險：低（不減少任何題；只是先跑）。要維護 preflight 清單（可由 `fail_stream` 歷史統計「最常見的紅」自動產生候選）。
- 回滾：環境變數 `MOTRIX_GATE_PREFLIGHT=0` ⇒ 回到現行順序（比照現有 `MOTRIX_GATE_SLICES=0`）。

**O2　產生檔自動重產＋自檢（作者端）**
- 做法：把 `dep_scan`／`test_map`／`unit_index` 重產與 `--check` 包成一個 `regen_all` 指令並在 commit 前掛鉤（或 preflight 第一項自動重產並提示提交）。
- 節省：消除「過期產生檔」這類紅（本班 2 次、第 45 班也有）。風險：低。回滾：不呼叫即可。

**O3　紅後續跑（resume）：同樹、已綠檔不重跑**
- 做法：failfast 中止時把「已完成且綠」的 nodeid／檔寫入段紀錄（`fail_stream` 已記錄失敗與 summary，需要補記通過清單）；重跑**同一棵 tree 上只改測試或修紅題**的情形，用 `stage_select` 的相依選題把「與改動無關、且上一輪已綠」的檔沿用。
- 節省：紅後重跑由 66 分降到「受影響檔」（約 5～15 分）；累積效益最大（對應大戶 #1、#3）。
- 風險：中——沿用需要正確的相依圖（`test_map.json`／`dep_graph.json`）；漏相依＝漏測。`stage_select.py` 已有「fail closed」設計（計算錯誤、基準缺失、硬底層改動、unmapped ⇒ full），但目前**只是 dry‑run、未接線**。
- 等價性論證（必要，才可上）：①沿用只限「基準 tree 已嚴格全綠且同一天」；②硬底層（`db.py`、`conftest.py`、`core/`、`helpers/` L1）任何改動 ⇒ 一律全量；③**發布候選樹仍須一次完整全綠**（見 O4），增量只用於迭代期。
- 回滾：`MOTRIX_STAGE_INCREMENTAL=0`（預設關，逐步開）。

**O4　分層閘門：分支＝增量＋slice0／整合樹＝唯一完整全量**
- 做法：作者分支只跑 preflight＋slice0＋該分支動到的模組目錄（`pre_train_check --changed-modules` 已有）；**完整非 e2e＋e2e 只在整合樹跑一次**（就是 node‑d8 本班臨時採用的做法）。
- 節省：每個分支省 20～45 分（本班 wip/t46‑baseline‑118 的 7 245 題全量重複了整合閘門）。
- 風險：低到中——分支單獨紅／綠的歸屬會比較晚才知道；以 `pre_train_check`（合併後預演）補。**發布閘門本身不變。**
- 回滾：流程規定，無程式開關；需要時作者可自行跑全量。

**O5　worker 數 2 → 4（實體核心 6 的 2/3），記憶體足夠**
- 做法：非 e2e 用既有 `default_workers`（=4）；全機鎖仍保證同時只有一套大測試。
- 節省：非 e2e 3 938 s → 預期約 2 200～2 700 s（**非線性，未實測**；省約 20～28 分／次）。
- 風險：中——計時敏感題在 CPU 被搶時會紅（`build_deploy_package.ps1` 的「獨佔」註解就是為此）；與其他視窗共用機器；**目前團隊規則「最多 2 worker」**。
- 回滾：`--workers 2`（`run-stage` 已支援）。**需使用者裁示**（規則本身要改）。

**O6　分段指紋：把「沒有任何測試讀到的檔」排除出指紋**
- 做法：指紋分成「程式（含測試讀到的檔）」與「純文件」兩部分；`test_map.json` 已有 tests→檔 的對應，可算出「被任一測試讀取的檔集合」；僅動到集合外的檔（例：`docs/windows/**`、`docs/quick/**`）⇒ 指紋不變。
- 節省：純文件／備註類 commit 不再使 66＋25 分失效（本班未直接發生，但每班都有 docs commit）。
- 風險：中——`build_test_reuse.py` 註解明載「文件不排除：測試會讀 docs/」，漏判＝漏測；必須以 `test_map` 可證明（讀檔集合要含 `open()` 動態路徑 ⇒ 難完全證明）。
- 等價性論證要求：對每個被排除的路徑樣式，附「全樹 grep 無測試／程式讀取」證據與守門題（出現讀取就使排除失效）。建議**先只排除 `docs/quick/`**。
- 回滾：`REUSE_EXCLUDE` 還原。

**O7　補計時，讓下次不用猜**
- 做法：`delivery.py publish`、`final_drill` 總耗時、`stage` 的 preflight 耗時寫入 `deploy_manifest.json.durations_sec`／`test_results.jsonl`；`fail_stream` 補記每段「通過檔清單」（O3 前置）。
- 節省：本身不省時間，但補掉本文 §1.1 的「未量測」。風險：極低。回滾：欄位可忽略。

**O8　建包／演練／發布並行化**
- 做法：演練（2.7 分）與 e2e 同時跑（演練用另一個 port、不搶 e2e 的瀏覽器）；建包 43 s 與發布不是瓶頸。
- 節省：約 3 分。風險：低到中（CPU 搶佔）。**優先序最低。**

**不建議**：取消 failfast（紅時要等整段才知道，更慢）；放寬 e2e 或跳過 e2e；把 flaky 題登記進 `known_flakes.json` 來「變綠」（本班已確認該題是順序相依，應修題而非登記）。

## 4. 建議組合與預估（到 30 分鐘目標的路徑）

| 步驟 | 內容 | 預估每班可省 | 累計「第一次就綠」路徑 |
|---|---|---|---|
| 現況 | 非 e2e 66＋e2e 25＋演練 3＋建包 1 | — | ≈ 93 分（不含紅燈重跑；有紅燈的班 160～200 分） |
| O1＋O2 | preflight＋自動重產 | 紅燈浪費 40～100 分 | 93 分（但不再因便宜守門重跑） |
| O4 | 分支不跑完整全量 | 每分支 20～45 分 | 93 分（整合樹仍一次完整） |
| O5 | 非 e2e 4 worker | 20～28 分 | ≈ 65～73 分 |
| O3＋O6 | 同樹續跑／分段指紋 | 迭代期每輪 50～60 分 | 迭代期每輪 10～20 分；**發布候選仍 ≈ 65 分** |
| ？ | 要在**發布候選**上達到 ≤30 分 | | 只靠上面做不到：65 分的下限要靠「增量沿用已綠基準」（O3）＋e2e 並行；見 §5 的裁示題 |

**誠實的結論**：在**不弱化任何閘門**的前提下，「完整發布候選一次全綠」的下限約 65 分鐘（O5 之後）。要把**每班實際花費**壓到 ≤30 分鐘，主要靠 **O1／O2／O4（消除重跑與重複）**——它們把「有紅燈的班 160～200 分」壓回「一次綠的 ≈ 65～93 分」；
而 ≤30 分的**發布候選**只有在使用者接受「發布閘門採增量沿用（O3，附完整全量的週期保證）」時才可能，這屬弱化，需書面等價性論證（§5）。

## 6. 建議的落地順序
1. 先做 **O7**（補計時）與 **O1**（preflight）——兩者都不碰任何閘門，且 O1 直接對準 §1.2 的最大浪費。

4. 請使用者裁示 **O5**（4 worker）；其餘 O3／O6 在 O1／O4 上線後看實測再議。
