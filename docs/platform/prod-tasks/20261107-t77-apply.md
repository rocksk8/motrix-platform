## 已知殘留／本班「沒有」的東西
- **發票上傳通知**：①財務收件對象以 `users.role`（finance／superadmin）判斷，不是 `duty_roles` 職責旗標——既有全站缺口，非本功能新增，走既有 `to_group=True` 群組機制沒有新增寫死判斷；②同一請求多檔＝一封，但**沒有跨請求合併／節流**，連續分次上傳會對全體財務連發，可能觸發 SMTP 限流（例如 Gmail 421）且不重送；要不要加合併是產品決定，本版不做；③已退訂 `module_activity` 的人（正式機 queena、sundy）**仍會收到**這個新類型（退訂以類型為單位，不是繼承），上線說明請寫明；④收件人是否收到取決於帳號有無 Email、有無自行退訂該類型。
- **逐行對應**：①**整行對應不存金額快照**——逐行金額一律取派發單目前的值，之後若有人改了派發單某行的金額（總額不變），已對應金額會跟著變且沒有警示（派發單核准後改品項通常要重送審，主要發生在待審核階段）；②可逐行的判準是**整數分相等**（比最初規格草案寫的容許 0.005 更嚴，對不上就只能整張）；③行層級拆分若超過目前行金額，整行拆分忽略（不按比例裁減），Σ份＞行金額在存檔時會被擋（422）；④外包人員（點工）只在整張層級，沒有逐行；⑤**手填成本（材料／額外支出）與派發單之間完全沒有防呆**——如果同一批工作同時填了手填成本又掛了派發單，系統不會示警；這是既有缺口，本班的逐行對應沒有擴大也沒有縮小這個缺口（已記錄為後續待規劃項目，不在本班範圍）。
- 本班刻意不動：簽核流向、報價單、案件記錄欄位讀寫、其他既有通知類型、設定中心既有群組。T76 的 `quote_approval.reconfirm_mode` 維持使用者裁示的現狀（本班不涉及，未調整）。
