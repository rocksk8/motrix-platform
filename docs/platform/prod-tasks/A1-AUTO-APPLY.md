> 範圍：只有我們自己的正式機（M1）。客戶主機版本、跳台、更新中樞（M2）尚未開工，設計全文在 `D:\Claude-pm\t87-design\A1-auto-apply.md`。

## 它取代了什麼

步驟檔（例如 `20261114-t86-apply.md`）的「步驟 0 記錄套用前狀態」與「步驟 3 套用後驗收」原本由人手工做。M1 把這兩段做成程式，並在套用前多一道**預演**。
套用本身沒有改：仍是 `delivery.apply_staged`，備份、預演、停服、複製、重啟、健康檢查與**腳本內建的自動回復到套用前**都照舊。

## 正式機上的使用方式（PM 裁示 2026-11-14）

**平常不執行。** 只在更新的時候，由操作的人用遠端桌面登入正式機後**手動啟動**；只綁 127.0.0.1；套用完成就關掉。**不加排程、不加開機啟動、不開防火牆埠。**

1. **啟動**（在正式機的命令提示字元；Python 與 `autostart.bat` 啟動 ERP 的是同一個 Python312）：
   ```
   cd /d C:\Users\Motrix\Desktop\V9.0\backend\tools
   C:\Users\Motrix\AppData\Local\Programs\Python\Python312\python.exe deploy_dashboard.py
   ```
   視窗會印 `MOTRIX 部署儀表板：http://127.0.0.1:8765`，**這個視窗要一直開著**（關掉就是停止）。路徑以正式機實際的 `autostart.bat` 為準。
2. **開瀏覽器**：在**正式機自己的桌面**（遠端桌面裡）開 `http://127.0.0.1:8765`。從別台電腦連不到（只綁本機，請求層也只收本機）。
3. **套用**：照上面「操作流程」。
4. **關閉**：在啟動視窗按 Ctrl+C（或直接關視窗），再用 `netstat -ano | findstr :8765` 確認沒有人在聽。
5. **沒有開著時**：套用流程照舊用步驟檔（儀表板不是套用的必要條件；M1 只是把驗收做成程式）。

**正式機上的健康檢查位址**：開發機的儀表板從外面讀正式機（`PROD_BASE_URL`＝對外位址）。裝在正式機上時，`PROD_HOST` 是**這台機器自己的位址**，程式（`_prod_status_base_url`）會偵測到並改連**本機 ERP**（`_erp_base_url()`，預設 `127.0.0.1:666`），**絕不連自己的對外 IP**；本機 ERP 位址若被環境變數設成非本機，就什麼都不連（畫面顯示「沒有檢查」）。交付資料夾已設定時本來就不連線。兩種位置都有測試（`test_deploy_dashboard_prod_self_2026_11_14.py`）。

**在正式機上，儀表板連本機 ERP 要輸入 TOTP（正式機設定不准改）**：本機最高管理者帳號從「外部」登入要過 TOTP。正式機的 `external_login.loopback_is_internal` 是**預設值（不算內部）**，所以儀表板（在正式機上）→ 本機 ERP（`127.0.0.1:666`）這條連線**被 ERP 視為外部連線，一定要輸入 TOTP**。儀表板的「套用」區本來就有 TOTP 欄位（`dl-totp`；ERP 回 `totpRequired` 時走 `/api/auth/login/totp`）；操作的人要準備好驗證器。**這個設定不准為了省 TOTP 而改**——改了等於放寬正式機的登入防線。
（只有**演練**例外：演練是全新的暫存資料庫，沒有 TOTP 裝置，所以 `a1_drill.py` 在演練資料庫裡把 `loopback_is_internal` 設成 1，並寫在演練報告的「與正式機不同之處」；正式機不受影響。）

**Python 套件（PM 2026-11-14 在正式機實測）**：正式機 Python312 **沒有 `requests`**，有 urllib3 2.7.0、fastapi 0.141.1、uvicorn 0.52.0、pydantic 2.13.4、websockets 17.0.1；**不在正式機另外安裝套件**。因此 `deploy_dashboard.py` 的 HTTP 呼叫改用標準庫 `urllib.request`（檔內自帶的小物件，保留 `requests.get／post／RequestException` 名字；行為：HTTP 4xx／5xx 當回應回傳、連線／逾時／TLS 失敗丟 `RequestException`、`verify=False` 不驗自簽憑證、逾時秒數不變）。`auto_apply.py` 本來就只用標準庫。守門測試（`test_deploy_dashboard_stdlib_http_2026_11_14.py`）：這兩個檔的第三方 import 必須在 `backend/requirements.txt` 或上列「正式機實測有」清單內；並在擋掉 `requests`／`urllib3` 的乾淨行程裡實際 import 一次。以後這兩個檔想 import 新的第三方套件，這個測試會擋下，要先由 PM 決定。

**演練埠**：`a1_drill.py` 的 ERP／儀表板預設用 **6866／8866**（避開其他視窗常用的 6766；可用 `--erp-port`／`--dash-port` 改，不可是 666 或 8765，兩者不可相同）；preflight 兩個埠都要沒人聽才會開跑。

## 操作流程（儀表板「6. 套用更新」）

1. 選包，按「準備」：複製到安裝目錄外、驗簽章與逐檔雜湊（與以前相同）。畫面多一行預估耗時。準備進行中不能同時預演或套用（`preparing` 旗標）。
2. 按「預演」：在正式資料庫的**線上備份副本**上，用新包的 `migrate_like_startup.py` 跑一遍，畫面列出預期的資料庫變更。預演只讀正式庫，不需要密碼。
   預演結束後立刻再驗一次暫存包（簽章清單、逐檔雜湊、不得有清單外多出的檔）；預演在暫存包留下的任何新檔（`.pyc`、備援資料庫、`logs`…）會被清掉並記在注記，清不掉或檔案被改過則**預演不通過**。
3. 確認內容後輸入本機最高管理者帳密，按「套用」。下列任一情況都會被拒絕，而且**在要求密碼之前**就拒絕：
   - 沒有通過預演、預演超過 12 小時、畫面上看到的預演結果與目前有效的不同；
   - 暫存的包與簽章清單不符（被改過、或多出任何檔案）；
   - 預演之後暫存的包被換過（包摘要不同）。
4. **預演是一次性的**：按下套用的那一刻預演就作廢，不論之後成功、失敗或還原；再套用必須對「現在的」正式庫重新預演。
5. 套用開始前再比一次正式庫的**結構雜湊**（schema_version、模組版號、資料庫物件、欄位；不含設定鍵名，因為執行中的服務會寫設定）：與預演副本不同＝預演之後結構變動過，預演預期已不適用，擋下並要求重新預演。
6. 套用後系統自動驗證，畫面逐項列出結果；同時寫 `backend\logs\a1_report_<時間戳>.md／.json`，並發通知（見下）。

**在套用開始之前被擋下**（準備失敗、驗證不通過、預演不通過、或上面第 3 點的任一項拒絕）：同樣留下白話報告 `backend\logs\a1_report_blocked_<時間戳>.md`（包名、停在哪一步、原因、「正式系統沒有被改動」），並在 `a1_audit.jsonl` 加一筆 `apply_blocked`（含 `step`、`report`）；畫面上也會顯示報告檔名。**這個階段不發通知**（操作的人就在畫面前）；通知只在套用開始之後才發。報告寫不出來不會讓準備、預演或套用本身出錯。準備與預演不需要密碼，所以有防灌爆：同一個步驟、包、原因 60 秒內只寫一份報告與一筆稽核（再按只回上一份的檔名）；換包名或原因也繞不過的全域上限：每個安裝目錄 10 分鐘內最多寫 20 份報告（超過的只計數、不寫檔，每個視窗只留一筆 `apply_blocked_throttled` 稽核，回最後一份的檔名）；報告檔只留最新 50 份；包名只准英數與 `_-`（否則報告記成「名稱不合法」與長度）；原因的換行與控制字元壓成空白、每則最多 300 字。附加稽核只讀檔尾，不隨檔案變大而變慢。

「預演綁定值」（畫面上顯示的 digest）是**介面一致性用的標記**，不是授權憑證：本機任何人都讀得到 `/api/delivery/rehearse/status`。真正的授權是本機最高管理者的帳密與兩步驟驗證。

## 事後驗證項目

| 項目 | 通過條件 |
|---|---|
| 健康檢查 | `/api/ping` 回 200 |
| 資料庫完整性 | `PRAGMA integrity_check` ＝ ok |
| 資料庫變更與預演相符 | 結構差異（物件、欄位、模組資料結構版本、設定鍵名）與預演預期一致；多出或缺少都失敗；多出的設定鍵若是 `migration_*` 失敗，其他只警告 |
| 模組載入 | `logs\module_states.json` 是這次啟動寫的，且每個已載入模組的版號＝磁碟 `module.json` |
| server.log | 最後一次啟動標記之後沒有 Traceback 與包指定的禁止字串 |
| 已部署 commit | `.deployed_commit.json` 與包的 commit 一致 |
| 包專屬項目 | 包內選用檔 `backend\a1_expectations.json`（格式見下） |

事後驗證只打本機：系統位址（設定 `MOTRIX_DELIVERY_ERP_URL`，預設 `https://127.0.0.1:666`）的主機不是 `127.0.0.1`／`localhost`／`::1` 就拒絕（驗證連線不驗憑證，不能指向別的主機）。**這個檢查在要求最高管理者密碼之前**：位址不是本機時，`/api/delivery/apply` 直接回 409，驗密碼的函式也自己再擋一次，密碼不會送出本機。

## `a1_expectations.json`（包專屬驗證項，選用）

放在包內 `backend\a1_expectations.json`（在簽章清單涵蓋範圍內）。**目前計畫由 A2 的整合者一鍵工具在出包時自動產生**；沒有工具之前由包的作者手動放。所有欄位都選用：

```json
{
  "pages": ["/", "/login.html"],
  "auth_required": [{"method": "GET", "path": "/api/cases"}, {"method": "POST", "path": "/api/settings"}],
  "files": ["backend/modules/alpha/module.json"],
  "log_forbid": ["ImportError", "no such column"],
  "watch_settings": ["company_name"]
}
```

| 欄位 | 意義 | 通過條件 |
|---|---|---|
| `pages` | 要能開的頁面路徑 | 未登入 GET 回 200 |
| `auth_required` | 必須要求登入的 API（`method` 預設 GET） | 未登入回 401 |
| `files` | 安裝目錄下必須存在的檔（相對路徑） | 檔案存在 |
| `log_forbid` | server.log 最後一次啟動之後不得出現的字串 | 沒有出現 |
| `watch_settings` | 套用不得改動值的設定鍵 | 前後值雜湊相同（只存雜湊，不存值） |

格式檢查（縱深防禦，包雖有簽章）：`pages`、`auth_required.path` 必須以單一 `/` 開頭，不得含 scheme、`@`、反斜線、`//host`、空白；`auth_required.method` 只准 `GET`／`POST`／`HEAD`／`OPTIONS`；`files` 不得是絕對路徑或含 `..`。不合格的項目被略過並在報告注記。

**檔案不存在時的預設行為**：只做上表的通用驗證項（健康、完整性、資料庫變更、模組載入、server.log、已部署 commit），沒有頁面／未登入／檔案／日誌的專屬檢查，並在報告「注記」寫明「這個包沒有附 a1_expectations.json」。不當成失敗，也不假裝有驗過。檔案存在但讀不懂（不是 JSON、不是物件）＝同樣略過並注記。

## 驗證失敗或沒有驗證時

- 只停下來、產生報告、顯示回復到套用前的指令的**文字**；系統**不會**執行回復到套用前（PM 裁示 D1）。
- 套用腳本自己的健康檢查／公司資料閘門失敗所觸發的內建自動回復到套用前不受影響，結果照舊在 `rolled_back` 欄。
- **沒有驗證不准記成功**：套用腳本判定成功，但 `rolled_back` 不是 `applied`（成功出口只有這個值）時，不做事後驗證，結果記為「已套用，事後驗證未通過或沒有完成」（`verify_failed`），寫回開發機是 `failed`，報告有「後續處置」，通知是需要處理。
- 寫回交付資料夾的 `results\<包名>.result.json`：事後驗證沒過或沒做一律記 `failed`；細節在旁檔 `results\<包名>.a1.json`（白名單欄位：結果、未通過項目 id、鏈頭雜湊…，不含路徑、設定、報告全文）。
- 套用程序本身丟出例外（例如包裡缺腳本）：補一筆 `apply_end`（`crashed`）與報告，仍發通知。例外發生時 `apply_staged` 可能已經複製工具、啟動腳本或停了服務，所以報告與通知一律寫「**狀態未知，請人工確認現況**」，不說有沒有開始套用。
- 預演結果沒有記錄結構雜湊（`before_hash`）時，視為無法確認預演之後正式庫沒有變動，套用前擋下並要求重新預演（不是默默略過）。
- 稽核（`a1_audit.jsonl`）寫不進去：**不套用**，報告列出原因。

## 通知

套用結束一律通知，**成功、驗證未通過、失敗、被擋下、程序中斷**五種都發。做法沿用登入失敗告警（T81）的機制，沒有新通道：

| 通道 | 做法 |
|---|---|
| 站內通知 | 對最高管理者各寫一則（`notifications`，經 `helpers.audit._notify`） |
| Email | `email_notify.send_registered("system_update_result", to_group=True)`；收件人＝該信件類型登記的群組「僅最高管理者」加設定頁的覆寫與個人退訂 |
| LINE | 同一次呼叫內的獨立通道：只發給收件人控制裡勾選且已綁定的人，不群發；公司層 LINE 事件開關預設關，**上線後要有人在 LINE 設定頁勾選「系統更新結果」才會有 LINE**，Email 與站內不受此限 |
| ERP 稽核 | `audit_log` 一列 `system_update.apply`（經 `helpers.audit._audit`；該函式只認 session token，沒有 token 時 `username` 欄為空，套用者在 `detail.by`） |

這四件事由**安裝目錄裡的後端**執行（`a1_notify.py` 子行程），儀表板不載入 ERP 的 helpers；各自獨立、各自失敗，**不改變套用結果，也不擋套用**（通知在套用結束之後才跑）。
**沒有人收到就不算通知成功**：收件人 0 人（最高管理者清單是空的）、站內通知沒有寫進任何一則、或信件沒有排入佇列，子行程都以結束碼 2 回報，照下面的方式寫進報告與問題清單。沒有設定郵件的機器，每次套用的報告問題清單都會有「信件未排入」，即使套用成功也一樣：這只是提示，不改變套用結果，不要當成失敗。LINE 同一次呼叫內的 `line_key` 以鏈頭雜湊去重；沒有鏈頭時改用「包名＋時間」，所以同一個包名重試不會被當成重複而吃掉。
子行程失敗**不會被吞掉**：錯誤與子行程輸出末段寫進同一份報告的「通知」一節，也出現在畫面的問題清單與稽核檔的 `apply_notified`；此時請人工通知最高管理者。

**在 ERP 稽核頁查這筆紀錄**：動作是 `system_update.apply`。稽核頁列表顯示的是「操作內容」（`target_label`）與使用者欄；使用者欄因為 `_audit` 沒有 token 會顯示「（系統）」，**套用者寫在操作內容裡**（格式：`<包名>：<結果>（套用者 <帳號>）`），所以：
- 列表上直接看得到套用者；
- 用「關鍵字」搜尋（比對操作內容）輸入帳號或包名就搜得到；**不要用「使用者」篩選**，它只比對使用者欄，這筆是空的；
- `detail.by` 與鏈頭雜湊只在匯出的 JSON／資料庫裡，畫面不顯示也不能搜。

內容只有：更新包名、結果、停在哪一步、未通過項目 id、報告檔名。**不含**回復到套用前的指令全文、路徑、設定值、密碼、錯誤全文。信件類型 `system_update_result` 不鎖定（管理者可在通知設定關掉 Email；LINE 優先度為一般）。

## 已知限制（M1 刻意不做）

- **不做登入後的功能煙霧測試**（需要憑證）。事後驗證只做未登入可做的探測（頁面 200、API 401）加上資料庫、模組、日誌檢查；登入後的功能是否正常仍須人工看一眼。PM 已接受這個限制留到 M2 或另案。
- 實際停機時間以每 2 秒一次的 `/api/ping` 量測，是下限加一個輪詢間隔。
- 預估耗時來自歷次成功的 `apply_update_*.result.json`，含套用前備份與預演，並非只有服務停止的時間。
- `REQUIRE_REHEARSAL` 是程式常數（`deploy_dashboard.py`），不做成設定值；關閉它等於回到沒有預演的舊流程，需要改程式並走審查。
- 結構雜湊比對的是預演當下與套用當下的**結構**；資料列內容、設定值的變動不在比對範圍（執行中服務本來就會寫）。
- ERP 稽核列的 `username` 欄為空（`_audit` 只認 session token）；要有帳號需要在 `helpers/audit.py` 加一個以帳號寫入的介面，屬 L1 介面變更，未在 M1 做。**後續項目（backlog，需另案核准）**：在 `helpers/audit.py` 新增以帳號寫入的函式，之後 `a1_notify._erp_audit` 改用它，`target_label` 裡的套用者可保留或拿掉。
- **回復到套用前之後的備援**：若套用失敗後又還原成舊版，安裝目錄裡的後端可能沒有 `system_update_result` 信件類型（Email 路徑會回報「沒有登記」；`event_audience` 會退回最高管理者，站內通知仍可寫），甚至連 `a1_notify.py` 都不在了。此時通知可能整個沒發出去，**報告檔（`backend\logs\a1_report_*.md`）與儀表板畫面就是備援**，請人工通知最高管理者。
