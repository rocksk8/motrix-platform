## §1 · 🔴🔴 最嚴重：通知「先記已寄、再射後不理」

### 量到的

```
notify_* 函式總數                     47
  能回報失敗的（_send_raising）         3   ← 全部是標案雷達
  射後不理的                          44
「先寫已通知標記、再開執行緒」的位置    15   daily_tasks 13／dev_crm 1／reports 1
```

`_send()` 內有**兩條完全安靜的 return**（`enabled=False`、`_smtp_send_blocked()`），
其餘失敗只寫 `logger.warning` —— **而沒有人在讀那個 log**。

### ☠️ 後果

排程**先**把「已通知」寫進 `system_settings`，**再**開一條 daemon 執行緒去寄。
寄失敗時沒有任何回頭路 ⇒ **那一筆被永久記成已通知，不會補寄。**

**今天新寫的 §3w 也是這個形狀**：`daily_tasks.py:1870` `_mark(st)`、`1871` `threading.Thread`。
⇒ SMTP 密碼過期那天，每一筆逾期單都會被安靜地記成「已通知」。

### 🔑 為什麼這一條最值得修

**那 3 支能回報失敗的，正是之前為了同一個症狀修過的標案雷達。**
📌 〈診斷的層級決定覆蓋率〉：**一個正確的個案解釋掩蓋了系統性成因。**
修在一個地方，44 支沒有一般化。

### ✅ 建議

```
1  _send() 回傳成功與否（不改簽名的話，至少讓 _async_send 接一個 callback）
2  呼叫端「寄成功才寫已通知」——順序顛倒過來
3  寄失敗要有落點：一張待重試表，而不是只有 logger.warning
   🔑 〈計數器要有落點〉：沒有落點的失敗等於沒有發生過
```
⚠️ **反向控制不可少**：SMTP 故意設錯 ⇒ **「已通知」不可以被寫入**。
☠️ 沒有這一題的話，一個「寄失敗也照樣標記」的實作會全綠。

## §2 · 🔴 `sidebar.js:898-901` 權限會被一次不完整的 200 洗掉

```js
.then(function (d) {
  if (!d) return                      // ← 只擋 null
  ...
  stored.modules = d.modules          // ← d.modules 是 undefined 時
  localStorage.setItem('motrix_session', JSON.stringify(stored))
                                      //   JSON.stringify 把這個鍵整個丟掉
```

⇒ 畫面變成「**你沒有這個頁面的權限**」，**而且重新載入不會自己好**
（要等下一次 `/api/auth/me` 回一個完整的 200 才修回來）。

📌 視窗 D 用罐頭 API 實際重現過。
🔑 〈降級之後它還是會動〉＋〈讀不到的欄位要拒絕那一筆，不要送空值〉。

### ✅ 建議
**欄位缺就整筆不覆寫**：`if (!d || !Array.isArray(d.modules) || !d.role) return`。
⚠️ **判準要釘「缺欄位時 localStorage 不變」，不是釘那個 if。**

## §9 · ☠️ 這次檢核本身的教訓：**註解愈好，文字比對愈容易騙人**

**前三次掃描全部誤報，成因相同 —— 正則吃到註解與 docstring：**

| 誤報 | 真相 |
|---|---|
| `map_points.py:187` 用了 `with get_db()` | 那是一行**說它是錯的**註解，程式用的是 `db_conn()` |
| `guard_case_access` 洩漏連線 | docstring 裡寫著 `conn = get_db() → close()`，而連線是**參數傳進來的** |
| `auth_me`／`change_password` 無權限守門 | 它們**手動解析 Bearer token**，我的關鍵字清單沒涵蓋 |

**換成純 AST 之後，「連線洩漏」從 2 支變成 0 支。**

🔑 **這個 repo 的註解特別詳盡，反而讓文字比對工具在這裡特別不可靠。**
📌 對應記憶：〈診斷的層級決定覆蓋率〉——
**「文字比對答的是『有沒有被提到』，不是『有沒有被呼叫』，
而寫得好的文件讓粗糙的工具更容易騙人。」**
