### 規格

**① 供應商前置時間**（`SELLABLE-AND-MOBILE-SPEC.md` §5.1 第 4 項，實測 `lead_time` 0 處）

- `suppliers` 加 `lead_time_days INTEGER`（預設 NULL ＝ 未知）
- `parts` 也加一個同名欄位（**料號層級可覆寫供應商層級**——同一家供應商，
  現貨品項與訂製品項的前置時間差很多）
- 解析順序：`parts.lead_time_days` → 該料號最近一筆進貨的供應商 → NULL
- ⚠️ **NULL 要當成「未知」而不是「0」**。算不出來就明說算不出來，不要猜一個數字出來。
  架構地圖 §6.6 當初刻意不做 ETA 的理由就是「從未追蹤前置時間」——
  現在補了欄位，但**沒填的那些仍然是未知**，不可以因為欄位存在就假裝算得出來。

**② 採購建議帶 ETA ＋ 下單狀態**（架構地圖 §6.6 自述「v1 刻意不含」）

- `GET /api/inventory/purchase-suggestions` 每一列加 `lead_time_days` 與 `eta`
  （`eta` ＝ 今天 ＋ 前置時間；前置時間未知 → `eta` 為 `null`，**不要填今天**）
- 新增狀態：`suggested`（預設）→ `ordered`（已下單，記下單日）→ `received`（已到貨）
- 狀態存哪裡由 B 決定，但**必須能回答「這筆建議是什麼時候被處理的」**
- 已是 `received` 的建議不再出現在待辦清單

### 驗收條件（C 先寫成紅的）

1. `suppliers` 與 `parts` 都有 `lead_time_days`，**預設 NULL**
2. 料號有填 → 用料號的；料號沒填、供應商有填 → 用供應商的
3. **兩邊都沒填 → `lead_time_days` 與 `eta` 都是 `null`，不是 0、不是今天**
4. `eta` ＝ 今天 ＋ 前置時間（用固定日期測，**不要用 `date.today()` 當預期值**——
   那樣測試會驗到自己算的同一個東西）
5. 狀態轉移 `suggested → ordered → received` 走得通，每一步都記得下時間
6. **跳過中間狀態（`suggested → received`）要被拒絕**，不是靜默接受
7. `received` 的建議不再出現在待辦清單
8. 🔴 **`LICENSE_GATE_ENABLED = False` 時，沒有金鑰也照樣 200**（凍結期的安全保證）
9. 既有題數不可少於上一輪（上一輪 1,111，見協定 §4 ⑥）

### 反向驗證（C 做，兩題）

1. 把「料號覆寫供應商」的判斷反過來 → **第 2 題精準變紅**

   **而那是一個看起來很正常的錯誤答案**）

### 交付物

### 規格（照這個寫，不要自己擴充）

**金鑰內容**（JSON，再連同簽章一起 base64）：
```
{
  "customer":    "某某公司",
  "tax_id":      "12345678",
  "machine":     "<指紋 sha256 前 16 碼>",
  "modules":     ["quotation", "case_manage", "..."]  或 ["*"] 代表全開,
  "issued":      "2026-09-21",
  "expires":     "2027-09-21",
  "sig":         "<Ed25519 簽章>"
}
```

**核心函式**（`helpers/licensing.py`）：
- `machine_fingerprint() -> str` — 主機板 UUID ＋ 第一張實體網卡 MAC 的 sha256 前 16 碼
- `sign_license(payload: dict, private_key_pem: bytes) -> str`
- `verify_license(blob: str) -> LicenseStatus` — 回
  `{valid, reason, env, customer, modules, expires, days_left}`；
  `reason` 是 `ok` / `missing` / `bad_signature` / `machine_mismatch` / `expired` / `malformed`

**端點**：`GET /api/license/status` — **本輪先只要求登入即可讀**，第 3 步再收權限。

### ⚠️ 雙金鑰對：開發用臨時金鑰必須「結構上」分得出來

> 使用者 2026-09-21 裁示：**私鑰先用開發用臨時金鑰，正式的之後再決定。**
>
> 這件事的風險不在「臨時金鑰不能用」，在**它能用**。開發金鑰跟正式金鑰簽出來的
> 授權長得一模一樣、行為一模一樣，所以它被帶進出貨包的那一天，不會有任何錯誤訊息。
> 壞掉會被報修，**降級不會**。因此不靠命名慣例、不靠記得，**做成結構上可偵測**：

- `helpers/licensing.py` 內嵌**兩把公鑰**：`_PUBKEY_DEV` 與 `_PUBKEY_PROD`。
- `verify_license()` **兩把都試**，並在回傳值裡帶 **`env`**：
  用開發公鑰驗過的 → `env="dev"`；用正式公鑰驗過的 → `env="prod"`；都驗不過 → `bad_signature`。
- 本輪 `_PUBKEY_PROD` **先放空字串**（正式金鑰尚未產生），驗證時自動略過，**不可以丟例外**。
- `GET /api/license/status` 回傳中要有 `env`。

這樣「這台機器裝的是開發金鑰」就變成一個**查得到的事實**，而不是一個要記得的事。
日後打包關卡只要檢查 `env != "prod"` 就能擋，不必翻檔名或問人。

**公私鑰**：
- 兩把公鑰**硬編在 `helpers/licensing.py`**，進 git（公鑰本來就是公開的）。
- 開發私鑰產出後存 `backend/tools/_license_private_key_dev.pem`。
- **`.gitignore` 已由 A 於 `0ea90d6` 之後預先補好**（`backend/license.key`／
  `backend/tools/_license_private_key*.pem`／`**/*_private_key*.pem`）——

### 驗收條件（C 先寫成測試，寫完應該是紅的）

1. 簽一把有效金鑰 → `verify_license` 回 `valid=True, reason="ok"`
2. **改動 payload 任何一個位元組 → `reason == "bad_signature"`**
   （⚠️ 這題最容易寫成假綠燈：不要驗「簽章字串不一樣」，要驗 `verify_license` 的回傳值）
3. `machine` 換成別的指紋 → `reason == "machine_mismatch"`
4. `expires` 設成昨天 → `reason == "expired"`，且 `days_left` 是負數
5. 檔案不存在 → `reason == "missing"`，**不可以丟例外**（服務要起得來）
6. 亂碼／截斷的 blob → `reason == "malformed"`，**不可以丟例外**
7. `machine_fingerprint()` 同一台機器連呼叫兩次結果相同
8. `GET /api/license/status` 未登入回 401、登入後回得到 `customer` 與 `days_left`
8b. **沒有金鑰檔時，status 端點回 `200` ＋ `{valid:false, reason:"missing", customer:null}`**
    —— **不是 402 也不是 404**。402 是第 3 步用來擋業務 API 的；
    status 端點本身必須永遠讀得到，否則現場沒授權時連「為什麼沒授權」都查不出來
    （這正是 B 在 `B.md` 問的第 3 題，A 確認採用 B 的判斷）
9. **開發私鑰簽的金鑰 → `valid=True` 且 `env == "dev"`**
10. **`_PUBKEY_PROD` 是空字串時，驗證要正常跑完不丟例外**
    （正式公鑰還沒產生，這是本輪的真實狀態，不是邊界情況）
11. **`GET /api/license/status` 的回傳裡有 `env` 這個鍵**
    ——沒有它，日後打包關卡就沒有東西可以檢查

＝**每個 request 都讀一次檔**。本專案有過簽核卡死 32.8 秒的前例，
**不要假設「檔案很小所以沒差」**。

- 要加快取就用 **mtime 判定重讀**，不要改成 import 時一次性載入。
- 🔴 **快取鍵必須同時包含「今天的日期」**（視窗 B 在第 2 輪提報，A 採納）。
  `days_left` 是拿 `date.today()` 算的，**只看 mtime 的話，一台不重啟的正式機
  會永遠沿用第一次算出來的值**——今天「還有 1 天」，明年還是「還有 1 天」，
  **年費授權會靜默變成永久授權**。
  這正是第 1 輪決定「不快取」的理由（「服務不重啟就永遠不會提醒」）；
  加快取等於把那個問題原封不動放回來，只是粒度變成一天以上。
  B 已實作，量測成本 0.76 微秒。
- **必須保留「測試能換掉 `LICENSE_PATH` 與公鑰」這個性質**，否則測試會變成
  只有某一台機器跑得動。
- C 要寫一題：**改了金鑰檔之後，下一次呼叫要讀到新的內容**（這題才擋得住快取寫錯）。

### 驗收條件（C 先寫成紅的）

1. 有效金鑰 → 業務 API（挑 `GET /api/customers`）正常回 200
2. **沒有金鑰檔 → 同一支 API 回 402**，而且**測試要同時釘住那條 route 存在**
3. 簽章被竄改 → 402，`reason == "bad_signature"`
4. 機器指紋不符 → 402，`reason == "machine_mismatch"`
5. **`kind="subscription"` 且已過期 → 402**
6. **`kind="perpetual"` 且已過期 → 仍然 200**（只提示不擋）
7. **沒有 `kind` 的舊金鑰且已過期 → 402**（預設 subscription，往安全的一邊倒）
8. 未授權時豁免清單裡的四支路徑仍然通（逐支驗，不要只驗一支）
9. 402 的回應內容含 `reason` 與中文訊息，**不是空 body**
10. **改了 `license.key` 的內容之後，下一次呼叫讀到的是新的**（擋快取寫錯）
11. `kind` 被竄改 → `bad_signature`（證明它在簽章範圍內）
12. **既有的 1,084 題在有效金鑰下全部仍然綠**（這題是整輪的保險絲）
13. 🔴 **沒金鑰 ＋ 未登入 → 必須是 401 不是 402**（視窗 B 提議，A 採納）。
    這是「middleware 寫反了也全綠」那個洞的**迴歸鎖**——
    寫反了的話守門會在最外層先跑，**對還沒通過身分驗證的人洩漏「這台機器沒有授權」**。

### 反向驗證（C 做，三題）

1. 把 middleware 的授權檢查整段拿掉 → 第 2～7 題該紅、第 1 題仍綠
2. 把 `kind` 的判定改成永遠回 `"perpetual"` → **第 5、7 題紅、第 6 題仍綠**
3. 把快取改成「只在啟動時讀一次」 → **第 10 題紅**
   （沒紅就代表第 10 題沒在驗快取，退回重寫）
