## §1 🔑 這一件為什麼存在：**既有的拒絕是對的，而它擋住了合法的情況**

```python
# helpers/bonus.py:254
if not people:
    return False, [], NO_ELIGIBLE_PEOPLE      # 「無可發放對象」
# routers/bonus.py:593
if not good:
    raise HTTPException(400, "「%s」%s。" % (item["name"], note))
```

⚙️ 而那個拒絕有很好的理由（`people_for_item()` docstring 逐字）：
> ☠️ 靜默算 0 的兩個後果，第二個更糟：
> ① 那個項目從來沒出現在任何一張獎金單上 —— 而**沒有人會發現一個從來不出現的東西**
> ② **把金額併給別的項目** ⇒ 別人領多了，**而總額對得起來**

> ### 🔑 ⇒ `BN18` **不是要拿掉那道拒絕**，
> ### 是要給「**確實有人該領，而資料裡沒有**」一條出路。

```
⚠️ 那兩件事在今天的畫面上是同一句話：「無可發放對象」
🔴 ⇒ 而 `BN18` 做完之後它們就分開了：
   「資料裡沒有，**而我知道是誰**」 => 手動指定
   「資料裡沒有，**而我也不知道**」 => 仍然拒絕
```

## §2 🔴 A 的 ①（存在單層還是項目層）：**那是一個假二分**

> A 讀：「使用者說的是『**產生獎金單時**』⇒ 我讀成**單層不是項目層**」

```
🔑 「產生獎金單時」說的是**時機**（相對於 `BN14` 的「事先定義群組」），
   **不是存放層級**。
```

### ⚙️ 而存放層級由既有結構決定 —— **只能是項目層**

```python
# routers/bonus.py:588-596  _plan_allocations()
for alloc in allocations:                       # <= **逐項目**
    item = items.get(int(alloc.get("bonus_item_id") or 0))
    good, people, note = people_for_item(item, case)   # <= **逐項目解析**
    shares = alloc.get("person_pct") or {}             # <= **逐項目的比例**
    pairs = [(p, int(shares.get(p, 0))) for p in people]
```
```
⚙️ 而 `bonus_award_lines` 的鍵是 (award_id, **bonus_item_id**, username)
=> 一張單裡，**不同項目可以發給不同的人、不同的比例**
```

> ### ☠️ 做成單層（整張單一份名單）的後果：
> ### **「這個項目該發給誰」這個問題會消失** —— 而 `people_for_item()` 的整個設計就是在回答它。

```
🔴 而它會**安靜地**壞：一張單裡若只有一個項目（今天全部 5 張都是），
   單層與項目層**產生的結果完全相同** => 測試全綠
☠️ 等到有人建第二個獎金項目的那天才出事
```
📌 ⇒ 驗收要**造一張兩個項目的單**（§6 ⓓ）。

## §4 🔴 A 的 ③（覆蓋 vs 只在 0 人時出現）：**兩個都不要，用第三條**

```
甲 覆蓋（alloc 帶了 people 就不呼叫 people_for_item）
   ☠️ A 指出的：**會不小心蓋掉正確的解析結果**
   🔑 而它的失敗是安靜的 —— 蓋掉之後金額照算、總額照樣對得起來

乙 只在回 0 人時才出現
   ⚠️ 使用者**必須先撞一次錯誤**才拿得到這個功能
   ☠️ 而「這個案件沒有執行人」與「這個項目設定錯了」在那個錯誤裡是同一句話
      => 他會以為是自己設錯了，而去改獎金項目
```

### ⇒ 丙：**明著宣告**，而落點是**既有欄位**

```
alloc 多兩個欄位：
   "person_source_override": true        <= **明著宣告**，不是「有值就覆蓋」
   "people": ["jeff", "alice"]           <= username 陣列
```
```python
if alloc.get("person_source_override"):
    people = _validate_manual_people(conn, alloc.get("people"))   # 查不到就 400
    source_snapshot = "**manual**"
else:
    good, people, note = people_for_item(item, case)
    if not good:
        raise HTTPException(400, "「%s」%s。" % (item["name"], note))
    source_snapshot = item["person_source"]
```

> ### ✅ 而 `person_source_snapshot` **這一欄已經存在且已經在運作**（今天存 `'sales_person'`）
> ### 🔑 ⇒ 手動指定存 `"manual"`，**事後看得出這一列是怎麼來的**。

```
☠️ 少了這一格，一張手動指定的單與一張解析出來的單**在資料上分不出來**
   => 而「為什麼這個人會領到這筆錢」是獎金這件事最常被問的問題
⚠️ 而 `"manual"` **不可以**加進 `PERSON_SOURCES`
   （那是「獎金項目可以選的來源」清單，手動指定不是一個可選的來源，
     它是一次性的覆寫）=> 🔑 兩個集合不同，不要合併
```

⚠️ **而「明著宣告」要擋住一種寫法**：
```
❌ `if alloc.get("people"):`  <= 那等於甲（有值就覆蓋）
✅ `if alloc.get("person_source_override"):`
🔴 守門釘：`_plan_allocations` 裡**不可以**出現「以 `people` 的真假值決定分支」
   ⚙️ 誘餌：一個帶 `people` 而**沒有** override 旗標的 alloc
      => 必須走解析那一條，**而不是用那份 people**
```

## §4c 🔴 而 A 的問題底下有一個**真的**問題：**覆寫是取代，還是加減？**

```
情境：某個獎金項目的來源是「**後勤單位**」群組（假設 5 人），
      而這一次只要發給其中 **3 人**（兩個人請長假）
```

```
甲 **完全取代**（§4 丙目前的形狀）
   => 他要手動把那 3 個人一個一個挑出來
   ✅ 實作最單純，而 `person_source_snapshot` 記 `"manual"` 說得通
   ☠️ 而**紀錄上看不出「本來是那個群組」** ——
      日後問「為什麼那次只有 3 個人」時，答案不在資料裡

乙 **在來源之上加減**
   => 先解析出群組的 5 人，再讓他勾掉 2 個
   ✅ 紀錄保留得住「來源是群組、而這一次排除了誰」
   ⚠️ 資料形狀要多兩個欄位（`excluded` / `added`），而**它們也要凍結**
   ☠️ 而它讓 `people_for_item()` 從「回一份名單」變成「回一份名單＋一組修改」
```

> ### 📌 **我傾向甲**，而理由不是實作成本：

```
🔑 乙把「**這一次的例外**」變成一個**結構** ——
   而結構會被重用：下一個人會拿 `excluded` 去做「永久排除」
   ☠️ 那就變成一個沒有人維護的第二份群組定義
⇒ 甲的缺點（看不出本來是哪個群組）**用一個欄位就補得起來**：
   `person_source_snapshot` 除了 `"manual"`，
   再記一個 `manual_basis`（「覆寫前解析出來的來源是什麼」）
   ✅ 那是**一筆紀錄**，不是一個結構 —— 沒有人能拿它去做別的事
```

⚠️ 而這一格**是我提出來的，不是使用者說的** ——
🔑 他只說「產生獎金單時能手動指定人」。⇒ 見 §8b。

```
   ⚠️ 而這一格**是我提出來的，不是他說的** —— 他只說「產生獎金單時能手動指定人」
   ⇒ **若他要「加減」**：§4 丙的資料形狀要多兩個欄位（`excluded`／`added`）
      且兩者都要凍結；`people_for_item()` 的回傳要從「一份名單」變成
      「一份名單 ＋ 一組修改」—— 那會動到 `BN14` 的群組解析

① ⏳ **提示的措辭**（A 裁乙：「這個案件沒有指派執行人，要不要順便去補」）
   我裁：提示**不可以變成阻擋**
   依據：他的原始問題就是「帶不進來」
   ⇒ **若他要更強的**（例如「必須先補才能手動指定」）：
      那會讓這一件變回它要解決的那個問題 —— 要先確認他知道這一點

② ⏳ **草稿階段改手動指定的名單，要不要留記錄**（§5②）
   我裁：**要**，落點 `bonus_award_edit_log`
   依據：手動指定**最容易打錯人**，而不給改的話他只能作廢重開
   ⚠️ 而 C 實查：`bonus.py` 的 `append_edit_log` **零筆**
      => 那是「接一條新的線」不是「呼叫既有函式」（見 `SPEC-BN17 §5`）
   ⇒ **若他不要記錄**：那 §5② 的「可以改」要改成「不可以改」——
      ☠️ 兩者要一起決定，**不可以「可以改而不留記錄」**
```
