# `SPEC-BN18` · 產生獎金單時手動指定人員

> 座標：`15ec6bd`（工作樹：本檔為新增）
> 作者：視窗 A-2 ／ 2026-09-23
> 使用者原話：「過往很多**沒有填寫案件管理專案執行人**，導致**無法帶入**」
> 使用者選的選項：「**產生獎金單時能手動指定人**」

---

## §1 🔑 這一件為什麼存在：**既有的拒絕是對的，而它擋住了合法的情況**

```python
# helpers/bonus.py:254
if not people:
    return False, [], NO_ELIGIBLE_PEOPLE      # 「無可發放對象」
# routers/bonus.py:593
if not good:
    raise HTTPException(400, "「%s」%s。" % (item["name"], note))
```

⚙️ 而那個拒絕有很好的理由（`people_for_item()` docstring 逐字）：
> ☠️ 靜默算 0 的兩個後果，第二個更糟：
> ① 那個項目從來沒出現在任何一張獎金單上 —— 而**沒有人會發現一個從來不出現的東西**
> ② **把金額併給別的項目** ⇒ 別人領多了，**而總額對得起來**

> ### 🔑 ⇒ `BN18` **不是要拿掉那道拒絕**，
> ### 是要給「**確實有人該領，而資料裡沒有**」一條出路。

```
⚠️ 那兩件事在今天的畫面上是同一句話：「無可發放對象」
🔴 ⇒ 而 `BN18` 做完之後它們就分開了：
   「資料裡沒有，**而我知道是誰**」 => 手動指定
   「資料裡沒有，**而我也不知道**」 => 仍然拒絕
```

---

## §2 🔴 A 的 ①（存在單層還是項目層）：**那是一個假二分**

> A 讀：「使用者說的是『**產生獎金單時**』⇒ 我讀成**單層不是項目層**」

```
🔑 「產生獎金單時」說的是**時機**（相對於 `BN14` 的「事先定義群組」），
   **不是存放層級**。
```

### ⚙️ 而存放層級由既有結構決定 —— **只能是項目層**

```python
# routers/bonus.py:588-596  _plan_allocations()
for alloc in allocations:                       # <= **逐項目**
    item = items.get(int(alloc.get("bonus_item_id") or 0))
    good, people, note = people_for_item(item, case)   # <= **逐項目解析**
    shares = alloc.get("person_pct") or {}             # <= **逐項目的比例**
    pairs = [(p, int(shares.get(p, 0))) for p in people]
```
```
⚙️ 而 `bonus_award_lines` 的鍵是 (award_id, **bonus_item_id**, username)
=> 一張單裡，**不同項目可以發給不同的人、不同的比例**
```

> ### ☠️ 做成單層（整張單一份名單）的後果：
> ### **「這個項目該發給誰」這個問題會消失** —— 而 `people_for_item()` 的整個設計就是在回答它。

```
🔴 而它會**安靜地**壞：一張單裡若只有一個項目（今天全部 5 張都是），
   單層與項目層**產生的結果完全相同** => 測試全綠
☠️ 等到有人建第二個獎金項目的那天才出事
```
📌 ⇒ 驗收要**造一張兩個項目的單**（§6 ⓓ）。

## §3 🔴 A 的 ②（綁帳號不存自由文字）：**那條界線今天已經是破的**

### ⚙️ `bonus_award_lines.username` 今天裝的是**中文顯示名**

```
id 1  username = '**高晟耀**'
id 2~5 username = '**黃玉龍**'
   person_source_snapshot = 'sales_person'
```

> ### ⇒ 那一欄叫 `username`，而裡面沒有一個是 username。

```
🔑 成因在上游：`people_for_item()` 走 `case.get("sales_person")`
   而 `quotations.sales_person` 裝的是顯示名（`QS1`）
✅ 而 A 已裁「`BN14` 現在修」＝把這一欄改成真的裝 username
```

### ☠️ ⇒ `BN18` 的定位要講準

```
❌ 不是「維持那條界線」—— 界線今天沒有立起來
✅ 是「**不要在它修好之前，先開一個新的入口**」
🔴 而手動指定是**當場打字最容易產生自由文字**的地方 ——
   一個文字輸入框就足以讓這一欄永遠修不乾淨
```

> ### ⇒ **硬性要求：挑人的 UI 是「從清單選」，不是「輸入」。**

```
✅ 送到後端的是 `username`（帳號），前端顯示 `display_name`
🔴 後端**要驗**：每一個手動指定的 username 必須
   `SELECT 1 FROM users WHERE username=? AND active=1` 查得到
   ☠️ 查不到 => **整批 400 拒絕**，不要只跳過那一個
      （〈拒絕的路徑上不可以留下副作用〉—— 與 `resolve_picks()` 同一個做法）
⚠️ 而**不可以**用 display_name 當鍵去反查 ——
   那正是 `_m010` 回填失敗的那條路（`QS1 §2`）：**同名或改過名就查不到，而它靜默**
```

### 🔴 順序相依（要 A 排）

```
`BN14`（把 username 欄改成裝真 username）**應該在 `BN18` 之前或同一輪**
☠️ 反過來的話：手動指定寫入真 username，而解析出來的寫入中文名
   => **同一欄同時有兩種值，而沒有任何東西會說**
   🔑 那正是 `QS1` 的病，而這次是我們自己造的
```

## §4 🔴 A 的 ③（覆蓋 vs 只在 0 人時出現）：**兩個都不要，用第三條**

```
甲 覆蓋（alloc 帶了 people 就不呼叫 people_for_item）
   ☠️ A 指出的：**會不小心蓋掉正確的解析結果**
   🔑 而它的失敗是安靜的 —— 蓋掉之後金額照算、總額照樣對得起來

乙 只在回 0 人時才出現
   ⚠️ 使用者**必須先撞一次錯誤**才拿得到這個功能
   ☠️ 而「這個案件沒有執行人」與「這個項目設定錯了」在那個錯誤裡是同一句話
      => 他會以為是自己設錯了，而去改獎金項目
```

### ⇒ 丙：**明著宣告**，而落點是**既有欄位**

```
alloc 多兩個欄位：
   "person_source_override": true        <= **明著宣告**，不是「有值就覆蓋」
   "people": ["jeff", "alice"]           <= username 陣列
```
```python
if alloc.get("person_source_override"):
    people = _validate_manual_people(conn, alloc.get("people"))   # 查不到就 400
    source_snapshot = "**manual**"
else:
    good, people, note = people_for_item(item, case)
    if not good:
        raise HTTPException(400, "「%s」%s。" % (item["name"], note))
    source_snapshot = item["person_source"]
```

> ### ✅ 而 `person_source_snapshot` **這一欄已經存在且已經在運作**（今天存 `'sales_person'`）
> ### 🔑 ⇒ 手動指定存 `"manual"`，**事後看得出這一列是怎麼來的**。

```
☠️ 少了這一格，一張手動指定的單與一張解析出來的單**在資料上分不出來**
   => 而「為什麼這個人會領到這筆錢」是獎金這件事最常被問的問題
⚠️ 而 `"manual"` **不可以**加進 `PERSON_SOURCES`
   （那是「獎金項目可以選的來源」清單，手動指定不是一個可選的來源，
     它是一次性的覆寫）=> 🔑 兩個集合不同，不要合併
```

⚠️ **而「明著宣告」要擋住一種寫法**：
```
❌ `if alloc.get("people"):`  <= 那等於甲（有值就覆蓋）
✅ `if alloc.get("person_source_override"):`
🔴 守門釘：`_plan_allocations` 裡**不可以**出現「以 `people` 的真假值決定分支」
   ⚙️ 誘餌：一個帶 `people` 而**沒有** override 旗標的 alloc
      => 必須走解析那一條，**而不是用那份 people**
```

## §5 ✅ A 的 ④（凍結）：天然成立，而要**明著寫**

```
✅ `bonus_award_lines` 存的是**當下算好的結果**（username／person_pct／amount）
=> 手動指定的名單在寫入那一刻就凍結了，**與 BN14 的群組同一個道理**
```

### 🔴 而「事後改不動」要說清楚是**哪一種改不動**

```
① 這張單**已送審／已核准** => 一律改不動（既有的狀態機管）
② 這張單**還是草稿**       => 🔴 **可以改**，而改了要留記錄
   🔑 理由：手動指定最容易打錯人，而草稿階段不給改 ⇒ 他只能**作廢重開一張**
   ☠️ 而作廢重開在傳票那邊今天是有缺陷的（`JV24`）——
      不要把使用者推去走一條更長的路
```
### ✅ 而「留記錄」的落點**存在**（補查）

```
⚙️ `bonus_award_edit_log` 這張表**已經存在**
   （與 `voucher_edit_log`／`daily_task_edit_log` 同一族）
⇒ §5② 的「改了要留記錄」**有落點**，不是一個做不到的要求
```
⚠️ 而我**沒有讀它的 schema，也沒有讀寫入它的程式碼** ——
🔑 「表存在」只證明落點存在，**不證明現在有人在寫它**
⇒ B 動工前先確認它今天有沒有被寫入（今天已經踩過一次「有 schema 沒有寫入端」）。

## §6 驗收（`AC1`）

```
① 後端  `person_source_override` 旗標；手動 username 逐一驗存在且 active；
        `person_source_snapshot` 寫 `"manual"`
② 前端  挑人是**從清單選**（不是文字輸入）；送 username、顯示 display_name
③ 頁面  ⓐ 一個**沒有執行人**的舊案件 -> 產生獎金單
           => 改之前：400「無可發放對象」
           => 改之後：可以手動挑人並產生成功
           🔑 ⓐ 是這一件的來由（使用者原話）
        ⓑ 產生後查 `bonus_award_lines`
           => `person_source_snapshot` == `"manual"`
           => `username` 是**帳號**不是中文名
           ☠️ ⓑ 的第二點在 `BN14` 落地前會紅 —— **那是對的**，見 §3 的順序相依
        ⓒ 負對照：一個**有**執行人的案件，且 alloc **帶了 `people` 但沒有旗標**
           => 仍然走解析，**用解析出來的人**，不是 `people` 裡的
           🔑 少了 ⓒ，「有值就覆蓋」的實作會全綠
        ⓓ 🔴 造一張**兩個獎金項目**的單，兩個項目指定**不同的人**
           => 兩個項目各自的 lines 正確
           ☠️ 少了 ⓓ，「單層」的實作會全綠 —— 因為今天每張單都只有一個項目（§2）
        ⓔ 手動指定一個**不存在的 username** => **整批 400**，
           且**沒有任何一列寫進資料庫**
           🔑 驗的是「拒絕的路徑上沒有副作用」，不是錯誤訊息的文字
        ⓕ 手動指定一個 `active = 0` 的帳號 => 同樣 400
           ⚠️ 少了 ⓕ，「只驗帳號存在」會放行離職的人
```
