## §0 🔴 最重要的一條：**正式不等於含糊**

```
現況（email_notify.py:1889）
  「這通常不需要處理——對方站台維護或網路暫時不通，下次排程會自動再試。」

❌ 錯的改法   「無須處理。」
              => 語氣正式了，而**把三件事拿掉了**：
                 為什麼不用處理／系統接下來會做什麼／什麼時候
              ⇒ **比原本更糟**

✅ 對的改法   「此情形多屬來源網站暫時無法連線。系統將於下次排程自動重試，
               無須人工介入。」
```

🔑 **口語的問題是**語域**，不是**字數**。**
☠️ 而「改得比較短」是最容易被誤認成「改對了」的結果 ——
**它看起來更正式，而收件人少知道了三件事，且沒有人會回報這件事。**

📌 ⇒ 本份的驗收**同時管語氣與資訊量**，而兩者的守法不同（`§2`）。

## §1 範圍：那條線畫在哪

```
✅ 在範圍內   使用者／收件人看得到的文字
              郵件 intro／note／title、畫面文案、API 錯誤訊息（HTTPException detail）
              PDF 上的文字、通知內容
❌ 不在範圍   **程式碼註解與 docstring**
              那是寫給維護者的，**口語在那裡是優點**
```

### ⚠️ 而 `email_notify.py` 裡兩者**混在同一個函式**

```python
def notify_tender_fetch_failed(error, since=""):
    """標案雷達**抓不到對方網站** → 所有 admin/superadmin。
    ⚠️ 只在「進入異常」那一次寄…**狼來了的告警等於沒有告警。**   ← ❌ 不在範圍（很口語，很好）
    """
    intro = ("標案雷達連不上政府電子採購網，今天沒有抓到任何標案。"
             "<b>這通常不需要處理</b>——…")                        ← ✅ 在範圍
```

🔑 **那條線不是「哪一個檔案」，是「這個字串會不會離開這台機器到一個非維護者手上」。**

**⇒ 可判定的形式（`ast`，不是 `grep` —— `§189`）**
```
在範圍   ast 裡作為**值**出現的字串：關鍵字引數（intro=／note=／title=）、
         HTTPException(...) 的引數、return 的訊息欄位
不在範圍 ast.Expr 且其 value 是 Constant，且位於 module/class/def 的**第一個敘述**
         （＝ docstring）；以及 `#` 註解（`ast` 根本看不到它們 ⇒ 天然排除）
```
⚠️ **不要用「這個檔是不是 `*_notify.py`」當範圍** —— 那會把 docstring 一起掃進來，
而它們正是這個 repo 最有價值的部分。

## §2 🔴 判準怎麼寫 —— **守門不讀文字**

A 的界線：**不可以用關鍵字黑名單**。理由成立且我再補一個：

```
黑名單的兩種失敗
① 誤判  規格／測試／docstring 裡**引用使用者原話**的地方會被判成違規
        （本檔第 12 行就有一句使用者原話，任何黑名單都會打到它）
② 漏判  口語**不是由某幾個詞構成的**，是語域
        ⇒ 換一批詞照樣口語，而守門說它過了 ⇒ **假綠燈**
```

### ✅ 解法：**把文案搬到一個地方，讓守門只管「位置」，人只管「語氣」**

```
現況   45 處 intro= ／ 12 處 note= 的值是**行內字面值**，散在 1924 行裡
改成   全部指向一個具名常數區（例如 helpers/wording.py 的 WORDING dict）
       呼叫端：intro=WORDING["tender.fetch_failed.intro"]
```

🔑 **守門驗的是「呼叫端不可以出現行內字串字面值」** ——
```
它完全不讀那些字 ⇒ **零誤判**（引用使用者原話的地方不是呼叫端）
而語氣變成**一份可以一次讀完的清單**，由人審閱
```
📌 〈守門要驗「有沒有人做過決定」〉：這道守門驗的是**文案有沒有被收進那份清單**，
不是「它寫得好不好」—— **後者沒有人有辦法自動判定，而前者可以。**

⚠️ **它擋不到的那一側**（必須寫出來）：
```
有人把一句口語的文案**放進**常數區 => 守門照樣綠
⇒ 這道守門把問題從「散在 1924 行」縮小成「一份清單」，**不是消滅它**
⇒ 所以它要配一條人的規則：**新增或修改 WORDING 的 commit，diff 必須被讀過**
```

## §3 資訊量：**四格**，而它是結構不是散文

異常／失敗類的通知**必須回答四個問題**。散文寫不寫得到，靠人；
而**寫成四個具名欄位之後，守門就驗得到「有沒有寫」**：

```python
WORDING["tender.fetch_failed"] = {
    "what":   "標案雷達無法連線至政府電子採購網，本日未取得任何標案資料。",
    "impact": "本日標案彙總信不會寄出。",
    "system": "系統將於下次排程自動重試；本通知僅於狀態由正常轉為異常時發出一次。",
    "action": "若連續多日未收到標案彙總信，請至標案雷達頁面查看「雷達健康狀態」。",
}
```

```
what    發生了什麼
impact  影響是什麼（**最常被漏掉的一格**）
system  系統會自己做什麼
action  需要人做什麼（**沒有就明著寫「無須人工介入」**）
```

⚙️ **守門驗得到**：異常類的每一筆 `WORDING` 四個鍵都非空。
☠️ 而 `action` 留空與寫「無須人工介入」是**兩回事** ——
留空讓收件人不知道該不該動，**而不知道該不該動的人會去問人**。

📌 ⚠️ 一般（非異常）通知不強制四格：報價單送審那類只需要 `what` ＋ `action`。
**哪些算異常類，寫成一張明確的清單**，不要用「函式名字裡有 failed」去猜。

## §4 參照語域**已經在這個 repo 裡**，不必發明

```
✅ 已經正式（簽核通知，45 處 intro 的多數）
   「您好，以下報價單已進入簽核流程，敬請於系統中完成審核作業。」
   「您好，前層審核已完成，報價單現已進入第 N 層審核階段，敬請登入系統完成審核。」

❌ 過度口語（標案雷達）
   「這通常不需要處理」「下次排程會自動再試」
   「這封信只在「從正常變成異常」的那一次寄出，連續失敗不會每天寄」
   「如果連續多天都沒有收到標案彙總信，請到系統的標案雷達頁面看…」
```

🔑 ⇒ **改寫的目標語域＝簽核通知那一組**，不是某本公文寫作手冊。
📌 而 `_build_html` 的頁尾本來就是正式的
（「本郵件由 MOTRIX 專案管理系統自動發送，請勿直接回覆。」）
⇒ **同一封信裡語域不一致**，那正是使用者讀到的違和感。
