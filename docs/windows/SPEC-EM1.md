### 🔴 它們共同的形狀：**訊息裡出現的是程式的詞彙，不是畫面上的詞彙**

```
參數名／JSON 鍵   status／year_month／action／log_date／user_id／
                  cycle_start_day／backend／scanHours／notifyHours
內部列舉值        unreceived／received／void／return_to_stock／
                  local_drive／s3／pending_acceptance／accepted
協定／標頭名      X-Map-Position／Origin／RP ID
我們自己的註解    第 6 條（uvicorn access log 那一句，**132 字**）
```

### ⇒ 處置：**同樣的資訊，換使用者的詞彙**

⚠️ **不是 `EM3` 的處置。** 兩類差別很大：
```
EM3   **非預期例外** => 使用者做什麼都沒有用 => 固定文案 ＋ 追蹤碼 ＋ 全文進 log
EM1-C **使用者輸入錯誤** => 他**改得動** => 訊息必須說出「改成什麼」
☠️ 套 EM3 的處置 => 「操作失敗，代碼 A1B2C3」 => **把一個可以自己解決的問題
   變成一通電話**
```
🔑 **對齊的是工具（`helpers/errors.py` 在哪、log 怎麼寫），不是處置。**

**改寫的判準（三條）**
```
① 參數名 -> **畫面上那個欄位的標籤**
   「year_month 格式錯誤」 -> 「請選擇月份（格式 2026-09）」
② 內部列舉值 -> **使用者在畫面上看到的選項文字**
   「action 需為 void / return_to_stock / edit_note」
   -> 「請選擇「作廢」「退回庫存」或「修改備註」」
   ⚠️ 而那三個中文**必須與畫面上的按鈕文字逐字相同** —— 否則他找不到
③ 資訊量**不可以減少**（`WD1 §0`）
   「cycle_start_day 需介於 1～28 之間（**29 以後的日子二月沒有**）」
   -> 那個括號是好的，**留著**，只換掉參數名
```

### ☠️ 第 6 條（132 字那一條）是**另一件事**

```
「座標不可以放在網址上：uvicorn 的 access log 會把整串 query string
  寫進 logs/server.log（一個永久追加的檔案）。請改用 X-Map-Position…」
```
🔴 **那是我們寫給自己的設計理由，而它被放進了 `detail`。**
⇒ 使用者看到的應該是「請改用 `X-Map-Position` 標頭傳座標」（或更上層的一句話），
**而那段理由的落點是程式碼註解**。
📌 而**註解裡那一段要留著** —— 它是這個決定的唯一記錄（〈散文對工具是隱形的〉的反面：
它現在寫在一個工具讀得到、而人讀不到的地方）。

### ⚠️ 三條是**超級管理員設定頁**專用（9／10／11 那一組所在的 `system.py`）

```
RP ID／Origin／backend=local_drive|s3
⇒ 讀者確實是懂技術的人 => **它們可以留著技術詞彙**
⚠️ 而「參數名 vs 畫面標籤」那一條**仍然適用**：
   設定頁上那一格叫什麼，訊息就叫什麼
```
📌 ⇒ 這一組的判準不是「要不要技術詞彙」，是「**與畫面一致**」。

## §2 A 類：28 條**不要動**

⚠️ 而**「不要動」要寫成一條可驗的**，否則下一個人會順手改。

```
28 條的共同特徵（我逐條讀過）
  用**畫面上的名詞**（報價單／完工單／簽核／回簽／部門）
  說出**出路**（請先取消回簽／請重新送審／請聯絡最高管理員）
  括號裡是**理由**不是參數（如需修正請透過案件資料整體編輯）
```
📌 其中 `case_extra_expenses.py:554` 是**目標語域的樣本**：
> 「這筆額外支出已核准，附件已上鎖。要補憑證請按「編輯」提出變更申請，
> 新附件會在簽核通過後一併生效」
🔑 **發生了什麼 ／ 現在的狀態 ／ 怎麼做 ／ 做了會怎樣** —— 四件都在，而它不是散文。
⇒ **改寫 C 類時以它為範本**，不要另外發明一種語氣。

### ⚠️ 兩條讀起來卡，而我**建議不動**

```
quotations.py:477  「…此操作不支援於已結案案件…」   語句稍硬，而意思清楚
quotations.py:4266 「請**請**申請人收回並重新送審」  疑似贅字
```
📌 **本項的範圍是「讀者錯了」，不是校對。**
⇒ 標著給使用者看，他要改再改 —— ☠️ **順手改文字會讓 `EM1` 的 diff 混進 28 條沒有人要求的改動**，
而複查的人分不出哪幾條是這一項該改的。

## §3 驗收

```
① 🔴 **C 類 13 條，改完之後訊息裡不含程式詞彙**
   ⚙️ 判定：那 13 條的新文案**不得包含**它對應的參數名／內部列舉值
      （逐條釘，**不是**一張關鍵字黑名單 —— `WD1 §2`）
   ☠️ 而它擋不到「換了一個字而仍然是程式詞彙」 => 配一條人的規則：
      這 13 條的 diff 必須被讀過
② 🔴 **資訊量不減**：每一條改寫前後**逐句對照**，原文說了幾件事，新文案要說幾件
   ⚙️ 人工題，而要留下對照紀錄（同 `WD1 §6③`）
   ☠️ 這一題紅而其他全綠 = 我們把訊息改得更像人話而更難用
③ **A 類 28 條一個字都沒變**
   ⚙️ 判定：那 28 條的字串在改動前後**完全相同**
   🔑 它擋的是「順手改」—— 而順手改的那些**產出是對的**，所以沒有人會抓到
④ 內部列舉值換成中文之後，**與畫面上的按鈕文字逐字相同**
   ⚙️ 觀測點：訊息裡的那幾個詞要在對應的 html 裡找得到
   ☠️ 不一致的話使用者照著訊息去找按鈕**找不到**
⑤ `map_points.py:429` 那 132 字：**理由搬進註解**，而註解裡那一段**必須還在**
   ⚙️ 正對照：改完之後 `grep 'access log'` 在 `.py` 裡仍然命中
```
