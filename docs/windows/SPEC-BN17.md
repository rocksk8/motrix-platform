## §2 🔴 三個缺口，而**第一個最便宜也最該先做**

### ① `reject_award` **不擋空原因** —— 而同一支檔案裡另外兩支擋了

```python
# bonus.py  reject_award()

⚙️ 而同一個系統裡需要理由的另外兩支：
```

```

> ### 🔑 三支需要理由的端點，**兩支擋、一支不擋** —— 而理由是同一個。

⚙️ `mark_award_paid()` 的 docstring 逐字：
> ⚠️ 原因不可為空：空字串存得下去的話，**日後沒有人回得出這筆錢為什麼走系統外**。

```

  「日後沒有人回得出這張單**為什麼被退回**」
☠️ 而 `void_voucher()` 的註解更直接：
  「**沒有理由的作廢等於沒有留痕：事後沒有人回得出為什麼。**」
```

📌 ⇒ 這不是「漏掉一個檢查」，是**同一條規則在第三個地方沒有被套用**。
🔴 ⇒ 守門要釘的是**那一族**，不是這一支（見 §5）。

### ② 退回原因只進 `audit_log` ⇒ **730 天後消失**

> ### ⇒ 與 `JV22 §2b` **完全同一格**，而 A 在那邊已經裁過：
> ### **退回原因必須也寫進 edit_log。**

```

⚠️ 而**不要把 `_audit` 拿掉** —— 兩者職責不同
   audit_log   誰在什麼時候做了什麼（**操作軌跡**，可清理）

### ③ 🔴 `approval_json` 被清成 `'{}'` —— **清除是對的，而沒有留底是另一件事**

```
✅ 所以清是對的 —— 那一格不要動
🔴 而「**上一輪誰簽過、什麼時候簽的**」就這樣**永久消失了**

⚙️ 欄位存在（INTEGER），5 張單**全部是 0** => 從來沒被寫過

> ### ☠️ 而這一個最刺：它正好是**退回流程的終點**。
> ### 使用者退回一張單 ⇒ 作廢 ⇒ 重建 ⇒ 而**沒有任何欄位說這三張是同一件事**。

甲 **退回後要能改內容**（加 PUT）

   ⚠️ 範圍大很多：改金額／人員／比例都要重算，且要擋住已核准的
   🔑 而它讓 `JV22 §6` 的成對顯示**真的成立**

乙 **維持現況**（退回＝只能作廢重建），而把 `supersedes_id` 接起來
   ✅ 範圍小，且它讓三張單串得起來
   ⚠️ 而使用者要走「退回 -> 作廢 -> 重建」三步，
      ☠️ 中間那一步**沒有人告訴他要做**

```

📌 **我傾向乙＋一句提示**，理由不是成本：
```
🔑 甲是一個**新功能**，而使用者這次要的是「退回要有記錄」

⚠️ 而那句話**要說得出為什麼** —— 不要只寫「無法編輯」
```

⚠️ 而**不論裁甲或乙**，§4①②③ 都要做（擋空原因／寫 edit_log／approval_json 留底）。

## §4 處置

### ① 擋空原因（一行）

```python
reason = (body.get("reason") or "").strip()
if not reason:
    raise HTTPException(400, "請填寫退回原因。")
```
⚠️ 而**措辭要與另外兩支一致**（「請填寫…原因。」）—— 不要另外發明一句。

### ② 退回時寫 `bonus_award_edit_log`，`retention='permanent'`

```python
append_edit_log(conn, award_id, _user_name(user), [
    {"field": "status",        "from": status,        "to": "草稿"},
    {"field": "approval_json", "from": row["approval_json"], "to": "{}"},
    {"field": "退回原因",       "from": "",            "to": reason},
], table="bonus_award_edit_log", retention="permanent", changed_at=now)
```

```
🔴 第二列是 §2③ 的留底 —— **在 UPDATE 之前讀 `row["approval_json"]`**
   ☠️ UPDATE 之後才讀就是 `'{}'`，而那一列會寫成 `{} -> {}`
      => **一列看起來很正常的紀錄，而它什麼都沒記住**
      📌 〈假綠燈：斷言驗到自己設的值〉的寫入端版本
⚠️ 第三列的 `from` 是空字串 —— 那**不是**缺改前值：
   退回原因是**新產生的**，本來就沒有舊值
   ✅ 而 `validate_changes()` 用 `"from" not in ch` 判**鍵在不在**
      （docstring 逐字：「`from` 是 `None` 或空字串**算有值**」）=> **合法**，已查
```

### ③ 讀取端：**只有一半成得立** —— 見 §3b

```
🔑 `JV22` 解的是「**上次退回** 與 **這次編修**要成對」
🔴 而獎金單**沒有「這次編修」** —— 它改不了（§3b）
⇒ 本規格的顯示是：「上一輪由 X 覆核、Y 主管簽過，在 <時間> 被 Z 退回，原因：…」
⚠️ 而**不要留一個空的「這次編修」區塊** ——
   ☠️ 它會顯示「（無）」，而使用者會以為是壞了
```

### 🔴 ④ 這一區**不可以有任何編輯或刪除控制項**（沿用 `JV22 §6`）

```
使用者原話（JV22）：「長期記憶，**這個不能刪除**」
⇒ 同一句話對獎金單成立，而 A 已在 JV22 裁成守門 —— 直接沿用
```

## §5 🔴 守門要釘**那一族**，不是這一支

```
✅ 釘：**每一支「需要理由的狀態變更」端點都要擋空字串**
   ⚙️ 母體判準：函式體裡出現 `(body.get("reason") or "").strip()`
      => 必須在其後有一個 `if not reason: raise HTTPException(400, ...)`
   ⚙️ 今天的母體 = **3 支**（reject_award／mark_award_paid／void_voucher）
      🔴 而**加總自檢**：母體 3 = 已擋 2 + 未擋 1（改完變 3 + 0）
```

> ### 🔑 釘這一族的理由：**這不是漏掉一個檢查，是同一條規則在第三個地方沒被套用。**
> ### ☠️ 只修這一支的話，**第四支出現時同樣不會有人想到**。

```
⚙️ 誘餌（合成）：
   A  一支讀了 reason 而沒有擋空的假端點  => **必須亮**
   B  一支讀了 reason 且擋了的            => **不可以亮**
   C  一支根本不收 reason 的               => **不可以亮**（不在母體裡）
   D  註解裡寫 `reason = ...`             => **不可以亮**（用 `ast` 不用 regex）
```

✅ 第二道：**`bonus_award_edit_log` 的寫入端 ≥ 1**
```
🔑 今天是 **0** —— 而「表存在」讓它看起來像已經在用了
   （我自己就差點這樣交出去，C 實查才發現零筆）
⚠️ 而**不要**釘筆數或資料列數 —— 釘**呼叫點存在**
   ☠️ 釘資料列數的話，一個「測試跑完清空資料庫」的環境會讓它紅
```
