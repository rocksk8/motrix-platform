> execute 做可檢查的成品 → review 有足夠的清單跟證據 → fix deploy 處理完上線，
> 讓每個流程都能清晰。」

**這份取代 `MULTIWIN-PROTOCOL.md` 的 §2（角色）與 §4（一輪的七步）。**
**§3（檔案佔用）與 §5 以後的硬規則全部不變，繼續適用。**

## §0 · 為什麼換：今天的失敗幾乎全在交接點

2026-09-21 一天的實測數字：

```
產品碼 17 個 commit ｜ 測試 31 ｜ 文件 190
近兩小時            產品碼 1 ｜ 測試 9 ｜ 文件 35
```

🔴 **190 比 17。** 而那 190 幾乎都是 A。
**不是任何一輪做錯，是迴圈的目標函數被設成了「把每件事裁決並記錄」。**

而當天的重大缺陷，逐一歸類之後**落在交接點的佔多數**：

| 失敗 | 交接點 |
|---|---|
| 「我裁示了 SL17/SL18」而它從來沒被寫出來 | spec → execute |
| §3l 後端做完就算完成，**使用者去找地址欄位找不到** | execute → 完成 |
| A 轉述 C 的回報時換掉了前提（一天兩次） | review → spec |
| D 的語法錯誤回報到 A 手上時已經過期 | research → spec |

🔑 **⇒ 五個階段有四個交接。多分階段本身不會讓流程清晰 ——**
**要清晰的是「每個交接有沒有機器驗得出來的收件條件」。**

## §1 · 五個階段

```
research  →  design&spec  →  execute  →  review  →  fix&deploy
   ↑                                        │
   └────────── 回流（§4，正常路徑）──────────┘
```

### ① research · 研究資料包

**交付物**：一份研究包，格式固定四欄（2026-09-21 由視窗 D 實測長出來的）。

```
as-of          時間、相關檔案 mtime、HEAD sha
方法           逐字貼出用的比對式／查詢／指令
【掃過且確定】  查了什麼範圍，結論是什麼
【沒掃到那裡】  🔴 這個方法看不到什麼
```

🔴 **第四欄是這份格式的全部價值。**
當天兩次靠它救回結論：
1. D 的 regex `assert X == N` **對 `>=` 盲目** ⇒ 而前提斷言幾乎都寫 `>=`
   ⇒ 它系統性地漏掉「防假綠燈的斷言」，**讓測試看起來比實際脆弱**
2. A 派的「全新安裝 − 升級上來」差集法，**涵蓋範圍只有 3 個 key**
   ⇒ `B − A2 = 0` 不是「沒有缺口」，**是這個方法看不到缺口**

⚠️ **沒有那一欄，那兩個 `0` 都會變成「已確認沒問題」。**
📌 **一個空的差集，跟一個看不到東西的方法，輸出完全一樣。**

**退出條件**：第四欄非空。寫不出「我看不到什麼」＝這份研究包不收。

### ② design&spec · 工作規格

## 🔴 交付物不是文字，是**一組紅燈測試**

**這是整份流水線唯一的結構性改動，理由如下：**

> **一份文字規格可以「被裁示」而不存在。**
> **一份紅燈測試沒辦法假裝存在：它要嘛在那裡而且是紅的，要嘛就不在。**

2026-09-21 的實例：A 對兩個視窗都說過「SL17／SL18 已加」——**它們從來沒被寫出來。**
視窗 C 診斷出機制：
> **「你跟我都把『我裁示了』當成『它存在了』，而中間那一步（有人真的寫出來）沒有任何東西在守。」**

**交付物三件**：
1. **一組紅燈**（每一條規格編號對應一支 `def test_<編號>_...`）
2. **一支編號覆蓋率守門**（規格檔裡的編號 ⇄ 測試檔裡的函式名，diff 並指名缺的）
3. **人工驗收項另列**（進 EXEMPT 並寫理由，不可以默默不寫）

**退出條件**：
- 🔴 **覆蓋率守門跑起來是紅的，而且指名得出缺哪幾條**
- 🔴 **每一支新紅燈都答得出「什麼改動會讓它紅」** —— 答不出來的那一支是假綠燈候選
- 🔴 **每一個「上限／不重複／沒有增加」的斷言，都配一條「至少發生過一次」**
  （否則「什麼都不做」永遠滿足它 —— `assert len(x) <= 2` 在 `len(x)==0` 時是綠的）

**⚠️ 規格本身會錯，而且當天錯了至少三次**：
SL3/SL5/SL16 互斥、SL9 把一個語意錯誤的斷言「穩定化」、
A 把使用者指名要拆掉的舊行為寫成不變量。
⇒ **看到測試在斷言某個「看起來很合理的舊行為」，回去對使用者的原話，不要對程式碼現況。**
📌 **程式碼與測試都是上一版需求的化石。**

### ③ execute · 可檢查的成品

## 🔴 「成品」從使用者的座位定義，不從實作者的

2026-09-21 的實例：§3l 被宣告完成，而它只有後端。
```
frontend/pages/company-profile-settings.html   欄位只有 name/tax_id/contact_info/bank_*
                                               沒有 address
frontend/pages/tender-radar.html               呼叫 5 個端點，沒有 /map
```
**使用者去找地址欄位，找不到。**

**退出條件**：
- 🔴 **使用者打得開、看得到、按得下去** —— 端點存在不算成品
- **新端點必須有前端呼叫者**（`check_endpoint_entrypoints.py` 守這件，
  ⚠️ 而它自己的限制要記得：**它把子字串命中當成有入口**，`.../confirm` 會被 `confirmed` 命中）
- **不寫測試**（防假綠燈；測試是 ② 的交付物）
- **範圍凍結**：發現的別的問題**登記**，不順手修
  📌 「我發現的」≠「該做的」——順手做掉的那件沒有人派也沒有人排過順序

### ④ review · 清單與證據

## 🔑 review 不是「再跑一次測試」，是「**這組測試沒覆蓋到什麼**」

②已經把「符不符合規格」變成機器答得出來的問題。
⇒ **review 唯一不可取代的工作是找出規格與測試共同的盲區。**

**交付物**：
1. **證據清單**：每一條結論配「什麼時候、對哪個 sha、什麼條件下量的」
2. **盲區清單**：這組測試放過哪一類錯誤實作
3. **判準本身的自評**：🔴 **「我漏掉的那一類，跟我要找的那一類有沒有相關性？」**
   有相關性的話，**結論的方向已經被判準決定了**

**兩個當天量到的必查項**：
- **fixture 有沒有把系統擺進一個正式機到不了的狀態**
  （`radar_ready` 每次都先 `_set_setting` ⇒ 14 題全在「已設定」下跑，
  而正式機那兩個 key **根本不存在**，且**全新安裝也沒有** ⇒ 那是**每一個安裝的預設狀態**）
- **被 monkeypatch 掉的函式，有沒有另一題讓它真的跑一次**
  （`notify_backup_stale` 被三個測試換掉 ⇒ 本體從未執行 ⇒ 藏了一個 `NameError` 到今天）

### ⑤ fix & deploy · 處理完上線

**退出條件**：
- 全量回歸對**指名的 sha**跑過，紅的逐題等於事先寫下的名單
- **升級路徑驗過**：拿正式機備份的複本實跑 `db._run_migrations()`，
  ⚠️ **複製到 scratchpad 再開，不可直接開 `G:` 上的 sqlite**（開啟會寫 WAL）
- **打包與部署是使用者自己的動作** —— 這一階段交付的是「可以升」這個結論與它的證據

## §2 · 四個交接的收件檢查

🔑 **每一條都要是機器驗得出來的。「我看過了」不算收件檢查。**

| 交接 | 收件檢查 | 當天的反例 |
|---|---|---|
| research → spec | 研究包**第四欄非空**＋**as-of** | D 的語法錯誤回報到 A 手上已過期（mtime 差 55 秒） |
| spec → execute | **編號覆蓋率守門是紅的且指名得出缺哪幾條** | 「SL17/SL18 已加」而它們不存在 |
| execute → review | **端點有前端呼叫者**＋使用者打得開 | §3l 只有後端 |
| review → fix | **轉述附原始輸出，不是摘要** | A 兩次在「更正別人」時換掉了前提 |

### ☠️ 最後那一條特別標出來

> **視窗 B：「你這則訊息裡同時有一個正確的更正與一個錯誤的前提。**
> **更正裡的推論最不會被複驗 —— 因為更正本身讀起來很像已經查過的東西。」**

🔑 **成因**：一個更正必須帶著一個「正確版本」，
**而那個正確版本是順著更正的動能寫出來的，不是查出來的。**
⇒ **寫「我要更正一件」的那一刻，把後面那一段當成全新的主張來查。**

## §3 · 角色分配

### 🔴 硬規則：一個視窗不可以同時站在三個階段上

2026-09-21 的實例：A 同時是 design&spec ＋ review ＋ 協調
⇒ **190 個文件 commit 對 17 個產品碼 commit。瓶頸不是能力，是一個人站在三個關卡上。**

| 階段 | 視窗 |
|---|---|
| research | **D** |
| design&spec | **C**（寫紅燈）＋ A（只決定要做什麼，不寫規格細節） |
| execute | **B** |
| review | **D**（證據與盲區）＋ C（覆蓋率守門） |
| fix & deploy | **B** ＋ 使用者 |

**A 在這套裡只剩兩件事**：**決定做什麼、決定什麼時候停。**
⚠️ **A 不再寫長裁決。** 要記的一句話帶過，需要落地的寫進權威檔，
**而「權威檔」不是 commit message —— commit message 不在任何人的必讀鏈上。**

## §4 · 回流通道（正常路徑，不是例外）

🔴 **execute 或 review 發現規格錯了，要能喊停，而且那不算失敗。**

2026-09-21 規格被發現有錯至少三次：
1. **C 在寫碼前發現 SL3/SL5/SL16 互斥** —— 三題不可能同時綠，**而那不是佈置寫錯，是規格本身矛盾**
2. **D 發現 SL9 的處置（「三條都加時間控制」）只會讓一個語意錯誤的斷言變得穩定**
3. **A 把使用者指名要拆掉的舊行為（每日一次）寫成了要保護的不變量**

**回流的規矩**：
- **停在原地**，不要「先照做再說」
- **喊停的人不負責改規格** —— 它回到 ②
- 🔑 **改完規格要重問一次「原本那個風險還在不在」** ——
  **推翻一個前提不會自動支持它的替代結論**
  （當天實例：B 正確推翻了「舊值在 settings 裡」，
  但舊狀態確實存在，只是在 `tender_fetch_log`；而 B 自己的新實作
  `"YYYY-MM-DD:N"` 存進 `system_settings` **正是那個「升級當下不存在的新標記」**）
