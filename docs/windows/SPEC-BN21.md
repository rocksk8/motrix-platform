# `SPEC-BN21` · 獎金池三層分攤 —— 三組共同分攤同一個池

> 2026-09-23 ／ 視窗 A-2
> ⚙️ 使用者逐字：**「由業務、各執行階段負責人、後勤三組共同分攤這 10% 的金額」**

---

## §1 🔴 核心改動是一句話，而那句話也是最危險的地方

> ### **`total_pct` 從「佔淨利的比例」變成「佔獎金池的比例」——**
> ### **同一個欄位、同一個數字、換一個母體。**

```
現在  amount = base × total_pct × person_pct            （兩層）
之後  amount = base × pool_pct × group_pct × person_pct  （三層）
                      ↑ 新的      ↑ 就是現在的 total_pct
```

☠️ 〈守門守的對象被搬走〉：**斷言沒變、字面值沒變，而決定行為的已經不是它了。**
🔑 ⇒ `total_pct == 1000` 這種斷言，改制前後**都會通過**，而它驗的是兩件不同的事。

### ⚠️ 而問題的嚴重度：**現在沒有任何地方檢查「所有項目加起來 ≤ 100%」**

```
⚙️ routers/bonus.py:950 只擋單一項目：total_pct > 10000 => 400
☠️ 業務 10% ＋ 執行 10% ＋ 後勤 10% = **發掉淨利的 30%**，而系統不會說話
```

## §2 ⚙️ 現況實查（A 交代的三件，全部查到答案）

### ① 三個佔比存哪 —— **`total_pct` 已經隨單凍結了，而池佔比無處可放**

```
⚙️ total_pct 來自**請求 body**（routers/bonus.py:913 `alloc.get("total_pct")`）
   —— 不是範本、不是設定（bonus_templates／bonus_template_versions 都是 **0 列**）
⚙️ 它存進 bonus_award_lines.total_pct —— **每一列都存一份** => ✅ 已經隨單凍結
⚙️ 而 bonus_items **沒有 total_pct 欄位**（實查 PRAGMA）
🔴 bonus_awards 的 20 個欄位裡**沒有任何佔比欄位**
```

> ### ⇒ **三組佔比不必加欄位** —— 它就是現在的 `total_pct`，換一個母體。
> ### 🔴 ⇒ **要加的是「獎金池佔比」**，而它是**單層級**的（一張單一個值）。

```
⇒ bonus_awards 加兩欄：
     pool_pct          INTEGER NOT NULL DEFAULT 1000   # 萬分位，預設 10%
     pool_pct_note     TEXT    NOT NULL DEFAULT ''     # **選填**備註（§3③，不擋）
⚠️ 加在 bonus_awards（不是 lines）—— 一張單只有一個池
✅ 而它天生隨單凍結（那一列就是那張單的）
```

### ② ✅ 既有 5 張獎金單：**換算後金額完全不變**（驗算過，5/5）

```
5 張全部：total_pct = 1000（10%）／person_pct = 10000（100%）／單一項目

  單   base       舊制 amount   新制三層    實際值   相符
  id=1  11,242        1,124       1,124      1,124    ✅
  id=2 483,813       48,381      48,381     48,381    ✅
  id=3   1,041          104         104        104    ✅
  id=4  10,117        1,011       1,011      1,011    ✅
  id=5   2,342          234         234        234    ✅
```
```
⇒ migration：total_pct=1000 拆成 pool_pct=1000 ＋ group_pct(=total_pct)=10000
   舊：(base × 1000//BP) × 10000//BP
   新： base × 1000//BP  →  ×10000//BP  →  ×10000//BP     ← 同一個數，捨去不變
```

> ### 🔴 ⚠️ **而這個安全取決於資料，不是取決於算式。**
```
5 張**全部**是「單一項目 ＋ person_pct=100%」——
☠️ 若正式機上有**多項目**或 person_pct < 100% 的單，換算不一定無損
   （多一層捨去 ⇒ 尾差變大 ⇒ 個人金額可能少 1 元）
🔑 而我們**不碰正式機** ⇒ 見 §6①
```
### 🔴 而「正式機上有沒有舊獎金單」**目前沒有答案，不要寫成有**

```
✅ 使用者逐字：「目前今天做的都沒上正式機」
⚙️ A 實查：本機 deploy_packages/ 只有兩個包（都 09-22），兩個都**沒有獎金模組**
   （正對照：同一個查法對 `quotations` 命中 2 檔 => 查法有效）
🔴 ⚠️ **而包的歷史不完整** —— 他記得存在的 033314 那個已經不在磁碟上
```
> ### ⇒ **證明得了的是「這兩個包裡沒有」，證明不了「獎金模組從來沒出過」。**
> ### 🔑 〈判準的寬窄都會騙人〉：**報「查不到」要同句講出查的範圍。**

```
⇒ migration 要對**兩種情況都成立**：
   沒有舊單  => 它什麼都不做（冪等）
   有舊單    => 照 §2② 換算，而**多項目／person_pct<100% 的那一種要能識別**
⚠️ 而識別不出來時**不要靜默沿用** —— 同一個數字在新舊制下是兩個金額
```

### ③ 🔴 尾差：三層之後不變量會變，**而它現在寫在 docstring 裡**

```
⚙️ helpers/bonus.py:157 逐字：「不變量：Σamount <= pool，且 pool - Σamount < 人數」
⚙️ remainder_of(base, total_pct, lines) = pool_for(...) - Σamount   （:175）
```
> ### ✅ **B 實算過（他只讀不寫）：公式本身仍然正確，變的是上界的推導。**

```
✅ pool - Σ最終金額  —— 它就是「池減掉實際發出去多少」，**分幾層都不會漏算或多算**
🔴 而上界變了：
   兩層  remainder < N_people
   三層  remainder < **N_groups ＋ Σ人數**（多一層 floor）
☠️ ⇒ 直接沿用「remainder < 總人數」當守門，三層會出現
   **正確而被判成缺陷的假紅燈**（上界抓太窄）
```

> ### ⇒ **處置（採 B 的保守版）：分兩道各自驗證，不要合併成跨三層的單一斷言。**
```
① pool → group   那一層自己的 remainder < **組數**
② group → person 那一層自己的 remainder < **該組人數**
```
🔑 理由是他寫的：**未來加第四層時不必重算界線。**

```
⚠️ 而 remainder_of() 的**簽章仍然要改** —— 它現在收 total_pct，
   而三層之後池是 base × pool_pct ⇒ 它算不出正確的 pool
🔑 那與「公式正確」不衝突：**公式對，而餵給它的參數意義變了。**
⚠️ 而 helpers/bonus.py:157 docstring 裡那句「pool - Σamount < 人數」
   ☠️ 要一起改 —— 否則下一個人會拿一個不再成立的上界去判斷程式對不對
```

## §3 處置

### ① 資料層

```
bonus_awards 加 pool_pct（預設 1000）＋ pool_pct_note（選填）
migration：既有 5 張填 pool_pct=1000，lines 的 total_pct **不動**（見 §2②）
⚠️ 而 migration 要**冪等**，且不可以呼叫會演進的 helper
   （〈凍住的歷史不要呼叫活的程式碼〉）
```

### ② 計算層

```
pool_for(base, pool_pct)                    # 母體＝淨利
group_amount = pool × group_pct // BP       # 母體＝**池**   ← 新的一層
amount       = group_amount × person_pct // BP
```
> ### ⚠️ `total_pct` 這個名字**不要留著當「組佔比」** ——
> ### ☠️ 同一個名字換一個母體，是這一件最容易出錯的地方（§1）。
> ### ⇒ 新欄位／新參數叫 **`group_pct`**，而 `bonus_award_lines.total_pct` 這個**欄位名保留**
> ### （改欄位名要動 migration 與所有讀取端，代價大於收益）——
> ### 🔑 **而它的 docstring 要明著寫「這一欄的母體是獎金池，不是淨利」。**

### ③ 守門：**合計必須等於 100%**

```
Σ group_pct ≠ 10000  =>  「產生」鈕 disabled（前端）＋ 400（後端）
⚠️ 兩邊都要 —— 只擋按鈕的話，擋不住請求（同 BN20 §3②）
```
```
而 pool_pct 覆寫：**選填備註，不擋、不必填**
   ⚙️ 使用者重述逐字：「**預設 10% 但要更改也可以**」
   ✅ 誰改的、改成多少，`bonus_awards` 那一列本來就記得住
```

> ### ~~而 pool_pct 覆寫：= 1000 不必填原因 ／ ≠ 1000 **必填原因**，空的擋 400~~
> ### 📌 **上面那一條已撤銷（A 加的，不是使用者原話）。**
```
☠️ 而撤銷它的是**使用者重述了同一件事，而重述裡沒有那一條** ——
   **不是有人發現它錯了**。
🔑 ⇒ 那個區別決定下一個人能不能再提它：**它沒有被否決，只是沒有被要求。**
⚠️ 而它的形狀是〈我發現的≠該做的〉：**那條沒有人派、也沒有人排過順序。**
```

## §4 驗收（`AC1`：後端＋前端＋頁面）

### ① 必過

```
① 三組合計 100% => 產生成功，Σamount ≤ pool
② 三組合計 90%  => 400，而訊息要說**現在是多少**（不是只說「不等於 100」）
③ 三組合計 110% => 400
④ pool_pct 不填 => 用預設 1000
⑤ pool_pct = 1500、備註**留空** => **成功**（備註是選填，不可以擋）
   🔴 這一題是在擋「把撤銷掉的必填又加回來」——見 §3③ 那個刪除線
⑥ pool_pct = 1500 ＋ 備註 => 成功，且 pool = base × 15%
⑦ 既有 5 張（migration 後）重新讀取 => amount **與 migration 前逐筆相同**
⑧ 前端：合計 ≠ 100% 時「產生」鈕 disabled，且畫面上看得到目前合計是多少
```

### ② 🔴 誘餌：**擋住「換母體」這個缺陷本身**

```
誘餌：base=1,000,000／pool_pct=1000／三組各 10000（即各 100%，合計 300%）
   ✅ 正確實作 => 400（合計 ≠ 100%）
   ☠️ 而**沒有改母體**的實作 => 三組各拿 base×10% = 300,000，

🔑 ⇒ 這一題同時驗「新守門在」與「母體真的換了」
```
