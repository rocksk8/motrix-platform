## §2 ① 判定來源與時間戳 —— 🟢 **兩個都已經存在，不必加欄位**

```sql
-- 一個候選憑證 (type, docNo, fileId) 有沒有被用過、什麼時候
SELECT va.voucher_id, va.uploaded_at, v.voucher_no, v.voided_at
  FROM voucher_attachments va
  JOIN vouchers_all v ON v.id = va.voucher_id
 WHERE va.source_type    = ?
   AND va.source_doc_no  = ?
   AND va.source_file_id = ?
   AND va.deleted_at     = ''        -- §2b
   AND v.voided_at       = ''        -- §3
 ORDER BY va.uploaded_at DESC
```

> ### 🔑 **這一件不需要新欄位** —— 這一格原本會決定規模，而答案是「規模小」。

### §2b `deleted_at` 要濾掉 —— **照既有慣例，不要自己發明**

```
routers/vouchers.py:890  _attachments_of(conn, voucher_id, include_deleted=False)
   docstring 逐字：「**預設不列已刪的**」
   而「已刪的那幾列**留在表裡也留在備份裡** —— 一個被刪掉的憑證與一個
     從來不存在的憑證，在紀錄上必須分得開」
```
⇒ `JV18` 的查詢**沿用同一條**：`deleted_at = ''`。
🔑 理由不是「比較乾淨」，是**它已經是這張表的讀取慣例**，另開一種會出現兩種「已刪」的意思。

### §2c 🔴 `source_*` 的三種寫法 —— **查詢的 `WHERE` 要看這一節**

`_insert_attachment()` 有 **3 個呼叫點**（`routers/vouchers.py`）：

```
:969   直接上傳     source_type=""    source_doc_no=""        source_file_id=""
                    🔴 **三個都是空字串**
:987   帶入         item["source_type"] / ["source_doc_no"] / ["source_file_id"]
                    ✅ 真實的來源三元組
:1166  作廢重開複製  COPY_SOURCE_TYPE   str(old_id)            att["file_id"]
                    🔴 **= "voucher"** —— 指的是**舊傳票**，不是原始憑證
```

#### 🔴 後果一：空值會造成**滿畫面假紅字**

```
直接上傳的每一列都是 ("", "", "")
=> 查詢若不排除空值，**它們全部互相匹配** => 全部亮紅字
☠️ 而那是**假的紅字，比沒做還糟** —— 使用者會開始不相信這個標記
```
⇒ `WHERE` 必須排除：
```sql
AND va.source_type    <> ''
AND va.source_doc_no  <> ''
AND va.source_file_id <> ''
```

#### 🔴 後果二（A 沒問到，我查出來的）：**作廢重開之後找不到原始憑證**

```
憑證 X 被傳票 A 帶入       => A 的那一列 source_* = (原始 type, docNo, X)
A 作廢重開成 B            => B 的那一列 source_* = ("voucher", A_id, A 的 file_id)
                             🔴 **不再指向 X**
=> JV18 去查 X 時**找不到 B** => X 顯示成「**未計算**」
```

> ### ☠️ 而那是**假的「未計算」** —— 它正被 B 使用中。
> ### 🔑 這一種錯的方向與空值那一種**相反，而且更貴**：
> ### 空值讓人不信任標記；這一種讓人**照著標記去重複入帳**，而那正是要防的事。

#### ⚠️ 而 `supersedes_no` **存在而從來沒有被寫入**

```
db.py:4855  supersedes_no TEXT NOT NULL DEFAULT ''   # 本張取代了哪一張
⚙️ 全 backend 的寫入點 = **0**
   （只有 db.py 的建表、helpers/voucher.py:27 的一句註解、一支測試的 docstring）
void_voucher 的 INSERT 欄位清單（vouchers.py:695）**沒有它**
```
🔑 ⇒ 目前 **A→B 的唯一連結就是附件的 `source_*`** ——
所以不能只是「把 source_* 改回原始值」，那會把那條連結也刪掉。

#### ✅ 建議處置：**丙** —— 兩個資訊各歸各位

```
① _copy_attachments_to() 複製時**沿用來源列的原始 source_***
   （att["source_type"] / ["source_doc_no"] / ["source_file_id"]）
   => 憑證 X 在 B 上仍然查得到
② void_voucher(reopen=True) 的 INSERT **補寫 supersedes_no**
   => 「B 取代了 A」這件事回到它本來就該在的欄位（db.py:4855 的註解逐字寫著）
```

**顧慮**：作廢重開之後，原始憑證在新單上查不到 ⇒ 假的「未計算」⇒ 重複入帳。

**丙這個處置自己的副作用**（分開寫）：
```
⚠️ ① 它動到 `void_voucher` 與 `_copy_attachments_to` —— **兩支都不是 JV18 的範圍**
      => 要 A 決定是併進 JV18 還是另開編號
⚠️ ② **既有資料不會回溯修好** —— 已經存在的重開單，source_* 仍指向舊傳票
      ⇒ 查詢**仍要處理 source_type='voucher' 的舊列**（防禦性），不能假設它不存在
      📌 而開發機目前只有 2 張傳票／1 筆附件 => 實務上幾乎沒有既有資料
         ⚠️ **正式機要先查過再說這句話**
⚠️ ③ 補寫 supersedes_no 之後，**會有人以為它一直都有值** ——
      舊資料那一欄是空的，任何讀它的地方都要能吃空值
```

## §3 ② 已作廢的傳票用過的憑證 —— **不算已使用**，而理由比「那筆帳不存在了」硬

A 的傾向是對的，**而真正的理由在作廢重開那條路上**：

```python
# routers/vouchers.py:690-712  void_voucher(reopen=True)
#   🔴 **另開一張**（新的 voucher_id）—— 與「退回升版」不同
copied = _copy_attachments_to(conn, voucher_id, new_id, who, now)
```

```
作廢重開 => 附件被**複製**到新單 => 同一個 source_file_id
           **同時掛在作廢單與新單上**（兩列 voucher_attachments）
```

> ### ☠️ 若作廢單也算「已使用」，**每一次作廢重開都會讓憑證被標記兩次** ——
> ### 而其中一次指向**一張不存在的帳**。

🔑 而更貴的一面：若日後有人把「已計算」從**標記**升級成**擋住**，
**作廢重開這條合法的路會被自己的守門擋死** ——
一張單作廢了、重開的那張要補帶同一份憑證，而系統說「已計算」。
📌 〈防護的副作用落在盲側〉：加守門要問「**它擋不到／誤擋的那一側會不會更難看見**」。

## §6 落地形狀

### §6a 後端：`case_attachments()` 多回三個欄位

```python
# helpers/voucher_attachments.py:348
out.append({
    …既有欄位…,
    "usedBy":  [ {"voucherNo": …, "voucherId": …, "usedAt": …}, … ],   # 新
    "usedAt":  最近一次的 uploaded_at 或 "",                            # 新，排序用
    "used":    bool(usedBy),                                            # 新
})
```

⚠️ **一次查詢**，不要每一筆各查一次：
```
先把這個案件底下所有候選的 (type, docNo, fileId) 收齊，
一次 SELECT … WHERE (source_type, source_doc_no, source_file_id) IN (…)
☠️ 逐筆查的話，一個有 40 個憑證的案件會打 40 次 DB
```

### §6b 排序在**後端**做

```
未使用的  維持現有順序（依 _CASE_SCOPED 的型別順序 → doc_no → 檔案順序）
已使用的  **排在最後**，依 usedAt **DESC**（新到舊）
```
🔑 **不要讓前端排** —— 排序規則寫在兩個地方就會有兩種順序，
而「它們有一天不一樣了」不會有人報修。

### §6c 前端：紅字 ＋ 不可 disable

```
voucher.html:316 那顆按鈕目前是
   :disabled="!canEdit || (it.exists === false)"
🔴 **不要把 used 加進 :disabled**
```

> ### ☠️ 使用者要的是「**備註**（紅字＋已計算）」，**不是擋住**。

```
他沒有說不可以再帶入 —— 而擋住是一個**他沒有要求的行為改變**
⚠️ 而擋住之後，作廢重開那條路會踩到 §3 的問題
📌 〈推翻的證據不會自動支持替代方案〉：
   「應該要防止重複入帳」是一個成立的顧慮，
   **而「擋住」是一個沒有被檢驗的處置。**
```

## §7 驗收（`AC1`）

```
① 後端  case_attachments() 回 used／usedAt／usedBy；已作廢的傳票**不計入**
        ⚙️ 一次查詢（不是 N 次）
② 前端  紅字「已計算」＋ 點得開看被誰用的
③ 頁面  ⓐ 案件有 3 個憑證，其中 1 個已被傳票 A 帶入
           => 開新傳票的「已上傳檔案」頁籤：那 1 個在**最後**、有紅字
        ⓑ 點紅字 => 看得到「傳票 A」與時間
        ⓒ 把傳票 A **作廢** => 重整 => 那個憑證的紅字**消失**
           🔑 ⓒ 是 §3 的驗收 —— 沒有它就分不出「有處理作廢」與「剛好沒人試」
        ⓓ 同一個憑證被**兩張**傳票帶入 => 紅字要列出**兩張**
           🔑 ⓓ 是 §5 的驗收 —— 只顯示最近一張的話，重複入帳那筆正好被藏起來
        ⓔ 🔴 **負對照：已計算的憑證仍然按得下去**（不是 disabled）
           🔑 沒有這一題的話，「**順手擋掉更安全**」不會被任何東西發現，
              而它會踩死 §3 那條**作廢重開**的合法路
        ⓕ 直接上傳的附件（source_* 全空）**不可以互相亮紅字**（§2c 後果一）
        ⓖ 作廢重開之後，原始憑證**仍然標著已計算**（§2c 後果二）
```

### ⚠️ 給 C：兩個容易寫成假綠燈的地方

```
☠️ ⓐ 的「排在最後」：若清單只有 1 筆已使用、而它本來就在最後 => **排序壞掉也會綠**
   ⇒ 造 **2 筆已使用 ＋ 2 筆未使用**，且已使用那兩筆的 uploaded_at **要不同**
☠️ ⓒ 的「紅字消失」：若那個憑證從頭到尾就沒有紅字 => 也會綠
   ⇒ **先斷言作廢前有紅字**，再作廢，再斷言消失（同一題兩段）
```
