# `SPEC-JV21` · 傳票摘要要能帶入案件底下的支出項

> 座標：`a719963`（工作樹：本檔為新增）
> 作者：視窗 A-2 ／ 2026-09-23
> 使用者原話：
> 「**摘要部分帶入案件的內容**，例如我點選案件，這裡面有甚麼**支出項有發票的**
> 都需要能帶入，例如**承攬商有發票有支出**、**叫料有發票有支出**，
> **點選案件內的案件可以帶入子項目**」

---

## §1 現況：`summary-sources` 列的是**案件本身**與**檔案**，沒有「支出項」

```
頁籤① 案件         SELECT quote_no, customer_name, project_name, status FROM quotations
                   => 只有案件本身
頁籤② 已上傳檔案   case_attachments(conn, quote_no)
                   => 列的是**憑證檔案**，不是**支出項目**
```
🔴 ⇒ 使用者要的是**第三種東西**：案件底下的**各筆支出**（有金額、有發票）。

---

## §2 ① 「支出項有發票」在資料層是什麼 —— 🔴 **三個來源，三種「有發票」**

### 用結構圈母體（`PRAGMA table_info`，不用名字猜）

```
⚙️ 全 DB 97 張表裡，**同時**有「金額型欄位」與「發票型欄位」的 = **1 張**
   contractor_dispatches   金額 total_amount ／ 發票 invoice_no, invoice_files_json
```

### 🔴 而 A 點名的五張候選裡，**有一張不存在**

```
contractor_dispatches   ✅ 存在  金額✅ 發票✅（**欄位**）
case_extra_expenses     ✅ 存在  金額✅ total_cost   發票❌（**沒有發票欄位**）
invoice_vouchers        ✅ 存在  金額✅ amount       發票❌
payment_requests        ✅ 存在  金額✅ amount       發票❌
🔴 material_orders      **這張表不存在**
```

### 🔑 「有發票」**不是一個欄位** —— 三個來源各自不同

| 來源 | 金額在哪 | 「有發票」怎麼判 |
|---|---|---|
| **承攬商派工**<br>`contractor_dispatches` | `total_amount`（＋`items_json`／`personnel_json`，見 ⚠️） | `invoice_no` **欄位** ／ `invoice_files_json` **附件** |
| **叫料**<br>`quotations.data_json.materials[i]` | `qty × unitCost` | `invoiceFiles` **陣列**（JSON） |
| **案件額外支出**<br>`case_extra_expenses` | `total_cost` **欄位** | `files_json` **附件** ＋ `doc_no`（憑證單號） |

⚠️ **叫料不是一張表** —— 它在 `quotations.data_json.materials`，
而它的發票走 `POST /api/quotations/{no}/materials/{idx}/invoice-files`。
📌 ⇒ A 說的「用結構圈母體不要用名字猜」在這裡的結果是：
**三個來源裡只有一個是「表」，另外兩個一個在 JSON、一個發票在附件。**

### ⚠️ 而 `contractor_dispatches.total_amount` **不是那一筆的總額**

```
`ACC-BN6 §3` 已經踩過這一顆：
   grandTotal = (items 小計 × (1+稅率)) ＋ **外包人員費用**
   而 total_amount 少了稅、也少了人員
☠️ 帶入摘要若用 total_amount，**金額會比實際少**
⇒ 用 `vendor_contractors.py:147` 已經算好的 `grandTotal`
```
🔑 **這個坑今天已經有人踩過並記下來了** —— 不要再踩一次。

### 🔑 而「案件底下有哪些憑證來源」**已經枚舉過了**

```python
# helpers/voucher_attachments.py:54  SOURCE_TYPES
"quotation_signed"    # 報價單回簽檔
"case_update"         # 案件動態
"payment_item"        # 收款項目的發票影本
"material"            # 叫料清單的附件
"material_invoice"    # 叫料清單的發票／包裝清單
"extra_expense"       # 案件額外支出
"invoice_voucher"     # 開票申請
"contractor_dispatch" # 承攬商派工
"contractor_invoice"  # 承攬商發票
```

> ### 📌 **`JV21` 要的「支出項」是這份清單的子集 ＋ 金額。**

```
✅ 是支出      contractor_dispatch ／ contractor_invoice ／ material ／
              material_invoice ／ extra_expense
❌ 不是支出    payment_item（**收款**，發票是開給客戶的）
              quotation_signed ／ case_update（不是支出）
⚠️ 待判        invoice_voucher（開票申請 —— 那是**開給客戶**的票，不是我們的支出）
```
🔑 ⇒ **不要新寫一份來源清單** —— 沿用 `SOURCE_TYPES` 並標出哪幾種是支出。
📌 而 `case_attachments()` 已經在跑這份清單 ⇒ `JV21` 是**同一批來源、換一種輸出**
（回「項目＋金額」而不是「檔案」）。

## §3 ② 🔴 「點選案件內的案件」—— **子案件不存在，這句話要回去問**

### 實查

```
quotations 共 **31 個欄位**
⚙️ parent／child／sub／root 命中 = **0 個**
=> **沒有子案件這種結構**
```

### 兩個候選讀法，**我不猜**

```
甲 「案件內的案件」是口語／筆誤，指的是「案件內的**項目**」
   => 兩層：案件 -> 該案件底下的支出明細
   ✅ 與同一句的前半「這裡面有甚麼支出項有發票的都需要能帶入」一致
   ✅ 與「可以帶入**子項目**」也一致（子項目 = 支出明細）

乙 真的有第二層案件概念
   ⚠️ 系統裡最接近的是 `dev_cases.converted_quote_no`（業務開發案 -> 報價單）
      —— 但那是**前身**不是**子案件**
```

> ### 📌 **請 A 向使用者確認一句：**
> ### 「『案件內的案件』指的是**案件底下的支出明細**，還是另一層案件？」

⚠️ 在確認之前本規格**照甲寫**，而甲乙的差別**只在第三層要不要做** ——
若答案是乙，§4 的資料形狀要多一層，其餘不變。

## §4 ③ 帶入之後長什麼樣 —— 🔴 **不可以存來源 id**

`JV7` 的裁定逐字（`vouchers.py:312-320`）：

> 帶入只是**省打字** ⇒ 帶完之後那一格仍然要打得動，
> 而最終值是**使用者打的那個**，不是來源 id 再組一次。
> ☠️ 存來源 id、開啟時重組的實作，症狀是「使用者改完、存檔、關掉；
> **下次打開才變回來**」—— 中間隔了幾天，他不會把兩件事連起來。

### ⇒ 形狀

```
點一筆支出 => 把**一段文字**寫進當前那一行的摘要欄
           => 之後它就是一段普通文字，**系統不記得它從哪來**
```

### 文字內容（建議，A 可改）

```
承攬商派工   「{廠商名}－{範圍}　NT$ {grandTotal}」
叫料         「叫料－{品名}　NT$ {金額}」
額外支出     「{備註}　NT$ {total_cost}」
⚠️ **金額要帶**（使用者原話「有發票**有支出**」⇒ 他要的就是金額）
⚠️ 而**發票號碼**要不要帶：承攬商派工有 `invoice_no`，另外兩種沒有
   🔑 ⇒ **有的才帶**，不要為了一致而留一個空欄位
      （`describe_missing()` 的既有慣例：缺的留空並回報，不要編）
```

## §5 ④ 閘門 —— **顧慮變大了，而處置不變**

`summary-sources` 的 docstring 已經警告過：

> 這裡會列出**案件**（客戶名、報價單號）—— 那是業務資料不是傳票資料。
> ☠️ 閘門放鬆的話，等於**從一個記帳畫面繞過去看客戶清單**。

```
🔴 而 JV21 多列了**每一筆支出的金額** => 那個顧慮從「看得到客戶清單」
   變成「**看得到每個案件的成本結構**」
```

### ✅ 處置：**閘門不放鬆，而且要明著寫「為什麼不放鬆」**

```
維持 `_require_voucher_access(_require_user(authorization))`
   —— 與其餘 14 支傳票端點**同一道**（`SPEC-JV16 §2` 已驗過全部一致）
⚠️ 而 `JV21` **不要**因為「只是列個摘要來源」就降級成 `_require_user`
   🔑 那正是 `vouchers.py:60` 那段註解在擋的事
```

⚠️ **而有一件要另外問**：`canSeeFinancial()` 那一層。
```
案件管理頁的「額外支出」頁籤有 `canSeeFinancial()` 這一層額外閘門
   （role ∈ superadmin/admin/sales 或有 financial_view 模組）
🔴 而 JV21 會讓「有傳票權限但沒有 financial_view」的人看到同樣的金額
⇒ **兩道閘門的寬窄不一致**，要 A 裁：以哪一邊為準
```

## §6 ⑤ `JV18` 的「已計算」標記 —— 🔴 **套不上，而依據是 `JV7`**

```
JV18 的標記靠的是 voucher_attachments 的 (source_type, source_doc_no, source_file_id)
   => **因為附件是被複製進來的，系統記得它從哪來**
JV21 的帶入寫的是**一段文字**，而 JV7 明著裁**不存來源 id**
   => **沒有任何連結可以查「這筆支出被哪張傳票用過」**
```

> ### ⇒ **套不上 —— 不是不想做，是沒有連結。**

### ⚠️ 而「要做就得違反 `JV7`」這件事要寫出來

```
若日後真的要標，只有兩條路：
甲 存來源 id  => **違反 JV7**（症狀：改完存檔關掉，下次打開才變回來）
乙 另外開一張「這張傳票參照了哪些支出」的關聯表，**與摘要文字無關**
   ✅ 它不會回頭覆蓋使用者打的字
   ⚠️ 而它要有人去維護（使用者改了摘要，關聯還在）
      => 那個關聯的語意變成「**他當初點過什麼**」不是「這張傳票記了什麼」
      🔑 而那兩件事不一樣 —— **不要用同一個欄位表示**
```
📌 ⇒ 本規格**不做標記**，而把乙寫下來當作日後的路。

## §7 ⚠️ 新增端點的**路由順序坑**（A 點名）

`vouchers.py` 在那條動態 GET 之前有一段寫在碼裡的警告：

> 要加**靜態** GET 路徑的人：**宣告在這一行之前**。
> 🔑 **422 讀起來像「我參數傳錯了」，而實際是「這條路還沒做」** ——
> 查的人會去翻自己的呼叫端，而問題在這個檔案的行號順序上。

```
🔴 JV21 若新增 `GET /api/vouchers/case-expenses`（或任何靜態路徑）
   => **必須宣告在 `@router.get("/{voucher_id}")`（:398）之前**
⚙️ 而驗收要有一題：打那支新端點**不可以回 422**
   🔑 釘 422 不是釘 404 —— 那才是這個坑的症狀
```

📌 **而更好的做法是不新增端點**：`summary-sources` 已經吃 `quote_no` 參數，
多回一個頁籤的資料即可 ⇒ **連這個坑都不必踩**。

## §8 驗收（`AC1`）

```
① 後端  summary-sources 多回一個「支出項」頁籤，
        來源沿用 SOURCE_TYPES 的支出子集，金額用 grandTotal 不用 total_amount
        閘門維持 _require_voucher_access
② 前端  第三個頁籤；點一筆 => 文字寫進當前行的摘要，**之後可以自由編輯**
③ 頁面  ⓐ 用 `MQ-202608-007`（4 筆派工）=> 支出頁籤列出 4 筆
           金額分別 187,992／63,000／16,275／**2,500**
           🔑 最後那筆 items=0、只有人員 —— 用 total_amount 會變成 **0**
        ⓑ 用 `MQ-202608-003` => 額外支出 1 筆 NT$3,500
        ⓒ 帶入後**改掉那段文字** -> 存檔 -> 關掉 -> 重開
           => **仍然是他改的那段**（`JV7` 的驗收）
        ⓓ 新端點（若有）**不回 422**
        ⓔ 沒有 cashier／finance 模組的帳號 -> **403**
```
