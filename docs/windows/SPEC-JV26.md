## §2 ⚙️ 八個欄位（逐一列名，不用「其餘」帶過）

```
account_name_snapshot       TEXT    NOT NULL DEFAULT ''
summary_template_id         INTEGER NOT NULL DEFAULT 0
summary_template_version    INTEGER NOT NULL DEFAULT 0
dept_code                   TEXT    NOT NULL DEFAULT ''
source_type                 TEXT    NOT NULL DEFAULT ''
source_id                   INTEGER NOT NULL DEFAULT 0
source_amount_snapshot      INTEGER NOT NULL DEFAULT 0
counterparty                TEXT    NOT NULL DEFAULT ''
```

⚠️ **逐一列名的理由**：
```
寫「其餘 8 欄」的話，日後 schema 再加一欄 => 那句話**自動涵蓋了它**
☠️ 而新欄位沒有人做過決定 —— 它只是被一句含糊的話收編了
📌 〈守門要驗「有沒有人做過決定」〉
```

### 🔴 而 `account_name_snapshot` **不屬於這一族**

```
它**有寫入端**：`helpers/voucher.py:602` 的 UPDATE
   （`post_voucher()` 過帳時整批重寫）
也**有消費端**：`get_voucher():313`（只在 status == '已過帳' 時讀）
⇒ ✅ **它已經接好線了**，只是不由那三支 INSERT 寫
```
🔑 ⇒ 真正未接線的是 **7 欄**，而 `account_name_snapshot` 列在上面
是為了讓「15 = 6 + 1(id) + 8」這個加總對得起來 —— **標明它是特例**。
☠️ 少了這一句，下一個人會把它一起接線，而那會與 `post_voucher()` 打架。

## §3 🔴 接線那天：**三個寫入點要一起改**

```
backend/routers/vouchers.py:212   create_voucher()
backend/routers/vouchers.py:706   void_voucher() 的作廢重開
backend/routers/vouchers.py:865   update_voucher()
⚙️ 今天三支寫的是**一模一樣的 6 欄**：
   (voucher_id, line_no, account_code, summary, debit, credit)
```

> ### ☠️ 只改其中一支的後果：
> ### **建立出來的單沒有值、重開出來的有值** —— 而兩者都是「正常的傳票」。

```
🔑 那比現在更難查：現在是**一致地沒有**，改一支之後是**不一致地有**
⚠️ 而 diff 上看不出來 —— 三支在不同的函式裡，
   改動只會出現在其中一支的那幾行
```

### ⇒ 守門要釘「**三支的欄位清單相同**」

```
✅ 釘：三支 INSERT 的欄名集合**逐字相等**
   ⚙️ 量法：`ast` 取那三個 `conn.execute()` 的第一個字串參數，
      解析 `INSERT INTO voucher_lines (...)` 的欄名，**比對三個集合**
   🔴 用 `ast` 不用 regex —— 那三句 SQL 都是**跨行字串串接**
      （`"INSERT INTO voucher_lines (voucher_id, line_no," " account_code, …"`）
      ☠️ 逐行 regex 只會看到半句
❌ **不要**釘「欄數 = 表欄數 − N」
   ☠️ 那個 N 會在 schema 加欄位時過期，而**它過期的樣子是紅燈**
   ⇒ 下一個人最省力的反應是**把 N 加一**，而那等於什麼都沒守
```

⚙️ **誘餌**（合成，不改產品碼）：
```
A  三段 INSERT 字串，其中一段少一欄            => **必須亮**
B  三段一模一樣（含今天的 6 欄）                => **不可以亮**
C  三段都多同一欄（模擬「一起接線」）            => **不可以亮**
   🔑 C 是這道守門的目的 —— 它守的是**一致**，不是**欄數**
D  註解裡寫一段假的 INSERT                      => **不可以亮**（ast 看不到註解）
```

## §4 🔑 這一族的形狀：**意圖存在、實作缺席**

```
同一輪的 `JV24` 裡出現了兩族：
   ① `vouchers_all.supersedes_no`
      註解逐字「本張取代了哪一張」，而**從來沒被寫過也沒被讀過**
      ☠️ 且 `helpers/voucher.py:24` 有一句 docstring 說作廢落在**四個**欄位上
         —— 第四個就是它 ⇒ **那句話有四分之一是假的**
   ② 本規格這 7 欄
```

> ### ⇒ **schema 先寫好、程式碼後補，而中間的空窗期沒有人在管。**

```
🔑 而空窗期的危險不在「沒有功能」，在**它看起來像有**：
   讀 schema 的人會相信那一欄有值
   讀註解的人會相信那件事做完了
☠️ 而 `JV24` 就是這樣出事的 —— 我拿 `PRAGMA` 當基準算出「丟掉 9 欄」
```

📌 ⇒ 建議（**不是本規格的範圍**，給 A 排）：
```
schema 上的「已規劃未接線」欄位要有一個**可以被數出來的**標記
   ⚙️ 例如註解統一寫 `-- TODO(未接線)`，並有一道守門數它的數量
🔑 判準不是「不要有未接線欄位」（那不可能），
   是「**未接線的欄位要數得出來**」
⚠️ 而我**沒有量過全庫有幾張表有這種欄位** —— 這一句是從兩個實例推的
```

## §5 驗收

```
① 後端  **無異動**
② 前端  **無異動**
③ 頁面  **無異動**
```

> ### 🔑 這份規格今天**沒有驗收項**，而那是它的正確狀態。
> ### ⇒ 它的「驗收」發生在**未來某次接線**的那一輪：
> ### 那一輪要引用本檔，並讓 §3 的守門先存在。

⚠️ ⇒ §3 的守門**可以現在就做**（它今天是綠的，且它守的是「不要變得不一致」）。
🔴 而那要 A 決定：
```
甲 現在就加守門  ✅ 未來自動擋住「只改一支」
                 ⚠️ 而它今天守的是一個**沒有人打算改的東西** => 可能被當成雜訊
乙 接線那天再加  ⚠️ 而那一天沒有人會想起這份規格
                 ☠️ 這正是「給未來的便條」最常見的失敗方式
```
### ✅ A 裁：**甲 —— 守門現在就加**（2026-09-23）

```
理由（我提、A 採用）：**另一條路的失敗不需要任何人犯錯就會發生。**
🔑 乙（接線那天再加）要靠「那一天有人想起這份規格」——
   而那正是「給未來的便條」最常見的失敗方式
```
⚠️ ⇒ 守門今天是**綠的**，而它守的是「**不要變得不一致**」，不是「現在有問題」。
📌 寫題時要在檔頭寫明這一點，否則下一個人會以為它是誤報而拿掉它。
