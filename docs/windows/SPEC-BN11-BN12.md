## §1 ① 「比照報價單」——**兩邊的階段逐項對照**

### 報價單

```
草稿 ──submit──▶ 待審核 ──(分層簽核)──▶ 簽核中 ──▶ **已送出**
                   │                                  │
                   │◀── recall（申請人自己收回）        │
                   │                                  ▼
                   ▼                            deal_tag：已成案 ─▶ 已結案
              reject ──▶ 草稿（**換單號升版** MQ-…-R1）
已送出 ──解鎖編輯──▶ 待審核（**強制重簽**，寫 editHistory + rev）
其他終態：已取消 ／ 已拒絕（`_STATUS_PATCH_WHITELIST`）
```

### 獎金分潤單（`BN8` 之後）

```
草稿 ──submit──▶ 待審核 ──▶ 簽核中 ──▶ **已核准**
                   │                        │
                   │                        ▼
                   │                  **已發放**（⚠️ 不是 status，見下）
                   ▼
              reject ──▶ 草稿（**不換號、不升版**）
任何狀態 ──▶ 作廢（voided_at／voided_by／void_reason）
```

### 🔴 差在**三格**

| # | 報價單有 | 獎金單 | 規模 |
|---|---|---|---|
| ① | **recall**（申請人自己收回待審核的單） | ❌ 沒有 | 小（一支端點） |
| ② | **reject 換單號升版**（`_next_revision_no`） | ⚠️ reject 有，**不升版** | 中（要有版本概念） |
| ③ | **解鎖編輯強制重簽**（`editHistory` + rev） | ❌ 沒有 | **大** |

### ✅ 三格的裁定（A 2026-09-23，② 上呈使用者）

#### ① **recall ⇒ 要做**

```
POST /api/bonus/awards/{award_id}/recall
   權限  **申請人本人**（approval_json.requestedBy）
   狀態  待審核／簽核中 -> 草稿，並清 approval_json
   ⚠️ 比照 quotations.py:1616 recall_quotation（「只有原送審申請人可以收回」）
```
🔑 A 的理由：**缺席的代價是「申請人送錯只能請簽核人退回」** —— 那是每天會遇到的麻煩。

#### ② **reject 換單號升版 ⇒ 不做**（**使用者裁**）

> 使用者選：「**不升版，退回就回草稿**」
> 理由：獎金單**不寄給客戶、不對外流通**，升版價值低，
> 而改單號會把 `QN1` 那個「下游存舊單號」的坑**再踩一次**。

🔴 ⇒ `bonus_awards.supersedes_id`（`db.py:4662`）**已裁定不寫入**
（使用者 2026-09-23）。

```
⚠️ 這一列要留著，理由：
   它是**第三個**「欄位存在而寫入點 0」（傳票 `supersedes_no`／獎金 `supersedes_id`）
   ☠️ 而下一個人看到一個空欄位**會以為是漏做的** ——
      標「已裁定不寫入＋日期」才擋得住他去「補」它
```

#### ③ **解鎖編輯強制重簽 ⇒ 🔴 前提不存在，而它不是「不做」**

```
`SPEC-BN8 §5e ①` 已查：**沒有任何端點可以改比例**
（allocations 只在 `POST /awards` 出現）
🔑 ⇒ **要先有「改比例」才談得上「改完要重簽」**
```

> ### 🔴 **寫成「前提出現時回來收斂」，不要寫成「不做」。**

```
📌 依據 `§293`（`BN7` 用印欄那一格的教訓）：
   **一個「因為 X 不存在所以先不做」的待決，在 X 被做出來之後不會自己收斂。**
⇒ 收斂條件寫死：
   **日後若新增任何可以改 `allocations` 的端點**，
   那一支落地的同一輪要回來處理「改完要不要重簽」。
⚙️ 而它要有一個**會翻臉的守門**，不是一句註記：
   斷言 `bonus.py` 裡寫入 `allocations` 的端點 **只有 `POST /awards` 一支**
   => 多出第二支的那天，這一題會紅，**而紅的訊息就是這一段**
```

### ✅ ④ **不會引進新終態**（A 問的那一格）

```
「已發放」**不是一個 status 值** —— 它由兩個來源推導（`is_paid()`）：
   voucher_no_payment（出納開傳票自動回填）／paid_manually_at（手動標記）
=> 「申請到發放」這條路 **BN8 已經全部涵蓋**
⚠️ 而報價單的「已成案／已結案」是**業務狀態**，獎金單沒有對應概念
   => 照搬會引進一個**沒有意義的終態**
```
📌 ⇒ **不要加 status 值。** 而 C 在 `BN7` 標的「沒有已過帳終態」是對的，
**而那是傳票的概念**（`vouchers_all.posted_at`），不是報價單的 ⇒ 不在這一條裡。

## §3 `BN12` ② `BN6`／`BN10`／`BN12` 的邊界 —— **一個版面，兩種資料**

### 三個編號指的是三個**時機**，而內容是同一份

```
BN6   「產生獎金單」段的預覽   —— **還沒有 award**（要先打案件編號查詢）
BN10  點開一張已產生的單       —— **已有 award**
BN12  ⓐ 申請階段預覽           —— **還沒有 award**（＝ BN6 的時機）
      ⓑ 匯出階段預覽           —— **已有 award**（＝ BN10 的內容 ＋ 匯出鈕）
```

> ### ⇒ **不是三個東西，是一個版面 × 兩種資料來源。**

```
甲 plan 來源   GET /api/bonus/awards/plan/{quote_no}   （bonus.py:259）
              => 回 settlement ＋ 試算的拆發明細，**沒有 award_id**
乙 award 來源  GET /api/bonus/awards/{id}               （已存的單）
              => 回 settlement ＋ 實際的拆發明細 ＋ 簽核狀態
```

### ✅ 落地形狀

```
一支前端元件（例：<bonus-detail>）吃一個正規化的物件：
   { settlement, allocations, remainder, approval|null, awardNo|null }
甲 用 plan 的回應組出來（approval=null、awardNo=null）
乙 用 award 的回應組出來
⇒ **版面只寫一次**，三個時機各自餵不同的來源
```

⚠️ **而「申請階段」比現在多的東西要明著列**：
```
現在按「預覽」只列出每個人試算到的金額 ＋ 尾差
使用者要的「詳細資料」= **精算明細（§2 的 11 列）＋ 拆發明細**
=> 申請階段要**多一張表**（精算明細），而它已經在 bonus.html 有了
   🔑 ⇒ 這一半的工作量比看起來小
```

## §4 `BN12` ③ 浮水印：**照搬 `JV10`／`JV11`，而順序不可以改**

使用者裁過傳票那次（`SPEC-JV5`／`JV11`）：

```
🔴 **作廢優先於未簽核**
   voided_at 非空       => 「本獎金分潤單已作廢」「僅供稽核存查」
   否則 簽核未完成      => 「尚未簽核完成」「預覽稿・尚未正式生效」
   否則                 => 不蓋
```
☠️ 順序顛倒的話：一張**還沒簽核就被作廢**的單會印「尚未簽核」
⇒ **有人會去把它簽完**（`voucher_pdf.py:141` 的 docstring 逐字記著這個理由）。

### 而三件要照搬的形狀

```
① 預覽用**原視窗 modal**，不開新分頁、不必等下載完
② 預覽的 HTML 與匯出的 PDF **來自同一次 build_html()**
   ☠️ 兩份版面的失敗模式是「預覽對、印出來不對」，而那要印出來才發現
③ **預覽隨時可看**（不看簽核狀態），**匯出才擋**
   🔑 `§228`：閘門綁端點，穿不過去 —— 預覽與匯出是**兩支不同端點**
```

📌 而 `JV17` 剛裁過：**匯出鈕只出現在預覽窗內**（避免不確認就按）。
⇒ `BN12` **照同一條**：獎金單頁面上只留「預覽」，匯出鈕在 modal 裡。
