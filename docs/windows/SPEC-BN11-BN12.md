## §1 ① 「比照報價單」——**兩邊的階段逐項對照**

### 報價單

```
草稿 ──submit──▶ 待審核 ──(分層簽核)──▶ 簽核中 ──▶ **已送出**
                   │                                  │
                   │◀── recall（申請人自己收回）        │
                   │                                  ▼
                   ▼                            deal_tag：已成案 ─▶ 已結案
              reject ──▶ 草稿（**換單號升版** MQ-…-R1）
已送出 ──解鎖編輯──▶ 待審核（**強制重簽**，寫 editHistory + rev）
其他終態：已取消 ／ 已拒絕（`_STATUS_PATCH_WHITELIST`）
```

### 獎金分潤單（`BN8` 之後）

```
草稿 ──submit──▶ 待審核 ──▶ 簽核中 ──▶ **已核准**
                   │                        │
                   │                        ▼
                   │                  **已發放**（⚠️ 不是 status，見下）
                   ▼
              reject ──▶ 草稿（**不換號、不升版**）
任何狀態 ──▶ 作廢（voided_at／voided_by／void_reason）
```

### 🔴 差在**三格**

| # | 報價單有 | 獎金單 | 規模 |
|---|---|---|---|
| ① | **recall**（申請人自己收回待審核的單） | ❌ 沒有 | 小（一支端點） |
| ② | **reject 換單號升版**（`_next_revision_no`） | ⚠️ reject 有，**不升版** | 中（要有版本概念） |
| ③ | **解鎖編輯強制重簽**（`editHistory` + rev） | ❌ 沒有 | **大** |

> ### 🔴 ②③ 兩格**我不寫進規格，要 A 裁**（照 A 的指示）

```
② 的代價：獎金單的 `supersedes_id` 欄位**存在而寫入點 0**
   （db.py:4662 宣告，全 backend **0 處寫入**）
   🔑 那是第三個「欄位存在而從來沒被寫入」的實例
      （傳票 `supersedes_no` ／ 獎金 `supersedes_id`）
   ⇒ 若要做 ②，那個欄位就是它的落點 —— **而它現在是死的**

③ 的代價：解鎖編輯要有「改了什麼」的紀錄才簽得下去
   ☠️ 而獎金單的「改」= 改比例 => `SPEC-BN8 §5e ①` 已查：
      **今天沒有任何端點可以改比例**（allocations 只在 POST /awards 出現）
   🔑 ⇒ ③ **今天沒有主體** —— 要先有「改比例」才談得上「改完要重簽」
```

### ✅ ④ **不會引進新終態**（A 問的那一格）

```
「已發放」**不是一個 status 值** —— 它由兩個來源推導（`is_paid()`）：
   voucher_no_payment（出納開傳票自動回填）／paid_manually_at（手動標記）
=> 「申請到發放」這條路 **BN8 已經全部涵蓋**
⚠️ 而報價單的「已成案／已結案」是**業務狀態**，獎金單沒有對應概念
   => 照搬會引進一個**沒有意義的終態**
```
📌 ⇒ **不要加 status 值。** 而 C 在 `BN7` 標的「沒有已過帳終態」是對的，
**而那是傳票的概念**（`vouchers_all.posted_at`），不是報價單的 ⇒ 不在這一條裡。

## §2 `BN11` 第一個問題：**三份怎麼變成一份？**

### 🔑 先釐清 —— **算的只有一份，顯示有兩份**

```
算   `settlement.html:931 calcSummary()`
     🔴 **10% 與 1% 只寫在這裡**（`bonus.py:205` 的註解逐字確認：
        「BN6 一個數字都不重算」）
存   `quotations.data_json.settlement.summary`
帶   `bonus.py:215 _settlement_fields()` —— **passthrough，不重算**
顯示 ① `settlement.html` 右欄對照表        **11 列**
     ② `bonus.html:291-320` 的 `bn-settle`  **11 列**（B 照 ① 逐字抄）
     ③ **PDF：現在沒有** ← `BN11` 要補的
```

> ### ⇒ 會漂移的**不是數字**（它們來自同一個已存的 `summary`），
> ### 是**列的順序與標籤文字** —— 而那正是 `EM2`／`EM13` 那一族。

### 🔴 而「十二格」那個數字的出處找到了

```
settlement.html 右欄對照表        **11 列**
bonus.html bn-settle              **11 列**（B 做的）
bonus.py:207 `_SETTLEMENT_FIELDS`  **12 鍵** = 上面 11 ＋ **`quotedTotal`**
                                   （含稅總額，它在 settlement.html 是 KPI 卡的
                                     **副行**，不是表格的一列）
```
🔑 **三個數字都對，而它們數的是不同的東西。**
📌 ⇒ `ACC-BN6 §1` 那一格結案：「十二」不是轉述錯，是**另一個單位**。

### ✅ 處置：**把「11 列」做成一份資料，三處都讀它**

```python
# helpers/bonus.py（或 helpers/settlement.py）
#: 精算明細表的**列定義**。順序即顯示順序。
#: 🔴 這是唯一一份 —— settlement.html／bonus.html／PDF 都讀它。
SETTLEMENT_ROWS = (
    ("quotedPretax",    "報價稅前收入",     "money"),
    ("itemActualTotal", "品項實際成本",     "money"),
    ("extraTotal",      "額外支出",         "money"),
    ("dispatchTotal",   "承攬商派發成本",   "money"),
    ("totalActualCost", "實際總成本",       "money"),
    ("grossProfit",     "真實毛利",         "money"),
    ("grossMarginPct",  "真實毛利率",       "pct1"),
    ("adminCost",       "管銷分攤（10%）",  "money"),
    ("charityDonation", "公益捐款（1%）",   "money"),
    ("netProfit",       "真實淨利",         "money"),
    ("netMarginPct",    "真實淨利率",       "pct1"),
)
```

```
PDF        直接迭代它
bonus.html 從 API 拿這份定義（或在 BN11 這一輪先只改 PDF，見副作用）
⚠️ `quotedTotal` **不在列定義裡** —— 它是 `quotedPretax` 那一列的**註記**
   （bonus.html:298 已經是這樣做的：`bn-settle__note`）
```

**這個處置自己的副作用**（分開寫）：
```
⚠️ ① `settlement.html` 的那一份是**前端寫死的 HTML 表格**（不是迴圈）
      => 要它也讀這份定義 = **重寫那張表** ⇒ 那不是 BN11 的範圍
      ⇒ 本輪**只讓 PDF 與 bonus.html 讀同一份**，settlement.html 留在原地
      🔴 而那表示**仍然有兩份順序** —— 要配一道守門（§5）
⚠️ ② 標籤放進後端常數之後，改文字要改後端 ——
      而 `EM2`/`EM13` 那邊正在把角色／模組名**動態化**
      ⇒ 這裡刻意**不動態化**（精算欄位名不是客戶可改的設定）
      🔑 ⇒ 判準：**客戶會改的才動態，我們定義的就寫死** —— 要寫進規格避免混淆
```

## §3 `BN12` ② `BN6`／`BN10`／`BN12` 的邊界 —— **一個版面，兩種資料**

### 三個編號指的是三個**時機**，而內容是同一份

```
BN6   「產生獎金單」段的預覽   —— **還沒有 award**（要先打案件編號查詢）
BN10  點開一張已產生的單       —— **已有 award**
BN12  ⓐ 申請階段預覽           —— **還沒有 award**（＝ BN6 的時機）
      ⓑ 匯出階段預覽           —— **已有 award**（＝ BN10 的內容 ＋ 匯出鈕）
```

> ### ⇒ **不是三個東西，是一個版面 × 兩種資料來源。**

```
甲 plan 來源   GET /api/bonus/awards/plan/{quote_no}   （bonus.py:259）
              => 回 settlement ＋ 試算的拆發明細，**沒有 award_id**
乙 award 來源  GET /api/bonus/awards/{id}               （已存的單）
              => 回 settlement ＋ 實際的拆發明細 ＋ 簽核狀態
```

### ✅ 落地形狀

```
一支前端元件（例：<bonus-detail>）吃一個正規化的物件：
   { settlement, allocations, remainder, approval|null, awardNo|null }
甲 用 plan 的回應組出來（approval=null、awardNo=null）
乙 用 award 的回應組出來
⇒ **版面只寫一次**，三個時機各自餵不同的來源
```

⚠️ **而「申請階段」比現在多的東西要明著列**：
```
現在按「預覽」只列出每個人試算到的金額 ＋ 尾差
使用者要的「詳細資料」= **精算明細（§2 的 11 列）＋ 拆發明細**
=> 申請階段要**多一張表**（精算明細），而它已經在 bonus.html 有了
   🔑 ⇒ 這一半的工作量比看起來小
```

## §4 `BN12` ③ 浮水印：**照搬 `JV10`／`JV11`，而順序不可以改**

使用者裁過傳票那次（`SPEC-JV5`／`JV11`）：

```
🔴 **作廢優先於未簽核**
   voided_at 非空       => 「本獎金分潤單已作廢」「僅供稽核存查」
   否則 簽核未完成      => 「尚未簽核完成」「預覽稿・尚未正式生效」
   否則                 => 不蓋
```
☠️ 順序顛倒的話：一張**還沒簽核就被作廢**的單會印「尚未簽核」
⇒ **有人會去把它簽完**（`voucher_pdf.py:141` 的 docstring 逐字記著這個理由）。

### 而三件要照搬的形狀

```
① 預覽用**原視窗 modal**，不開新分頁、不必等下載完
② 預覽的 HTML 與匯出的 PDF **來自同一次 build_html()**
   ☠️ 兩份版面的失敗模式是「預覽對、印出來不對」，而那要印出來才發現
③ **預覽隨時可看**（不看簽核狀態），**匯出才擋**
   🔑 `§228`：閘門綁端點，穿不過去 —— 預覽與匯出是**兩支不同端點**
```

📌 而 `JV17` 剛裁過：**匯出鈕只出現在預覽窗內**（避免不確認就按）。
⇒ `BN12` **照同一條**：獎金單頁面上只留「預覽」，匯出鈕在 modal 裡。

## §5 驗收（`AC1`）

```
① 後端  BN11：PDF 含精算明細 11 列，值來自 `_settlement_fields()` **不重算**
        BN12：預覽端點與匯出端點分開；預覽不擋簽核狀態、匯出擋
② 前端  一個詳細元件用在三個時機（BN6／BN10／BN12）
        頁面上只有「預覽」，匯出鈕在 modal 內
③ 頁面  ⓐ 用 `MQ-202608-007` 產生獎金單 -> 預覽
           => 11 列與 `ACC-BN6 §3` 的值**逐格相同**
        ⓑ 用 `MQ-202608-003`（有額外支出）-> 第 3 格是 **3,500** 不是 0
           🔑 ⓑ 是〈兩張合起來才蓋得滿〉—— ⓐ 那張的額外支出是 0
        ⓒ 匯出 PDF -> **與預覽逐格相同**（同一次 build_html）
        ⓓ 未簽核完成 -> 預覽**看得到**且有紅字浮水印；按匯出 -> **被擋**
        ⓔ 作廢的單 -> 浮水印是「已作廢」**不是**「尚未簽核」
           🔑 ⓔ 要用一張**還沒簽核就作廢**的單，否則兩種規則的順序驗不出來
```

### 🔴 守門

```
✅ 釘：PDF 的精算列**與 `SETTLEMENT_ROWS` 逐字相同**（標籤與順序）
✅ 釘：`bonus.html` 的 `bn-settle` 也讀同一份
🔴 而 `settlement.html` 那一份**本輪不動** ⇒ 要一道**對照題**：
   斷言 `SETTLEMENT_ROWS` 的 11 個標籤，在 `settlement.html` 裡**逐字找得到**
   ☠️ 沒有它，兩份順序會各自演化，而**症狀是兩張紙上的列不一樣**
⚠️ 而那道題**不是**「settlement.html 要讀常數」—— 它只驗**文字一致**
   🔑 那是明著接受一份重複，並用守門擋住它漂移（不是假裝它不存在）
```
