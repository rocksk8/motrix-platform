## §0 使用者原話（逐字）與四條規則

```
「例如1111已經有了，只能延伸建立例如1111-1這樣的科目，用延伸遞增去建立，
  父層級不可創立，且頁面須說明自建總數有多少」
```

```
① 編碼      {既有科目代號}-{流水號}，遞增
② 只能延伸  被延伸的代號**必須已經存在**
③ 父層級不可創立
④ 頁面顯示**自建總數**
```

🔑 **③ 同時解掉「層級深度」那個未決問題**：深度由**被延伸的科目**決定
⇒ 不必限制層數，而 `§29`「規格不可以寫死層數」仍成立且不衝突 ——
**使用者給的是產生方式，不是上限。**

✅ **而它不構成阻礙，有三層可以分**：
```

🔴 **第 ③ 層不是多餘的**：前兩層是給程式看的，**而使用者看到的是兩種長得一樣的 `-`**。
📌 它與使用者要的「自建總數」是同一個方向：**讓自建的那一群在畫面上是一個可辨識的集合。**

## §3 產生下一個代號

```
延伸 `1111` ⇒ 找出所有 parent_code = '1111' 且 source='custom' 的代號
             取其**尾碼的最大值 + 1**
```

### ☠️ 兩個不可以用字串做的地方

```
① 取下一號     "1111-9" 之後是 "1111-10"
               字串比大小：**"1111-10" < "1111-9"** ⇒ 下一號又算出 10 ⇒ **撞號**
② 排序顯示     account_items.py:76 目前是
               group.sort(key=lambda n: (n.get("level") or 0, n.get("code") or ""))
               ⇒ 同一層下 **1111-10 會排在 1111-2 前面**
```
🔑 **尾碼一律轉成整數再比。** 兩處都要改，而 ② 是既有程式碼。
⚠️ ② 那一行現在是對的 —— 因為**今天一個自訂科目都沒有**。
☠️ 它會在**第 10 個自建科目**那天才出錯，而症狀是「順序怪怪的」，沒有人會報修。

### 🔴 **前綴不是階層** —— 延伸用前綴，階層一律用 `parent_code`

D 實查（2026-09-23）：有 `parent_code` 的 539 筆裡，**232 筆（43%）的 `code`
不以它的 `parent_code` 為前綴**。
⇒ 本項的「延伸」**產生**的是有前綴關係的代號，**而那是本項的產物，不是全表的性質**。
☠️ 任何地方要找「某科目的子科目」一律 `WHERE parent_code = ?`，
**不可以用 `code LIKE '前綴%'`** —— 那會漏掉 43%。

⚠️ 同一條套在 `§6` 的「自建總數」上：
```
✅ 數 source='custom'
☠️ **不要數含 `-` 的代號** —— 會把 13 筆法定範圍代號算進去
```

### ⚠️ 取最大值，不是數筆數

```
數筆數   1111-1 1111-2 1111-3，刪掉 1111-2 => 剩 2 筆 => 下一號算成 3 => **撞號**
取最大   3 還在 => 下一號 4  ✅
```
📌 與 `helpers/voucher.py::next_voucher_no` 同一個理由（那裡的 docstring 有完整說明）。
⚠️ 而本項用**停用不刪除**（`§4`）⇒ 停用的仍然佔號 ⇒ 取最大值時**不可以濾掉停用的**。

### ☠️ 撞號時的行為，**取決於 `INSERT` 的寫法** —— 三種都不可以

`account_items.code` 是 `TEXT PRIMARY KEY`：

```
INSERT              -> IntegrityError    很吵，會被發現            ✅ 但訊息不可看
INSERT OR IGNORE    -> **靜默無事發生**  使用者按了建立而什麼都沒有 ☠️
INSERT OR REPLACE   -> **覆蓋**          舊列被改掉，而它可能已被傳票引用 ☠️☠️
```

🔴 **而 repo 裡現成的那一句正是 `OR IGNORE`**：
```
db.py:4298  "INSERT OR IGNORE INTO account_items (code, level, name, name_en, parent_code, source)"
```
⇒ **同一張表、欄位幾乎一樣、就在要改的那個檔案裡** ⇒ 它是最可能被照抄的一句。
⚠️ **本項一律用純 `INSERT`，並在應用層先查重、回一句看得懂的話。**

⚙️ 驗收釘的是**可觀察的差異**，不是實作用了哪一種：
```
讓一個已存在的 code 再被建立一次
  ✅ 必須回 400／409 **且訊息說出是哪一個代號**
  ☠️ 不可以 200 而什麼都沒發生（OR IGNORE）
  ☠️ 不可以 200 而舊列被改掉（OR REPLACE）
  ☠️ 不可以讓 IntegrityError 直接冒到使用者面前
```
📌 一題同時擋住三種寫法。而這也是〈停用不是刪除〉的真正機制：
**號碼不可以被重用** —— 重用的下場是三種裡的哪一種，由寫法決定，而三種都不可接受。

### 新列的欄位

```
code         {被延伸代號}-{流水號}
parent_code  **被延伸的代號**
level        被延伸者的 level + 1     （1111 是 L4 ⇒ 1111-1 是 **L5**）
source       'custom'                 ← 三層辨識的第一層
name         使用者填
name_en      空字串（不強迫填）

## §5 端點

```
GET   /api/account-items                      既有，**回應要加自建總數**（§6）
POST  /api/account-items                      延伸建立
PATCH /api/account-items/{code}               只改 is_active（停用／啟用）
```

**權限**：`require_superadmin=True`
—— 與 `POST /api/bonus/items` 同一級（會計科目是全公司共用的基礎資料）。

**`POST` 的 body**
```
{ "parent_code": "1111", "name": "零用金－台中" }
```
⚠️ **`code` 不由前端送** —— 它由後端產生（同 `voucher_no` 的理由：前端不發號）。

**要擋的（每一條都要有明確訊息，不可以只回 400）**
```
① parent_code 不存在                 => 「要延伸的科目「X」不存在。」
② parent_code 已停用                 => 「「X」已停用，不能在它底下新增。」
③ name 空白                          => 「請填寫科目名稱。」
④ **父層級不可創立**：body 帶了 code／level／parent_code 以外的結構欄位
   => 忽略，不要照收（白名單，不是黑名單 —— 同 vouchers.py 的 EDITABLE_FIELDS）
```

## §6 「頁面須說明自建總數有多少」

```
GET /api/account-items 的回應加一格： { "custom_count": N }
```
⚠️ **由後端算，前端不要自己數** ——
☠️ 前端數的是「**畫面上載入的那些**」，日後若加分頁或篩選，那個數字會安靜地變小。
📌 而它就是使用者要的那句話的落點：**頁面顯示自建總數。**

⚙️ 而畫面上自建的那些要**看得出來**（`§2` 第三層）：一個標記即可，
不要用顏色單獨表示（色盲／黑白列印都讀不到）。

## §7 驗收（`AC1`：後端＋前端＋頁面三者皆備）

```
後端 ① POST 延伸 1111 -> 回 200，新列 code=1111-1、parent_code=1111、
        level=**5**、source='custom'
     ② 連續建三個 -> 1111-1 / 1111-2 / 1111-3
     ③ **停用 1111-2 之後再建** -> 下一個是 **1111-4**（停用的仍佔號）
     ④ 🔴 **建到第十個** -> 下一個是 **1111-11**，不是 1111-10
        ⇒ 這一題釘的是「尾碼用整數比，不是字串」
        ☠️ 少了它，第 10 個那天才撞號，而症狀是「順序怪怪的」
     ⑤ 延伸一個**不存在**的代號 -> 400 且訊息說出是哪一個代號
     ⑥ 延伸一個**已停用**的科目 -> 400
     ⑦ PATCH 停用一個 **statutory** 科目 -> 拒絕（TRIGGER 或應用層都可，
        而**訊息要看得懂**，不可以是 sqlite3.IntegrityError 直接冒出來）
     ⑧ PATCH 停用一個 **custom** 科目 -> 200，且
        `validate_account_code()` 對它回 (False, "…已停用…")
        ⇒ **走產品路徑**，不是 raw SQL（見 §4）
     ⑨ 非 superadmin -> 403（**不是 500**）
     ⑩ GET 回應的 custom_count == 實際 custom 筆數
     ⑪ 先斷言 status_code in (200, 400, 403) 再看內容（`§166` 三種臉）
前端 ⑫ 會計科目頁有「延伸建立」與「停用／啟用」兩個會送出的動作
頁面 ⑬ 自建的科目在畫面上看得出是自建的；自建總數顯示在頁面上
```

⚠️ **④ 與 ③ 是這一份的核心。** 其他全綠而它們紅 ＝ 沒做到 ——
而它們是**唯二會在「用了一陣子之後」才爆的**。
