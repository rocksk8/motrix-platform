# PLAN-TEST-PERF：測試與建包的 CPU／時間／硬碟寫入優化方案

> 狀態：**方案討論稿，只寫文件、不實作**（實作等這次升級檔匯出後）。
> 主筆整合：hichan-bf（§0～§3、§5、§6）；§4 e2e：hichan-a3。派工：hichan-0a（2026-09-25）。

## §2 測試分層與「只跑受影響的題」

### 2.1 分層

| 層 | 內容 | 誰跑、何時 | 目標時間 |
|---|---|---|---|
| 快速層 | 靜態守門（spec_coverage、manifest、parts…）＋改動檔案直接對應的題 | 各視窗推前 | 1～2 分 |
| 受影響層 | 快速層＋選題器選出的題（§2.2） | 各視窗推前（取代「自己挑檔」） | 3～5 分 |
| 全量 | 全部（非 e2e＋e2e） | **建包，唯一的出貨關卡** | 見 §3 |

🔑 選題只用在**視窗內迭代**；建包永遠全量。選錯的代價是「晚一點在建包才紅」，不是「漏上正式機」。

### 2.2 選題器：三種做法比較

| 做法 | 追得到 | 追不到 | 評估 |
|---|---|---|---|
| (a) pytest-testmon（coverage 記錄每題執行過哪些 Python 區塊） | 後端 Python，含 live_server 的執行緒 | **前端 html／js／css**、json 資料檔、掃描型守門（讀檔／glob）、子行程（git、子 pytest）、時間 | 目前未安裝（還要 coverage，dev 依賴）；每個 worktree 要先跑一次帶 coverage 的全量建基準（慢 20～40%） |
| (b) 自建 import 圖（AST） | 測試直接 import 的模組 | 同上，而且 **`client` → `main` → 全部 router**：任何 router 一改就選到約 2,300 題，粒度等於沒有 | 不建議單獨使用 |
| (c) 混合（建議） | (a)＋明文規則：①前端檔改 ⇒ 原始碼提到該頁名／檔名的題＋全部掃描型守門；②`conftest.py`／`db.py`／`main.py`／`requirements*` 改 ⇒ 全量；③只改 docs ⇒ 文件守門 | 規則沒寫到的新依賴型態 | 見 2.3 |

**量到的依賴型態**（424 個測試檔）：
- **211 檔**讀前端檔案（`frontend`、`.html`、`pages/`、`static/`、`.js`）——coverage 完全看不到；
- 35 檔掃整個目錄（glob／rglob／walk／iterdir）；
- 29 檔跑 git 或子行程；16 檔讀 manifest／json 資料。
- 09-18 以來 1,617 個 commit 裡有 219 個動到 `frontend/`。

⇒ 只靠 (a) 會對**一半的測試檔**給出「不受影響」而其實有依賴 ⇒ 假綠。

### 2.3 怎麼證明選題器沒漏

1. **歷史回放**：取近 30 個「修 bug＋加題」的 commit，把修正**反向套用**（還原成有 bug 的版本）
   ⇒ 選題器必須選到那一支新題，而那一支新題在反向版本上必須紅。任何一個沒選到 ⇒ 選題器不可用。
2. **突變**：對近 N 個 commit 的改動行做突變（條件反轉、刪 return）⇒ 全量跑出「紅的題集合」R；
   選題器選出 S ⇒ 要求 R ⊆ S。量「漏選率」，> 0 就補規則。
3. 上線後每次建包都記錄「這一輪全量紅的題，當時視窗的選題器有沒有選到」⇒ 漏選有落點。

**工作量**：(a) 安裝＋建基準 半天；(c) 規則＋回放實驗 1～2 天。**建議先做回放實驗，不通過就不上。**

## §3 建包

### 3.1 同一 tree 已全綠就沿用

- 作法：建包已要求工作樹乾淨 ⇒ 以 `git rev-parse HEAD^{tree}`＋測試環境指紋（python 版本、
  `pip freeze` 雜湊、Playwright／chromium 版本、`pytest.ini`）為鍵，記錄在 build_history；
  同鍵、**同一天**、上次兩段都綠 ⇒ 跳過測試，打包時在 manifest 註明「沿用 <建包時間> 的測試結果」。
- 省：重建同一個 commit 時整段 2,075 s。**多久會發生**：今天兩次建包之間 master 有新 commit，
  不會命中；命中的是「測試過了、打包或匯出那一步失敗再建」。
- 風險：時間相依的題（VR1 比日期、跨午夜）、環境變了但指紋沒涵蓋（G: 掛載、系統時區）、
  上一輪是偶發綠。⇒ 限同一天；跨日一律重跑。
- 證明：沿用時仍跑快速層（1～2 分）當煙霧測試；每週至少一次強制全量。
- 工作量：小（build 腳本 30～50 行）。

### 3.2 e2e 平行

- 現況：e2e 序列 1,428 s。今天實測（-n 4，案件頁相關 134～159 題）約 250～290 s ⇒ 約 1.8 s／題。
  ⇒ 321 題 `-n 4` 估 **約 600 s，省約 800 s**。
- 風險：負載下時序題會紅。**今天的經驗是：-n 2 下偶發紅的 UR1 那題，查到的是真的產品競態**
  （點選後送出的未讀查詢把標記蓋回，已修 9d0b136）。⇒ 平行 e2e 的紅燈要照「偶發先當產品競態」處理，
  不可以加 retry／放寬 timeout 讓它綠。
- 另一個風險：一題卡住（evaluate 無逾時）會拖住一個 worker 直到整輪逾時——今天 A 包就發生過
  （`page.evaluate` 等一個沒人回答的對話框）。⇒ 需要逐題上限（pytest-timeout 或 conftest 自製），
  逾時要印出卡在哪一行。
- 🔴 前置條件（a3 §4.4-2）：`build_deploy_package.ps1:593` 把 e2e 逾時當警告放行。平行後逾時變多
  ⇒ 被放行的題變多 ⇒ 靜默少驗。**先改成「逾時算失敗」（或至少把放行題數寫進 build_history 並設上限 0）**，才平行。
- 證明：同一 tree 連跑 3 次 `-n 4`（a3 建議 5 次），紅燈與放行集合都為空才切換；抽 5 個已修的競態缺陷做突變，
  平行下要紅；切換後第一週保留一次序列跑對照。
- 工作量：小（build 腳本一行＋逐題上限＋逾時改判）。

### 3.3 workers 上限與建包獨佔

- 12 邏輯核／6 實體核。建包時的兩段是先後跑的：非 e2e 6 worker，e2e 4 worker。
- 問題：測試鎖目前是全機 2 格；建包時若另一個視窗也在跑 `-n`，建包的時序題會因為 CPU 被搶而紅，
  **而紅的樣子跟真的 bug 一樣**。⇒ 建包期間要**兩格都佔**（獨佔），其他視窗排隊。
- 風險：其他視窗等待變長（建包約 15 分鐘，§1～§2 做完後）。
- 工作量：小（build 腳本搶兩格；conftest 已支援多格）。

### 4.1 共用瀏覽器與伺服器（每題改開新 context 隔離）

**做法**
- conftest 提供 session（每個 xdist worker 一份）的 `pw_browser`，以及 function scope 的 `page`／`context` fixture。
- conftest 另提供 session 的 uvicorn，`live_server` 改成 function scope 的薄包裝：先依賴 `client`，保證本題的 DB 已經建好並 monkeypatch 了 `db.DB_PATH`，再回傳共用伺服器的 URL。
- **共用伺服器可行**：`live_server` 本來包的就是 session 級的同一個 `main.app`（`conftest.py::_app`）。DB 隔離靠 `client` monkeypatch `db.DB_PATH`，在 request 當下才讀；`main.py` 沒有 startup／lifespan handler。
  - 實證（`zz_perf.py`）：同一個 uvicorn，兩題各自建庫，各登入得到自己的帳號，另一題的帳號不存在。

**不能共用、或要特別處理的**
- **程序層全域狀態**：rate limit dict、`_export_times`、geo 快取、同時編輯的記憶體表等。它們**本來就跨題共用**（同一個行程），共用伺服器不會新增這一類風險；`client` 目前重設的那些照舊有效。
- `test_e2e_passkey`：把 `webauthn_origin` 寫成含 port 的網址。共用伺服器的 port 整個 session 固定，仍可用，但寫入要改在 `client` 之後、每題做一次（現在就是這樣）。
- `test_e2e_gov_name_search`：在起伺服器前 monkeypatch `dashboard._gcis_get`。共用伺服器下 monkeypatch 仍然對全行程有效，順序無關，可共用。
- 🔴 **遷移必須一次全轉**：session 級的 `sync_playwright()` 開著時，題目內再開一個會直接報 `It looks like you are using Playwright Sync API inside the asyncio loop`（實測）。所以不能逐檔漸進，要一個 commit 把 109 檔一起改。
- **題目中途重啟或關閉伺服器**：目前沒找到，但轉換時要 grep `should_exit`／`server.` 確認。

|---|---|---|---|
| 每題約省 0.48s（0.23＋0.34−0.09）× 278 ≈ **130s 牆鐘**（e2e 單程序）；另外省下每題一份 Chromium profile 的建立與寫入（寫入量由 bf 的取樣器量） | 前一題的 context 狀態殘留到下一題（localStorage、cookie）：每題新 context 就隔離了。不同 context 之間仍共用 HTTP 快取，靜態檔快取可能讓「改了 JS 卻沒生效」的題假綠 ⇒ 用 `browser.new_context()`（預設不共用快取），不要用 persistent context | ① 轉換前後收集到的 test id 集合相同 ② 同一份 master 新舊兩種寫法各跑一次，逐題結果相同 ③ 留 `zz_perf.py` 的「共用伺服器看得到各題自己的庫」當正式守門題 ④ 突變：還原 W-4、D8-1 等已修缺陷，新寫法下要紅 | conftest 0.5 天；109 檔 codemod＋逐檔檢查 1 天；必須一個 commit |

#### 4.1b 登入改用 API 取 token 注入（附帶項）

多數題用 UI 登入：登入頁 → index → 再 goto 目標頁。改成用 API 取 token 後以 `add_init_script` 寫進 `localStorage`，直接開目標頁：每題約省 1s（UI 登入 0.76s＋index 頁載入）。

#### 4.3b 固定等待

靜態總和約 155s（`wait_for_timeout` 130s＋`sleep` 25s），還沒算迴圈與參數化。分兩種：
- **等某件事發生**：改成條件等待（`wait_for_function`／`expect`），可以省。
- **確認某件事沒發生**（例如「300ms 後橫幅仍在」「1.5s 內沒有送出請求」）：不能拿掉。改短會降低抓出競態的機率，**不建議動**。

### 4.4 e2e 平行化的風險（建包時 e2e 加 `-n`）

平行化是 e2e 最大的槓桿，建包流程的部分是 bf 的 ③，這裡只列風險：

1. **時序題在負載下變慢**：「X ms 內沒發生」這一類，在 CPU 滿載時會把「還沒來得及發生」誤判成通過（假綠）；「等 X ms 後應該已經發生」則會偶發紅。
2. 🔴 **建包腳本把 e2e 逾時當成警告、不算失敗**（`build_deploy_package.ps1:593`）：平行化後逾時變多，被放行的題就變多，**等於靜默地少驗了**。平行化前要先把這條改成「逾時要重跑一次、重跑仍逾時算失敗」，或至少把被放行的題數寫進 `build_history`。
3. **Edge PDF 子程序**：`EDGE_PDF_SEMAPHORE` 在 xdist 下已壓成每個 worker 1 個；e2e 平行化時會一起疊上 Chromium，CPU 會吃緊。
4. **背景執行緒寫錯庫**：`spawn_bg_thread` 在題目結束、monkeypatch 還原後才寫入，會落到同一個 worker 的下一題的庫。這個風險現在就存在，平行化不會讓它變少；共用伺服器也不會讓它變多。
5. **每個 worker 各一份 Chromium 與 uvicorn**：記憶體約 200～300MB × worker 數。workers 上限由 bf 的 ③ 決定。
6. **偶發紅燈要先當產品競態查**（見記憶「偶發失敗先當產品競態」）：平行化之後冒出來的偶發紅，不能用重試或拉長等待打發。

| 預估效益 | 漏驗風險 | 怎麼證明沒漏驗 | 工作量 |
|---|---|---|---|
| e2e 牆鐘約 ÷ min(worker 數, 4)（受 CPU 與 Edge 限制） | 上面的 1、2 | 平行化前後各連跑 5 次，比較每題的通過率；把逾時放行的題數記下來；抽 5 個已修的競態缺陷做突變，平行下要紅 | 由 bf 的 ③ 統整 |

## §5 硬碟寫入量

⚠️ 「用完即刪」（8523796）只解決**佔空間**，不減少**寫入量**；SSD 損耗看寫入量。

### 5.0 量法

- 行程 I/O 計數（`GetProcessIoCounters`／WMI `WriteTransferCount`）。**正對照**：寫 5,000,000 bytes 的檔 ⇒ 量到 5,000,004。
  （第一次量到 0 是 ctypes 沒宣告參數型別，計數函式靜默失敗——已修，並留正對照。）
- 抽樣全量：取樣器每 2 秒記錄 pytest 行程樹每個行程的累積寫入（短於 2 秒的子行程會漏 ⇒ 下限）。
  **正對照**：假行程寫 8,000,000 bytes ⇒ 取樣器量到 7.6 MB。
  （第一版取樣器量到「0 個行程」：PowerShell 雜湊表鍵 UInt32／Int32 不相等、中文註解無 BOM 被 PS 5.1 解錯吃掉一行。
  兩個都是**靜默**失敗——沒有正對照的話，「寫入 0」會被當成結果。）

**抽樣結果**（1/8 檔、503 題、單程序，現行程式碼）：

| 行程 | 寫入 | 推估全量（×6.9；e2e 部分 ×9） |
|---|---|---|
| python.exe（pytest＋伺服器執行緒：建庫、測試資料） | **3,165 MB** | **約 22 GB** |
| msedge.exe（PDF 產出；寫入大宗是 Edge 自己的 profile／快取，PDF 檔本身合計只有 3.5 MB） | 374 MB | 約 2.6 GB |
| chrome-headless-shell.exe（e2e 瀏覽器，含每次 launch 的新 profile） | 97 MB | 約 0.9 GB |
| node.exe（Playwright driver） | 27 MB | 約 0.2 GB |
| **合計** | **3,662 MB** | **約 25 GB／輪** |

basetemp 殘留只有 636 MB（`.db` 532 個、631 MB）⇒ **實際寫入是殘留的 5 倍**：migration 反覆改表，同一份資料被重寫很多次。
「用完即刪」只刪掉那 636 MB 的殘留，寫入的 3.6 GB 已經發生。

### 5.1 建庫（第一大宗）——範本庫

| 作法 | 每個庫寫入 | 每個庫時間 |
|---|---|---|
| 現行 `init_db`（WAL＋synchronous=NORMAL，116 個 migration） | **5.93 MB** | 178～234 ms |
| 同上＋`journal_mode=MEMORY`、`synchronous=OFF` | 5.15 MB | 235 ms |
| 同上＋`journal_mode=OFF` | 5.15 MB | 304 ms |
| **複製已遷移好的範本檔** | **1.19 MB**（＝檔案大小） | 2 ms |

- `client` 每題建兩個庫 ⇒ 約 12 MB／題 × 2,315 題 ≈ **27 GB／輪**（只算建庫）。
- 🔑 PRAGMA 幾乎沒用：寫入大宗是 migration 本身的改表／重建表，不是日誌。**只有「不要每題重跑 migration」有效。**
- 範本庫：session 開始時用**同一支 `init_db`** 建一次（migration 仍然每輪真的跑一次），
  `PRAGMA wal_checkpoint(TRUNCATE)` 後關閉，每題 `copyfile` 兩份。⇒ 約 2.4 MB／題 ≈ 5.5 GB／輪，**省約 22 GB**。
  再進一步：demo 庫改成用到才建（多數題不碰 demo）⇒ 再省約 2.7 GB。
- 會不會驗不到正式機行為：
  - 正式機的庫是**逐版升級**上來的，不是一次 init；測試用「一次 init 的結果」和現在每題 init 是同一件事，沒有變少。
  - WAL：範本檔仍是 WAL 模式的檔案庫，每題照常以 WAL 開啟 ⇒ WAL 行為仍被測到。
  - 要驗 migration 本身的題（自己呼叫 `init_db`／`_run_migrations`）不受影響。
- 證明沒漏驗：①新增守門題：範本複製出來的庫與新鮮 `init_db` 的庫，`sqlite_master`（全部 DDL）、
  `schema_version`、`PRAGMA journal_mode`、種子資料列逐一相同；②切換後跑一次全量，紅燈集合與切換前相同。
- 工作量：小（conftest 約 30 行＋守門題）。

### 5.2 不採用：SQLite 記憶體庫

- 量到寫入 0，但**不可行**：產品每個請求 `db.get_db()` 開新連線、live_server 在另一條執行緒；
  `:memory:` 每條連線各一份。改用 `file::memory:?cache=shared` 會換掉鎖定語意、**完全不走 WAL**
  ⇒ 驗不到正式機的併發行為（今天的存檔排隊、衝突偵測都靠它）。

### 5.3 PDF／Edge 產出

- 36 個測試檔會產 PDF（Edge headless）。抽樣：msedge 寫入 374 MB，其中 PDF 檔本身只有 3.5 MB
  ⇒ 寫入大宗是**每次啟動 Edge 的 profile／快取**，不是 PDF。全量推估約 2.6 GB。
- 方案 A：Edge 用固定的 `--user-data-dir`（每個 worker 一份、session 內重用）⇒ profile 只建一次。
  風險：前一次渲染的快取影響下一次（測試 PDF 的內容來自本機 HTML，影響小）；要驗「重用 profile 產出的 PDF 位元組與新 profile 相同」。
- 方案 B：只驗「有產出、長度、頁數」的題改成不實際渲染；**看版面的題留實產**。風險：PDF 版面回歸只剩少數題守。
- 建議先做 A（不減少驗證），B 不做。工作量：A 半天。

### 5.4 Playwright

- 全 repo 沒有開 trace／video／HAR（只有 2 處 `screenshot(`）⇒ **這一項沒有可省的**。
- 每次 `chromium.launch` 建一個新的暫存 profile（a3 指出）⇒ 共用瀏覽器（§4.1）同時省 profile 寫入。
  抽樣：chrome-headless-shell 37 題 e2e 寫入 97 MB（約 2.6 MB／題）⇒ 全量約 0.9 GB；共用瀏覽器後大部分省下。
- 佔空間（不是寫入）：`ms-playwright` 裡 1223、1228 兩套舊版瀏覽器約 1.4 GB 用不到（a3 查）⇒ 可刪，e2e 仍能啟動即可。

### 5.5 不採用：RAM 磁碟

- 要裝第三方核心驅動（ImDisk 等）。這台機器 2026-09-15 才發生過資安事件（無檔案 C2），
  新增核心驅動是擴大攻擊面；而且 5.1 做完後寫入已降到約 5 GB／輪。⇒ 不建議。
