## §1 判準（保留，它仍然是這一類的定義）

```
EM9   `if (r.ok) {…}` 無 else  =>  失敗時**畫面沒動**
                                   使用者：「我按了，沒反應」
EM11  **先改畫面**再送請求，而請求 `.catch(() => {})`
                                   使用者：「我按了，**成功了**」
```

> ### ☠️ 一般靜默失敗是「**他不知道失敗了**」。
> ### 這一類是「**他看到了一個假的成功狀態**」。

🔑 代價在**下一次開頁面**才出現：那個值變回去了，
**而那時候看起來像系統把他的資料弄丟了**。
📌 ⇒ 排查方向也不一樣：使用者會說「**資料不見了**」，
而工程師會去查刪除路徑 —— **而根本沒有人刪它，它從來沒有被存進去**。

## §3 🔴 而同一支函式裡**還有一個殘留**（複查時撿到）

```js
// quotation-form.html:3201  —— **在請求之前**
this.q.exportLog = [...(this.q.exportLog || []), { at: …, mode }]
// :3213                      —— **在成功之後**
this.q.exportCount = (this.q.exportCount || 0) + 1
```

> ### ☠️ **計數器誠實了，而紀錄還是樂觀的。**

### 它看得到，而且是**同一個畫面上的兩個數字對不起來**

```
匯出紀錄 modal（quotation-form.html:2183-2212）
   :2190  標題    「… 共匯出 <exportCount> 次」
   :2198  清單    x-for="(entry, idx) in (q.exportLog || []).slice().reverse()"
```

```
POST 失敗時：
   exportCount  **不加**  => 標題說「共匯出 2 次」
   exportLog    **加了**  => 下面列出 **3 筆**
=> 使用者看到「2 次」與 3 列紀錄，**而畫面上沒有任何一句話解釋**
```

⚠️ 它比修好之前**更容易被發現**（兩個數字並排），
🔑 而那正是為什麼要報它：**修了一半的不一致，比整個都是樂觀的更顯眼。**

### 建議處置

```
把 :3201 那一行搬進 `if (r.ok)` 區塊，與 exportCount 同進退
⇒ 兩個數字永遠一致
```

**這個處置自己的副作用**：
```
⚠️ 離線那條路（:3220-3221）本地累加 exportCount 而**不會**有 exportLog
   => 離線列印後，計數會加而清單不會多一列 —— **同一個不一致換一個方向**
⇒ 離線分支也要一起補上 exportLog 的 push
🔑 ⇒ 判準是「**exportCount 與 exportLog 的每一條路徑都要成對**」，
   不是「把那一行搬走」
```

## §5 守門（若 A 決定做 §3）

```
✅ 釘：**先改畫面再送請求**的地方，失敗時必須有明確處置
   ⚙️ 判準：同一支函式裡，一個 `this.X = …` 的賦值**在** fetch **之前**，
           而那支 fetch 只接空的 `.catch(() => {})`
   ⚙️ 正對照 **§3 那一行**（exportLog）
   ⚙️ 負對照 §2 修好的那兩處 **不可以亮**
             🔑 它們是「修對了長什麼樣」的樣本

⚠️ 而這道守門**不要釘「空 `.catch` = 0」**
   ☠️ 空 `.catch` 在 fire-and-forget 的紀錄上是**合法的**（見 `SPEC-EM12 §4`）
   🔑 這裡違規的是「**先改畫面**」，不是 `.catch` 本身
      => 兩個條件**同時成立**才亮
```
