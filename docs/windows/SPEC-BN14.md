# `SPEC-BN14` · 獎金人員來源要有群組

> 座標：`326e85f`（工作樹：本檔為新增）
> 作者：視窗 A-2 ／ 2026-09-23
> 使用者原話：
> 「獎金分潤的**人員來源要有群組的區分**，可以把**後勤單位**的人列入人員來源，
> **如有複數人員自動計算比例**」

---

## §1 前置：**結構已經存在，不必建表**（A 查、我複驗）

```
divisions    **2 列**   總經理辦公室 ／ 測試、自動化
departments  **5 列**   智能解決方案中心 ／ 行政營運管理中心 ／ 策略開發整合中心
                        ／ 測試區 ／ 自動化
             （division_id -> divisions.id，UNIQUE(division_id, name)）
users.department_id  ✅ 存在
```

### ✅ 而 A 擔心的「`department_id` 可能全是 NULL」—— **開發機上不成立**

```
users 共 13 ／ department_id 為 NULL 的 = **1**（8%）
   dept=1 三人 ／ dept=2 兩人 ／ dept=3 一人 ／ dept=4 四人 ／ dept=5 兩人
```

⚠️ **而那是開發機。** 正式機要先查 ——
📌 同 `geocode_cache` 那一格：**開發機有值不代表正式機有**。
```
🔴 若正式機大量 NULL ⇒ 這個功能在那裡是**空的**，而畫面上看起來正常
⇒ 驗收要有一題：**選一個群組而它解析出 0 人時，走的是 §3 的拒絕路徑**
```

---

## §2 ① 🔴 「群組」是哪一層 —— **「後勤單位」不在名單裡，要問**

```
使用者說「**後勤單位**」
而 departments 的 5 個名字裡**沒有「後勤」兩個字**
   最接近的是「**行政營運管理中心**」
```

> ### 📌 **請 A 向使用者確認兩件事：**
> ### ①「後勤單位」是指「**行政營運管理中心**」嗎？
> ### ②「群組」要選到 **department**（部級，5 個）還是 **division**（處級，2 個），還是兩層都要？

### ⚠️ 而兩層的差別不只是粒度

```
division（處）  2 個 —— 其中一個叫「測試、自動化」，**那是測試資料**
department（部）5 個 —— 其中 2 個（測試區／自動化）也是測試資料
=> **真實的部門其實只有 3 個**（智能解決方案／行政營運管理／策略開發整合）
🔑 ⇒ 選單上會出現測試部門，而那不是這一件要解決的事
   ⚠️ 但驗收時要知道：**畫面上會有 5 個選項而只有 3 個是真的**
```

⚠️ 在確認之前**本規格照 department 寫**（使用者說「單位」，而部級才是「單位」的常見指稱），
而若答案是兩層都要，§3 的解析要多一個分支，其餘不變。

## §3 ② 成員解析 —— **走既有接縫，不要在呼叫端加 if**

```python
# helpers/bonus.py:146  —— **唯一真相**
PERSON_SOURCES = (
    "sales_person",             # 業務
    "case_stages.assigned_to",  # 各執行階段負責人（JSON 陣列）
)
# helpers/bonus.py:155  people_for_item(item, case) -> (ok, people, note)
#   🔴 解析出 0 人 ⇒ **拒絕該項目**，不是靜默算 0
```

### ⇒ 新來源加在**同一個 tuple**，解析加在**同一支函式**

```
PERSON_SOURCES += ("department",)     # 或 "department:{id}" 形式，見下
people_for_item() 多一個分支
```

☠️ **不要**把「群組」做成散在各處的判斷：
```
🔑 `PERSON_SOURCES` 是唯一真相，`people_for_item()` 是唯一解析點
⇒ 在呼叫端加 `if source == "department"` = **把接縫拆成兩個**
   而第二個接縫**沒有人會記得去維護**
```

### ⚠️ 而「哪一個群組」要存在哪裡

```
PERSON_SOURCES 的值是**型別**不是**實例** —— "sales_person" 不帶參數
而「department」要帶**哪一個 department**
⇒ 兩條路：
   甲 `bonus_items` 加一個 `person_source_ref` 欄位（存 department_id）
   乙 來源字串本身帶參數：`"department:2"`
```

**建議甲**，而理由是乙的副作用：
```
⚠️ 乙會讓 `PERSON_SOURCES` 從**閉集合**變成**開集合**
   => 現在可以 `assert source in PERSON_SOURCES`，之後不行
   ☠️ 而 `person_source_snapshot` 已經在存那個字串（bonus_award_lines）
      => 存 "department:2" 進去之後，**部門被刪掉時那個字串仍然在**
         而它看起來像一個合法的來源
⇒ 甲把「型別」與「實例」分開，`assert` 仍然成立
```
🔴 **而甲要動 `bonus_items` 加欄位 ⇒ migration ⇒ `db.py` 是鎖定檔，動前要宣告。**

### 🔴 0 人時走既有那條，不要另外發明

```
群組沒有人（部門空了、人都離職了）=> `people_for_item()` 回 (False, [], note)
=> **拒絕該項目**，與 `case_stages.assigned_to` 空陣列走同一條
🔑 `bonus.py:158` 的 docstring 逐字：「**空是常態不是例外**」
```

## §4 ③ 🔴🔴 「自動計算比例」＝**均分，而均分一定有尾差**

```
⚙️ 單位是**基點**（1/10000）—— 實測 bonus_award_lines：
   total_pct = 1000  （= 10%）
   person_pct = 10000（= 100%，因為只有一個人）
☠️ 送 50 當 50% 會變成**應得的 1/100**，而它看起來完全正常
```

### 均分：**3 個人分不盡**

```
3 人均分 10000 基點 => 3333 / 3333 / 3333，餘 1
🔴 那 1 基點去哪？
```

### ✅ **沿用 `BN6` 已經有的「尾差（歸公司留存）」，不要另外設計**

```
✅ 均分後的餘數 ⇒ 尾差
❌ 不要「給第一個人」 —— 那會讓「每個人都是 1/3」這句話變成謊
❌ 不要四捨五入到某人身上 —— 同上
🔑 而使用者是**拿比例去驗的**（`ACC-BN6 §5`）
```

⚠️ 而**基點層與金額層各有一次尾差**：
```
① person_pct 均分 10000 => 餘 1 基點
② amount 由 pool × person_pct // 10000 算 => 再有一次餘數
=> **兩次都要進尾差**，而不是只算一次
```

## §5 ④ 🔴 成員名單**要凍結**（同 `QL25` 一族）

```
☠️ 群組成員**會異動**（離職、調部門）
=> 一張已產生的獎金單，**重印時人員名單會變**
```

### ✅ 而現況**已經有凍結的慣例**

```
bonus_award_lines 的欄位：
   item_name_snapshot       <= 項目名**快照**
   person_source_snapshot   <= 來源**快照**
   username / total_pct / person_pct / amount
=> **每一個領款人是一列，而那一列就是凍結**
```

> ### 🔑 ⇒ **凍結已經是這張表的形狀** —— `BN14` 不必新增機制。
> ### 產生獎金單那一刻把群組展開成 N 列，**之後群組怎麼變都不影響它**。

📌 而 `QL25` 那次的判準在這裡同樣成立：
> **「現在該去哪裡找」要即時；「當時發生了什麼」要凍結。**
> 獎金單回答的是「**當時該發給誰**」⇒ **凍結**。

## §6 🔴 而「存什麼」有一個**既有缺陷**

### 實測

```
bonus_award_lines.username 的值：'高晟耀'／'黃玉龍'
⚙️ 比對 users：username 命中 **0**／display_name 命中 **1**
=> 🔴 **欄位叫 `username`，而裝的是 `display_name`**
```

### 而上游更糟：**同一個欄位裝兩種東西**

```
quotations.sales_person 的相異值：
   'Test2'  'Test3'  '高晟耀'  '黃玉龍'   => display_name
   '**test3**'                          => **username**
=> **同一欄混了兩種識別**
而真正的帳號欄位是 data_json.**salesPersonUsername**（25 張裡 14 張有）
```

> ### ☠️ `display_name` **會改**（使用者改名）⇒ 已產生的獎金單指向一個可能消失的名字。
> ### ☠️ 而**兩個人同名時分不出來誰是誰**。

📌 🔑 而傳票那邊**已經解過同一題**：
> `vouchers.py` 的 `_user_name()` docstring 逐字：
> 「寫進 `*_by` 欄位的值：**`username`，不是 token，也不是 id**」

### ⇒ `BN14` 的處置與**要 A 裁的一格**

```
✅ `BN14` 解析群組成員時，**存 `username`**（那是穩定識別）
🔴 而那會讓**同一張表出現兩種語意**（既有列是 display_name、新列是 username）
⇒ 兩條路，要 A 裁：
   甲 `BN14` 只管自己，既有的**另開編號修**
      ⚠️ 過渡期同一張表兩種語意 ⇒ 顯示端要能吃兩種 ⇒ **相容分支永遠不會被刪**
   乙 一起修（把既有 4 列回填成 username，並改 sales_person 那條來源）
      ⚠️ 它動到 `quotations.sales_person` 的讀取端 ⇒ **範圍變大**
```
📌 **我傾向乙** —— 理由：`bonus_award_lines` 今天只有 **4 列**（全是測試資料），
**現在修的成本是全系統最低的一刻**，而甲的相容分支會活很久。

```
BN3     manual   = 「**我自己列一份名單**」
BN14    群組     = 「**照組織表動態解析**」
```

> ### 🔴 **`BN14` 不取代 `BN3`。**

```
☠️ 否則 B 會以為做完群組就不用做 manual
⚠️ 而 `BN3` 的 9 題**還紅著**
🔑 兩者的差別在**誰決定名單**：manual 是人、群組是組織表
   => 一個部門調動之後，manual 的名單**不會變**（那正是它的用途）
```

## §8 驗收（`AC1`）

```
① 後端  PERSON_SOURCES 多一個值；people_for_item() 多一個分支
        產生獎金單時把群組展開成 N 列 bonus_award_lines
        均分的兩次尾差都進「尾差（歸公司留存）」
② 前端  獎金項目的「人員來源」下拉多一個「部門」＋選哪一個部門
③ 頁面  ⓐ 選一個**有 3 人**的部門 => 產生後看到 3 列，每列 person_pct = 3333
           而尾差 = 1 基點（以及金額層的餘數）
        ⓑ 各列金額加總 ＋ 尾差 = 總發放額，**一元不差**
        ⓒ 產生後**把其中一人調到別的部門** -> 重開那張獎金單
           => **仍然是 3 列**（§5 的驗收）
        ⓓ 選一個**空部門** => **拒絕該項目**並說明，不是產生 0 列
           🔑 ⓓ 是 §3 的驗收 —— 而正式機可能大量 NULL，這條路會真的被走到
        ⓔ 負對照：`manual` 來源的行為**完全不變**（§7）
```

### 🔴 守門

```
✅ 釘：`PERSON_SOURCES` 是**閉集合**，而 `people_for_item()` 是**唯一解析點**
   ⚙️ 掃 `backend/**`：`if .* == "department"` 這類判斷**只出現在 people_for_item 裡**
   ☠️ 散出去的話，第二個接縫沒有人會記得維護
✅ 釘：均分後**各列 person_pct 之和 ＋ 尾差 = 10000**
   ⚙️ 正對照 3 人（分不盡）／4 人（分不盡）／2 人（分得盡）**三種都要**
   🔑 只測分得盡的那種，尾差的路徑**一次都不會跑到**
```
