## §1 🔴 **不接組織架構 —— 獎金模組自己建群組**（使用者 2026-09-23 裁）

> 使用者原話：「**後勤單位只在這邊獨立設定，不需要共用**」

### ⚠️ 而「為什麼不接」要寫下來

```
系統裡**已經有** divisions（2 列）／departments（5 列）／users.department_id
⇒ ☠️ 下一個人看到 `users.department_id` 就在那裡，**會覺得我們漏用了它**
🔑 ⇒ 不接是**使用者的決定**，不是疏漏
```

### ✅ 而這順便解掉一個風險

```
db.py:1556 的註解逐字：組織架構是「**純組織分類用途**…先預留給未來簽核路由使用」
=> 它是一個「**預留而未使用**」的結構
⚠️ 而「預留」的意思是：**正式機上可能沒有人填過**
   （開發機實測 users.department_id NULL 只有 1/13，**而那是開發機**）
🔑 使用者這一句讓那個風險**完全不存在** —— 群組是獎金模組自己的，建了就有
```

### 🔴 而我上一版寫的「後勤單位不在 departments 名單裡」**作廢**

```
❌ 上一版：「departments 的 5 個名字裡沒有『後勤』，最接近是『行政營運管理中心』
            ⇒ 要問使用者是不是指它」
✅ 現在：**不接組織架構** ⇒ 使用者自己建一個叫「後勤單位」的群組就好
🔑 那一問**問錯了層級** —— 我在問「它對應到現有的哪一個」，
   而使用者要的是「**讓我自己建一個**」
```

## §2b ① 群組存哪 —— **新表，不要 `system_settings` 的 JSON**

> A 的判準：**它要不要被稽核／要不要知道「誰在什麼時候把某人加進來」**

```
✅ 新表 bonus_groups(id, name, is_active, created_by, created_at, updated_at)
        UNIQUE(name)
   新表 bonus_group_members(group_id, username)
        UNIQUE(group_id, username)
❌ 不要 system_settings 的一個 JSON 值
```

理由（三條，而第一條是 A 的判準）：
```
① **要稽核**：「誰把某人加進後勤單位」是會被問的問題
   而 system_settings 只有一個 `updated_at`，**答不出是誰加了哪一個人**
② 要能回答「**這個人在哪些群組裡**」 ⇒ JSON 查不動
   📌 與 `SPEC-BN2-BN5 §2` 選新表不選 JSON 欄位**同一個理由**
③ `UNIQUE(group_id, username)` 讓「同一個人加兩次」在**資料層**被擋
   ☠️ JSON 裡放什麼都塞得進去
```

🔴 **而加表要動 `db.py`（鎖定檔）⇒ 動前要宣告。**

## §3 ② 成員解析 —— **走既有接縫，不要在呼叫端加 if**

```python
# helpers/bonus.py:146  —— **唯一真相**
PERSON_SOURCES = (
    "sales_person",             # 業務
    "case_stages.assigned_to",  # 各執行階段負責人（JSON 陣列）
)
# helpers/bonus.py:155  people_for_item(item, case) -> (ok, people, note)
#   🔴 解析出 0 人 ⇒ **拒絕該項目**，不是靜默算 0
```

### ⇒ 新來源加在**同一個 tuple**，解析加在**同一支函式**

```
PERSON_SOURCES += ("group",)          # 而「哪一個群組」另存，見下
people_for_item() 多一個分支
```

☠️ **不要**把「群組」做成散在各處的判斷：
```
🔑 `PERSON_SOURCES` 是唯一真相，`people_for_item()` 是唯一解析點
⇒ 在呼叫端加 `if source == "group"` = **把接縫拆成兩個**
   而第二個接縫**沒有人會記得去維護**
```

### ⚠️ 而「哪一個群組」要存在哪裡

```
PERSON_SOURCES 的值是**型別**不是**實例** —— "sales_person" 不帶參數
而 "group" 要帶**哪一個群組**
⇒ 兩條路：
   甲 `bonus_items` 加一個 `person_source_ref` 欄位（存 bonus_groups.id）
   乙 來源字串本身帶參數：`"group:2"`
```

**建議甲**，而理由是乙的副作用：
```
⚠️ 乙會讓 `PERSON_SOURCES` 從**閉集合**變成**開集合**
   => 現在可以 `assert source in PERSON_SOURCES`，之後不行
   ☠️ 而 `person_source_snapshot` 已經在存那個字串（`bonus_award_lines`）
      => 存 "group:2" 進去之後，**群組被刪掉時那個字串仍然在**
         而它看起來像一個合法的來源
⇒ 甲把「型別」與「實例」分開，`assert` 仍然成立
```
🔴 **而甲要動 `bonus_items` 加欄位 ⇒ migration ⇒ `db.py` 是鎖定檔，動前要宣告。**
📌 ⚠️ 而 `bonus_groups` 也是新表 ⇒ **兩個 migration 合成一輪**，不要分兩次。

### 🔴 0 人時走既有那條，不要另外發明

```
群組沒有人（建了而沒加人、或人都離職了）=> `people_for_item()` 回 (False, [], note)
=> **拒絕該項目**，與 `case_stages.assigned_to` 空陣列走同一條
🔑 `bonus.py:158` 的 docstring 逐字：「**空是常態不是例外**」
```

## §4 ③ 🔴🔴 「自動計算比例」＝**均分，而均分一定有尾差**

```
⚙️ 單位是**基點**（1/10000）—— 實測 bonus_award_lines：
   total_pct = 1000  （= 10%）
   person_pct = 10000（= 100%，因為只有一個人）
☠️ 送 50 當 50% 會變成**應得的 1/100**，而它看起來完全正常
```

### 均分：**3 個人分不盡**

```
3 人均分 10000 基點 => 3333 / 3333 / 3333，餘 1
🔴 那 1 基點去哪？
```

### ✅ **沿用 `BN6` 已經有的「尾差（歸公司留存）」，不要另外設計**

```
✅ 均分後的餘數 ⇒ 尾差
❌ 不要「給第一個人」 —— 那會讓「每個人都是 1/3」這句話變成謊
❌ 不要四捨五入到某人身上 —— 同上
🔑 而使用者是**拿比例去驗的**（`ACC-BN6 §5`）
```

⚠️ 而**基點層與金額層各有一次尾差**：
```
① person_pct 均分 10000 => 餘 1 基點
② amount 由 pool × person_pct // 10000 算 => 再有一次餘數
=> **兩次都要進尾差**，而不是只算一次
```

## §5 ④ 🔴 成員名單**要凍結**（同 `QL25` 一族）

```
☠️ 群組成員**會異動**（離職、調單位、使用者手動改群組）
=> 一張已產生的獎金單，**重印時人員名單會變**
```

### ✅ 而現況**已經有凍結的慣例**

```
bonus_award_lines 的欄位：
   item_name_snapshot       <= 項目名**快照**
   person_source_snapshot   <= 來源**快照**
   username / total_pct / person_pct / amount
=> **每一個領款人是一列，而那一列就是凍結**
```

> ### 🔑 ⇒ **凍結已經是這張表的形狀** —— `BN14` 不必新增機制。
> ### 產生獎金單那一刻把群組展開成 N 列，**之後群組怎麼變都不影響它**。

📌 而 `QL25` 那次的判準在這裡同樣成立：
> **「現在該去哪裡找」要即時；「當時發生了什麼」要凍結。**
> 獎金單回答的是「**當時該發給誰**」⇒ **凍結**。

## §6 🔴 而「存什麼」有一個**既有缺陷**

### 實測

```
bonus_award_lines.username 的值：'高晟耀'／'黃玉龍'
⚙️ 比對 users：username 命中 **0**／display_name 命中 **1**
=> 🔴 **欄位叫 `username`，而裝的是 `display_name`**
```

### 而上游更糟：**同一個欄位裝兩種東西**

```
quotations.sales_person 的相異值：
   'Test2'  'Test3'  '高晟耀'  '黃玉龍'   => display_name
   '**test3**'                          => **username**
=> **同一欄混了兩種識別**
而真正的帳號欄位是 data_json.**salesPersonUsername**（25 張裡 14 張有）
```

> ### ☠️ `display_name` **會改**（使用者改名）⇒ 已產生的獎金單指向一個可能消失的名字。
> ### ☠️ 而**兩個人同名時分不出來誰是誰**。

📌 🔑 而傳票那邊**已經解過同一題**：
> `vouchers.py` 的 `_user_name()` docstring 逐字：
> 「寫進 `*_by` 欄位的值：**`username`，不是 token，也不是 id**」

### ✅ A 裁（2026-09-23）：**切成兩半 —— 這張表現在修，上游另開編號**

```
✅ **做**：`bonus_award_lines.username` 改成真的裝 `username`
   理由：今天只有 **4 列且全是測試資料**
   🔑 **現在是全系統修它最便宜的一刻，而這個便宜只會愈來愈貴**
   ☠️ 而「只管自己、既有不動」的代價是：**同表兩種語意 ⇒ 相容分支永遠不會被刪**

🔴 **另開 `QS1`**：`quotations.sales_person` 同一欄混兩種識別
```

#### 🔑 而切開的理由不是「範圍大」，是「**一個做得完、一個做不完**」

```
bonus_award_lines  4 列全是測試資料          => **做得完**
quotations.sales_person
   25 張裡只有 **14 張**有 `salesPersonUsername`
   => **11 張沒有帳號可回填** —— 那 11 張怎麼辦是一個**獨立的決定**
```

> ### ☠️ **把一個「做得完」的與一個「做不完」的綁在一起，結果是兩個都卡住。**

📌 ⇒ 本編號**只改 `bonus_award_lines`**，而群組成員一律存 `username`。

## §7 ⑤ 群組**停用／刪除**之後，已經引用它的項目怎麼辦

📌 `BN3` 的邊界問題**不存在了** —— 它已併入本編號（§2）。

### 照 `CA1` 那一族的精神：**不可以讓既有的單失去意義**

```
已**產生**的獎金單    ✅ 不受影響 —— bonus_award_lines 已經是凍結的 N 列（§5）
                         群組怎麼變都不影響它
引用它的**獎金項目**  🔴 這才是問題：item.person_source_ref 指向一個停用／刪除的群組
```

### ⇒ 三條規則

```
① 群組**可停用，不可刪除**（`is_active=0`）
   🔑 照 `CA1`（停用仍佔號）的形狀 —— 刪掉的話，
      `person_source_snapshot` 裡那個字串會指向空氣
② 停用的群組**不出現在新項目的下拉選單**，而**既有項目仍然指得到它**
   ⚠️ 而畫面上要標「（已停用）」—— 不要讓它看起來正常
③ 🔴 用停用群組**產生新獎金單**時 => **拒絕**，走 `people_for_item()` 的既有路徑
   ☠️ 不要靜默解析成 0 人 —— 那會讓一張單少一個項目而沒有人知道
```

⚠️ 而「停用之後成員還在不在」要明著寫：
```
停用 = 不能再被選，**而成員清單保留**
=> 重新啟用之後它**還是同一群人**
☠️ 停用時清空成員的話，重新啟用會是一個空群組，而畫面上看起來正常
```

## §7b ✅ 群組維護畫面**放獎金設定頁**（A 裁）＋ 容器實查

### A 的裁定理由

```
`BN2` 已裁「**獎金項目只有最高管理者可見**」
而群組是**獎金項目的附屬設定**
☠️ 放使用者管理旁邊 => **權限判斷會分散在兩處**，而兩處遲早會漂移
   📌 今天 `EM13` 那一整族就是這個
```

### ✅ 而容器**存在** —— 這一件是「**加一個區塊**」不是「加一個頁」

```
frontend/pages/bonus.html（**528 行，唯一的獎金頁**，側欄一個入口 sidebar.js:765）
它的結構是三個 <section class="bn-sec">：
   :147  「**獎金項目**」     x-show="isManager && itemsLoaded"
   :222  「**產生獎金單**」   x-show="canCreateAward"
   :392  （獎金單清單）       x-show="loaded"
```

> ### ⇒ 群組管理是**第四個 `bn-sec`**，
> ### 而 `x-show` 照抄「獎金項目」那一條（`isManager && …`）。

🔑 **權限判斷因此只有一處** —— 那正是 A 裁它放這裡的理由。

⚠️ 而**順序**要放在「獎金項目」**之前**：
```
使用者的動線是「先有群組 -> 才能在項目上選它」
☠️ 放在後面的話，他會先看到一個下拉裡沒有任何群組，
   而**不知道要去哪裡建**
```

## §8 驗收（`AC1`）

```
① 後端  PERSON_SOURCES 多一個值；people_for_item() 多一個分支
        產生獎金單時把群組展開成 N 列 bonus_award_lines
        均分的兩次尾差都進「尾差（歸公司留存）」
② 前端  獎金項目的「人員來源」下拉多一個「群組」＋選哪一個群組
        ＋群組管理**區塊**（建群組／加成員／停用）—— 位置見 §7b
③ 頁面  ⓐ 建一個**有 3 人**的群組 => 產生後看到 3 列，每列 person_pct = 3333
           而尾差 = 1 基點（以及金額層的餘數）
        ⓑ 各列金額加總 ＋ 尾差 = 總發放額，**一元不差**
        ⓒ 產生後**把其中一人從群組移除** -> 重開那張獎金單
           => **仍然是 3 列**（§5 的驗收）
        ⓓ 選一個**空群組**（建了沒加人）=> **拒絕該項目**並說明，不是產生 0 列
           🔑 ⓓ 是 §3 的驗收 —— 而正式機可能大量 NULL，這條路會真的被走到
        ⓔ 負對照：`manual` 來源的行為**完全不變**（§7）
```

### 🔴 守門

```
✅ 釘：`PERSON_SOURCES` 是**閉集合**，而 `people_for_item()` 是**唯一解析點**
   ⚙️ 掃 `backend/**`：`if .* == "group"` 這類判斷**只出現在 people_for_item 裡**
   ☠️ 散出去的話，第二個接縫沒有人會記得維護
✅ 釘：均分後**各列 person_pct 之和 ＋ 尾差 = 10000**
   ⚙️ 正對照 3 人（分不盡）／4 人（分不盡）／2 人（分得盡）**三種都要**
   🔑 只測分得盡的那種，尾差的路徑**一次都不會跑到**
```
