## §2 🔴 純裁示的那一格：**哪些舊單號是歷史事實？**

> A 2026-09-23 明著提出，而它**不是量測問題** ——
> 答錯的兩個方向都很貴：
> **改了＝竄改歷史 ／ 不改＝使用者搜舊單號搜不到。**

### 建議的判準（**沿用使用者已經裁過的那一條**）

`QL10`／`QL16` 那次使用者裁定的判準逐字是：

> 匯款帳號要回答「**現在**該匯到哪」，而薪資單的抬頭回答的是
> 「**當初是誰付的**」。**那不是同一個問題。**

⇒ 同一把尺套在這裡：

```
這個欄位回答的是「**現在該去哪裡找**」    => **要改**（它是關聯）
這個欄位回答的是「**當時發生了什麼**」    => **不可以改**（它是歷史）
```

### 而 A 點名的難題（`case_updates` 的文字內容）**用這把尺會自己分開**

```
case_updates.quote_no（**欄位**）      現在該去哪裡找  => **改**
case_updates 的**文字內容**           當時某人寫下的字 => **不改**
```

🔑 ⇒ **不是「這張表算歷史還是算資料」，而是「這個欄位是關聯還是內容」。**
> **關聯一律改，人寫下的字一律不改。**

☠️ 而**混在一起問**的時候它看起來是兩難的 —— 因為同一張表兩種都有。

### ⚠️ 而「使用者搜舊單號搜不到」這個代價**仍然存在，要另外處置**

改欄位不改內容之後：
```
✅ 關聯不會斷
🔴 而使用者拿著舊單號（紙上、信裡、他記在腦子裡）**搜不到**
```

**建議**：`quotations` 保留一份**曾用單號**，搜尋時一併比對。

```
quotations.data_json["previousQuoteNos"] = ["MQ-202609-001", ...]
⇒ 每次改名 append，**不覆蓋**
```

**這個處置自己的副作用**（分開寫）：
```
⚠️ 搜尋要多比對一個欄位 —— 成本小，但它是 data_json 裡的陣列，
   若搜尋走 SQL LIKE 會變成掃描（要量，本規格沒量）
⚠️ 而它**不解決紙本**：外面那張舊紙上的號碼，系統裡的單已經是另一個號
   => 搜得到它、而搜到的那張與手上那張**內容可能已經不同**
   🔑 那是使用者裁「舊紙不算數」的直接後果，**不是缺陷**
      ⇒ 搜尋結果要標「**此單號已更新為 X**」，不要靜默導過去
```

### ✅ A 2026-09-23 已裁（兩件都不上呈）

```
① 判準  **關聯一律改，人寫下的字一律不改**
   理由照原文：它看起來兩難是因為同一張表兩種都有 —— 問「這張表」就答不出來
② 搜尋  **要留** previousQuoteNos（append 不覆蓋），搜尋一併比對
        並且**標「此單號已更新為 X」，不要靜默導過去**
   🔑 A 的理由：**使用者裁的是「舊紙不算數」，不是「舊單號要從系統裡消失」**
      —— 兩者不是同一件事，而把它讀成後者會讓一個每天會用到的動作壞掉
```

### 🔴 而 A 加的那條界線要落在驗收裡，不是落在註解裡

> 「SQL LIKE 會不會變掃描**你沒量**」⇒ **落地時要量**。

```
❌ 不可以寫成「可能會慢」就算處理過了
✅ 驗收要有一個數字：在 quotations 現有筆數下，
   帶 previousQuoteNos 的搜尋與不帶的差多少毫秒
📌 〈已知的代價 vs 要修的東西〉：**寫成註解之後它看起來像被處理過了。**
```

## §3 交易邊界 —— **這一格不裁會直接變成更糟的狀態**

```
🔴 連動**必須**與 `UPDATE quotations SET quote_no=` 在**同一個交易**裡
☠️ 不同交易 ⇒ 中途失敗 = **報價單改名了而下游沒改**
   => 那比現在更糟：現在至少是「全部都指著舊號」，
      中途失敗會變成「**一半指舊號、一半指新號**」
```

```python
conn = get_db()
try:
    conn.execute("BEGIN IMMEDIATE")       # ⚠️ 明著開，不要靠隱式交易
    for table in _QN1_TABLES:             # §4 ①
        conn.execute('UPDATE "%s" SET quote_no=? WHERE quote_no=?' % table,
                     (new_no, old_no))
    _rewrite_embedded(conn, old_no, new_no)   # §4 ②
    conn.execute("UPDATE quotations SET quote_no=?, … WHERE quote_no=?", …)
    conn.commit()
except Exception:
    conn.rollback()
    raise
finally:
    conn.close()
```

⚠️ **順序**：先改下游、最後改 `quotations` ——
```
`quotations.quote_no` 是 UNIQUE（db.py:409）
=> 先改它的話，中途若失敗，新號已經佔住而下游還是舊號
```

⚠️ 而 `reject_quotation` 目前是 `conn.execute(...)` ＋ `conn.commit()`，
**沒有明著開交易** ⇒ 這一件會動到那一支的結構，B 要留意。

## §4b 🔴 A 問「舊檔怎麼辦」—— **而那個前提我去查了，它不成立**

A 給的兩個選項：
```
甲 只改新的，舊檔用舊路徑（=> 兩種命名並存，讀取端要能吃兩種）
乙 一次性搬遷（=> 搬了一半而它不在任何交易裡）
```

### ✅ 先查前提：**改單號會不會讓既有檔案失聯？**

```
helpers/uploads.py:107-110  逐字註解：
   「直接用 `target["path"]` 存的**完整相對路徑**（已含 demo 前綴）」
   full = os.path.join(UPLOADS_ROOT, target["path"])

voucher_attachments.py:235／voucher_pdf.py:129／quotations.py:2220,2240
   全部是 abs_path(x["path"]) ／ join(ROOT, f["path"])  => **讀存下來的字串**

routers/quotations.py:4922  _resolve_archived_pdf(base, rel)
   rel = docVersions[].file                              => **讀存下來的字串**

⚙️ 反向查：quotations.py／pdf_gen.py 裡的 glob／listdir／scandir
   只有兩處（:2224/:2253），而它們是**刪除後清空目錄**，不是找檔
```

> ### ⇒ **沒有任何讀取端是用當前單號去算路徑的。**
> ### 改單號**不會**讓既有檔案失聯 —— 路徑是存下來的字串，不是算出來的。

☠️ 而 `delete_document_file(subfolder, doc_no, existing_files, file_id)` 那兩個參數
**根本沒有被用來定位檔案**（它用 `target["path"]`）—— 那是**看起來會壞而其實不會**的一處。

### ⇒ 所以真正的問題**比 A 寫的小**，而它是兩件別的事

```
① 目錄名與當前單號對不起來 —— **人**去 uploads/ 翻檔案時看到舊號
   => 運維／稽核的可讀性問題，**不是功能問題**
② 退回之後**新寫入**會用新單號 => 同一張單的檔案散在兩個目錄
   ☠️ 而 :2224/:2253 的清空邏輯不會清掉舊目錄（裡面還有檔）
```

### ✅ 我選 **丙**：什麼都不搬，只把**未來的寫入**改成不含單號

```
照 vouchers 那個先例（`vouchers.py:955`：doc_no 用 str(voucher_id)）
=> uploads/{subfolder}/{quotation_id}/…
既有檔案**原地不動**，它們的 path 已經存在資料庫裡，讀得到
```

**顧慮**（本題要解的）：退回改名之後，同一張單的檔案不在同一個地方。

**丙這個處置自己的副作用**（分開寫）：
```
⚠️ ① 過渡期會有**兩種目錄名並存**（舊的含單號、新的含 id）
      而人工翻檔案時要知道這件事 => 要寫進維運文件，不是只寫進碼
⚠️ ② 既有的舊目錄**永遠不會被整理** —— 它不會壞，而它會一直在
      🔑 而「它不會壞」正是我選丙的理由，**這兩件事是同一件事的兩面**
⚠️ ③ 若日後有人寫一支「依單號列出所有檔案」的功能，**它在舊資料上會漏**
      => 規格要明著禁止：**不可以用目錄名當索引**，一律走資料庫的 path
```

### 🔑 而丙**沒有**甲的那個副作用

A 先起頭的那一條：
> 甲的副作用：**讀取端吃兩種格式 ⇒ 那個相容分支永遠不會被刪掉**，
> 而三年後沒有人知道它為什麼在那裡。

```
丙沒有相容分支 —— 因為**讀取端從一開始就不解析路徑格式**，它只是把字串拿去 join
=> 兩種目錄名對讀取端是**透明的**
```
📌 ⇒ 甲與丙看起來很像（都是「舊的不動」），**而它們的差別在讀取端有沒有分支**。
☠️ 而那個差別只有在**去讀讀取端**之後才看得到 ——
從「要不要搬檔案」這個問法**問不出來**。

## §5 守門 —— **加總型**

> 🔑 唯一會**自己翻臉**的檢查是加總。其餘每一項都只會說「通過」。

```
✅ 掃 DB schema 找出**每一張**有 `quote_no` 欄位的表，
   斷言 **每一張都在「連動清單 ∪ 排除清單」裡**
   => 將來新增一張表時，它會**自己翻臉**
☠️ **不要釘一個數字**（例如「17 張」）——
   新增表那天最省力的反應是把數字加一，
   而**沒有人會去看那一張表該連動還是該排除**
   📌 守門從「檢查」退化成「記帳」，而那一步不留痕跡

✅ 同理 ②：掃每個 `*_json` 欄位的**值**，斷言不存在「指向已不存在單號」的內嵌
   ⚙️ 正對照 造一張退回過的單，斷言下游全部指到新號
   ⚙️ 負對照 稽核軌跡裡的舊號**必須還在**
      🔑 少了這個負對照，「全部改掉」也會全綠 —— **而那正是竄改歷史**
```

## §6 驗收（`AC1`）

```
① 後端  退回一張有下游資料的單 -> 所有連動表指到新號、排除表維持舊號
        ⚠️ 而「有下游資料」要**實際造出來**，不可以只退一張空單
② 前端  無異動（除非 §2 的「曾用單號」搜尋落地）
③ 頁面  ⓐ 退回前記下舊號 -> 退回 -> 用**新號**開得到案件的全部資料
        ⓑ 用**舊號**搜尋 -> 依 §2 裁定：搜得到且標「已更新為 X」，或明確查無
        ⓒ 稽核紀錄裡**還看得到舊號**
```
