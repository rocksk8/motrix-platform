## §2 🔴 A 問的第一格：「送審中」對到兩個狀態 —— **合併，而理由是系統自己的**

### ⚙️ 兩個「要人動手」的地方，都把它們當成**同一個集合**

```python
# bonus.py:843   核准
if status not in ("待審核", "簽核中"):
# bonus.py:903   退回
if status not in ("待審核", "簽核中"):
```

> ### 🔑 **系統在每一個要人動手的地方，都沒有區分它們。**
> ### ⇒ 「還沒簽完的」是一個真實的集合，而它已經被寫成程式碼了。

⚙️ 而兩者的差別只是**進度**：
```
待審核  已送出，**第一關還沒動**
簽核中  至少一關簽過（`nxt = "已核准" if idx >= len(tiers) else "簽核中"`，:861）
=> 兩者**要找的人是同一個**：當前那一關的簽核者
```

### ⚠️ 而合併有一個代價，要處理掉

```
A 的規則：「篩選標籤要與畫面上既有的狀態文字**逐字相同**，不要另外發明一套」
🔴 而「送審中」**不是**四個 status 之一 => 合併等於發明一個新詞
```

> ### ⇒ 解法：**「送審中」是集合的名字，`待審核`／`簽核中` 是成員的名字。**

```
篩選標籤   「送審中」          <= 集合
每一列的狀態欄  `待審核` 或 `簽核中`  <= **逐字不變**
☠️ 畫面上**不可以**出現「這張單的狀態是送審中」——
   那才是發明了一套並行的命名
```
⚙️ 守門釘得到：**`待審核` 與 `簽核中` 這兩個字串仍然出現在列的狀態欄**。

## §4 A 問的第一格（呈現）：**一排頁籤，而且互斥**

### ⇒ 建議

```

```

```

送審中          status in ('待審核','簽核中')
已核准・未撥付  status == '已核准' && **!is_paid**
已撥付          **is_paid**
```

### 🔑 為什麼把「已核准」與「未撥付」寫成**一格**

```
使用者列了五個詞，而其中「已審核」與「未撥付」**在結構上是同一批單**
（今天那四張同時滿足兩者）
❌ 做成兩個頁籤 => 同一張單出現在兩個地方，而計數加不起來
❌ 只做「已核准」 => 使用者說的「未撥付」沒有落點
✅ 合成一格且**標籤同時含兩個詞** => 兩個詞都在畫面上，而集合只有一個
```

> ### ✅ 而互斥帶來一個**會自己翻臉**的守門：
> ### **四個頁籤的計數相加，必須等於總筆數。**

```
🔑 其餘每一種檢查都只會說「通過」——
   而加總在分類重疊或漏掉時**會自己算不平**
☠️ 若哪天有人把「已核准」拆成獨立頁籤，這道守門當天就紅
```

⚠️ 而「顯示已作廢」是**獨立的一個核取方塊**，不是第六個頁籤：
```
它是第三個維度（有效／作廢），與狀態正交
✅ 沿用既有的 `GET /awards?include_voided=`，**不要另做一個**（A 已指出）
⚠️ 而勾選之後，作廢單要**併進各狀態頁籤**還是獨立列出 —— 見 §7①
```
