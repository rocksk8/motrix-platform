# `SPEC-BN20` · 已核准的獎金單也要能退回

> 2026-09-23 ／ 視窗 A-2
> ⚙️ 使用者逐字：**「已核准，也要有退回」**
> （起因：他問「獎金分潤的退回鈕在哪邊」—— 而已核准的單退不回來。）

---

## §1 🔴 先答那個查證：**核定會不會開傳票？** —— 答案是三層的

A 的兩個分支（「會開 ⇒ 孤兒傳票，一天的工作」／「不會 ⇒ 十分鐘的小改動」）
**都不是答案**。實查之後是這樣：

### ① ✅ 程式上不會 —— `approve_award()` 只動一張表

```
⚙️ approve_award() 內：UPDATE bonus_awards ×2，**零 INSERT**
⚙️ 而 bonus.py 全檔 5 個 INSERT，插的是
   bonus_awards ／ bonus_award_lines ／ bonus_items ／ bonus_groups ／ bonus_group_members
   —— **一個都不是傳票表**
⚙️ 全 backend：INSERT INTO vouchers_all 只在 routers/vouchers.py（＋一支測試）
```

### ② 🔴 而連結**是存在的**，它在獎金單這一側

```
bonus_awards.voucher_no_accrual   TEXT  # 核定那筆傳票   （db.py:5004）
bonus_awards.voucher_no_payment   TEXT  # 發放那筆傳票   （db.py:5005）
```
> ### ☠️ 我第一次查是從 `vouchers_all` 那一側找「指向獎金單的欄位」——**找不到，而結論是錯的**。
> ### 🔑 **外鍵在哪一側，決定你要從哪一側查。** 反方向查會得到一個乾淨的否定答案。

⇒ 那正是 `archive.py:1626` 註解說的「`bonus_awards` **會開出兩筆傳票（核定／發放）**」。
📌 **那句註解沒有錯，它描述的是業務流程與欄位設計，不是「程式會自動開」。**

### ③ 🔴 而那兩欄**零寫入端、實際值全空** ⇒ 回填功能還沒做

```
⚙️ UPDATE bonus_awards SET ... 全 backend 只有三種：
      status（4 處）／voided_at（2 處）／paid_manually_by（1 處）
   => voucher_no_accrual／voucher_no_payment **沒有任何寫入端**
⚙️ 實際資料：5 張獎金單，兩欄**全部是空字串**
⚙️ 而 routers/bonus.py:1268 逐字：「自動回填（主路，**本規格未做**）」
```

> ### ✅ ⇒ **`BN20` 今天是安全的，而它的安全取決於一個還沒做的功能。**

```
🔴 那個回填功能一旦做了，BN20 就會變成一個問題：
   voucher_no_accrual 有值的單被退回 => 那張傳票指向一張回到草稿的獎金單
⇒ 本規格 §4④ 先把那道檢查寫進去（**今天永遠不會觸發，而它會等在那裡**）
```
⚠️ 而**不要因為「今天不會觸發」就不做** ——
☠️ 那正是〈已知的代價 vs 要修的東西〉：**當場認出缺陷卻寫成註解＝放過**。

## §2 ⚙️ 現況

### ① 後端 `reject_award()`（`routers/bonus.py:1203`）已經做了四件事

```
✅ 空原因擋 400（"請填寫退回原因。"）
✅ 狀態白名單：status not in ("待審核","簽核中") => 400「「X」的獎金分潤單不能退回。」
✅ UPDATE status='草稿'、approval_json='{}'
✅ 寫 bonus_award_edit_log（retention='permanent'）＋ audit_log
```
> ### ✅ 而 `approval_json` 的**舊值有被記進 edit_log**
> ### （`{"field":"approval_json","from":old_approval_json,"to":"{}"}`）——
> ### 🔑 所以「退回會清掉簽核記錄」**不是**一個風險，它留在永久保存的異動記錄裡。

### ② 前端三個分支（`frontend/pages/bonus.html:740/745/755`）

```
草稿                              => 只有「送審」
待審核 ／ 簽核中                   => 「簽核通過」＋「**退回**」
已核准 && !isAwardPaid(...)        => 只有「標記已發放」   <= **缺退回**
```

### ③ ⚙️ 而 `isAwardPaid()` 的定義（`helpers/bonus.py:389`）

```
已發放 = voucher_no_payment 非空  OR  paid_manually_at 非空
```

### ④ 🔴 母體：**已核准 4 張**

```
bonus_awards：已核准 4 ／ 草稿 1
```
⚠️ ⇒ 這個功能**一上線就有 4 張可以退** —— 不是一個假想情境。

## §3 處置

### ① 後端：狀態白名單加一個

```
status not in ("待審核", "簽核中")
=>
status not in ("待審核", "簽核中", "已核准")
```
> ### ⚠️ 而**已撥付不加** —— 見 §5①。

### ② 🔴 而已核准的單要多一道檢查：**已發放的不可以退**

```
if status == "已核准" and is_award_paid(award):
    raise HTTPException(400, "已發放的獎金分潤單不能退回。")
```
⚙️ 依據不是我的判斷，是**前端現況**：`已核准 && !isAwardPaid` ——
🔑 **畫面上已發放的單本來就沒有任何按鈕**，後端要與它一致。
☠️ 而只改前端不改後端，那道規則會變成「**只擋住按鈕，擋不住請求**」。

### ③ 前端：`已核准` 那個分支加「退回」

```
<template x-if="awardDetail.status === '已核准' && !isAwardPaid(awardDetail)">
   「標記已發放」 ＋ 「**退回**」
```
⚠️ 沿用既有的 `openAwardReason('reject', id)` —— **不要新增一套填原因的互動**。

### ④ 🔴 而那道「今天不會觸發」的檢查要現在寫

```
if (award.get("voucher_no_accrual") or "").strip():
    raise HTTPException(400, "這張單已經開過核定傳票（%s），不能退回。" % 那個號碼)
```
> ### 🔑 它今天**永遠是 False**（零寫入端、實際值全空）——
> ### ☠️ 而回填功能上線的那一天，**沒有人會回來想起要加這道檢查**。

⚠️ 而它需要一個**反向控制**，否則它與「沒有寫」在測試上長得一樣 —— 見 §4③。

## §4 驗收（`AC1`：後端＋前端＋頁面三者皆備）

### ① 必過

```
① 已核准的單 + 填了原因 => 200，status 變「草稿」
② 退回後 approval_json 變 '{}'，而 edit_log 裡**找得到舊值**
③ 空原因 => 400（沿用既有行為，不可退化）
④ 已發放的單（voucher_no_payment 非空）=> 400「已發放的…不能退回」
⑤ 已發放的單（paid_manually_at 非空，voucher_no_payment 空）=> **同樣 400**
⑥ 前端：已核准且未發放的單，畫面上看得到「退回」鈕；已發放的**看不到**
```
> ### 🔑 ④⑤ 是**兩條不同的路**（`isAwardPaid` 是 OR）——
> ### ☠️ 只測 ④ 的話，`if voucher_no_payment` 的寫法也會過。

### ② 🔴 而 `voucher_no_accrual` 那道檢查要用**合成資料**測

```
測試裡直接塞 voucher_no_accrual='V-2026-0001' => 退回要回 400
🔑 那是**合成輸入不是真實案例** —— 產品碼今天不會寫那一欄，
   ☠️ 而拿真實資料當誘餌的話，回填功能上線那天誘餌就失效了
```

### ③ ⚠️ 反向控制：**證明那道檢查真的在擋**

```
同一張單，voucher_no_accrual='' => 退回要**成功**（200）
```
> ### 🔑 沒有這一題的話，「永遠回 400」的實作也會過 ④⑤ 那幾題。
> ### 📌 而這一題是**綠的** —— 在一片紅裡新增綠燈對照組時要單獨跑它一次
> ### （〈在一片紅裡新增的綠燈對照組沒有人會多看一眼〉）。

### ④ ⚠️ 而要先證明它會紅

```
破壞方式（真實失效模式）：
   白名單只加 "已核准" 而不加 §3② 的檢查  => ④⑤ 要紅
   §3④ 那道檢查寫成 if False               => ② 要紅
```
