## §2 · 動工前必須先裁示的四件事

這四項會改變做法。**先決定再動手，否則會白做。**

### 2.1 側欄 vs 頂欄導覽 ← 最大分歧，影響最廣

參考稿是**頂欄導覽**（照官網版型）；現行系統是 **220px 固定側欄 ＋ 60px 頂欄**。

| 選項 | 做法 | 工作量 | 風險 |
|------|------|--------|------|
| **A** | 保留側欄，只換色票與元件樣式 | 小 | 低。但「像官網」的程度有限，首頁看起來仍是後台 |
| **B** | **首頁走頂欄版型，內頁維持側欄** | 中 | 中。兩套 chrome 要維護，但首頁是門面、內頁重操作，職能本來就不同 |
| **C** | 全站改頂欄 | 大 | 高。56 頁的 `margin-left:220px` 類版面假設全要改；深色模式的排除清單與 `test_dark_mode_chrome_structure_2026_09_13.py` 的結構前提要重寫 |

**建議 B。** 理由：內頁是每天操作的工作介面，側欄的「隨時可跳任一模組」在操作效率上勝過頂欄；
首頁則是一天只看幾次的門面，適合用官網語彙。C 的成本主要不在改版面，而在深色模式與測試前提
要一起重來——那是這次轉換不該扛的風險。

### 2.2 字型：**不可以引入 Google Fonts**

參考稿目前用 `fonts.googleapis.com` 載 Noto Sans TC + Inter。ERP 是內網系統
（§1 位址表：`https://motrix.internal:666`），正式機不保證連得到外網；連不到時
瀏覽器會**靜默**退回系統字體，整站字重與字距走樣而且不會有任何錯誤訊息。

| 選項 | 做法 |
|------|------|
| **A（建議）** | 維持 LINE Seed TW_OTF，只借官網的**字級／字重／字距規則**，不換字家族 |
| **B** | 自架 Noto Sans TC + Inter（需轉 woff2 放進 `frontend/fonts/`） |

附帶發現（**不綁進這次轉換**）：現有 4 個 OTF 共 21 MB 未轉 woff2，
`frontend/static/fonts/` 是空的殘留目錄。這兩件事該處理，但屬於另一張單。

### 2.3 主色要不要從藍換成紅

`--accent #2563EB` 改成 `#C8102E` 技術上是**改一個變數**的事。問題在語義衝突：

- 系統裡紅色目前是 `--danger #DC2626`（錯誤／刪除／逾期）。
- 主色一旦變紅，「這是主要按鈕」和「這是危險操作」在同一個色相上，**警示會失去辨識度**。

三個可行解：

| | 做法 | 代價 |
|---|------|------|
| **甲** | 主色維持藍，只換其餘語彙（段落標記、卡片、留白、字級） | 最安全，但與官網的識別連結最弱 |
| **乙** | 主色改紅，`--danger` 往深紅推（如 `#9F1239`）並一律強制配文字／圖示 | 要重跑一次全站對比檢查 |
| **丙** | 主色改紅，紅色**只**用在導覽與主要動作，危險操作改用「深紅框線＋文字」而非填滿 | 要逐頁檢視所有 danger 按鈕 |

**這題請您裁示**，我不預設。（先前參考稿 V2 試過「主色改靛藍、紅色專留警示」，
您已裁示退回官網配色，所以這裡不再列該選項。）

### 2.4 WCAG 不可退步

`style.css` 內已有三次無障礙修正紀錄（2026-08-28）：

- `--text-dim` `#9A9A9A → #767676`（2.81:1 → 4.54:1）
- `--success` `#16A34A → #15803D`（3.30:1 → 5.02:1）
- `--warning` `#D97706 → #92400E`（3.19:1 → 7.09:1）

**任何新色票上線前必須對白底重算對比，一律 ≥ 4.5:1**，不可回到 3.x。
這不是建議，是已經修過一次的回歸點。

## §3 · 轉換順序

原則：**每個階段都能獨立上線、獨立回退**，不做「全部改完才能看」的大爆炸。
每階段結束就是一個可部署的狀態。

### 階段 0 · 建立 token 對照層（**外觀零變化**）

把官網 v4 的設計常數以新 token 加進 `style.css` 的 `:root`，
**但不改任何既有 token 的值**，因此這一階段上線後畫面應完全不動。

新增（命名沿用官網語彙，與現有 token 並存）：

```
--v4-rail        ASML 直向網格線色
--v4-sec         段落上下留白 clamp(48px, 6vw, 84px)
--v4-max         內容最大寬 1200px
--v4-gutter      側邊留白 clamp(20px, 4vw, 48px)
--v4-mark        段落標記條（28×3）
--v4-ease        cubic-bezier(.2,.6,.2,1)
--v4-h1 / h2 / h3 / lead / sm / xs   字級階梯
```

- **影響檔案**：`frontend/css/style.css` 一個
- **驗收**：改動前後同一頁截圖逐像素比對應無差異
- **回退**：刪掉新增的 token 區塊

### 階段 1 · 共用元件（改一次、全站生效的部分）

4. 表格：`.data-table` 的表頭大寫字距、列分隔線
5. 徽章：`.badge` 系列
6. `sidebar.js` 生成的頂欄與側欄：字級、間距、hover 行為

- **影響檔案**：`style.css`、`static/sidebar.js`
- **驗收**：57 頁逐頁開一次、深色模式各開一次、`test_dark_mode_chrome_structure_2026_09_13.py`
  與 `test_e2e_dark_mode_sidebar_2026_09_13.py` 綠燈

## §4 · 風險與對策

| 風險 | 為什麼會發生 | 對策 |
|------|------------|------|
| **深色模式破版** | 深色是 `invert(1) hue-rotate(180deg)` 濾鏡，不是第二套色票；新色反轉後可能變成低對比 | 每個新色都要在深色模式下看過一次，不能只看淺色 |
| **側欄被包進容器** | 轉換時很容易順手加一層 wrapper；一旦 `.sidebar` 不是 `body` 直接子元素，深色排除清單失效、`position:fixed` 定位基準跑掉 | `test_dark_mode_chrome_structure_2026_09_13.py` 已經在守，每批跑一次 |
| **對比退步** | 換色時只看好不好看 | §2.4，上線前重算 |
| **改到後端** | inline `<style>` 與 Alpine 綁在一起，容易順手動到邏輯 | 每批 commit 前確認 `git diff --stat` 沒有 `backend/` |
| **正式機同時有人在改** | 已發生過（§0 落差紀錄 2026-09-10） | 每批動工前先確認，並留 `AGENT-HANDOFF-TEMPLATE.md` 交接檔 |
| **一次改太多頁難回退** | | 一批一 commit，commit 訊息寫清楚批次編號 |

### 階段 1 實際做了什麼（與原計畫的差異）

原計畫寫「階段 1 只動 `style.css` 與 `sidebar.js`，不碰任何一頁的 inline `<style>`」。
**這條在執行時證明行不通**：主色一改成紅，頁面裡 212 處硬寫的「舊主色藍」複本會留在原地，
全站變成一半紅一半藍，比不改更糟——階段 1 就不再是可獨立上線的狀態。
因此追加了一個 **階段 1b：舊主色硬寫值收斂**。

實際改動：

1. **色票**（`style.css`）：`--accent` 藍 `#2563EB` → 官網紅 `#C8102E`、
   `--accent-hover` → `#A60D26`、`--accent-light` → `#FBE9EC`。
2. **`--danger` `#DC2626` → `#B91C1C`**：順手補一個既有缺口——`#DC2626` 對站內主底色
   `--white #F5F4F0` 只有 **4.39:1**，本來就沒過 AA。2026-08-28 那輪的三個修正應是對
   純白 `#FFF` 算的（`#DC2626` 對純白 4.83:1 剛好過），對奶白底就不過。改後 5.88:1。
3. **按鈕三層形狀階梯**（丙案）：`.btn-primary` 實心紅／`.btn-reject` 白底 2px 粗紅框＋粗體／
   `.btn-danger` 淺紅底 1px 細框。`.btn-reject` 原本是實心 `var(--danger)`，主色改紅後會
   與主要動作長得一樣；**實測「換一個更深的紅」這條路不通**——`#9F1239` 實心對 `#C8102E`
   實心只有 **1.36:1**，並排根本分不出來，所以必須換形狀而不是換色階。
4. **狀態徽章脫鉤主色**：`.badge--sent`／`.stat-tag--accent` 原本吃 `var(--accent-light)`＋
   `var(--accent)`，主色改紅後「已送出」變成紅底紅字、跟「逾期」幾乎一樣（**實際截圖才看到**）。
   狀態徽章是一組狀態序列，本來就不該跟品牌主色連動，改用自有青色 `#ECFEFF`／`#0E7490`（5.15:1）。
5. **階段 1b**：34 個檔案裡 212 處舊主色藍，**只收斂 CSS 情境中確定是「主色複本」的 146 處**

   外加 5 處 SVG `stroke=` 與 JS `borderColor` 的字面值。
   **刻意不動剩下的 12 處**——`_GANTT_COLORS`／`_AV_COLORS`／`_MOD_COLORS`／拜訪類型／
   星期色／任務類型色都是**分類色票**，藍只是其中一個色相，改成紅會跟其他分類撞、
   而且把資料編碼改錯。盲掃會直接毀掉這些。
6. **圖表接上色票**（`index.html` `initCharts()`）：原本八個色值全硬寫，而且
   `success`/`danger`/`warning` 停在 2026-08-28 無障礙修正**之前**的舊值

**三個實作上的坦陣（都是實測才發現的）**：

1. **導覽列不能取名 `.topbar`**。那個 class 在深色排除清單裡，白底導覽列取那個
   名字會在深色模式整片發亮。取別的名字讓它照常被反轉才對。
2. **深色橫幅在深色模式會反轉成亮塊**。實際切過去看就看到了：主視覺與三欄帶
   變成全頁唯二的白底區塊。**正解是比照 `.topbar`／`.sidebar`**——它們本來就是
   「兩種模式都維持深色」的 chrome。已將 `.h-hero`／`.h-band` 升成 `<body>` 直接子元素
   並加進排除清單，同步更新 `test_dark_mode_chrome_structure_2026_09_13.py`
   （`CHROME_CLASSES` 與選擇器字面兩處）。這兩塊**必須**維持在 body 直下。
3. **y 軸刻度在空資料時會印出 `0.0008K`／`-0.0005K`**（既有問題，`(v/1000)+'K'`
   沒處理小於 1000 的值）。已補上門檻。

**圖表重排（使用者指示）**：原本月支出結構單獨一列、右邊 1fr 空著，而當月實收是
主圖表列的第三個子元素，被擠到下一個隱含列、落在 2fr 欄位，圓環因此比「應收款狀態」
大一圈。重排成兩列（A：銷售收入趨勢＋當月實收；B：月支出結構＋應收款狀態），
兩張圓環落在相同欄位，呈現方式自然一致，不需要改它自己的任何樣式。
