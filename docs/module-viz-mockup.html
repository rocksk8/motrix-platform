簽核佇列、案件管理、業務開發
改成看得見狀態的作業台

這三頁現在是同一個骨架：左清單＋右詳情。清單只排「有哪些」，狀態要點進去才知道， 所以它們都在回答「我可以打開什麼」，而不是「現在什麼卡住了、該先動哪一件」。 這份稿子照視覺化管理的作法重排：異常先浮出來、時效用顏色編碼、責任歸屬直接標在畫面上， 並把長期案件量變大之後的檢索骨架一起設計進去。

先把「顏色代表什麼」定死

簽核跑道

簽核佇列目前依申請人分組。但申請人不是決定我要不要動手的那個軸—— 決定的是「是不是輪到我」跟「這張單卡多久了」。這一版把軸換掉。

分組軸錯了。依申請人分組，等於要我先認人再認事；而「輪到我簽」的判斷（canApprove()）跟申請人無關。
看不到積壓。送審時間只印成一行 09/11 14:32，沒有任何地方告訴我「這張卡了 6 天」，也沒有跨張比較。
卡在誰身上要點開才知道。waitingForText() 已經算得出「等待林佩瑜簽核（第 2/3 層）」，但這句話只出現在右側詳情裡。
右半邊常態是空的。沒選任何單時，一半畫面是「📋 選取左側項目以查看詳情」。

案件關卡矩陣

系統對「完結案」已經定義了五項前置條件（執行進度 100%、款項收齊、單據簽核完成、成本精算完結、無額外支出送審中）。 那份清單本身就是一套現成的視覺化管理指標——但現在它只在按下「完結案」被擋下來的時候才會出現。 這一版把五個關卡攤成表格欄位，一案一列、一關一格。

要查五個地方才知道一件事。進度在「執行進度」頁籤、收款在「案件資訊」、單據在各自子頁籤、精算在「財務」——五個關卡散在五處，跨案件比較等於開五次。
跨案的到期資訊沒有出口。/api/quotations/stage-board 已經回傳每個案件每個階段的 dueDate／done／overdue，目前只被用來算左上角一個「已逾期 N」的數字。
清單卡片資訊太薄。單號、客戶、業務、金額、stage_done/stage_total——看不出哪一件快能結案、哪一件卡住。

1五關卡＝五個欄位。欄位順序照結案檢查的順序（進度→收款→單據→精算→變更）。整列五格全綠，右邊才會亮「5/5 可結案」——那句話等同「現在按完結案不會被擋」。
2空心灰是「不適用」，不是「沒做」。系統對沒有精算／沒有階段／沒有款項的舊案件本來就視為無需檢查；矩陣必須把這個語意畫出來，否則舊案件會滿排紅燈。
3預設排序是「最接近結案」。這是既有畫面完全給不出的資訊，也是最會改變行動的排序——先把差一步的收掉，再處理卡住的。
4到期帶用既有 API。stage-board 回傳的 dueDate/overdue 直接彙總成「已逾期／今日／未來 7 天」，點某一格就篩出那天到期的案件。
5左緣狀態脊。整列不染色（會蓋掉格子的燈號），只在最左邊留 3px 的脊，取該列最嚴重的燈號，讓長表格上下捲動時異常仍然浮得出來。
6詳情不消失。點一列仍然進現有的五頁籤詳情頁（?no=&tab= 深連結已經做好了），矩陣是它的上層索引，不是取代它。

開發漏斗與接觸溫度

業務開發的核心變數是接觸頻率：一個案子會不會死，看的是上次聯絡到現在多久。 系統已經算得出這件事（isStale()＝洽談中且逾 30 天未更新），但它目前只是清單上方一條警示列。 這一版把「距上次接觸幾天」升格成第一視覺編碼。

統計在選了案件之後就消失。「接洽成效總覽」「案件責任分布」掛在 x-show="!selectedCase"——正在看某個案子時，最需要對照的整體節奏反而看不到。
狀態是主編碼、溫度是附註。狀態（洽談中／成案／未成案／暫擱置）決定顏色，但同樣是「洽談中」，3 天前聯絡過跟 60 天沒動的，該做的事完全不同。
通路資料沒有出口。每筆記錄都存了通路（電話／Line／Email／面訪／視訊），只在明細裡印成一個小標籤，看不出某個客戶是「只用 Line 聊過」還是「跑過三次面訪」。

04長期案件量的檢索骨架

案件越積越多之後，怎麼找得到

上面三個版面都是為「現在要動的那幾十件」設計的。但案件只會單向累積： 今天資料庫裡是 26 張報價單、90 件業務開發案、499 筆開發記錄， 十年後同樣的節奏是十倍以上。檢索必須跟看板分開設計，而且要先解決一個現在就存在的天花板。

先講會先撞到的牆

資料目前量10 年推估目前實作的上限
報價單／案件 26 ~250 案件管理寫死 limit=500 一次全量拉回，篩選、排序、分頁全在瀏覽器做
業務開發案件 90 ~900 GET /api/dev-cases 完全沒有 limit／offset，永遠回全量；前端再做全部篩選
開發記錄 499 ~5,000 每選一個案件才抓該案記錄，這條沒問題
案件階段 49 ~1,300 stage-board 攤平回傳「案件×階段」全量，沒有時間範圍參數

這不是現在的缺陷——幾十筆的時候全量拉回反而最簡單、最不會出錯。但上面三個版面都要跨案件彙總， 等於把這個模式再往上壓一層，所以伺服器端篩選＋分頁應該跟版面一起做，不要等到卡了才回頭改。 另外 /api/quotations 目前只認 status／customer／month／deal_tag， 缺「業務員」與「跨欄關鍵字」，排序也寫死 ORDER BY id DESC——facet 篩選要用的話這三項要補。

三層檢索

第一層 · 作業區（少量、每天看）：上面那三個看板。只放「還沒結束」的東西，量天生有上限——手上同時進行的案件不會因為做十年就變十倍。
第二層 · 檢索區（全量、偶爾查）：facet 篩選＋年份摺疊的歷史清單。設計目標是「三次點擊之內收斂到 20 筆以內」。
第三層 · 直達（已知單號）：全域命令面板。知道單號或客戶名的時候，不該經過任何清單。

3歷史按年摺疊、預設全收合。年份列本身帶件數與金額合計——很多時候要找的答案（去年做了幾件、多少錢）在展開之前就得到了。

05可獨立上線、可回退

落地順序

照「先做不必動後端的、再做要動後端的」排。每一階段自己就是可上線狀態，不必等下一階段。

1
共通語彙進 style.css前端
燈號、時效色階、階梯、溫度條、狀態脊做成共用 class，三頁共用一份。只新增不改既有 token，畫面零變化，可先合。
2
簽核跑道前端
分組軸從申請人換成「輪不輪到我」，泳道依停留天數。所需資料 canApprove()／waitingForText()／tiers／requestedAt 全部已經在前端手上，後端零改動。
3
關卡矩陣前端後端小改
進度、單據、精算三格用 /api/quotations 現有欄位與 stage-board 就畫得出來；收款百分比與「額外支出送審中」目前在案件詳情才算得到，需要補進列表 API。
4
開發漏斗與溫度前端
溫度＝updatedAt 距今天數，既有 isStale() 就是紅色門檻。統計從 x-show="!selectedCase" 解綁、移到常駐區。通路圖標需要 dev_logs 的通路彙總，可在案件列表 API 帶一個 channels[]。
5
檢索骨架後端為主
/api/dev-cases 補 limit／offset；/api/quotations 補業務員篩選、跨欄關鍵字、排序參數與 facet 筆數；user_list_prefs 擴充成儲存檢視。前端接 facet 面板、年份摺疊、命令面板。
