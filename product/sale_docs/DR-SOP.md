# MOTRIX ERP — 災難復原 SOP（Disaster Recovery）

> 適用範圍：伺服器整體不可用時的復原流程。下文的 `<安裝目錄>`、`<伺服器 IP>` 請換成貴公司實際的安裝資料夾與伺服器固定 IP。
> 本文件只處理「機器掛了怎麼辦」；日常更新以更新包附的說明為準。

---

## 1 · 為什麼需要這份文件

「備份存在」跟「真的能在可接受時間內重建整套可運作的系統」是兩件事。這份 SOP 把「重建」寫成可以照著做的步驟，
建議**在正式出事之前，至少演練一次**，並把結果記在 §6。沒驗證過的備份等於沒有備份。

## 2 · 各情境的資料遺失與恢復時間（參考值）

| 情境 | 可能遺失的資料 | 估計恢復時間 |
|------|----------------|--------------|
| ERP 服務程序當掉，機器本身正常 | 0（開機自動啟動的 crash-restart 迴圈接手） | 約 5 秒 |
| Windows 需要重開機，機器本身正常 | 0 | 開機時間＋約 90 秒（開機自動啟動的排程延遲） |
| SQLite 檔案損毀，機器硬體正常 | 至多一天（上次每日備份） | 人工還原，估計 30–60 分鐘（請自行演練確認） |
| 需要還原到 60 天以前的時間點 | 該月的月備份（一個月一份） | 請自行演練 |
| **整台機器硬體故障** | 同上（取決於雲端備份是否可用） | 請自行演練；§4 是完整步驟 |

## 3 · 備份來源與保留

還原時優先序：**本機 `backend\db_backups`（舊硬碟還能讀）** → **雲端每日備份**（保留 60 天）→ **雲端月備份**（永久保留，含整份 `.db`）→ **JSON 重建（最後手段）**。
要還原三個月以前的時間點，只剩月備份那一層。做 DR 時先確認手上那份來源的日期落在哪一層。

**個資資料夾**：整庫 `.db` 與含個資的欄位只放在獨立的個資資料夾（與一般存檔資料夾並列），一般存檔只留去掉個資的 JSON 與一般單據鏡像。

- 個資資料夾由人建立一次、由人設定雲端共用權限（程式永不自動建立根目錄）；不要建在已分享的資料夾裡（子資料夾會繼承上層分享，權限反而更寬）。
- Windows 的「安全性」權限管不到雲端；雲端的存取只由雲端硬碟的共用設定決定。
- 個資資料夾未建立時：設定頁會標示「未上雲」，並每日寄告警信，直到資料夾建好；這段期間雲端沒有整庫備份，還原來源只剩本機備份。
- 從 JSON 重建時（最後手段），個資欄位要用同一天的個資資料夾同名檔合回。

**存檔所有權標記**：雲端存檔根目錄有 `.motrix_archive_owner`，內容是舊資料庫的識別碼。
「用舊資料庫還原到新機器」時識別碼跟著資料庫走，不需要處理；**從 JSON 重建新資料庫**時識別碼會重新產生，
新機器會被自己的防呆擋下、雲端備份全部停寫並寄信——這時**刪掉 `.motrix_archive_owner` 再重啟**即可重新認領。

## 4 · 完整重建 SOP（最壞情境：需要換一台全新機器）

### Step 1 — 準備新機器環境

1. 全新 Windows 機器，建立本機帳號
2. 安裝 Python（版本依 `backend\requirements.txt` 的說明），安裝相依套件：
   ```powershell
   pip install -r backend\requirements.txt
   ```
3. 安裝 Microsoft Edge（產生 PDF 依賴 Edge headless；路徑不在預設範圍時，用設定 API 手動指定）

### Step 2 — 取得程式

取得與當機前相同版本的完整安裝包（`.deployed_commit.json` 記錄了版本），依安裝說明解壓到 `<安裝目錄>`。

### Step 3 — 還原資料庫與檔案

1. 把還原來源的 `motrix_erp.db`（含 `-wal`／`-shm` 如果有）複製到 `<安裝目錄>\backend\`
2. 還原 `uploads\`（專案照片）：從雲端的上傳檔案鏡像整份複製回 `<安裝目錄>\uploads\`
3. 還原 PDF 存檔目錄：從雲端的 PDF 存檔鏡像，依類別複製回各自的 PDF 目錄（實際路徑見系統設定的 `pdf_base_path`）
4. **Migration 驗證**：先在資料庫「副本」上跑一次 `db.init_db()` 確認新版結構能正常套用，再套用到正式檔案

### Step 4 — 環境設定

1. 設定開機自動啟動：註冊「MOTRIX ERP Server Autostart」排程工作（`backend\setup_autostart_task.ps1`）；備份與心跳排程分別是 `backend\setup_backup_task.ps1`、`backend\setup_heartbeat_task.ps1`。這些腳本需要以 `<安裝目錄>` 的實際路徑執行
2. 確認 CORS 白名單：新機器的網址若和舊的不同，設環境變數 `MOTRIX_CORS_ORIGINS`（逗號分隔，例如 `https://<伺服器 IP>:666`）即可，不必重新打包。**一旦設了就完全取代預設清單、不是附加**，設錯會讓前端打不到自己的 API

### Step 5 — 驗證

1. 手動啟動（不透過排程）：`backend\start.bat`，確認 `http://127.0.0.1:666/api/ping` 回應正常（啟用 HTTPS 的安裝改用 `https://`）
2. 用一個一般帳號登入，確認能看到還原後的真實資料（挑幾筆熟悉的報價單／客戶核對）
3. 確認心跳設定 `heartbeat_config.json` 的 `ping_url` 還在，讓外部監控恢復收到打卡
4. 觀察 `backend\logs\server.log` 至少 10 分鐘，確認沒有異常錯誤

## 4a · 本公司資料設定

系統在「本公司資料」沒有被本安裝的最高管理員確認前，**除了設定頁以外的功能全部暫停**（API 回 428），含本公司資料的文件（報價單、請款單、報表…）不輸出。

**還原後一定會遇到**：確認紀錄綁的是「安裝識別檔」`backend\.install_identity`，它**不在備份裡**（與 `company_confirmation.sig`、`company_setup_grace.json` 同樣不進備份、不上雲）。還原到新機器或新目錄後必然是「未設定」。

| 情境 | 處理 |
|---|---|
| 還原到新機器／新目錄 | 最高管理員登入 ⇒ 自動導到「公司資料設定」⇒ 核對公司名稱、統一編號、電話／email ⇒ 勾選並按「確認本公司資料」⇒ 恢復 |
| 唯一的最高管理員不在 | 系統負責人在**伺服器本機**建暫時放行（下方指令，72 小時，記稽核）；之後補設第二位最高管理員 |
| 畫面頂端出現「本公司設定狀態無法判定」 | 判定程式本身出錯（例：設定資料毀損）：一般功能照常、對外文件暫停輸出；看 `backend\logs\server.log` 的 `company_setup` ERROR，修好資料後約 1 分鐘內自動恢復 |

**暫時放行（伺服器本機執行，不需要登入）**：

```
python backend\tools\company_setup_cli.py grace --root <安裝目錄> --hours 72 --reason "<原因>"
```

- 最長 72 小時，**不可延長**：伺服器以第一次看到這份檔案的時間起算；要再放行就重建一次（每次都記稽核、發告警）。
- 放行期間所有頁面頂端有橫幅；放行**不會**寫確認紀錄 ⇒ 到期自動恢復擋住。
- 查目前狀態：`python backend\tools\company_setup_cli.py status --db backend\motrix_erp.db --root <安裝目錄>`（只讀，不改任何東西）。

## 5 · 讓下次重建更快

| 項目 | 說明 |
|------|------|
| 備用硬體 | 找第二台機器（不必常駐開機），把「全新環境安裝」的時間壓縮到「開機＋還原資料」 |
| 還原演練 | 每季挑一份備份，還原到暫存目錄、跑 `init_db()`、在另一個連接埠起一個實例、打幾支 API 核對筆數，然後丟掉；結果記在 §6 |
| 雲端備份後端 | 若使用 S3／B2 類的物件儲存，請用真實帳號實測一次還原 |
